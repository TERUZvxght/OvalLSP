Ruby the editor

OvalLSP is a semantic language server for Ruby and Rails. It parses your code with Prism, indexes the whole workspace, and — in a trusted Rails workspace — asks your application itself what its routes and models really are. No regex guessing, no telemetry, no network access at runtime.

What it does

Language features that come from understanding the code

Every answer below is derived from a real parse tree, a workspace-wide index of declarations, and — where Rails is involved — the application's own runtime introspection. Where OvalLSP cannot know something, it says nothing rather than guessing.

Hover with inferred types

Literals, constructors, locals, Active Record finders and instance variables carried from a controller into its ERB view. Backed by a local type inference engine with RBS/RBI signature integration.

Completion that knows your app

Model columns and associations, the Active Record instance and class API, *_path/*_url route helpers, stdlib methods from RBS, and every class in your workspace — inserted as a call template with tab stops.

Navigation across the workspace

Go to definition for workspace methods, model columns and associations, and into the RBS signature for the stdlib. Find references, guarded rename, document symbols and workspace symbols on the same index.

Diagnostics that refuse to guess

Syntax errors, unknown methods on a class whose whole ancestry is known, unknown route helpers, and the wrong number of arguments. On a class that inherits from a gem, the check stays deliberately silent — reporting there would mean guessing.

A Runtime Agent, on your terms

In a trusted workspace containing bin/rails, a background agent introspects your own routes and models. In an untrusted workspace it never starts, and every Rails-derived feature degrades to its static answer by design.

Observed, not guessed

Opt-in runtime type observation records the call shapes your own test suite exercises — shapes only, never values — so what the engine cannot read from source, it can learn from a run you already make.

Rails

It doesn't infer your schema. It asks.

A Rails application's real shape lives in code that only runs: routes drawn at boot, columns read from the database, associations declared through DSLs. Static analysis alone has to approximate all of it.

When a workspace root contains bin/rails and the workspace is trusted, OvalLSP starts a Runtime Agent on a background thread, takes a snapshot of the routes and models your application actually defines, and feeds that into completion, definition and type inference. It never blocks on the agent: if the app can't be introspected, the agent crashes, or there is no Rails at all, OvalLSP carries on with static analysis alone.

  • Columns and associations with their real types, from the real schema.
  • Route helpers — completion, signature help and go-to-definition into config/routes.rb.
  • Rails DSLs — enum, scope and delegate resolved to the methods they define.
  • Controller → view — an @ivar in an ERB template gets the type its action assigned.
  • Reopened gem classes — class ActiveSupport::TestCase in your test helper is recognised as a reopening, not a definition, so it produces no false diagnostics.

Architecture

Four processes, one of which is yours

The extension is a thin LSP client. All the analysis lives in a standalone Ruby Core Server, which ships inside the extension and updates atomically with it.

No second download

The Core Server and its own runtime dependencies (Prism, RBS) ship inside the VSIX. No bundle install, no repository checkout, no background updater. Update the extension and the Core moves with it, atomically.

A handshake before any work

Extension and Core exchange version, protocol, build and Ruby/platform information at startup. A mismatch is reported, and the session keeps running while you decide; the specifics are in the Output channel (024.55 tracks the follow-through).

Nothing survives the window

Core Server and Runtime Agent lifetimes are tied to the workspace that started them, with crash-loop protection and exponential-backoff restart — and a verified guarantee that closing the window leaves no process behind.

Deliberate limits

What OvalLSP is not

It is a confidence-aware heuristic engine for editor features — not a Ruby type checker. These are design boundaries, not open bugs.

Dynamic definition is out of scope

method_missing and define_method outside the known Rails DSLs, class_eval/instance_eval with string arguments, and constant resolution that only exists at runtime are not modelled. Guessing at them would produce confident wrong answers.

One platform, for now

The published VSIX is built for darwin-arm64 and bundles native extensions compiled for it. On anything else the payload is not loaded: the extension checks whether your Ruby can load prism and rbs itself, runs against those with an Output-channel note when it can — an unverified configuration — and shows an error when it cannot, with the specifics in the Output channel. Intel Macs, including under Rosetta 2, are not supported in this Preview; nor are WSL, Dev Containers or Remote SSH.

Gem-derived methods aren't indexed yet

The unknown-method check only fires when a receiver's whole ancestry is known. A class inheriting from a gem — ApplicationController, and so most controllers and jobs — is silent instead. Indexing what the gems define is what lifts that, and is planned for 0.3.0.

Other Ruby language servers will overlap

VS Code combines results from every active provider rather than picking one, so running OvalLSP alongside another Ruby language server shows both sets of results at once. Nothing crashes; the suggestions just double up. Disable the others per workspace if you want only OvalLSP's answers.

Quick start

Three steps, assuming a Ruby 3.4

  1. Install the extension

    From the VS Code Marketplace, on the Pre-Release channel.

  2. Open a Ruby or Rails project

    Open any .rb file and the Core Server starts on its own. Trust the workspace when prompted to enable the Rails-aware features.

  3. Confirm what is running

    Run OvalLSP: Show Version Information to see the Extension and Core versions, protocol compatibility, and which Ruby was selected.

Full installation guide 
# Install from the command line
code --install-extension teruz.ovallsp --pre-release

# Check that a supported Ruby is reachable
ruby -v
# ruby 3.4.7 (…) [arm64-darwin24]

# If VS Code can't find it, pin it in settings.json
"ovallsp.rubyExecutablePath": "/opt/homebrew/bin/ruby"

OvalLSP does not install Ruby and cannot. It needs some Ruby 3.4.x already reachable — via mise, asdf, rbenv, Homebrew, your PATH, or an explicit setting. Everything else it needs is inside the VSIX.

FAQ

Questions worth asking first

Does it work right after installing, with no extra setup?

Yes, provided a compatible Ruby is already reachable on your system. OvalLSP needs some Ruby 3.4.x present — via mise, asdf, rbenv, Homebrew, or an explicit ovallsp.rubyExecutablePath. Given that, everything else needed to run ships inside the VSIX: no second download, no bundle install, no checkout.

If no compatible Ruby is found, OvalLSP does not half-start — it shows a diagnostic explaining what is wrong and what to do about it.

Does it send my code anywhere?

No. There is no telemetry integration of any kind, and no outbound HTTP client anywhere in the Core Server or the extension. The only network access in the whole project happens on the machine that builds a release, fetching gems from RubyGems.org to bundle into the VSIX. See Security & privacy for the full statement.

What does the Runtime Agent actually run?

Your application's own Rails and Bundler code, in a separate process, to read back the routes and models it defines. Because that is arbitrary code from the workspace, it only starts once you have marked the workspace trusted in VS Code. In an untrusted workspace it never starts and every Rails-derived capability degrades to its static answer — by design, not as a failure.

Can I use it with a plain Ruby project, no Rails?

Almost certainly it works — most of the engine is environment-independent, and the Runtime Agent simply never starts. But nothing in the test suite verifies it yet, so nothing is promised. Specifying and guaranteeing the plain-Ruby experience is one of the two things 1.0.0 is reserved for.

Why Apple Silicon only?

The VSIX bundles native extensions (Prism, RBS) compiled for one specific Ruby ABI, OS and CPU combination. Rather than shipping a build that might load and might not, OvalLSP publishes for the combination it can actually verify and refuses the payload elsewhere with an explanation. Publishing and verifying the remaining platforms is the other half of 1.0.0.

Can I contribute?

Not right now. The project is under active single-developer development, and external issues and pull requests are not being accepted, because reviewing them would be deprioritised against work already in progress and risk overlapping with it. The reasoning is in CONTRIBUTING.md. Security reports are the exception — see SECURITY.md.
