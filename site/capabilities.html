What is verified, and what is not

Two axes: what the feature is, and which environment it runs in. A capability with no end-to-end test is not a capability, and a capability whose test is skipped is not shipped — so this table is the promise, and everything in it is either backed by a test or explicitly marked as unbacked.

Verified

Verified end to end in that environment, by a test that fails if it breaks.

Unverified

May well work — much of the engine is environment-independent — but nothing verifies it, so nothing is promised.

0.3.0

Not built yet; the release it is planned for. Alongside “unverified” it means planned for that release but still unverified there.

n/a

Defined by Rails data only the Runtime Agent can supply — absent by design, not broken.

Everything below assumes the published artifact, which is darwin-arm64 only. No VSIX is published for Windows, Linux or Intel macOS; doing so, verified per platform, is what 1.0.0 requires.

Reading the table

Why some cells say nothing at all

Silence on a class that inherits from a gem

The two unknown-method rows fire only on a receiver whose whole ancestry is known — a workspace class, or an Active Record model whose methods the Runtime Agent reports. A class inheriting from a gem — ApplicationController, and so most controllers and jobs — is silent instead, deliberately: reporting there would mean guessing. Indexing what the gems actually define is what lifts that, and is why the row carries 0.3.0.

The inverse case: a file that reopens a gem class

A workspace file that reopens a gem class looks identical to one that defines it. test/test_helper.rb's class ActiveSupport::TestCase is the one every Rails application has, and it was a false positive through 0.1.6. As of 0.1.7 the Runtime Agent is asked where the class really comes from, so the static chain's claim to be complete is checked rather than trusted. Without a Runtime Agent — an untrusted workspace, or no Rails app — there is nothing to ask, and the old reading stands.

An undefined variable is not its own row

In Ruby a bare identifier that is not a local variable parses as a call on self, so a typo'd variable is reported by the same unknown-method check, under the same limitation. An unassigned @ivar is genuinely different — Ruby returns nil rather than raising — and so has its own row.

“n/a” is a design decision, not a defect

Those capabilities are defined by Rails data that only the Runtime Agent can supply. In an untrusted workspace the agent deliberately does not start, and outside a Rails app there is nothing for it to report.

The plain-Ruby column is not a prediction of failure

Most of it almost certainly works today. It carries 1.0.0 because guaranteeing it — giving the Rails conventions an explicit boundary and specifying what a non-Rails project should expect — is one of the two things 1.0.0 is reserved for. The other is publishing and verifying the remaining platforms. Until then, nothing in that column is promised.

What the version numbers mean

A patch means nothing new was announced — not that nothing a user sees changed. Patches routinely change what you see: 0.1.14 removed about twelve thousand wrong reports, which every Rails project noticed. A row here can still appear or turn Verified in one, when it names something the previous release was already understood to do and did not — 0.2.1 did that four times. A minor means a capability was announced; a major means something a user relied on stopped working. Planned rows name a minor release exactly, never a 0.2.x-style range, and several rows sharing a version ship together, the way 0.1.6 shipped five.

Each “Verified” corresponds to a row of EXTENSION_CAPABILITIES.md, which describes what the user does and what must happen, and is verified by core/spec/e2e/capabilities_spec.rb plus vscode/scripts/verify-installed-extension.sh.

Where the “Verified” column applies

Only combinations actually run and verified are declared supported. Design-document placeholders are never declared as-is.

Combination Tier Basis
macOS, Apple Silicon (darwin-arm64) Supported The development environment itself; full suite, VSIX packaging and VSIX semantic smoke all run here, green.
Ruby 3.4.x Supported The Core suite actually run and green under both 3.4.7 and 3.4.5.
Rails 8.1 Supported The real-Rails integration fixture pins ~> 8.1, and CI installs that exact version.
Ruby 3.3 / 3.5 Unverified A required_ruby_version >= 3.3 declares only that 3.3 is not rejected — never that it was run.
Rails 7.x and below Unverified Only Rails 8.1 is tested. Some behaviour assumes Rails 7.1+ defaults.
Linux Unsupported CI runs the Core and TypeScript suites green on ubuntu-latest, but the published VSIX's native payload is darwin-arm64 only, and no real-hardware install has been verified.
Windows Unsupported RubyInstaller detection is implemented; real-hardware verification has not been done.
macOS Intel / Rosetta 2 Unsupported An x86_64 Ruby takes the same probe path as any other mismatch: with prism/rbs loadable it runs as an unverified configuration — nothing about it is tested.
WSL, Dev Containers, Remote SSH Unsupported Unverified.
