Home/Security & privacy

A local tool, and it stays local

OvalLSP has no network listener and makes no network request at runtime. The risks that actually matter for a tool like this are different, and they are handled explicitly rather than assumed away.

No telemetry No analytics SDK, no crash reporter, no usage tracking
No network No outbound HTTP client anywhere in Core or the extension
No upload Your source code never leaves your machine
Threat model

The three risks that are real here

A language server talking to VS Code over stdio has no remote attack surface to speak of. What it does have is a habit of executing and logging things that came from somewhere else.

Untrusted workspaces

Opening someone else's repository, or checking out a malicious pull request, must not compromise the Core process or the machine just by opening the folder.

Untrusted plugins

A third-party OvalLSP plugin must not be able to hijack Core's internal state or reach the LSP protocol stream itself.

Secrets in logs

Core often logs a target Rails application's own exception text verbatim, which is exactly where credentials tend to appear.

Mitigations

What each of those actually does

  • The Runtime Agent fails closed. It can execute a target application's own code, so it only starts once a workspace is explicitly marked trusted in VS Code. A missing trust signal, a false one, or an absent one are all treated as “do not start” — never as a default-allow.
  • Plugins run in a real OS process boundary. Not a sandboxed namespace inside the same process — a genuine fork with no access to Core's live LSP transport or internal index objects. Only plain, Marshal-safe data crosses the boundary.
  • Runtime plugins — the highest-privilege kind — never load at all in an untrusted workspace.
  • Log output is redacted before it is written anywhere. Bearer tokens, basic auth, database connection strings, known vendor key formats and labelled credentials all go through the redaction pipeline first.
  • Every protocol boundary requires an exact version match. Agent ↔ Core and plugin ↔ Core alike: a mismatch is refused, not tolerated.
The full, itemised threat model and its mitigations are in docs/SECURITY_CHECKLIST.md (Japanese), summarised in SECURITY.md.
Privacy

What leaves your machine: nothing

This is verified against the actual codebase, not merely declared. Neither the Core Server nor the extension contains any network client code, any telemetry or analytics library, or any outbound HTTP call.

The only network access in the project

At packaging time, on the release machine only: fetching Core's runtime gem dependencies (Prism, RBS) from RubyGems.org so they can be bundled into the VSIX. This never happens on an end user's machine.

VS Code's own Marketplace updates are VS Code's behaviour, not OvalLSP's. There is no auto-download or self-update mechanism beyond it — the Core ships inside the extension and updates atomically with it.

What gets written to disk

The output channel and Core's stderr carry diagnostic messages about OvalLSP's own operation — startup, indexing progress, errors, the version handshake. They stay in VS Code's Output panel and are never transmitted.

The only thing OvalLSP itself writes to disk is its persistent parse cache under $XDG_CACHE_HOME/ovallsp/ — or ~/.cache/ovallsp/ when that variable is unset or empty — keyed by workspace, toolchain version and OvalLSP's own version. It contains parts of your source code. Alongside the parsed declarations and types it stores each method's body text and each parameter's default expression verbatim, and each file's absolute path. Nothing in it is transmitted anywhere, and deleting the directory is safe at any time. As of 0.2.1 OvalLSP also removes directories under that root at startup — this workspace's older generations beyond the eight most recent, and workspaces that no longer exist on disk. Since 0.2.3 a workspace that has disappeared is held for thirty days after it was last opened, because an unmounted volume looks exactly like a deleted project; the cost is that a deleted project's cached source outlives it by up to a month, and deleting the directory yourself is always safe.

An earlier version of this page said “not your source code's contents”. That was retracted in 0.1.12 and corrected in PRIVACY.md, which is the single source of truth for what is written where; this page carried the withdrawn wording until 0.2.0.

Opt-in

Runtime type observation

OvalLSP: Run Tests with Type Observation runs your own test suite and records the method call shapes it actually exercises, feeding real evidence back into the type engine.

It records shapes — which method was called on which class, with how many arguments of which types, returning what — and never argument or return values. It runs only when you invoke it, using the command in ovallsp.observation.testCommand (bundle exec rspec by default), and everything it records stays on your machine. OvalLSP: Clear Observed Types discards it; OvalLSP: Show Type Evidence shows what a given inference was based on.

Four things it records are worth naming here, because “shapes, not values” does not imply them: an identifier for the run, made from its start time, Core's process id and a random number; a digest of the file the observed method is in; that method's line number; and the time the run finished. The digest and the line number exist only to notice when a method may have been edited since it was observed.

The full statement is in PRIVACY.md, which also spells out what observation does not record. Until 0.2.0 this page's summary omitted the four items above; PRIVACY.md is the source of truth and this page had drifted from it.
Reporting

Found a vulnerability?

Report it privately rather than opening a public issue. Use GitHub's private vulnerability reporting for the repository — the Security tab, then Report a vulnerability.

Please include:

  • A description of the vulnerability and its potential impact.
  • Steps to reproduce it — a minimal Ruby or Rails fixture project, if relevant.
  • The extension version, Core Server version and environment. The output of OvalLSP: Show Version Information is a good start.

Reports are acknowledged as soon as possible, with a timeline once the issue is understood. Please don't disclose publicly before it has been addressed.
