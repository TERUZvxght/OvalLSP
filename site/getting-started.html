Install it, and know what it is running

One prerequisite you must supply — a Ruby 3.4.x — and everything else ships inside the extension. If something is wrong, OvalLSP tells you what and why rather than starting halfway.

Before you install

This is an early Pre-Release build. It targets macOS on Apple Silicon (darwin-arm64) only. On any other OS or CPU the bundled native dependencies are not loaded and OvalLSP shows a diagnostic rather than running in a guessed configuration. Intel Macs — including under Rosetta 2 — are not supported in this Preview, and neither are WSL, Dev Containers or Remote SSH.

Requirements

macOS on Apple Silicon

The published VSIX is built with vsce package --target darwin-arm64 and bundles Prism and RBS native extensions compiled for exactly that platform.

Ruby 3.4.x, already installed

Discoverable via an explicit ovallsp.rubyExecutablePath, or via mise, asdf, rbenv or Homebrew (/opt/homebrew). Tested against 3.4.5 and 3.4.7. 3.4 is what is verified. The VSIX bundles native extensions compiled for the version it was built under, so on any other Ruby they are not used. Since 0.2.1 the extension checks whether that Ruby can load prism and rbs itself: if it can, OvalLSP runs against those and notes it in the Output channel; if it cannot, it tells you to install them. Ruby 3.3 usually takes the first path — an unverified combination rather than a supported one.

VS Code 1.85 or newer

Declared as engines.vscode: ^1.85.0. An older VS Code will not install the extension at all, which is the intended failure — the language features it registers did not exist before that release.

No bundle install, no checkout, no second download. The Core Server and its own runtime dependencies ship inside the VSIX. OvalLSP does not install Ruby itself and cannot — it needs some Ruby 3.4.x already present. Given that one prerequisite, everything else needed to run is already there.
Installation

Five minutes, most of it VS Code's

  1. Install the extension

    From the Marketplace UI, or with the command opposite. It is published on the Pre-Release channel.

  2. Open a Ruby or Rails project

    Open any .rb file. The Core Server starts automatically, one per workspace folder.

  3. Trust the workspace

    Trust it when prompted to enable the Rails-aware features. The Runtime Agent never runs in an untrusted workspace.

  4. Confirm what is running

    Run OvalLSP: Show Version Information to check that the Extension and Core Server are on compatible versions, and see which Ruby was selected.

# Install the Pre-Release build
code --install-extension teruz.ovallsp --pre-release

The status bar shows the current state as it starts up:

Ruby resolution

How OvalLSP finds your Ruby

In this order, stopping at the first that answers. If VS Code was launched from the Dock or Spotlight rather than a terminal, its PATH may not include your shell's additions — which is the usual reason a Ruby that works in your terminal is invisible to the extension.

In that case, set ovallsp.rubyExecutablePath explicitly, or install Ruby through one of the version managers below: all of them are detected without relying on PATH. Run OvalLSP: Show Environment Diagnostics to see exactly what was tried and why each candidate was accepted or rejected.

  1. An explicit setting

    ovallsp.rubyExecutablePath wins over everything else.

  2. mise

    Resolved for the workspace folder's own pinned version.

  3. asdf

    Same — .tool-versions is read from the workspace, not the editor's ambient directory.

  4. rbenv

    Same, via .ruby-version.

  5. Homebrew

    Apple Silicon prefix, /opt/homebrew.

  6. Your shell PATH

    The last resort, and the one most likely to be missing under a Dock launch.

When something is wrong

Troubleshooting

In rough order of usefulness. OvalLSP is built to fail loudly rather than degrade quietly, so the answer is usually in one of the first three.

Nothing happens when I open a Ruby file

Run OvalLSP: Show Logs for the raw output channel, then OvalLSP: Show Environment Diagnostics to check Ruby resolution. The most common cause is a Ruby that your terminal can see and the extension host cannot.

It says the versions don't match

At startup the Extension and Core Server exchange version, protocol, build and Ruby/platform information. On a mismatch OvalLSP reports it — an error notification and the detail in the Output channel — and keeps running. It does not stop the session, so treat the answers you get afterwards as unreliable until the mismatch is resolved. Common causes: a stale process left by a previous Extension version, a payload that did not install correctly, or an incompatible custom ovallsp.server.path. Run OvalLSP: Show Version Information to see exactly what was detected.

Rails-specific features aren't working

Try OvalLSP: Restart Rails Agent, then confirm the workspace is trusted — the Runtime Agent never starts in an untrusted workspace. Check the status bar: Ready (static) means the agent is not contributing. A workspace root also needs bin/rails directly under it for the agent to be attempted at all.

Results look stale or the index seems wrong

OvalLSP: Re-index Workspace forces a full re-index. If a persistent cache seems corrupted, it lives under ~/.cache/ovallsp/, keyed per workspace, Ruby, Prism, Gemfile.lock and RBS combination — deleting the relevant directory forces a fresh index.

I'm getting two of every suggestion

You almost certainly have another Ruby language server extension active in the same window. VS Code combines results from every registered provider rather than picking one, so hover, completion and go-to-definition return both sets at once. This has been verified side by side with Shopify's Ruby LSP: no crash and no install-time conflict, but go-to-definition went from one candidate to four with both active. It is a property of VS Code's provider model, not of any one extension. Disable the others for that workspace if you want only OvalLSP's answers.

What is ovallsp.server.path for?

Pointing OvalLSP at a Core Server outside the bundled one — for development against the repository, for example. A custom path is checked for protocol compatibility exactly as the bundled Core is, but is never treated as “the standard bundled Core” for version, build or payload comparisons, and is never auto-updated.

How does the Core Server get updated?

With the extension, atomically. The Core ships inside the VSIX, so there is no separate download step and no independent background updater. When VS Code updates the extension, the next workspace activation runs the Core that shipped with the version you now have.
