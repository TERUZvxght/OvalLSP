# Apple Silicon Marketplace Preview — 既知の制限事項

[English version](KNOWN_LIMITATIONS.md)

本文書は、最初のMarketplace Pre-Releaseにおいて意図的にscope外として
いる事項の一覧です(バグとは区別する)。実際の検証結果に基づく
supported/unsupportedの一覧は
[docs/SUPPORT_MATRIX.ja.md](SUPPORT_MATRIX.ja.md)を参照してください。

## Platformのscope

- **macOS Apple Silicon(`darwin-arm64`)のみを対象としています。**
  VSIXは`vsce package --target darwin-arm64`でビルドされ、その
  platform向けにコンパイルされたnative extension(Prism、RBS)を
  同梱しています([ADR-0005](design/adrs/0005-platform-scoped-vsix-with-runtime-compatibility-check.md)参照)。
  それ以外のOS/CPUでは、同梱されたnative依存は単純にロードされません。
  代わりに起きること — 0.2.1 から、後述「Rubyバージョンのscope」節と
  同じ経路です: 拡張機能は選ばれたRuby自身が `prism` と `rbs` を
  読めるかを確認します。読める場合(素の Ruby 3.3+ には両方が入って
  います)、セッションはそちらで動き、Outputチャンネルにその旨が出ます —
  **未検証**の構成であって、拒否された構成ではありません。読めない
  場合はエラー通知が出て、Output チャンネルの詳細が
  `gem install prism rbs` を示します。
- **Rosetta 2変換下も含め、Intel Macはこのpreviewでは非対応です** —
  非対応であって、拒否ではありません。x86_64のRuby(Apple Silicon
  Mac上にIntel Homebrew経由でnativeにインストールされたものも含む)は
  他の不一致と同じ確認経路をたどります。`prism`/`rbs` が読めれば
  未検証の構成として動き、その組み合わせについて何もテストされて
  いません。
- **同梱されたnative extensionには、packagingを行ったマシン自身の
  絶対Rubyインストールパスが埋め込まれており、Extension側の起動時
  対応で緩和しています。** packageされた`prism.bundle`/
  `rbs_extension.bundle`に対する`otool -L`は、*packagingを行った
  マシン自身の*rbenv `libruby`パスへの絶対`LC_LOAD_DYLIB`参照
  (例: `/Users/<packager>/.rbenv/versions/3.4.7/lib/libruby.3.4.dylib`)
  を示しており、再配置可能な`@rpath`参照ではありません — これは
  macOS上の標準的な`rbenv`/`ruby-build`の`--enable-shared`の挙動です。
  直接再現済み: あるRuby 3.4.xインストール下でビルドされた
  `prism.bundle`が、*別の*絶対パスにある異なるRuby 3.4.xインストール
  下でrequireされると`LoadError: linked to incompatible
  .../libruby.3.4.dylib`が発生する — これは実質的にほぼ全ての実際の
  利用者に影響しうる問題で(ユーザー名が違うだけで発生する)、
  ADR-0005自体のengine/version/platform互換性チェックでは捕捉できない
  種類の不一致です。**修正済み**: Core Server起動前に、Extensionは
  解決済みRubyの`RbConfig::CONFIG["bindir"]`/`["libdir"]`を問い合わせ
  (`platformCompatibility.ts`の`queryRubyConfigPaths`)、version
  manager shim(mise/asdf/rbenvはいずれもshim scriptに解決される)を
  完全に迂回して*実体の*`<bindir>/ruby`バイナリを直接起動します —
  その際、その実体バイナリ自身の`libdir`を`DYLD_LIBRARY_PATH`/
  `DYLD_FALLBACK_LIBRARY_PATH`に設定します。この問い合わせ自体は
  *workspace folder自身の*working directoryで実行され、省略しては
  いません — version manager shimは、現在のworking directory自身の
  `.ruby-version`/`.tool-versions`に基づいて実際に実行するRuby
  versionを解決するため、`cwd`を省略すると、workspaceの固定version
  ではなく*extension host自身の*ambientなworking directoryが解決する
  Rubyを暗黙に問い合わせ(そして起動)てしまいます。実体バイナリの
  直接起動と`cwd`を指定した問い合わせの両方が必要です: 起動される
  コマンドがshim scriptのままであれば、環境変数を設定するだけでは
  何も効果がありません — macOSは`/bin/bash`を経由して起動される
  あらゆるプロセスから`DYLD_*`環境変数を除去するためです(直接
  確認済み — rbenvのshimに限った話ではなく、system shellを経由する
  あらゆるものに対するmacOSの一般的な挙動です)。実際にvendored
  payloadをビルドしたものとは異なるRuby versionへ強制されたrbenv
  shimを通して、この失敗を実際に再現し、同一の開発マシン上に既に
  存在する2つのRuby 3.4.xインストールを使って修正がend-to-endで
  解決することを確認済み(`docs/design/tasks/023.8-*.md`参照)。この
  緩和策はdarwinでのみ適用されます — 問い合わせ自体が失敗した場合
  (異常に古いRuby、spawnエラー)は、この修正が存在する前と同様、
  元々解決されていたコマンドのままCore Serverを起動します。
- **Linux・Windowsはこのpreviewでは非対応です。** Ruby resolverには
  Windows RubyInstaller検出ロジックが実装されており、Core Server
  自体もplatformに依存しないRubyコードですが、このpreviewの
  packaging・testing・supportの範囲はまだいずれのOSもカバーして
  いません。
- **WSL・Dev Container・Remote SSHはこのpreviewでは非対応です** —
  単に未文書化なのではなく、未検証です。

## Rubyバージョンのscope

**公開している拡張機能がビルドされているのは Ruby 3.4.x 向け**で、実際に
検証しているのは 3.4.5 と 3.4.7 だけです。VSIX はビルド時の `major.minor`
向けにコンパイルされた Prism と RBS のネイティブ拡張を同梱しているため、
それ以外の Ruby では同梱物は使われません。

**別の Ruby でも拒否はせず、確認します。** 0.2.1 から
`vscode/src/platformCompatibility.ts` は、その処理系が `prism` と `rbs` を
自前で `require` できるかを尋ねます。できればそちらで動かし、その旨を
Output チャンネルに出します。できなければエラー通知で、Output チャンネルの
詳細が `gem install prism rbs` を促します。Ruby 3.3 はどちらも同梱して
いるので、たいていは前者になります
— **つまり「検証済みの組み合わせ」ではなく「未検証の組み合わせ」で動きます。**
3.3 について検証しているのは CI 上の `core/` 自身のスイートだけで、そこでの
prism のバージョンは gemspec の下限より古い可能性もあります。サポートでは
なく自己責任で動かすもの、と捉えてください。

Ruby 3.5.x はどちらの意味でも未対応です。実際に検証するまで変わりません。

0.2.0 のラウンド22で CI のマトリクスを 3.3 と 3.4 に広げ、この節はそのとき
「3.3 と 3.4 に対応」と但し書き無しで書きました。**それは 3.3 の利用者を、
起動を拒否する拡張機能のインストールへ案内する記述でした。**「スイートが
3.3 で通る」と「成果物が 3.3 で動く」は別の主張で、前者は後者を保証しません。

## 配布・更新モデル

- Core ServerはExtensionの**内部**に同梱され、Marketplace自身の
  Extension更新機構を通じてExtensionと同時にアトミックに更新されます
  — [ADR-0006](design/adrs/0006-marketplace-bundled-core-update-atomicity.md)
  を参照。独立したCore Serverのダウンロードや、独立したバックグラウンド
  self-updaterはありません。将来このモデルが変わる場合(例えば、
  Extensionのリリースとは独立したCore更新をサポートする場合)は、
  それはこのpreviewが暗黙に行うことではなく、新たに明示的に設計される
  機能になります。
- カスタムの`ovallsp.server.path`はprotocol互換性のみチェックされ、
  自動更新されることは決してなく、同梱Core自身のversion/build/payload
  の期待値と比較されることもありません。

## 静的解析の限界(Apple Silicon固有ではないが、previewとして改めて記載)

OvalLSPはRuby型チェッカーではなく、LSP機能のための確信度付き
ヒューリスティックエンジンです。設計上、以下は追跡しません:

- 既に認識している特定のRails DSL(`enum`、`scope`、`delegate`)以外の
  `method_missing`/`define_method`/`alias_method` ベースの動的メソッド定義。
  これは単なる未対応ではありません。下の「現在まちがっている報告」に、これ自体が
  生む誤報を挙げています。
- 文字列引数による`class_eval`/`instance_eval`のコード生成。
- 実行時にのみ解決されるconstant解決(動的引数を伴う`const_get`等)。
- opt-inのruntime型観測に関して、テスト実行で一度も実行されなかった
  コードパス(実際に実行された経路にのみevidenceが存在します)。

3点目の帰結は、0.1.6まではすべてのRailsアプリケーションで目に見えていましたが、
0.1.7で修正しました。ワークスペースが定義していないクラスの再オープンは、
そのクラスを定義するコードと構文上まったく同じであるため、
`test/test_helper.rb` の `class ActiveSupport::TestCase` はgemの親を持たない
素のクラスとして読まれ、`parallelize` と `fixtures` の呼び出しが未定義メソッド
として報告されていました。現在は静的な読みを信用せず、動作中のアプリケーションに
確認します(`docs/design/tasks/024-deferred-review-findings.md`、024.R5)。
したがって、動作中のアプリケーションが判断できない場合には引き続き当てはまります。
問い合わせ先が存在しない場合(信頼されていないワークスペース、Railsアプリでない
プロジェクト)、Agentのプロセスが読み込んでいないgemの場合(Agentは `development`
で起動するため `group :test` のgemはそもそも存在しません)、そして何もmixinせずに
再オープンされたgemクラスの場合(祖先がどちらの証拠も持ちません)です。
各ケースは024.R5に列挙しています。

ワークスペースが*コア*クラスを再オープンする場合、同じ問題が1段外側で
起こります(024.13)。`lib/core_ext/array.rb` はRailsでは定型的な書き方
ですが、`Array` を再オープンすると祖先鎖(`Array`・`Object`・`Kernel`・
`BasicObject`)がすべて既知の状態になるため、未定義メソッド検査は
レシーバを「閉じている」と判断します。gemは `Array` に追加し続けるのに、
です。**0.2.16でこれが現れる範囲が広がりました。**`self` に型が付いたため、
そうしたクラスの中で `self.digest` と書いた呼び出しも、同じファイル内の裸の
`digest` と同じように報告されます。欠陥は同じで、`self` が何か分からなかった
ために見えていなかった書き方にも及ぶようになった、ということです。
Runtime Agentが接続されていれば実際の祖先を報告して解決しますが、
問い合わせ先がない場合(信頼されていないワークスペース、Railsアプリでない
プロジェクト)は判断できません。 <!-- documents: 024.13 -->

ただし実際に届く範囲は語感より狭く、しかも**利用者が最初に試すであろう
呼び出しは、再現しない側**なので、正確に書いておきます。エンジンがコンテナ
として推論するレシーバ(`[1, 2, 3]` や、それを代入したローカル変数)は
未定義メソッド検査の対象外です。したがって `[1, 2, 3].second` も
`a = [1, 2, 3]; a.second` も報告されません。報告されるのは、レシーバが
素のクラスそのものである呼び出し — 再オープンの内側にあるレシーバなしの
呼び出しです。

```ruby
class Array
  def to_sentence_ish
    second        # 報告される: "Array has no method named `second`"
  end
end
```

**ブロックの内側は型が付きません。** 例外は、エンジンがコンテナとして
モデル化しているレシーバ — `Array`、Active Recordの `Relation`、
`CollectionProxy`、およびそこから `map`・`select`・`find`・`each`・
`reduce` が渡すもの — だけです。`Hash` は*含まれません*。したがって
`hash.each do |k, v|` の内側には何も型が付かず、自分で定義したクラスを
レシーバにしたブロックの内側も同様です。ホバーは推測せずに何も答えず、
診断はすべて判断を控えます。**0.2.0でここが変わったので、気づくかも
しれません。** 0.1.13までは、この位置は*外側の呼び出し*の型を答えて
いました。つまりホバーは何かを言っていた — 多くの場合まちがったことを、
です。今は何も言いません。これは意図的な取引です。代案は仮定ではなく
実測して退けており、どちらもより悪いものでした。*外側の呼び出し*の型を
答えると `opts.on("-x") do` の中の
文字列リテラルを `OptionParser` として報告してしまい、ブロックのボディを
読みに行くと、潜在的なオフセット誤解決が表面化してRuby標準ライブラリ全体で
未定義メソッドの報告が230件増えました。3つのうちどの検査も動かないのは
Unknownだけです。前者2つが依存しているオフセットの規則は独立して修正中で
(024.20、未解決)、それができればボディを読めるようになります。

同じオフセット規則には、利用者が直接出会うもう1つの影響があります。0.2.15 まで
この文書が書いていなかったものです — **ブロックの直後に `.` を書くと何も
答えません。** `[1, 2].map { |x| x }.first` でブロックの直後にカーソルを置いても、
ホバーも補完もシグネチャヘルプも出ません。エンジン自身はそのレシーバを
`Array[Integer]` と型付けできますし、別の位置で尋ねれば実際にそう答えます。
誤って答えるのではなく黙るという方向は正しいのですが、答え自体はすでに
持っているものです。 <!-- documents: 024.20 -->

## 現在まちがっている報告

**名前空間つきの型が、自分自身と互換でないと報告されること。** `sig/` が
名前空間の中でパラメータを宣言していて(`module App; class Registry;
def fetch: (Key key) -> Key`)、それを呼ぶ Ruby も同じ名前空間の中に
書かれている場合、宣言側の型は修飾された形で、推論側の型は裸の形で届き、
引数型検査はこの2つの綴りを別のクラスとして比較します。`rbs` gem 自身の
89 個の手書きシグネチャに対して動かすと、出てくる argument-type の報告は
すべてこの形です — ``expects RBS::TypeName here, but TypeName is given``。
この2つは同じクラスです。あなたのコードは何も間違っていません。 <!-- documents: 024.224 -->


このエンジンの基準は一貫して「誤った報告は見逃しより悪い」です。以下は
現時点で事実でないことを言っている箇所です。1つは色として、残りは診断として
です。いずれも記録済みで、しかもごく普通のコードで目に見えます。自分で
見つけてもらうのではなく、ここに挙げておきます。

**最初に出会うのは `.` を打ったときのものです。** 半分は 0.2.1 で直りました。
メソッドの末尾で `a.` と打っても、クラスに `end` というメソッドがないとは
言わなくなりました。もう半分は直っていません。気づく手がかりがないからです
— `a.` の次の行が `b = "str"` の場合、それは `a.b = "str"` を意味する正しい
Rubyであり、そのとおりに報告されます。

```ruby
a = Article.new
a.
b = "str"        # → Article has no method named `b=`
```

次の行が `value`・`if true`・`return 1` でも同じで、`puts 1` や
`other_thing(1)` では出ません。名前を打ち終えれば消えます。同じコードを
意図して書いた場合と区別できないため、検査を足すのではなく「まだ打っている
最中は発行しない」のが正しい直し方で、本リリースには入っていません
(024.41)。 <!-- documents: 024.41 -->

このリストがかつて抱えていた2つは、本リリースではなく過去のリリースで
修正され、無くなりました。**ルートが1つも読み込まれていないときに
`*_path`/`*_url` の呼び出しを「存在しないルート」として報告することは、
なくなりました**(024.24、0.2.0 で修正)。信頼されていないワークスペースとRailsでない
プロジェクトがこれに当たり、空のルート表が「知らない」ではなく「そんな
ルートはない」と答えていました。Rubyの標準ライブラリで8件、すべて誤りでした。
現在は0件です。0.2.0はプロジェクト全体に診断を出すので、直していなければ
この8件を開いていないファイルにも配っていたことになります。

このリストがかつて抱えていた最大のものも無くなりました。クラスボディの
マクロ(`private`・`attr_reader` など)が未定義メソッドとして報告される件と、
それらのDSLが定義する属性リーダーの件です。このプロジェクト自身のソースで
**62件中49件**、Rubyの標準ライブラリ全体では12,134件を占めていましたが、
本リリースに持ち込まず0.1.14として修正・公開しました(024.23)。

さらに7つ、本リリースより古く、本リリースが手を付けていない形があります。

- **ワークスペースが読んでいないモジュールを include したクラスでは、クラス
  レベルのマクロが報告されます。** `include SomeGem::Model` に続く
  `validate :ensure_ok` は、Concern が `validate` を入れるにもかかわらず報告
  されます。0.1.14 で入り、本リリースでは直していません(024.35)。 <!-- documents: 024.35 -->
- **ループで定義したメソッドは未定義として報告されます。**
  `EVENTS.each { |id, _| alias_method "on_#{id}", :_dispatch_1 }` は生成
  コードでよくある形ですが、名前がリテラルでないため索引には何も残らず、
  その呼び出しはすべて報告されます。計算された名前の `define_method` も同じ
  形です。「静的解析の限界」ではなくここに挙げているのは、このエンジンの基準が
  「誤った報告は見逃しより悪い」であり、これが見逃しではなく誤報だからです。
  0.2.0 が変えるのは影響範囲です。開いていないファイルにも診断を出すように
  なったため、見つけに行かなくても Problems パネルに出ます。(この項目は
  「1ファイルで525件(prism の `translation/ripper.rb`)、このエンジンが出す
  誤報の最大の集中箇所」と書いていました。同じリリースがその報告を消す前に
  計測した数字です。現在このファイルが出すのは10件で、しかもこの形は1件も
  ありません。修正した後に測り直さなかった数字でした。)

## 0.2.0で追加した検査が意図的に見ないもの

0.2.0が追加する診断はどちらも「誤った報告は見逃しより悪い」を基準に
しているため、意図的に狭くしてあります。その代償は次のとおりです。

- **引数の個数**は検査しますが、これまでに計測したコードに対しては1件も
  報告しません。Ruby 3.4.10 の標準ライブラリ・Rails 8.1.3.1 の5つのgem・
  minitest の 2,095ファイルに対して**0件**です。同じコーパスで以前は
  **109件**出しており、そのすべてが正しく動く Ruby でした。下の「引数の型」
  と同じように読んでください。書いたコードの誤りを見つけてくれるものではなく、
  異を唱えてはこないもの、ということです。判断しない形が2つあり、どちらも
  以前は報告していました。読み取れないブロックから `define_method` で
  定義されたメソッドと、`delegate` や `scope` が生成するメソッドです —
  後者は引数をそのまま転送するので、個数を宣言している箇所がありません。
  以前の報告にはそれぞれ原因があり、いずれも修正済みです。`def Const.method`
  がインスタンスメソッドとして記録される件(024.32)、ブロックの `self` が
  外側のクラスとして読まれる件(024.31)、そして
  `define_method(:warn) { |*messages| }` が引数を*取らない*ものとして
  記録される件 — これ単独で、コーパス中のすべての `warn` と `p` の呼び出しが
  報告されていました。コミット済みのコードに対して何も報告しないのは、この検査に
  とって正しい状態です — 動作している Ruby が自分のメソッドを誤った引数の個数で
  呼ぶことはなく、この検査が捕まえる間違いはエディタ上で作って数秒後に直すもので、
  コーパスには入りません。そこで逆向きに計測しました。意図的に誤った呼び出しを
  書いたところ、クラスに対しては **31 / 31**、モジュールに対しては **0 / 16** を
  検出しました。理由は下の「モジュールに対する呼び出しのタイプミス」の節にあります。
  つまり、このような構成のコードベースでは引数個数の間違いの約 3 分の 1 が報告されず、
  そのすべてがモジュールをレシーバとする呼び出しです。
- **引数の型**の検査はきわめて狭く、これまでに計測したコードでは1件も
  報告しません。Rubyの標準ライブラリ・Rails の5つのgem・minitest の
  2,042ファイルに対して**0件**、prism に自身のRBSを読ませても**0件**
  でした(024.37)。0.2.0の最後の修正前はこの2つのコーパスでそれぞれ795件と
  151件出しており、そのすべてが誤りでした。誤りを見つけてくれるものではなく、書いたコードに
  異を唱えてはこないもの、と捉えてください。理由は以下の条件です。 <!-- documents: 024.37 -->

  入力がすべて*宣言されている*場合にだけ検査します。
  期待される型がRBS/RBIの宣言由来であること(Rubyのソースは引数の型を
  宣言しません)、オーバーロードがちょうど1つであること、宣言側も引数側
  も素のクラスであること。判断できない呼び出しは推測せずに通すので、
  union・interface・ジェネリクス・複数オーバーロードの中にある本物の
  不一致は報告しません。

  「黙る」ではなく「誤る」形が1つ残ります(024.19)。ただし **0.2.11 まで
  この段落が書いていたよりも狭い範囲です**。名前空間を書いた名前
  (`::Vendor::Gadgets::Widget` や `Vendor::Gadgets::Widget`)は、もはや
  索引の「最後の1区切りで一致させる」フォールバックに到達せず、何も宣言が
  なければ constant 解決不能として*報告されます*。残るのは、ワークスペース内の
  ちょうど1つのクラスだけが名乗っている**修飾なしの**名前です — `Widget.make(1)`
  は、あなたが意図したレシーバが別の `Widget` であっても、そのクラスの
  シグネチャに対して判断されます。手がかりになるのは、レシーバの名前空間と
  無関係なところから来た型名がメッセージに現れることです。 <!-- documents: 024.19 -->
- **何も代入されない `@ivar` の読み出し**はERBビューだけが対象で、
  代入の集合を完全に列挙できる場合に限ります。これは高い水準であり、
  次のどれか1つでも該当すればそのビューでは検査自体が黙ります。直近の
  親クラスが読めていない、`instance_variable_set` を使っている、
  モジュールをmix-inしている、モデル化していないコールバック形式がある、
  **継承鎖のいずれかのクラスのボディが `private`/`protected`/`public`・
  `before_action`・`skip_before_action` 以外を呼んでいる**(鎖全体が対象なので、
  `ApplicationController` のボディがその下の全ビューについてこれを決めます。
  `after_action`・`around_action`・`prepend_before_action` も黙らせる側です)(gemのマクロ —`load_and_authorize_resource`・
  `expose`・Devise・ActiveAdmin— はすべてここに該当します。何を仕込むかは
  024.R7で索引が帰属を持つまで見えないためです)、**ビューが何かを
  renderしている**、**継承鎖のいずれかのクラスが複数ファイルに分かれて
  宣言されている**(祖先1つにつき1ファイルしか解決しないため、クラスを
  再オープンする2つ目のファイルは読まれません)。兄弟アクションでの代入も、意図的に黙らせます。

  **`rails new` が生成するアプリケーションでは、この検査は一度も発火
  しません**(024.22)。Railties 7.2・8.0・8.1はいずれも、ボディで
  `allow_browser versions: :modern` を呼ぶ `ApplicationController` を
  生成します。この呼び出しはモデル化済みの5つに含まれず、規則は継承鎖
  全体に及ぶため、既定のRailsアプリケーションでは全ビューが黙ります。
  G16の能力行が通っているのは、手書きの空の `ApplicationController` に
  対してであり、それは `rails new` が生成する形ではありません。 <!-- documents: 024.22 -->

  結果として報告されるのは、素のRubyで書かれたコントローラと、partialを
  renderしないビューです。「黙る」ではなく「誤る」形が2つ残ります。どちらも024.18に記録済みです。
  *別の*コントローラのアクションが描画するビュー(`render "users/show"`)
  では自分のコントローラのivarしか見ていません。また継承が3段以上あり、
  最上位のワークスペースクラスがまだ読めていない場合、防護は1段目にしか
  効きません。 <!-- documents: 024.18 -->
- **開いていないファイルの診断**は1回のパスで2,000ファイルまでで止まります。
  それを超えるワークスペースでは残りに診断が出ません。パスはソート順に歩くので、
  出ないのは保存のたびに変わるのではなく常に同じ末尾です。上限に達したことは
  Coreがログに出します。ここでの「ファイル」は診断を発行したファイルのことで、
  開いているファイル・存在しないファイル・例外になったファイルは数に入りません。
  (0.2.1 まで、この項目には「実物のRailsアプリに対するE2E検証がなく、そのために
  書いた例が45秒経っても何も出さなかった」とも書いてありました。実際には動きます。
  実物のRailsアプリでは、一度も開いていないファイルにプロセス起動から1.4秒で
  答えが返ります。G17 の行と例が現在あり、元の計測が何を踏んだと考えられるかは
  024.14 に記録しています。)

## コアクラスと同じ名前を持つ自作クラス

**名前空間の中にあると、その receiver の間違いが報告されなくなります。**
`Billing::Range`・`Admin::File`・`Reporting::Time` を、Rubyが自分の
名前空間の中からクラスを参照する普通の書き方 — 修飾なしの名前 — で書いた
場合、ホバー・定義へ移動・補完・シグネチャヘルプはすべて答えますが、
その receiver に関する診断は黙って抑止されます。`Billing::Range` 上の
`r.tagg` のような打ち間違いは一度も指摘されず、名前の重ならないクラス上の
同じ打ち間違いは指摘されます。エンジンはあなたが書いた `Range` と
リテラルが生む `String` を区別できないため、リテラルを守るための抑止が
自作クラスまで黙らせるのです。さらに、**同じ名前の**リテラルは代償の
もう半分を払います。`Billing::Range` がある状態では `(1..5).` の補完は
Range ではなく `Billing::Range` のメンバー(`each` ではなく `tag`)を
出し、`(1..5).each` のホバーは本物の Range から答えます — 読み手どうしが
食い違っており、どちらが正しいかはエンジンの持たない情報に依存します
(024.47)。名前の重ならないリテラルは影響を受けず(あなたのクラスに
`…::String` がない限り `"hello".` はいつもどおり String を補完します)、
トップレベルにあるコアクラスと同名のクラスも影響を受けません。 <!-- documents: 024.47 -->

(0.2.3 より前、この節は逆のこと — 0.2.1 でホバー・定義・補完が答えなく
なった — を書いていました。それは 0.2.1 のレビューループ内で作られ、
出荷前にロールバックされた配置の説明です。0.2.1 が実際に出荷したのは
上記の「診断の沈黙」です。)

## パッケージ済み拡張機能は、スモークテストはされますが駆動はされません

VSIX の中の Core Server — あなたが実際にインストールする、独自の native
extension を同梱したもの — は、公開時にホバー・定義ジャンプ・正常終了を確認する
スモークテストで検査されます。ただし、リポジトリ側のコピーのように**変更のたびに
エディタセッション全体を通して駆動されることはありません**。そのため、パッケージ
済みビルドでのみ現れる不具合は、レビュー時ではなく公開時に見つかります。 <!-- documents: 024.125 -->

## 「ワークスペース内のシンボルへ移動」は全シンボルを走査する

ワークスペースシンボルの検索は、専用の索引を使わず、入力のたびに索引内
の全シンボル名と照合します。ワークスペースが大きいほど遅くなり、さらに
この走査はインデックス構築と同じロックを保持するため、同時に走っている
インデックス構築を待たせることがあります。ファイル内のシンボル検索と
「定義へ移動」は別経路のため影響を受けません。 <!-- documents: 024.137 -->

## バージョン不一致のときに実際に起きること

**知らせて、そのまま続きます** — Core Server が起動した*あと*に見つかる
不一致については。拡張機能と Core がバージョン・プロトコル・ビルド識別子・
ペイロードのハッシュのいずれかで食い違うと、エラー通知が出て詳細が Output
チャンネルに出ますが、セッションはそのまま動き続けます。

これが効いてくるのは、目に見えない2つの場合です。ペイロードのハッシュ不一致は
同梱 Core がこのビルドの出荷物ではないことを意味し、プロトコル不一致は両者が
通信の取り決めについて食い違っていることを意味します。どちらの場合も OvalLSP
はホバー・補完・定義への移動に答え続けます。不一致を解消するまで、それらの
応答は信頼できないものとして扱ってください。検出内容は
`OvalLSP: Show Version Information` で確認できます。

Core Server の起動*前*に走る検査の方は停止します。0.2.10 以降、このビルドの
同梱依存をロードできない Ruby の場合、Core Server はそもそも起動せず、その旨が
通知されます。

**この違いは意図的なもので、0.2.12 がその理由を記録しました。** Core は拡張機能に
同梱されているため、起動後の不一致に到達する道は `ovallsp.serverPath` を自分の
Core に向けることだけです。利用者が自分で設定したセッションを拒否するより、何が
一致していないかを伝える方が良い、という判断です。

## 編集の再解析にかかる時間

**数千行のファイルでは数秒です。** 1打鍵あたりで計測(署名の初回読み込みは
除外): `net/http.rb`(2,574行)で 2.1 秒、`rubygems/specification.rb`
(2,666行)で 5.3 秒。しかもファイルの大きさより速く増えます。Coreは要求を
1つずつ処理するので、ホバーも補完もシグネチャヘルプもその後ろで待ちます。

設計文書はここに 300ms と書いているので、これは好みの問題ではなく、
1桁以上外している要件です。0.2.1 までここに記載がありませんでした
(024.45)。本リリースで悪くなったわけではなく、0.2.0 でも同じです。
数百行のファイル — アプリケーションコードの大半 — は 0.1 秒を大きく下回ります。 <!-- documents: 024.45 -->

**入力が止まるまで報告を遅らせる方式は 0.2.2 で試されてロールバックされ、
0.2.10 で別の形で作り直されました。** 最初の試みは時間を測るデバウンスと
待機スレッドで、2つの競合を生み、1ファイルに対して何本の解析が同時に走るかを
抑えられず、4回連続のレビューラウンドがそれぞれ別の不具合を見つけました。
現在出荷されているものはデバウンスではありません — 間隔も待機スレッドもなく、
聞いているのは「他に読むべき入力があるか」だけです。1回の解析より速い連続入力は
打鍵ごとではなく数回の答えを返し、そして体感される部分として、**入力中に求めた
ホバーが保留中の解析より先に答えられます**(1.4秒ではなく約0.04秒)。打鍵ごとの
ままなのは、解析より遅い入力の場合です。落ち着いた編集は必ず解析される、という
性質の方が重要だからです。 <!-- documents: 024.57 -->

## 未定義メソッド検査が実コードで間違えること

**実測: インストール済み gem のソース 213 ファイルに対し 54 件の報告、
そのうち 53 件が誤りでした。0.2.6 でこれが 9 件になります。** 測定は毎回
同じもの — 同じファイル、同じサーバー、そして変更が影響し得ない分類を
対照として置いた上での比較です。

アプリケーションコードにとって重要だった原因はなくなりました。**同一ファイル内
で定義されたモジュールを、入れ子の名前空間の内側から `include` している**
クラスが、そのモジュールのメソッドを失い「存在しない」と報告される問題です。
Rails の concern がまさにこの形でした。メタプログラミング（`attr_atomic` 等、
静的解析には見えないもの）も同様で、この拡張機能が読めないマクロを本体で
実行しているクラスは「メソッド集合を把握できていない」扱いになり、推測せず
沈黙するようになりました。

**まだ誤って報告されるもの**と、その見え方:

- **別の Ruby 実装向けのファイル。** JRuby 専用のソースは `java` を呼びますが、
  あなたの MRI にはありません。9 件中 7 件。JRuby 固有のファイルを開かない
  限り目にしません。
- **サブクラスが与えるメソッド。** サブクラスが定義するメソッドを呼ぶ抽象
  クラス — 意図的な template method — は報告されます。そのクラス単体では
  実際に呼び出しが失敗するためです。9 件中 2 件。 <!-- documents: 024.76 -->

実行時に決まるモジュール — 変数やコンストラクタ引数に入ったものを `extend`
する形 — も以前は三つ目の種類でした。名前を特定できない祖先が「祖先なし」と
して記録されていたためです。現在は「名前を特定できない祖先がある」として
記録され、そのクラスのメンバーについては何も報告しません。

## ブロックの中に書いた `private` / `module_function`

`SOME_CONST.each { private }`、`helper { private }` のように、**この拡張機能が
レシーバを保証できない**ブロックの中に書いた場合、それ以降のメソッドに適用しません
(Ruby は適用することがあります)。クラスやモジュールの本体に直接書いた場合は
正しく働き、0.2.15 以降はリテラルを回すブロック(`[1].each { private }`、
`%w[a b].each { module_function }`、`[1].each { protected }`)でも正しく
働きます。以前のリリースではここに 0.2.13 と書いていましたが、それは誤りで、
実際に直ったのは 0.2.15 です。

残っているのは、その呼び出しがブロックに対して何をするかを知らなければ判断
できない場合です。`included do ... end` は実際に別のモジュールに対して `private`
を実行するので、これらを同じに扱うと、そのブロック以降のメソッドがすべて private
になってしまいます。これは誤った報告を増やすのではなく本来の回答を失わせる方向の
失敗なので、現状はブロックの中に閉じ込める側に倒しています。 <!-- documents: 024.221 -->

## モジュールに対する呼び出しのタイプミス

`PlainClass.nope` は報告され、`PlainMod.nope` は報告されません。モジュールの
祖先チェーンは自分自身なので、この拡張機能は「このモジュールが宣言するものを
すべて見た」と「このモジュールを再オープンするファイルを1つ見た」を区別でき
ません。0.2.10 は両者を同じものとして扱ってみて、`Rails.application`・
`Rails.env`・`Rails.logger` を「存在しない」と報告してしまいました。索引が
その違いを証明できるようになるまでは、報告しない側が安全な選択です。
`module_function` と `extend self` 自体は動作します — それらのメソッドは補完・
ホバー・定義ジャンプに出ます。 <!-- documents: 024.106 -->

## 呼び出せないメソッドが補完に出ること

クラスに対して（`Post.`、`Circle.`）、および素の Ruby プロジェクトでは
どのレシーバに対しても、private メソッドが一覧に入ります。実際に動いている
アプリケーションに「その名前が本当に呼べるか」を問い合わせた実測で、Rails の
モデルクラスでは 816 件中 91 件、素のプロジェクトの自作クラスでは 121 件中
69 件（`initialize` を含む）。選ぶと `NoMethodError` になります。Runtime Agent
が接続された Rails プロジェクトのインスタンス側の一覧は正常
です。 <!-- documents: 024.99 -->

## 4つの機能が同じ位置で食い違うこと

- ビューの `<% @posts.each do |post| %>` の後の `post.titel`: ホバーは `Post`
  と答え、補完は Post のカラムを出し、未定義メソッド検査だけが何も言いません。
  `<% Post.all.each do |post| %>` と書けば報告され、`.rb` ファイル内の同じ
  コードも報告されます。
- `p.update`、`p.save!`、`q.destroy`: ホバーは何も表示せず定義も見つからない
  のに、補完はそれらを出し、検査も受理します。
- シグネチャヘルプは `Post.new(`、`Circle.new(`、`Post.find(`、`p.update(`
  で無言な一方、自作メソッドや `"abc".split(` では答えます。オーバーライド
  したメソッドはシグネチャが二重に出ます。 <!-- documents: 024.100 -->
- **view の中では、補完と定義ジャンプが答える位置でホバーだけが何も
  答えません。** `<%= @user.full_name %>` のモデルメソッドにカーソルを
  置くと、補完はそのメソッドを出し、定義ジャンプは開くのに、ホバーは
  空です。同じ呼び出しを `.rb` に書けば通常どおり表示されます。 <!-- documents: 024.240 -->
- **Find References が、コメント・裸の数値・`end` からも答えます。**
  メソッド本体の中であればどこにカーソルを置いても — コメントの中で
  あっても — そのメソッドの呼び出し箇所が一覧されます。名前の上に
  カーソルがあるかのように扱われるためです。同じ位置で rename を
  求めると、そちらは正しく辞退します。 <!-- documents: 024.241 -->
- **ローカル変数に入れたクラスは、宣言されたオーバーロードを落とすこと
  があります。** `Zoo.pick(1)` と `k = Zoo; k.pick(1)` は同じ呼び出し
  ですが、後者はあなたの `sig/` が宣言しているシグネチャのうち狭い
  範囲からしか答えません。 <!-- documents: 024.242 -->

## 動く Ruby なのに未定義メソッド検査が報告するもの

2つの形があり、いずれも実際に動くコードです。rspec-core / i18n / psych /
reline の 177 ファイルに対する実測で 16 件です。

- **include したモジュール由来のメソッドへの `alias`。** `include Escaping`
  の後に `alias safe_escape escape` と書くと、`safe_escape` の呼び出しが
  報告されます。同じクラス内の `def` への alias は問題ありません。 <!-- documents: 024.238 -->
- **自作クラスの中に書いた `URI(...)`。** `Kernel#URI` は gem 由来で、この
  拡張はまだ gem が定義しているものを索引していないため、見えていません。
  gem が供給する他の `Kernel` メソッドも同様です。 <!-- documents: 024.R7 -->

この節は 0.2.16 まで「4つの形・41 件」と書いていましたが、そのうち2つは
数リリース前から既に起きていませんでした。元になった指摘を分割する際に
測り直したところ、記述が両方向に古くなっていたものです。`Struct.new` /
`Data.define` で作ったクラスの再オープン、`Class.new do … end` の中の
`define_method` と `attr_reader`、リテラル名でループ内定義したメソッド —
これらはもう報告されません。検査がその本体ごと辞退するようになったためで、
裏を返せばそこに書かれた本物の打ち間違いについても何も言いません。誤った
答えではなく沈黙であり、それでも欠落ではあります。 <!-- documents: 024.237 -->

## Runtime Agent が居ないときに未定義メソッド検査が間違えること

プロジェクトがコアクラスを再オープンしている場合 — `initializers/core_ext.rb`
など、`class String` を含むもの全般 — この拡張機能はそのクラスを完全に把握して
いるものとして扱い、**gem** が追加しているメソッドを片端から「存在しない」と
報告します。`String has no method named squish`、`Integer has no method named
minutes` など。ActiveSupport と ActiveModel 自身のソースに対する実測で 74 件。

ワークスペースにコードが無い gem のモジュールを include している場合も同じ
です。`include Singleton` の後の `.instance`、`include Sidekiq::Worker` の後の
`sidekiq_options` — この2つは 0.2.6 で直しましたが、この系統を完全に答えられる
のは、クラスが実際に応答するものを報告する Runtime Agent です。

**つまりこれは、Agent を動かせない場所でこそ最も鳴ります**: Agent を持たない
素の Ruby プロジェクトと、VS Code の Restricted Mode の Rails プロジェクト
（フォルダを信頼するまでは全ての Rails プロジェクトがそうです）。ワークスペース
を信頼すれば解消します。 <!-- documents: 024.83 -->

## 定数のホバーが返すもの

**その定数自身の名前を、クラスとして返します。** `MAX_RETRIES = 3` の後の
`MAX_RETRIES` は `Integer` ではなく `ClassOf[MAX_RETRIES]` とホバーします。
文字列・浮動小数点・配列・凍結ハッシュでも同じです。定数の後の補完は何も出さず、
定数から代入したものも使える型を持ちません。 <!-- documents: 024.84 -->

## 別のメソッドで代入されたインスタンス変数

`before_action` で代入された `@article` を action で読む場合、**ビューでは**型が
付き、**コントローラでは**付きません。`show.html.erb` でホバーすると `Post` で
補完候補は 408 件、同じ名前をコントローラでホバーすると何も出ず候補は 0 件です。
あるメソッドで書いて別のメソッドで読む ivar は全てこうなります。 <!-- documents: 024.86 -->

## relation が relation でなくなる場所

`Post.where(published: true)` は解釈されます。`Post.where(published:
true).where(user_id: 1)` は解釈されず、`.order`、`.limit`、`.includes`、
`.count`、2つ目の scope も同様です。2つ目の連結でホバーが空になり、未定義
メソッド検査も止まります — `Post.published.where(user_id: 1).titel` は報告され
ません。 <!-- documents: 024.87 -->

## 2つの型を取りうる値の補完

`x = cond ? "s" : 1` は `String` の全メソッド **と** `Integer` の全メソッドを
出します。片方を選ぶともう片方の分岐で失敗します。

0.2.15 からは、どちらがどちらかは一覧に現れます。**両方**の分岐が持つメソッドが
先に並び、片方だけが持つものはその後ろに並びます。これは並び順であって警告では
ありません — `Integer` かもしれない値に対して `upcase` を出すこと自体は変わり
ません。

*以前のこの段落は「未定義メソッド検査は同じ値について逆の(安全な)立場を取るので、
2つの機能が食い違います」と書いていました。その位置で実測すると、検査は何の立場も
取っていません。`String | Integer` に対しては、どちらの分岐もそのメソッドを持たない
場合でさえ黙りますし、ただの `String` に対しても黙ります。理由は下にある
「コアライブラリのレシーバ」の項目という別のものです。ここで書かれていた対比が
成り立つのは、自分で定義したクラスに対してだけです。* <!-- documents: 024.88 -->

## シグネチャヘルプが表示するもの

引数を打ち進めてもハイライトが移動せず、呼び出しのあいだずっと最初のパラメータに
留まります。これは誤動作ではなく、この製品がまだ持つと表明していない機能です。
`docs/ROADMAP.md` が 0.4.0 の項目として「シグネチャヘルプがカーソルのある引数を
強調する」を挙げています。

*0.2.15 より前は、パラメータ自体も削ぎ落とされて表示されていました。
`def simple(a, b = 2, *rest, key:)` が `simple(a, b, rest, key)` と出て、
`key` が4番目の位置引数であるかのように見えていました。こちらは修正済みで、
書いたとおりの綴りで表示されます。*

## 細かいもの

- コアライブラリのレシーバに対するタイプミスは報告されません。`"hello".upcse` や
  `[1,2].siz` は無言です（同じ位置の補完は型を正確に把握しています）。 <!-- documents: 024.129 -->
- concern の `included do` の中で定義した scope は型を持ちません。 <!-- documents: 024.132 -->

## 部分テンプレートのローカル変数が解決するもの

**何も解決しません。** `_article.html.erb` の `article` は `render` を
呼んだ側が渡すもので、エンジンはその呼び出し側を読んでいません。そのため
ホバーは空のポップアップを返し、`article.` は何も補完しません。同じ
テンプレート内の `@ivar` は、代入したコントローラのアクションから解決します。
テンプレート自身が代入したローカル(`<% post = Post.new %>`)も解決します。
scaffold したアプリのビューでは、これがいちばん多い形です(024.44)。 <!-- documents: 024.44 -->

## 標準ライブラリ・gemのメソッドでシグネチャのポップアップが見せるもの

2つあり、どちらも「どのメソッドを見つけたか」ではなく*ラベル*の話です。

- **RBSが `self`・`void`・`untyped` と書いている戻り値が `Unknown` と
  表示され**、メソッド自身の型変数もそのまま出ます(`map() -> Array[U]`)。
  エンジンは「ここから何も結論できない」を表す語を1つ持っていて、それを
  人が読むための場所にも使っています。RBSが実際に書いた語を出す方が
  親切です(024.42)。 <!-- documents: 024.42 -->
- **stdlibの祖先だけが宣言しているメソッドを呼ぶと、ポップアップが一切
  出ません。**同じメソッドを補完は出します。レシーバを書かない `puts(` が
  最もよく出会う形ですが、レシーバの有無の問題ではありません。自分のクラスが
  stdlibのクラスを継承している場合、`MyErr.new.full_message(` のように
  レシーバを明示しても同じように失敗します。シグネチャヘルプはレシーバを
  そのままシグネチャに対応づけるだけで、祖先をたどりません(024.43)。
  *以前のこの行は「レシーバなしの経路は囲みクラスの祖先が宣言するものを
  尋ねており、その中にKernelが無いためです」と書いていました。実際にはそうでは
  なく、そこで言及されている祖先探索はKernelを正しく返します。シグネチャヘルプが
  それを呼んでいないだけです。* <!-- documents: 024.43 -->
- **ファイルのトップレベル、どのクラスにも属さない位置では、シグネチャヘルプが
  何も出ません。** クラス本体ではなくスクリプトとして書いた `puts(` がこれです。
  テストをすべて通したうえで事態を悪化させる直し方が存在します。自分で定義した
  トップレベルのメソッドの呼び出しに対して、同名のstdlibメソッドを答えて
  しまうもので、`open` が最も衝突しやすい名前です。急いで直すのではなく、
  正しく直します(024.229)。 <!-- documents: 024.229 -->
- **ファイルのトップレベル、どのクラスにも属さない位置で定義したメソッドは、
  どこからも見つかりません。** ホバーも補完もシグネチャヘルプも定義ジャンプも
  効きません。Rubyはこうしたメソッドを `Object` に置きますが、この拡張機能は
  所有者を記録していないため、探しようがありません(024.230)。 <!-- documents: 024.230 -->

## マクロが宣言したメソッドのリネームは拒否されます

`attr_accessor :name`、`delegate :title, to: :author`、`enum`、`scope` は、
識別子トークンではなく*シンボル引数*の位置でメソッドを宣言します。
アウトラインはその引数を指すようになり、マクロが宣言する名前それぞれが
自分の項目を持ちます。ただし各項目が選択するのは宣言元のトークンであって、
その項目自身の名前とは限りません。`attr_accessor :alpha` は1つのトークンで
2つのメソッドを宣言するため `alpha=` は `alpha` を選択し、`enum` の述語
`active?` は導出元のラベル `active` を選択します。**リネームは
そのトークンを編集せず、拒否します。**

その引数はマクロが読み取るソースであってメソッド名そのものではないため、
書き換えることはリネームとは別の編集になります。`attr_reader :name` は
読み出す `@name` の名前でもあるので、書き換えると誰も代入していない ivar
を読むリーダーになります — 動きはするが `nil` を返すファイルです。
`attr_accessor :name` は同じトークンから `name=` も宣言するため、1回の編集が
2つのメソッドをリネームし、計画に入っているのは一方の呼び出し箇所だけです。
`enum status: { active: 0 }` の `active` はラベルで、列に保存されるのは `0`
です。同じラベルはスコープ `Order.active` の名前でもあり、`Order.statuses`
のキーでもあります。`delegate :name, to: :company` が指すのは
*`Company` 側*のメソッド名で、リネームが触ってはいけないものです。

`scope :recent` と `define_method(:calc)` は引数が本当に名前だけの2つの形
ですが、これらも一緒に拒否されます。拒否の判断地点には、どのマクロが何を
宣言したかを示す情報が無いためです。VS Code は自前の「名前を変更できません」
を出します。理由が届くのはCoreのログだけです(024.28)。 <!-- documents: 024.28 -->
