# 055 — 0.3.1: what a restart forgets, and what four documents got wrong

**Branch:** `release/0.3.1`, merging into `main` by pull request.
`CLAUDE.md`'s "Where a release's work lives" has the rule, and as of
this release `scripts/check_release_pointers.rb` fails when a release
branch exists that no task document names — which is what this line is.

**Scope:** a patch. Nothing here moves a capability row. It began as one
performance fix and grew a second: the two register entries targeted at
0.3.1 were driven, and driving them changed what both of them were.

## What was owed, and what driving it found

`024.294` and `024.295` were the only entries targeted at 0.3.1. Both
were written without being re-driven, and both turned out to be wrong
about the thing they asserted.

**`024.294` said the undefined-method check never acts on an `@ivar`
receiver.** In ordinary Ruby it does, and has since 0.3.0's `H8`. The
entry was split off from `024.86` while that half was being fixed and
never re-driven — `024.130`'s shape exactly, a limitation published in
both languages that the product does not have. The template half is
real, and the entry is now about that; it moved to 0.4.0, because
turning that decline into an answer needs the render-target index
`024.18` owns.

**`024.295` asked for a per-gem-version cache key, and that key cannot
work.** The Agent attributes a module by definition site, so a model's
generated association and relation modules are filed under
`activerecord-8.1.3.1` — driven twice with `Gemfile.lock` byte-identical,
adding one model and then one scope changed that gem's slice. Its two
published numbers were also stale: 1,815 KB, not 938 KB, and the walk is
17–26 ms rather than the wait. It moved to 0.3.2 with the key question
reopened.

**What that investigation found instead is what this release fixes.**
`#restart_agent` drops `@ancestry_registry` under a comment arguing that
a fact from the old process cannot survive a restart — "what comes back
may be a different Gemfile, a different environment". The gem index is
the same kind of fact and was kept. A `bundle install` routes to a
restart, so the old gems' method sets went on answering for the new
ones:

    FRESH: ["MyCtl has no method named `definitely_not_a_method_either`"]
    STALE: ["MyCtl has no method named `performed?`",
            "MyCtl has no method named `definitely_not_a_method_either`"]

`performed?` exists in the gems that came back. That is a wrong answer,
which section 0 ranks below saying nothing — and `KNOWN_LIMITATIONS`
told users in both languages that "nothing is reported wrongly in the
meantime".

## What was pinned

**0.3.0's `H8` was unpinned.** Mutating the ivar receiver's type away
left 1,156 examples green across every spec file naming `unknown-method`.
A capability the release counts, with nothing failing when it goes, is
the defect `CLAUDE.md` names in its own right.
`core/spec/ovallsp/diagnostics/view_ivar_receiver_spec.rb` holds both
halves now — the plain class reports, the template declines — with the
constant receiver in the same template as the control that keeps the
silence from being vacuous.

## What was mechanised

Three of `docs/DOCUMENTATION_MAP.md`'s twenty-one trigger rows have a
"Checked by" column that read as nothing at all and had, measurably,
gone stale.

- **The Core↔Agent protocol.** The document stated `protocolVersion: 1`
  against the Agent's 2, had no section for `agent/gemIndex`,
  `agent/status` or `agent/ancestors`, and specified seven methods that
  appear nowhere in `core/lib` — six of them written as an ordinary
  specification, which is exactly what that row says a section for
  something unimplemented must not be.
  `scripts/check_protocol_doc.rb` asks all three questions.
- **Where a release's work lives.** `release/0.3.1` existed and no
  document named it: 028's shape, which had 0.2.3 prepared twice in
  parallel. `scripts/check_release_pointers.rb` and the first line of
  this file.
- **A working agreement's own guard.** The branch convention changed
  from `feat/<version>` to `release/<version>` on 2026-09-01 and
  `AGENTS.md`, `CONTRIBUTING.md` and `.ja.md` were all updated — but the
  spec guarding `AGENTS.md` against reacquiring a hard-coded release
  claim still hunted for the retired spelling. Driven: `Work for the
  next one lives on \`release/0.3.2\`.` passed the old pattern and fails
  the new one, with the generic `release/<version>` form and ordinary
  citations unaffected.
