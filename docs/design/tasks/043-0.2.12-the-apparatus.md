# 043 — 0.2.12: the apparatus, and what it found

[`042`](042-second-enumeration.md)'s **D7, D8, D6 and D4**. The four
classes it put first, and not because they were the largest: they are the
ones whose failures make every *other* class's measurement untrustworthy.
Two of the three corpus comparisons in the 0.2.9–0.2.11 cycle were
invalidated by D8 alone, one of them in the script whose own comment
forbids exactly that.

## The mechanism, and the four things it found

`core/spec/meta/pinned_mutations.yml` names, per decision, the exact
replacement that inverts it and the one example that must fail.
`scripts/check_pinned_mutations.rb` applies each and requires the
failure; a gating CI job runs it, and the manifest's own shape is checked
in the ordinary suite so a renamed example fails locally rather than on a
push.

This is the hunk sweep turned around. The sweep asks whether *anything*
fails when a line is reverted; this asks whether *this example* fails
when the decision it names is inverted — which is what a comment saying
"an implementation that did X would fail this example" is claiming, and
which nothing checked.

**It reported all four mutations uncaught on its first run**, because a
copy of `core/lib` on the load path is not what gets loaded: the Gemfile
has a `gemspec`, so Bundler puts the real one at the front of
`$LOAD_PATH` ahead of anything `-I` adds. Worth recording on its own
terms: *a checker that cannot see the thing it checks reports exactly
what a working checker reports when nothing is pinned.* That is `024.122`
happening to the thing built to prevent a different defect.

Once it worked:

1. **A documented deliberate trade-off that was dead code.**
   `concern_marker_name?`'s `|| name.split("::").last == "Concern"`,
   added in 0.2.11 with a comment explaining the loosening it bought.
   `canonical_name` already resolves Rails' bare `extend Concern` to
   `::ActiveSupport::Concern`, so the clause never ran and the trade was
   never being made.
2. **A fix recorded as shipped that had never been written.** Asked about
   0.2.9's decisions, the mutation for the alias-visibility rule could
   not be expressed — the method it was supposed to invert did not exist.
   0.2.9's round designed that fix and it never reached a commit, while
   the register carried `024.105`, `024.107` and `024.108` as fixed and
   completion offered a name that raises. `024.123`.
3. **An example that guaranteed nothing.**
   `member_availability_spec.rb`'s "is frozen, so a reader cannot be
   handed one that changes under it" asserted the *Data* was frozen,
   which it is whatever the class does. It passed with every `freeze` in
   the file removed. One of `024.109`'s two reports whose identity was
   lost with the round's list.
4. **A claim about which example pins which decision, pointing at the
   wrong example.** `024.30` says its last unpinned term is now covered;
   the example I first named reads exactly right and is about something
   else. The checker said so.

None of these is visible by reading. They were all passing.

## D4, which found three readers rather than the two its entry named

`024.80` is an ancestor the index could not identify, expressed as an
entry whose `name` is `nil` — and `nil` is also the owner a top-level
`def` is indexed under, so asking one for its members answered with every
top-level method in the workspace. Two readers guarded it by hand, each
guard added after the bug was found in that reader.

Making the value refuse — `identified_name` as the member, `#name`
raising, `AncestorEntry.unidentified` the only way to build one — turned
up three more the same run. One would have compared `nil` against
`::BasicObject`; one asked RBS for a signature under the `nil` owner,
taking whatever the top level happened to declare. Each was waiting for
the bug to be found a third time.

## The corpus, and what it is evidence of

Four gems, control `unresolved-constant` identical at 1,099:
**`unknown-method` 84 → 84, 0 added and 0 removed.**

That is a control, not evidence. Every user-visible fix in this release
fires on a shape those gems do not contain — a workspace class method on
`Object`, an ancestor named ambiguously, a private alias — so the
evidence is the examples run against the interpreter, one at a time, and
the number's job is to show that nothing *else* moved.

## Two things worth carrying forward

**A partial green run is not a green suite.** One commit went out on
`spec/ovallsp/semantic` and `spec/ovallsp/diagnostics` being green; a
construction site in a third directory failed the full run. The commit
that fixed it says so rather than quietly correcting.

**The third round on one place buys a countermeasure, not a third
guess.** `024.120`'s watcher example failed twice on Linux and both fixes
were about the spec's own timing. The cause was not timing: a
second-level directory created after the extension host started never
became watched at all, so rewriting the file could not help — it is not
the file that is unwatched. The directories are committed now.

## What is open, and where it goes

`024.121` — the third layer. This release's mechanism makes a *stated*
claim unable to be false; it is opt-in, so a decision nobody thought to
list is as unprotected as before. Whole-tree mutation coverage with a
ratchet is what needs nobody to remember anything, and `024.71`'s
fixture isolation is its precondition.

`024.122` — 72 measured places where a failure becomes a plausible value.
Raised by the maintainer during this release and scoped to 0.2.13, with
its policy step deliberately last: declaring the rule before the tree
obeys it would make a rule with 72 exceptions on the day it was written.
