## Where it starts, and the measurement that decided the shape

`045` puts `024.R9` first — the register is cheapest to move when
nothing is appending to it, and this release is a review loop that will
append. Measured here rather than taken from that sentence:

| | |
|---|---|
| register | **20,703 lines, 287 entries, 1.1 MB** |
| resolved (`fixed`/`done`) | **239 entries, 15,670 lines — 75.7%** |
| open | 48 entries, 4,560 lines — 22.0% |
| generated index at the head | 473 lines |
| tracked files naming the register **by path** | **26** |
| tracked files citing an entry **by number** | 278 |

Two things follow, and both are the kind of thing `024.R9` says to
measure at the revision that moves it rather than read out of its own
prose.

**The blast radius is 26 files, not 278.** Entries keep their `024.`
numbers — the entry is explicit that this is a move plus an index and
never a renumber — so every citation in the tree survives untouched. It
is the paths that break.

**And the split the numbers support is by state, not by path.**
`024.R9`'s "proposed shape" is a move to the top of `docs/`; its
alternative is a split by state. A move changes the path string and
nothing else, while a split by state takes the file every session reads,
and every scripted edit risks, from 20,703 lines to about 5,000.
`024.225` records a scripted edit that took this file from 11,555 lines
to 25,878 twice over, with "the diff far too large to read" — and 76% of
what was in the way is archive.

The constraint that decides the design is `024.R9`'s own: **one place to
look.** A reader holding `024.N` must not have to know which file it went
to.

## Three checks caught the split before the suite did

Each was reading the live file directly, and each said something
confidently wrong:

- `measured_claims_spec`'s `register-entries` deriver said **48** where
  the tree has 287;
- its citation check called **every citation of a resolved entry** a
  dangling pointer, `.github/workflows/ci.yml` first;
- `deferred_findings_spec`'s index check compared the index against the
  live file's own headings.

The third then failed again for a different reason, and that time the
check was wrong rather than the split: it compared *ordered* lists, which
was right while the register was one file in numeric order and is not
across two, where the combined order is state-then-number. Compared by
entry key now. The live file's numeric order and index currency are still
asserted byte-for-byte elsewhere; the archive's own order had nothing
asserting it and now does.

## The move is a script, and preflight's tenth check says it was run

Resolving an entry means moving it across, and a split that depends on
somebody remembering is not a split. `scripts/archive_resolved_findings.rb`
does the move; `--check` reports without writing and is preflight's tenth
check. Verified by planting a resolved entry back into the live register:
the script named it and exited 1, and `register_split_spec` failed.

A script rather than a hand edit because this exact file is where this
repository has its worst editing record — `024.225`, a scripted `sub`
that took it from 11,555 lines to 25,878, twice.

## First capability: `textDocument/documentHighlight` (F1, F2)

`045` orders it first of the four that need only what already exists —
the reference index answers occurrences workspace-wide, so scoping to one
file is nearly free.

**The deferral note in `server.rb` named the trap, and it is the whole
design.** References and Rename call `#ensure_reference_index_current`,
whose rebuild is O(workspace), and *the editor asks for highlights on
every cursor move*. So this answers from the open file's own summary,
narrowing candidates by name before resolving any, and the third example
asserts the reference index's generation does not move across five
requests. An implementation that reached for `references_result` would
pass the two behavioural examples and rebuild the workspace index on
every keystroke.

**A local is `Text`, not `Read` or `Write`.** The parser records one
`local_variable` candidate kind for every mention, assignment and read
alike, so telling them apart would mean re-deriving it from the source at
this layer. Section 0 ranks a wrong answer below no answer and the
protocol has `Text` for exactly this. A `method_call` candidate *is* a
call, so it is `Read`; a declaration is `Write`. Neither of those is a
guess — one comes from `reference_candidates` and the other from
`declarations`.

Four decisions, each mutated by hand and each caught:

```
  scope match dropped     3 examples, 1 failure
  kind flattened to Text  3 examples, 1 failure
  declaration row dropped 3 examples, 1 failure
  index warmed anyway     3 examples, 1 failure
```

All four are in `pinned_mutations.yml`; the manifest is 104 and every one
is caught by the example that names it.

### A check that could not see a new capability group

`capability_coverage_spec` matched capability ids with `[BHCDGSTW]\d+` —
a letter list somebody remembered, which is the defect that file's own
comment describes about `\d` versus `\d+`. A capability group under a new
letter would have been invisible to **both** directions, so a row with no
example *and* an example with no row would have passed.

Widened to `[A-Z]+\d+` and verified by planting an `F1` row with no
example: it now reports it. **Then the same list turned out to have a
third copy**, in the Japanese-pair example, and it was missed when the
first two were widened — the list-somebody-remembered defect appearing a
third time inside the fix for it. Found by the check itself, on the real
rows.
