**Branch:** `release/0.3.0`, merging into `main` by pull request. That
convention was set on 2026-09-01 and arrived through its own pull
request; `CLAUDE.md`'s "Where a release's work lives" has the rule.

**Scope:** [`045`](045-0.3.0-scope.md), unchanged. This file is the
running record; `045` is the argument for the order.

## Where it starts, and the measurement that decided the shape

`045` puts `024.R9` first — the register is cheapest to move when
nothing is appending to it, and this release is a review loop that will
append. Measured here rather than taken from that sentence:

| | |
|---|---|
| register | **20,703 lines, 287 entries, 1.1 MB** |
| resolved (`fixed`/`done`) | **239 entries, 15,670 lines — 75.7%** |
| open | 48 entries, 4,560 lines — 22.0% |
| generated index at the head | 473 lines |
| tracked files naming the register **by path** | **26** |
| tracked files citing an entry **by number** | 278 |

Two things follow, and both are the kind of thing `024.R9` says to
measure at the revision that moves it rather than read out of its own
prose.

**The blast radius is 26 files, not 278.** Entries keep their `024.`
numbers — the entry is explicit that this is a move plus an index and
never a renumber — so every citation in the tree survives untouched. It
is the paths that break.

**And the split the numbers support is by state, not by path.**
`024.R9`'s "proposed shape" is a move to the top of `docs/`; its
alternative is a split by state. A move changes the path string and
nothing else, while a split by state takes the file every session reads,
and every scripted edit risks, from 20,703 lines to about 5,000.
`024.225` records a scripted edit that took this file from 11,555 lines
to 25,878 twice over, with "the diff far too large to read" — and 76% of
what was in the way is archive.

The constraint that decides the design is `024.R9`'s own: **one place to
look.** A reader holding `024.N` must not have to know which file it went
to.

## First capability: `textDocument/documentHighlight` (F1, F2)

`045` orders it first of the four that need only what already exists —
the reference index answers occurrences workspace-wide, so scoping to one
file is nearly free.

**The deferral note in `server.rb` named the trap, and it is the whole
design.** References and Rename call `#ensure_reference_index_current`,
whose rebuild is O(workspace), and *the editor asks for highlights on
every cursor move*. So this answers from the open file's own summary,
narrowing candidates by name before resolving any, and the third example
asserts the reference index's generation does not move across five
requests. An implementation that reached for `references_result` would
pass the two behavioural examples and rebuild the workspace index on
every keystroke.

**A local is `Text`, not `Read` or `Write`.** The parser records one
`local_variable` candidate kind for every mention, assignment and read
alike, so telling them apart would mean re-deriving it from the source at
this layer. Section 0 ranks a wrong answer below no answer and the
protocol has `Text` for exactly this. A `method_call` candidate *is* a
call, so it is `Read`; a declaration is `Write`. Neither of those is a
guess — one comes from `reference_candidates` and the other from
`declarations`.

Four decisions, each mutated by hand and each caught:

```
  scope match dropped     3 examples, 1 failure
  kind flattened to Text  3 examples, 1 failure
  declaration row dropped 3 examples, 1 failure
  index warmed anyway     3 examples, 1 failure
```

All four are in `pinned_mutations.yml`; the manifest is 104 and every one
is caught by the example that names it.

### A check that could not see a new capability group

`capability_coverage_spec` matched capability ids with `[BHCDGSTW]\d+` —
a letter list somebody remembered, which is the defect that file's own
comment describes about `\d` versus `\d+`. A capability group under a new
letter would have been invisible to **both** directions, so a row with no
example *and* an example with no row would have passed.

Widened to `[A-Z]+\d+` and verified by planting an `F1` row with no
example: it now reports it. **Then the same list turned out to have a
third copy**, in the Japanese-pair example, and it was missed when the
first two were widened — the list-somebody-remembered defect appearing a
third time inside the fix for it. Found by the check itself, on the real
rows.

### Not done here, and owed at release

The README matrix and `docs/ROADMAP.md` still show this item as planned

`DOCUMENTATION_MAP`'s roadmap row flips when the release does — README,

## Second capability: call hierarchy (W5, W6)

`045`: "an incremental step on the same index". Incoming calls are the
references the index already holds, **grouped by the method each one sits
inside** — which is the difference between a call hierarchy and the flat
list Find References gives.

**This warms the reference index and documentHighlight does not**, and
that is the same decision read from the other side: opening a call
hierarchy is a deliberate action, so paying for an O(workspace) rebuild
once is right where paying it per cursor move is not.

### The first fixture agreed with the code by accident

Mutated by hand, the first version of these examples pinned **one of
four** decisions:

```
  the enclosing-method guard   2 examples, 0 failures   <- unpinned
  innermost, not first         2 examples, 0 failures   <- unpinned
  the fromRanges               2 examples, 1 failure
  the outgoing kind filter     2 examples, 0 failures   <- unpinned
```

`CLAUDE.md`'s rule is that a spec whose fixture cannot distinguish the
two candidate behaviours is unpinned even though it passes. The fixture
had one caller, in one method, and every decision above happened to give
the same answer for it. Rebuilt so each is distinguishable:

- **a call at the top level**, which has no enclosing method — a caller
  invented for it is an assertion about the user's code nothing supports;
- **nested `def`s**, whose recorded ranges both contain a call. Probed
  rather than assumed: `inner` is recorded at lines 2..4 inside `outer`'s
  1..5, so taking the first declaration that contains the call names
  `outer`, which did not make it.

### One of the four turned out to be dead, and was removed

The outgoing side filtered resolved candidates by `CALLABLE_KINDS`.
Probed: a `:method_call` candidate resolves to a method kind or to
nothing — never to a constant or a class — and `inside` is already only
`:method_call` candidates. No fixture could tell the two behaviours
apart, so it is not a guard, it is a line. Removed rather than pinned.

The same constant's use on the **prepare** side is live and was also
unpinned; it has an example now (a class name offers no hierarchy, with
the method one line down as the control).

All four decisions are in `pinned_mutations.yml`; the manifest is 108.

## Third capability: go to type definition (D4, D5)

`045`: "cheap given `explainType` already resolves the type". The type
comes from the same `#type_at` that answers hover; the location from the
index's own class declarations.

**The control is inside the answer, and it had to be.** The example was
first written with go-to-definition at the same caret as the control —
D4 lands on the class, D1 lands on the assignment — and that control
turned out to be false: **go to definition on a local answers nothing
at all today**, measured, so it could not distinguish anything. The
control is now the line the answer names: line 0 is `class TdWidget`,
line 8 is the assignment, and a server that forwarded this request to
the definition handler would answer the assignment and look plausible.

### The E2E client could not tell a decline from a crash

D5 asserts the server answers *nothing* where the type is not a
workspace class. Removing the guard it exists for left it green — so it
was pinning nothing.

The cause was in the client, not the example: a JSON-RPC error response
carries no `result`, and `request` returned `response[:result]`, so a
handler that raised handed back `nil` — indistinguishable from an empty
answer. **Every example in this suite asserting "answers nothing" had
that hole**, not only D5.

`E2E::LspClient#request` raises on an error response now. With that, the
guard's mutation is caught, and the whole capability suite still passes
at 66 examples — so nothing was relying on an error reading as silence.

That is the same distinction section 0 is built on, arriving in the
harness rather than in the product.

## Fourth capability: inlay hints (I1, I2)

`045`: "the inference that already exists". Hover answers these today;
this puts the answer where the code is.

**The parser knew something it was throwing away.** `documentHighlight`
shipped answering `Text` for every local, on the argument that the layer
could not tell an assignment from a read. True of the layer, and wrong
about what was knowable: `ParserService` has four separate write
visitors and discarded the distinction at `#record_local_variable`.
`ReferenceCandidate` carries `write` now — inlay hints need the
assignment sites, and highlighting reads the same flag, so a local is
`Read`/`Write` rather than `Text`. Recorded here rather than quietly
changed, because the earlier reasoning is in the shipped comment.

### The parameter-name rule was about the wrong thing

The first version refused a `*splat` **at the call site** and labelled
only `:required` parameters. Both were measured wrong:

- A splat call records `positional: 0` and no argument locations, so
  there is nothing to label and the guard could not be made to matter.
- Refusing optionals was *under*-answering: on `resize(10, 20, 30)`
  against `def resize(width, height, scale = 1)` the mapping holds.

What actually breaks index-to-parameter mapping is the **declaration**,
and the interpreter settled it rather than an argument:

```
$ ruby -e '
def f(a, b = 1, c) = [a, b, c]
p f(1, 2)
'
# => [1, 1, 2]
# ruby 3.4.10
```

The second *argument* binds to the third *parameter*. So the rule is:
refuse a declaration with a `*rest` parameter or a required parameter
after an optional one; otherwise label positionally, optionals included.
The session is pasted at the site, which is what `check_interpreter_sessions.rb`
re-runs — 176 sessions, all reproducing.

Four decisions, all four measured unpinned first, all four pinned now.

### Re-aiming the manifest, and doing it the right way

Adding `write:` wrapped `#record_reference`'s call and changed four
visitor lines, so five existing manifest entries stopped matching. Three
attempts to retype their `from` by hand each missed on indentation. The
fourth took the line **out of the source file** and wrote it in — which
is what the manifest should have been doing all along, and is the same
"derive rather than type" rule this repository applies to every measured
number.

Manifest: 114, every one caught by the example that names it.

## Fifth capability: quick fixes (Q1, Q2, Q3)

`045`: "the diagnostics that already exist" — and the one `045`'s own
prose had dropped from that list, which `024.292` corrected.

**Three codes get an action and the rest do not, by design.** A code
action edits the user's file with one click and its reasoning is never
seen, so it is offered only where the diagnostic *defines* the edit:

- `unknown-method` → insert `def name; end` into the class the call was
  made **on** — the receiver's class, resolved through the type engine,
  not the file the call is written in;
- `unknown-route-helper` → the closest helper the application actually
  has, and **nothing past three edits**: rewriting one wrong name into
  an unrelated one is a wrong edit with a click, not a fix;
- `argument-count` → delete the surplus arguments when there are too
  many, and **offer nothing when there are too few**. There is no value
  to write; `nil` would be this engine putting a guess into the file.

That last refusal is the capability. The roadmap promises "fix the
argument count" and half of that has no defined edit, so half is what
ships, said plainly in the row and in both languages.

### Two fixtures could not tell the two behaviours apart

Measured before they were believed:

```
  insert into the receiver's class   3 examples, 0 failures   <- unpinned
  the distance ceiling               3 examples, 0 failures   <- unpinned
```

The first because the receiver's class was written first in the fixture,
so "the class the call was made on" and "whichever class this file
declares first" were the same edit. It is written second now. The second
because nothing asked what happens to a name close to nothing; a second
file does.

### Three things the code had wrong, each found by running it

- `candidate.receiver` is `{position:, written_self:}` — a point, not a
  range. Asking it for `[:end]` gave `nil`, so every fix needing the
  receiver's type answered nothing.
- `ROUTE_HELPER_PATTERN` requires the name to *end* in `_path`/`_url`.
  `posts_pathh` is an ordinary unknown method, not a route helper, so
  the first Q2 fixture exercised a different code path entirely.
- Q2's first fixture used a route the workspace does not have and
  **skipped**. A skipped example is not a passing one, and the row
  claims PASS. It uses `postss_path` against the `resources :posts` this
  workspace draws.

## Sixth capability: `@ivar` completion, and `024.86` (C15, H8)

Reproduced before anything was written, in the plain class `024.86`
names: `@thing` assigned in `setup` reads `Unknown` in `use` and
`Widget` where it is assigned.

**`#locate` gives each `def` a fresh environment.** Right for locals,
wrong for instance variables. It works in an ERB view for one reason
only — a view has no `def` for the descent to reset at — so what looked
like Rails machinery that had not been generalised was a seam one level
down. `#locate_in_def` seeds from the enclosing class's other methods
now, memoised per parse, and **declines where two methods assign one
name types that disagree**.

**The completion promise was three more things, each found by running
it.** `#capture_scope` dropped every `@`-prefixed name on the way out;
`#word_prefix_at_position` treated `@` as a boundary, so the prefix at
the sigil was empty and matched everything; and `@` was in
`BOUND_PREFIX_SIGILS`, the list this engine answers nothing for. `$`,
`:` and `@@` stay there — a global, a symbol and a class variable are
still names nothing here tracks.

**One regression, caught by an example nobody wrote for it.**
`#infer_ivars_for_method_node` replaces `@self_type_stack` wholesale and
the sibling walk runs inside a descent that owns it, so `def self.b`
calling `a` began answering `Unknown`. A Task 017 example found it.

**And one decision was unpinned for a reason worth keeping.** The sigil
scan was two identical lines — one for `@`, one for the second `@` — and
either could be deleted with the other still answering, so neither was
pinned. Written as one `while`, it is one decision and it is caught.

`024.86`'s second half — diagnostics not acting on an ivar receiver — is
filed as `024.294` rather than left inside a resolved entry, published in
both languages, and targeted at 0.3.1. It is a silence, not a wrong
answer.

## `024.R7`, first half: the Agent reports what the gems define

`045` puts this last and on its own — the largest item, and the only one
that needs the Runtime Agent to grow a responsibility. This is that
responsibility; the Core half is separate because it changes what the
engine *asserts* and therefore owes a corpus run with a control.

`agent/gemIndex` walks every loaded module once and attributes each to
the gem whose directory `Object.const_source_location` puts it in —
**by definition site, not by namespace**, so a class the application
reopens is still the gem's and a class named like a gem's but defined in
the app is not. Per class it reports its own methods, its ancestors, and
whether it defines `method_missing`.

Measured against this workspace's own Rails fixture rather than taken
from the entry's estimate:

| | |
|---|---|
| gems | **33** |
| classes attributed | **2,098** |
| methods defined directly on them | **14,617** |
| classes defining `method_missing` | **17** |
| JSON payload | **938 KB** |

`024.R7` estimated "roughly 365KB, names only". With ancestors included
it is 938KB, because `Object`'s chain repeats 2,098 times — asked once
per boot and persisted, never on the request path, which is what that
estimate was deciding.

### Two things this broke, both of them the guard working

**The protocol version.** Core refuses an Agent whose version differs, so
a protocol that gains a method is a new version — 1 → 2. Three stub
agents in `spec/fixtures/` wrote the number as a literal `1` and were
refused. They read the Core's constant now, which is the only form that
survives the next bump.

**And a leaked Agent process.** The new integration example had no
`ensure @manager&.stop`, which every other example in that file has. The
leak held the fixture bundle and the next eleven examples booted to
`static_only`. Bisected rather than guessed: with the example reverted
and the protocol bump kept, the file was green — which is what said it
was the spec and not the bump beside it.
