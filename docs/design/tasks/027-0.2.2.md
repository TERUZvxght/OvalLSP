# Task 027: 0.2.2 — the cache sweep incident

A single-purpose patch release. `026-0.2.1-review-loop.md` is the
previous file of this kind; the work that was being prepared as 0.2.2
before this happened is renumbered to 0.2.3 and continues in
`028-0.2.3-review-loop.md`.

Its opening rule applies here too: **anything not fixed exists only in
this file.**

## What happened

For six days, running `bundle exec rspec` deleted the maintainer's
installed applications.

`store_spec.rb` checked that an unreadable cache root does not raise:

```ruby
described_class.prune_generations(cache_root: "/nonexistent-cache-root", current: "/x", keep: 2)
```

The unreadable root was handled exactly as the example intended —
`prune_workspaces` enumerated nothing and returned. Then the *second*
statement of the same method aimed itself at `File.dirname(current)`,
which for `"/x"` is `/`. It enumerated the machine's root directory,
found fifteen entries against a `keep` of two, sorted by mtime, and
removed all but the newest. `/Applications` was first. It stopped when
`remove_entry` raised on a SIP-protected path, which is why some
applications survived and others did not.

`prune_generations` swallows every error, so nothing propagated and the
example's `.not_to raise_error` passed on every run.

Identified from an Endpoint Security (`eslogger`) trace naming `rspec`
as the process unlinking `/Applications/*.app`, with the parent `zsh`
running `bundle exec rspec`. Reinstalling macOS had not helped, because
re-cloning restores the cause — which is also why it was mistaken for a
hardware or filesystem fault, and why the 0.2.2 work was paused.

## Who was affected, established rather than assumed

Both halves of this were checked before the changelog was written,
because they decide what the release is allowed to claim.

- **Not users of the published extension, and not reachable by them.**
  `core/spec/**` is excluded from the VSIX (`.vscodeignore`), so the file
  never shipped. Independently, the one production caller
  (`Server#build_cache_store`) derives `cache_root` and `cache_dir` from
  the same base, so `current` is always two levels inside the root and
  `File.dirname(current)` cannot leave it. No setting separates them;
  `XDG_CACHE_HOME` moves both.
- **Anyone who checked this repository out at `28a041c` (2026-08-05) or
  later and ran the Core suite.** Tag `v0.2.1` contains it, as does
  `main` until this lands. `CONTRIBUTING.md` + `.ja.md` carry the
  disclosure with the window and the reason users are unaffected.

|---|---|

| The disclosure, in both languages | `CONTRIBUTING.md` + `.ja.md` |

Two working agreements that were already in the tree ride along, because
they are about the same thing — believing a green run:

- the local-gems prerequisite, and that without it two suites skip in
  full while `rspec` still exits 0 (`CONTRIBUTING`, `CLAUDE.md`,
  `AGENTS.md`);
- that a revert is the change most likely to leave documentation behind
  (`CLAUDE.md`, from 024.47).

**No engine behaviour changes.** Nothing here alters an answer the
server gives.

## Why the containment needed a guard rather than a test

`prune_workspaces`' two `remove_within` calls **cannot refuse anything
today**: `path` comes from `children_of(cache_root)`, so it is always the
root's own child. Reverse-applying either leaves the whole suite green,
and no fixture can change that — which by this repository's rule would
make them defects.

They are kept, because the day that loop enumerates something other than
the root's children is the day the sweep escapes again, and that is
exactly how it escaped the first time. The rule is answered a level up:
`spec/meta/cache_removal_containment_spec.rb` pins the property — *this
class removes a directory in exactly one place, and that place checks the
root* — rather than the individual lines. Modelled on
`tmpdir_hygiene_spec.rb`, for its stated reason: a reintroduced direct
`FileUtils` call leaves no failing test behind, only a destructive
capability nobody is looking at.

Both directions were watched failing:

- a direct `FileUtils.remove_entry` restored in `prune_workspaces` → the
  guard reports two removal sites instead of one;
- `inside?` removed from `remove_within` → the guard's own refusal
  example fails, and so does the bystander regression test.

An entry-point guard was written first and then removed: with
containment already at the removal it changed nothing a spec could
observe, and an unpinned line is a defect here whichever direction it
errs in.

## The review gate was waived, deliberately

`CLAUDE.md` requires a clean independent review round before a release,
and says a waiver is the maintainer's call that must be written down. **No
review round ran for 0.2.2.** The maintainer asked for it to be released
and published on 2026-08-11, and it went out on that instruction.

What makes the waiver defensible, on the same terms 0.2.1's was judged:

- **Not releasing was the more dangerous option.** The default branch was
  deleting the files of anyone who cloned it and ran the suite. Every day
  the gate held is another day of that, and a review round cannot make
  the tree safer than landing the fix does.
- **The change set is one defect wide**, which is the condition 0.2.1
  learned the hard way — its nine rounds each reviewed a change set that
  had grown since the last one. There is nothing here to drift.
- **No engine behaviour changes**, so the class of defect a review round
  is best at finding has no surface in this release.
- **Everything the fix rests on was watched failing**: the regression
  test against the un-contained code, and the containment guard in both
  directions.

Recorded here rather than left implicit, because a rule broken in silence
stops being a rule.

## Not done, deliberately

- **A GitHub Security Advisory.** `SECURITY.md`'s scope covers `core/`
  and the offending file is in `core/spec/`, so it qualifies by the
  letter of the policy. Against: there is no attacker and no
  vulnerability in the shipped product. For: the repository is public,
  the destructive commit is tagged, and an advisory is the mechanism
  people subscribe to. Left as the maintainer's call.
- **Anything else.** This release is one defect wide on purpose. The
  0.2.1 documentation cleanup, the register entries and the
  hover/completion countermeasure all belong to 0.2.3.
