# Task 040: 0.2.10 — an answer knows what it was computed from

`037`'s C3 and C9, which were moved out of 0.2.9 once C2's size was
measurable rather than estimated in advance, plus the entries that
slipped past the release they named.

The branch is **`feat/0.2.10`**, and `AGENTS.md` names it. `036` records
where this sits on the way to 1.0.0.

## Why this release exists

A diagnostic is computed from a particular text and then attributed to a
`uri` and an integer. Neither identifies the text it was computed from:

- The **buffer path** hands the funnel `document.version`, an integer
  the client chooses. Across a close and reopen the client is free to
  start again at 1, so two genuinely different buffers can present the
  same integer, and the funnel's `version < last` comparison is then
  comparing two things that are not on the same scale. `024.56` is the
  neighbourhood this already bit once.
- The **workspace path** reads a file from disk, analyses it, and
  publishes with `version: nil`. If the file changed on disk inside that
  window — a `git pull`, a formatter, a generator — the findings describe
  text that no longer exists, and nothing in the publish says so.

Both are the same shape: *what an answer was computed from is re-derived
at the end rather than carried*. That is C3.

C9 is the other half, and 037 says why they are not separable: making the
publish path refuse anything that is not the document it was computed
from also refuses a **slower analysis of the same buffer** — which the
current rule accepts. 0.2.8's drive round measured 22 such publishes for
one method name typed on a 4,006-line file, with the panel clean 6.55 s
after the developer stopped — a figure this release re-measured and only
half of which survived; see below. Whether those should exist at all is C9's
question, so building C3 alone means either changing that behaviour
without measuring it, or keeping the integer comparisons anyway.

## Sizes, counted rather than estimated

Derived from the tree at the head of this branch:

- **The publish surface is three places**: `Server#publish_findings`
  (the funnel), `Server#publish_diagnostics` (buffer), and
  `WorkspaceDiagnostics#publish_for` (workspace, through the `publish:`
  callable it is constructed with). Nothing else writes a
  `publishDiagnostics`.
- **`TextDocument` is already an immutable, deeply frozen value** as of
  0.2.7's M-2, so it can be compared by identity without a caller being
  able to mutate one under the funnel.
- **`WorkspaceDiagnostics` constructs its own document** from the file
  it read, which is exactly the value C3 wants carried — it is discarded
  today.

That is the whole of C3's mechanical extent. What is not small is what
it *refuses*, which is why C9 ships with it and why each part carries its
own before-and-after.

## The preventing logic

| | The defect | The logic under which it cannot arise |
|---|---|---|
| C3 | an answer is attributed to a uri and an integer, neither of which identifies the text it was computed from | the publish takes the document it was computed from; the funnel compares by identity and keeps the document, not an integer |
| C9 | analysis runs per event rather than per settled state, so a burst of edits produces a burst of answers about superseded text | one analysis in flight per uri; a newer one supersedes the older, which is cancelled rather than allowed to finish and publish |

## C3 shipped, and what measuring C9 found

**C3 is in**, and it turned out to be separable after all. 037 argued the
two go together because refusing anything that is not the document an
answer was computed from *also* refuses a slower analysis of the same
buffer. It does not have to: `buffer_id` is carried across edits, so an
answer computed from an earlier snapshot of the same buffer is still
recognisably that buffer's and is ordered by version exactly as before.
Only a *different* buffer is refused. The behaviour C9 owns was left
untouched, deliberately, so that C9 could be measured rather than altered
as a side effect. That is a departure from 037's sizing and is recorded
here rather than left to be noticed.

### The 22, measured twice, and the first measurement was wrong

`scripts/measure_typing_publishes.rb`, added for this, drives a real
server over a pipe and counts `publishDiagnostics`.

**The first version of this section said the "22 wrong intermediate
publishes" did not reproduce. That conclusion was wrong, and the reason
is worth more than the number.** The harness typed by *appending a
comment*, so every intermediate state was valid Ruby with nothing to
report — ten publishes, none wrong, and the answer looked like a
refutation. `024.101` describes a different act: typing a method name
that exists, one character at a time, where each intermediate state calls
a prefix that really is undefined.

Measured in `024.101`'s own scenario, both sides run from separate
worktrees printing their own revision:

| 12 keystrokes, 0.03 s apart | before (`6faf5f6`) | after |
|---|---|---|
| publishes | 12 | **1** — see the correction below |
| of those, reporting the unfinished name | **12** | 1 |
| hover latency during the burst, median | 1.430 s | **0.042 s** |
| wall time for the client to send 12 edits | 15.93 s | **0.52 s** — see below |

> **Corrected in 0.2.11.** A stocktake re-ran this three consecutive
> times on the same tree and got **4, 2, 2** publishes and 5.04 / 2.02 /
> 2.19 s of client wall time — never 1, never 0.52 s. The direction
> holds (12 → 2–4) and the hover latency reproduces solidly (~0.04 s
> against 1.42–1.48 s), but **the single-publish figure was one run of a
> quantity that varies with machine load and was recorded as if it were
> stable.** The number to cite for C9 is the hover latency; the publish
> count says only "fewer, not one per keystroke".

So `024.101` is right: every intermediate publish reported something the
finished line does not. The remaining "1" after the change is the
harness's own artifact — twelve keystrokes of a twenty-one character
name leave it genuinely unfinished — not a defect.

**What the wrong first measurement cost, and what caught it.** Nothing
shipped on it: the correction was written into `036`, `037`, `039` and
`024.57` and had to be taken back out. What caught it was reading
`024.101`'s text closely enough to notice its scenario was not the one
being run — which is the same failure as measuring a harness instead of
the product, one section down, on the same day. A measurement is a claim
about a *specific* thing happening, and the specific thing has to match.

### What C9 is for, on both counts

Correctness *and* latency, and the second is the one nobody had measured.
Every analysis runs on the dispatch thread holding
`@index_mutation_mutex` — the lock a hover needs — so a developer who
pauses to read a hover while typing waits about a second and a half for
it, and almost all of that is analyses of text they have already
replaced, queued in front of their question.

At reading speed (10 keystrokes 0.15 s apart) the publish count is
unchanged at 10, which is the property that matters more than the
coalescing: **an edit that settles is always analysed**. What changes
there is only that the question is answered first.

### C9, and what it moved

**Not a debounce.** There is no interval to tune and no waiter thread —
`024.57` records what tuning one cost: four rounds, four defects, and a
rollback. A `didChange` records that its uri needs analysing; the
analysis runs only when nothing else is waiting to be read. The question
asked is "is there more input", and a reader that cannot answer it says
no, which analyses immediately, exactly as every release before this one.

Measured with `scripts/measure_typing_publishes.rb`, which now prints the
HEAD it is running and whether the two files under test are modified —
both sides confirmed to have run different code, which three of this
project's earlier comparisons did not.

**Typing faster than one analysis** (12 keystrokes, 0.03 s apart,
3,907-line file):

| | before | after |
|---|---|---|
| publishes | 12 | **1** (version 13, the settled state) |
| hover latency during the burst, median | 1.419 s | **0.040 s** |
| wall time for the client to send 12 edits | 15.61 s | **0.52 s** |

The last row is the one that says what was actually wrong: the client's
writes blocked because the server was not reading — the dispatch thread
was inside an analysis of text the developer had already replaced. 0.36 s
of that 15.61 s is the harness's own sleeps.

**Typing at reading speed** (10 keystrokes, 0.15 s apart) — the control,
where nothing should be coalesced because each edit settles before the
next arrives:

| | before | after |
|---|---|---|
| publishes | 10 | **10** |
| hover latency, median | 1.431 s | **0.040 s** |

Ten answers, unchanged, which is the property that matters more than the
coalescing: an edit that settles is always analysed. What changed is that
the developer's *question* is answered first — a hover waiting in the
pipe is dispatched before the pending analysis drains.

### `024.103`, and the corpus run that measured the harness instead

Fixed: `WorkspaceIndex` takes the nesting and walks it outward before any
heuristic, which is Ruby's rule; `LocalInferencer` keeps `Module.nesting`
in its own stack; and the **two** places that turned a constant node into
a class name now read one.

That second point is the release's clearest example of why one place
matters. Teaching only `#eval_constant` left `Config.new` resolving to
`App::Config` and `Config.new.app_only` still reported — the defect
surviving its own fix, in the same file, because a second reader existed.

**The measurement went wrong twice, and both are worth keeping.**

1. The first comparison came out **byte-identical over 6,772 findings**.
   Identical output is the signature of a measurement error, which is the
   only reason it was looked at — and `scripts/corpus_diagnostics.rb`
   built its `LocalInferencer` without the `workspace_index:` the fix
   reads. The harness was measuring a *different program* from the one
   the server runs. It is now wired like the server, with a comment
   saying why that is not optional.
2. The re-run then showed **five new false positives and none removed** —
   `Queue.new` inside `debug`'s `module DEBUGGER__` answered
   `ActiveRecord::ConnectionAdapters::ConnectionPool::Queue`. The cause
   was rewriting the name even when the nesting decided *nothing*: the
   fallback heuristic's answer was being written into the type, replacing
   a bare name that RBS could still resolve. `#nested_type_name` answers
   nil when the nesting decides nothing, and both it and
   `#resolve_type_name` read the same `#nesting_match`.

Final, 40 installed gems, both sides printing their own path and
revision, `unresolved-constant` as the control:

| | base (`6faf5f6`) | head |
|---|---|---|
| `unresolved-constant` (control) | 6,331 | 6,331 |
| `unknown-method` | 437 | 437 |
| `argument-count` | 4 | 4 |
| findings added / removed | — | **0 / 0** |

No movement on this corpus, which is the right result for a rule that
only fires where a workspace declares the same short name twice — and the
number that matters is the second one above, which was a regression this
change would have shipped.

Findings 1–6 are defects this release introduced. Finding 1 is the one
that would have mattered most: it is "a wrong answer is worse than no
answer" at a scale of 228 false reports on shipped Rails source, and the
release's own suite was green through all of it.

**And it is the reviewer's note on the measurement that explains why.**
The corpus comparison recorded above was run at `024.103`; `024.104` and
`024.106` landed after it, so the two commits that changed what the
engine will *assert* about were never corpus-measured. A green suite is
not a blast radius, and this release proved it a second time.
