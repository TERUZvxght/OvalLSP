## 調査結果

### バージョン管理の現状

- Extension version: `vscode/package.json`の`"version": "0.0.1"`。
- Core version: `core/lib/ovallsp/version.rb`の`Ovallsp::VERSION = "0.0.1"`。
- LSP `initialize`応答(`core/lib/ovallsp/server.rb`)は`serverInfo: { name: "ovallsp", version: Ovallsp::VERSION }`のみを返す。protocol version・build ID・Ruby/platform情報の交換は**存在しない**。
- `vscode/src/extension.ts`が送る`initializationOptions`は`{ workspaceTrusted }`のみ。clientInfo/version相当の情報は送っていない。
- Core↔Runtime Agentの`RuntimeAgent::Agent::PROTOCOL_VERSION`、Core↔Pluginの`Plugins::CURRENT_PROTOCOL_VERSION`はいずれも既存だが、**Extension↔Coreの protocol versionとは無関係**の別レイヤー。Extension↔Core向けのprotocol version機構は新規に作る必要がある(既存の流用ではない)。

### Extensionのcore選択方式

- `vscode/src/serverConfig.ts`の`resolveServerConfig`が、`ovallsp.server.path`未設定時はExtension自身のインストールディレクトリ配下の`core/bin/ovallsp`(vsce packageで同梱、`copy-core.js`がvendoring)を優先し、それが無ければmonorepo相対パスへフォールバックする(ローカルF5開発用)。globalStorageの利用は無い。
- Core更新の仕組み(Extension自体の更新以外)は存在しない。

### VSIX native gem / Apple Silicon Ruby解決

- `core/vendor/PLATFORM_MANIFEST.json`(`copy-core.js`が生成)は現状`rubyEngine`/`rubyVersionMajorMinor`/`rubyPlatform`の3項目のみを記録。ExtensionバージョンやCoreバージョン、protocol version、payload hashは含まれていない(ADR-0005の時点でのスコープ)。
- `vscode/src/rubyResolver.ts`の優先順位: 明示設定 → mise → asdf → rbenv → chruby(マーカーのみ、実体解決なし)→ **Homebrew(今回追加、Task 023.4で完了)** → PATH → Windows RubyInstaller。GUI起動時のPATH不足問題への対応は、chrubyまでの各strategyが`env.home`ベースの絶対パスを直接チェックする設計のため、mise/asdf/rbenv/Homebrewの4つはPATHに依存しない。残るPATHベースの解決(`pathRuby`)のみがGUI起動時のPATH不足の影響を受ける。

### package.json / Marketplace文書の現状

- `vscode/package.json`: `name`/`displayName`/`description`/`version`/`publisher`/`license`/`engines.vscode`/`categories`/`activationEvents`/`main`/`contributes`(commands 8個、configuration 4項目)は存在。**欠落**: `keywords`、`icon`、`galleryBanner`、`repository`、`homepage`、`bugs`、`extensionKind`。`"private": true`のまま(Marketplace公開時は要検討・要ユーザー確認)。
- 既存コマンド8個のうち、Task 023 Section 2が要求する「`OvalLSP: Restart Language Server`」「`OvalLSP: Open Language Server Logs`」は、既存の`ovallsp.restartServer`("OvalLSP: Restart Server")・`ovallsp.showLogs`("OvalLSP: Show Logs")と実質的に重複する。**新規に別コマンドを追加せず、既存コマンドをそのまま使う**(Task 023.2で決定・記録)。真に新規なのは`OvalLSP: Show Version Information`のみ。
- アイコン(PNG, 128x128以上)は**リポジトリ内に存在しない**(`find`で確認、node_modules/.vscode-test配下の無関係なファイルのみ)。Marketplace公開には必要— 出所が明確な素材が要る(Task 023.6で棚卸し、無ければユーザーへ確認)。
- `vscode/`直下に`README.md`等のMarketplace文書は存在しない。ルートの`README.md`はmonorepo開発者向けで、Marketplace向けではない(そのままでは使えないが、実装済み機能一覧の一次情報源として活用できる — 17行目以降のリスト)。
- `docs/`配下の既存文書: `RELEASE_CHECKLIST.md`、`SBOM.md`、`SECURITY_CHECKLIST.md`、`SUPPORT_MATRIX.md`。Task 023 Section 5が要求する`THIRD_PARTY_NOTICES.md`、`SECURITY.md`(Marketplace向け)、`SUPPORT.md`、`CONTRIBUTING.md`、`CODE_OF_CONDUCT.md`、`PRIVACY.md`、`docs/PUBLISHING.md`はいずれも未作成。

## Decision: 配布/更新モデル

[ADR-0006](../adrs/0006-marketplace-bundled-core-update-atomicity.md)として記録。要旨:

- Core更新は独立したnetwork self-updateを作らず、**Marketplace Extension自体の
  自動更新に完全に委ねる**。ExtensionとCoreは常に同一VSIX内の同一バージョンの
  組として配布・更新される。
- globalStorageへの展開は今回のPreviewでは行わない(Extensionディレクトリ配下
  から直接起動する既存方式のまま)。将来globalStorage展開が必要になった場合の
  要件(version-tagged directory + hash検証 + atomic rename)はADR-0006に設計
  メモとして記録済み、実装は行わない。
- custom server path(`ovallsp.server.path`)は自動更新の対象外、互換性チェック
  のみ行い不一致時は拒否する(既存の`platformCompatibility.ts`の枠組みを
  Task 023.2で拡張)。
