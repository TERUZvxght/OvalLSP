# 0.4.0 — what this release is for

**Branch:** `release/0.4.0`, merging into `main` by pull request.

## Why this release exists

0.4.0 is the second release that may add capability, and the first since
0.3.0. `docs/ROADMAP.md` has promised the same three things at this
version for long enough that both READMEs and three site pages carry
them:

- per-check diagnostic severity, so a check you disagree with can be a
  hint rather than a warning, or off;
- auto-`require` insertion;
- signature help highlighting the argument the cursor is in.

That is the contract. Everything below is about how to keep it, and what
else is owed by the same version without being what the version is *for*.

## The forty-four are a queue, not a scope

When this release opened, forty-four open entries carried
`target: 0.4.0`, and none of them builds any of the three:

    ruby scripts/issues.rb list --target 0.4.0 --status open

**They arrived through the 0.3 line's closing sweeps**, derived at each
tag rather than recalled:

    v0.2.18   0
    v0.3.0   23
    v0.3.1   24
    v0.3.2   42
    v0.3.3   44

    for t in v0.2.18 v0.3.0 v0.3.1 v0.3.2 v0.3.3; do
      git show "$t:docs/design/tasks/024-deferred-review-findings.md"
    done   # then count entries whose target is 0.4.0 and whose status is open

The register's legend says `target:` is "the release its fix is routed
to", so what these entries share is that a patch could not hold them — an
eligibility queue, and eligibility is not a plan.

**0.3.2 is the precedent for how to work one.** It was handed thirty-four
and drove every one before touching it: nineteen closed, fifteen moved on
with a measurement saying why, and **three turned out to be wrong about
their own subject** — a premise that had been false for two releases, a
measurement that could not reach what it claimed, and an entry that had
had three releases to reproduce and had not. Drive before working. The
table in `056` gives fifteen of the forty-four a measured reason already;
carry it forward rather than re-deriving it.

**Where they actually land**, which is more useful than their count.
Grouping the forty-four by the first path in each entry's `Area`:

| entries | area |
|---|---|
| 10 | `core/lib/ovallsp/diagnostics/engine.rb` |
| 9 | `core/lib/ovallsp/server.rb` |
| 6 | `core/lib/ovallsp/local_inferencer.rb` |
| 3 | `core/lib/ovallsp/semantic/query_service.rb` |
| 16 | one each, across fourteen other files |

Twenty-eight of forty-four are in four files. A release that takes them
one at a time will touch those four files forty-four times; one that
takes them by file will read each once. That is a scheduling fact, not a
plan either — but it is the one to plan against.

## Where to start, and why it is the smallest of the three

**Signature help's active parameter.** It is the most nearly built thing
in this release, and it is startable today:

- `core/lib/ovallsp/server.rb` advertises
  `signatureHelpProvider: { triggerCharacters: ["("] }` and emits no
  `activeParameter`;
- `COMMA: :comma` is already in the server's token table and **nothing
  reads `:comma`** — `grep -rn ":comma\b" core/lib core/spec` finds the
  table entry and nothing else;
- three comments, in `server.rb` and `semantic/query_service.rb`,
  describe what `activeParameter` would point at, so the shape was
  already reasoned about;
- `030-0.2.4-review-loop.md` records the design constraint from the
  attempt that was removed in 0.2.4, which is the part a fresh attempt
  would otherwise rediscover.

It is not first because it is easiest. It is first because it is the one
of the three whose inputs already exist, so it can be built while the
other two are still being decided.

## Two decisions that come before any code

### `diagnosticsMode` has three values and only one is reachable

`Diagnostics::Engine::MODES` is `%i[safe standard strict]`, `#analyze`
defaults to `:safe`, and `Server` reads `diagnosticsMode` out of
`initializationOptions`. The extension sends
`initializationOptions: { workspaceTrusted, ovallspClient }` and nothing
else, so **`:safe` is the only value the shipped product ever runs
under.**

Its immediate consequence is not small: `unresolved-constant` is gated on
mode ≥ `standard` (`diagnostics/engine.rb`), so **that check cannot fire
in the shipped product at all.** Every corpus number this project has
recorded for it was measured through `corpus_diagnostics.rb`, which runs
`mode: :standard` deliberately and says so.

Per-check severity either replaces this knob or has to agree with it, and
that is a decision rather than an implementation detail. It belongs here,
before the first commit. No register entry names this; if the decision is
to keep the mode knob, one should.

### Auto-`require` should not be started until its trigger exists

Three facts, each checked rather than recalled:

- its natural trigger is `unresolved-constant`, which by the paragraph
  above cannot fire in the shipped product;
- nothing anywhere maps a constant to a require path —
  `Semantic::GemIndex::Entry` carries methods and ancestors and no path,
  and `RuntimeAgent::Agent#gem_for` computes a path and keeps only the
  gem name from it;
- `024.R3`'s own row for it reads "Worth revisiting only after the
  plain-Ruby story (024.R1) exists", and `024.R1` is `target: 1.0.0`.

So the choice is to move the row or to record the decision to build it
anyway. Moving it is a coordinated edit across `docs/ROADMAP.md` + `.ja`,
both READMEs and two site pages, which `roadmap_parity_spec` and
`check_site_links.rb` will hold to each other. **Not deciding is the one
option that costs something**: the release would carry a public promise
whose first requirement is unbuilt.

## What `042` says about this release, and what happened to it

`042-second-enumeration.md`'s execution plan assigned two design classes
to releases that have shipped:

- **D1** — resolution answering a name *and its basis* — to 0.2.14;
- **D3** — one `ReceiverResolver#at(document:, position:)` for the four
  features — to 0.3.0.

**Neither was built.** `ReceiverResolver` appears in `042` and in the
register and nowhere under `core/`. What did happen is that both classes
shrank without their mechanism: of D1's eight entries four are still open
(`024.13`, `024.19`, `024.37`, `024.47`), and of D3's eleven, four
(`024.42`, `024.44`, `024.88`, `024.100`).

That is worth knowing before either is proposed again. Half of each class
was closable one entry at a time, which is evidence about the class, not
only about the entries — and it is the opposite of what `042` predicted
for D3, whose argument was that its failure mode is "two features
disagree" and therefore invisible to per-entry work. `042` carries no
amendment saying any of this; this release should either write one or
build one of them.

## The rule this release runs under

`AGENTS.md`'s card, unchanged, with three lines that bite hardest here:

- **Drive before working.** Every entry gets its reproduction re-run
  against this tree before anything is written for it. 0.3.2's three
  wrong records are the reason.
- **A capability changes what the four features answer**, so
  `docs/EXTENSION_CAPABILITIES.md` gains a row *and* an E2E example for
  each of the three, and `docs/DOCUMENTATION_MAP.md`'s capability row
  names the other five places that move with it.
- **Five of the forty-four carry attempts already measured unsound or
  rolled back** — `024.13`, `024.38`, `024.47`, `024.224`, `024.243`.
  `024.224` states in its own body that under the same-place rule no
  third hand fix will be written for it. Treating those as ordinary
  backlog spends the first round re-deriving 0.2.16.

## What opening the release found

**`release.rb open` and the shipped-target guard disagreed, and the guard
was wrong.** `open` writes the changelog section at the start of a release
— that is where the bullets accumulate — and
`open_entries_targeting_a_shipped_release` reads the changelog as evidence
that a version has shipped. So the moment 0.4.0 was opened, all
forty-four entries the release is *working on* were reported as naming a
shipped release, and preflight went red. It would have stayed red from
`open` until the tag.

That is `059`'s B2 one reader over. B2 was the same defect in
`check_changelog.rb` — "preflight was red for the whole release window" —
and its fix was to make the branch the evidence of what is being
prepared. This guard did not get that fix, which is `024.173`'s shape:
one reader taught, its sibling not.

Fixed the same way and spelled the same way:
`preparing_version` reads `release/<x.y.z>` off the branch, and the
version being prepared is subtracted from the shipped set. Off a release
branch the argument is `nil` and the guard is exactly as strict as
before — which is what `main` gets, so an entry still naming 0.4.0 after
this merges is caught again.

Two examples, each stated with the case that must fail, and a pinned
mutation: reverting the subtraction fails the example that names it.
