# Task 037: 0.2.7 — the concurrency foundations under the answers

**A patch.** No capability row moves. What changes is that answers stop
being able to arrive in the wrong order or be read half-written.

**The branch is `feat/0.2.7`.** (Named here per CLAUDE.md's residency
rule, so a session resuming this release finds it from `main`.)

## Why this release exists

`036-road-to-1.0.0.md` put `029`'s `M-2` and `M-3` here, and `024.56` is
the reason: a reproduced publish sequence for a closed file — **findings,
the clear, the findings again** — present in *every shipped build*,
carrying a `0.2.4` target it has now missed three times.

It is user-visible in the plainest way. You close a file and its
diagnostics come back. Section 0.4 asks whether a path is one people
walk; closing a file is not a corner.

Underneath it, a document that could be read half-written. **This
release's first draft justified that by "the client's staleness filter
accepts a new version number", and that is false of this product's
client** — `vscode-languageclient` ignores `params.version` and queues
diagnostics by uri, which `server_publish_invariant_spec.rb` already said
in this same tree. The sentence came from `029`'s M-2 and was carried
here without being checked; a review round caught it. Recorded rather
than quietly fixed, because it is exactly the shape section 0.6 exists to
prevent: an inference restated until it reads as a measurement.

What is true, and is stronger: the **offsets** half. A reviewer measured
`position_to_byte_offset` against a concurrent change loop on `main` and
got **1,977,450 of 1,977,451 calls returning an offset belonging to
neither document** — MRI preempts between `text=`'s two statements and
the document sits torn for a whole quantum. Every position-based answer
runs through that arithmetic. `029` called this window "by lock
inventory"; it is far wider than that.

## Review

Under the arrangement rewritten in 0.2.5: a round closes when a reviewer
that has not seen the change set, using a method the previous round did
not use, reports nothing; three rounds finding defects, then ship with
what is open recorded.

0.2.6 ran all three and all three found defects — including two
measurements of this project's own that did not reproduce. The lesson
carried forward: **measure the thing that shipped, not the prototype**,
and prefer an assertion about ordering or ownership to one about a clock.

## The hunk sweep

**The figures first written here did not reproduce, and a review round
re-ran them.** They said "9 behavioural hunks, 5 pinned, of the four
that were not, two are comment-only". Re-measured, each hunk
reverse-applied alone with a full suite run: **9 hunks, 6 pinned, 3
unpinned**, and exactly one changes no code. The `TextDocument` hunk is
pinned rather than merely load-breaking — 769 failures, because it breaks
construction, not parsing. "9 *behavioural* hunks" was wrong for the same
reason the comment-only count was.

That is the second time in two releases that a count of my own did not
survive being re-run, after 0.2.6's open-surface measurement. The pattern
is the same both times: a number produced while doing the work, written
into the record, and never re-derived. **A count is a measurement and
gets the same treatment as one** — CLAUDE.md already says so, and it
still had to be enforced by somebody else.

The three unpinned: `document_store`'s class comment (no code), the
`#clear_diagnostics` removal, and the `text=` removal — dead code,
unpinned by definition once nothing calls it. One was real:

**`clear_findings(uri)` at the watched-files delete site** could be
reverted to `publish_findings(uri, [])` with the whole suite still green.
A versionless publish writes an empty list without touching the memory,
so a file that left the workspace kept the version it was last published
at — and a rename arrives as a delete plus a create, so the file coming
back at a lower version is the ordinary case. It would then publish
nothing until edited past the old number. Pinned.

Worth recording about the example that pins it: the first version of it
passed against both branches, because the version-9 publish it set up was
itself dropped — the buffer was already closed, and a versioned publish
requires an open buffer. The fixture could not reach the state it was
about. Ordering the setup correctly is what made it distinguish.

The `TextDocument` hunk is pinned by 769 failures, and its internal
decisions are pinned separately as well by
`text_document_snapshot_spec.rb`, which drives freezing, the absence of
mutators, and that a document's offsets always match its own text — the
whole-block shape CLAUDE.md warns about needs that even when the hunk
does fail on its own.

One more thing the re-run found, and it is about how the sweep is run
rather than about this change set: the reviewer's first result for that
hunk was contaminated by a manual revert in the same worktree while the
sweep was running it. CLAUDE.md's rule against concurrent mutation during
a sweep earned itself again, on the reviewer checking whether it had.

## The review loop

Two rounds against a fixed tree at `c3e8280`, by reviewers that had not
seen the change set, using `attack` and `reproduce` — the two methods
0.2.6's rounds did not both use. Both found defects.

### The regression, found by both at once

**The first version of this funnel introduced a defect worse than the one
it fixes.** The open-buffer rule asked whether *anyone* has the file open
now, not whether the buffer these findings belong to is the one open.
Close a tab while a republish is in flight, reopen it — the editor hands
out a fresh document at version 1 — and the stale publish at version 47
finds an open buffer and an empty memory, is admitted, and sets the
memory to 47. Every edit afterwards is refused as older.

Measured on both sides. `main` self-corrects on the very next edit;
`c3e8280` shows the pre-close errors on text already fixed and stays
wrong for as many edits as the old buffer had accumulated — hundreds,
since the version bumps per keystroke.

A buffer never publishes ahead of itself, so a version above what the
store holds now belongs to a closed instance. That is the rule now.

**What it says about the first attempt:** the register entry for `024.56`
pins the mirror image of this outcome — "a reopened file would show
nothing until edited nine times" — as the bad thing the funnel-routed
clear exists to prevent. The same outcome arrived through a route the
examples did not cover, in the change set that recorded the sentence.

### The other three

- **The mutex ordered the decision, not the write.** `publish_findings`
  released the lock and *then* wrote, so an admitted older publish could
  still reach the client after a newer one — demonstrated by parking a
  thread between the two. The lock spans the write now, which costs
  nothing because `FramedWriter` serialises frames anyway, and a
  concurrent example asserts what the client is left holding.
- **A versionless publish could erase an open buffer's diagnostics.**
  `WorkspaceDiagnostics` believes it never answers for an open file and
  guards that with a two-statement check a `didOpen` can land inside. The
  funnel holds the uri and now refuses it outright. The comment recording
  the opposite as deliberate was wrong: not ordering by *number* is
  right, refusing a disk answer for a file someone is editing is a
  different rule.
- **The architecture section's lock inventory was wrong on its first
  release** — "27 `Mutex.new` sites" against 29, in the section whose
  stated purpose is that it stopped contradicting the code, and the order
  it stated named 3 of the 9 `Server` mutexes. Corrected, with the
  nestings that actually exist and the threads the table had omitted.

### Two claims of mine that were not true

- **"The client's staleness filter accepts them."** Carried from `029`'s
  M-2 into three files here without being checked.
  `vscode-languageclient` ignores `params.version` entirely, and
  `server_publish_invariant_spec.rb` said so in this same tree. Corrected
  in all four places including `029`, and the real justification — the
  offsets half, 1,977,450 of 1,977,451 calls wrong under a concurrent
  change loop — is stronger than the one it replaced.
- **`KNOWN_LIMITATIONS` claimed this release stops a slower analysis
  overwriting a corrected answer.** It does not: the funnel lets the same
  version through twice on purpose. Measured identical on both sides.
  Restored to the sentence the rewrite deleted, and recorded as `024.97`
  with a direction — order a repeat by the `generation` every `Finding`
  already carries, not by the document version.

### Recorded, not fixed

- `024.97`, above.
- **`029`'s M-3 claimed the memory would "subsume the workspace pass's
  window".** It does not, and now it does not need to: the pass's window
  is closed directly by refusing a versionless publish for an open uri.
  The subsumption as specified never arrived; saying so here rather than
  leaving `029` reading as delivered.
- **No corpus run, which `024.56` asked for.** The instrument cannot
  produce one: `scripts/corpus_diagnostics.rb` never constructs a
  `Server`, so it cannot exercise the funnel at all. What this change set
  can be measured by is the end-to-end reproduction of `024.56`'s own
  sequence on both sides, which both rounds ran and which comes out
  `[2, 0, 2]` on `main` and `[2, 0]` here.
