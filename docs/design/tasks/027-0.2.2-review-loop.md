# Task 027: 0.2.2

State of `fix/0.2.2`, written for whoever continues. 0.2.1 shipped on
2026-08-06 as `b759fc111a32b441164d9796f31a94947dcf73c0d77e817ea045c5f155141e22`.

Read [`026-0.2.1-review-loop.md`](026-0.2.1-review-loop.md) first — it
holds rounds 23–31 and, at its end, the two things this release exists to
act on.

## The rule this release is being run under

**During a review loop, fix; do not add.** 0.2.1 ran nine rounds and
seven of them found a defect in code the *previous* round had written.
Not the loop failing — the loop being asked to review a change set that
kept growing. Three capabilities were added mid-loop and all three went
back to the roadmap before shipping, and the machinery they justified
produced most of rounds 25–31's findings.

So: a capability a reviewer asks for is an entry in `024`, not work to do
before the next round. This is now in `CLAUDE.md`; it is repeated here
because it is the single most expensive thing 0.2.1 learned.

a substitute for reading them.

| ~~`024.51`~~ | First launch after upgrading blocks while it sweeps the old cache — **fixed** | `cache/store.rb` |

| `024.43` | `puts(` gets no signature help while completion offers `puts` | `query_service.rb#signature_owners` |
| `024.42` | An RBS label says `Unknown` where RBS says `self`; type variables leak | `signatures/type_converter.rb` |
| `024.44` | A partial's local resolves to nothing | `server.rb#ivars_for_view` |

`024.41` and `024.45` were read as wanting the same thing — **debouncing
`didChange`** — and 0.2.2 did it. It answers `024.45`, whose problem *is*
the repeated work. It does not answer `024.41`, and reading them as one
item produced this release's worst mistake: three documents claiming a
fix that had not happened, and a spec that could not tell.

**And then `024.41` turned out not to be a defect at all.** The
maintainer asked what Ruby actually does with

```ruby
a.
b = "str"
```

and the answer settles it: `ruby -c` says `Syntax OK`, running it raises
`undefined method 'b='`, Prism parses `CallNode name=b=`, and OvalLSP
reports the same name on the same line the interpreter points at. A
trailing `.` is Ruby's line continuation. The engine is not misreading
anything — the text genuinely means that until you finish typing.

Four rounds classified it as an engine defect without anyone running the
two lines through Ruby. It had been filed alongside the `a.end` half,
which *was* a real recovery defect, and inherited its classification.
**The lesson is not about this entry.** When a finding says "the engine
reads X wrongly", the cheapest possible check is to ask the language, and
it was never made because the finding arrived already labelled.

It is retargeted to **0.4.0** as a refinement, and out of 0.x's scope:
catching a misreading the language itself calls `Syntax OK` is not
something the 0.x line promises. See `ROADMAP.md`.

## The three capabilities 0.2.1 built and moved back

They are on the roadmap again (`documentHighlight` and `@` completion at
0.3.0, `activeParameter` at 0.4.0) and **their code was removed, not
disabled**. Rebuilding them is not a revert of a revert: what was removed
had known defects, listed here so the next attempt does not rediscover
them.

- **`documentHighlight`.** Calls `ensure_reference_index_current`, and
  the comment on that method says to defer index rebuilding until Find
  References or Rename needs it because it is O(workspace). The editor
  asks for highlights on every cursor move. Measured: 183 ms on a
  300-file workspace, 625 ms on 1,000, after every edit. Whatever version
  ships needs a per-file answer that does not rebuild the workspace
  index.
- **Completion after `@`.** The environment has to be scoped to the class
  the cursor is in, and the owner name comes from
  `declaration.symbol_id.name` — which is *already* fully qualified.
  Joining the owner onto it silently produces `::Admin::::Admin::Importer`
  and every `@ivar` feature goes silent in a namespaced class. Test the
  positive direction: 0.2.1's first two specs both asserted `not_to
  include`, which an empty answer satisfies.
- **`activeParameter`.** Needs `activeSignature` with it, or the index
  points into an overload that does not have that parameter (RBS orders
  overloads shortest-first). And the token map must cover every token
  Prism gives the same character: `BRACKET_LEFT_ARRAY`, `LAMBDA_BEGIN`,
  `PARENTHESIS_LEFT_PARENTHESES`. An unmapped opener still meets a mapped
  closer.

## Round 32

**One reviewer, not three.** 0.2.1's rounds used two or three in
parallel; the maintainer's instruction during this round was that
parallel reviewers given the same neutral instructions converge on the
same defects, so the extra runs buy repetition rather than coverage. The
way to vary method is *between* rounds. The one that ran was the one with
no method suggested to it — the other two had been given a starting point
(end-to-end driving, and the hunk sweep), and a starting point narrows
what one reviewer looks at.

`CLAUDE.md`'s instruction rules were kept: no exclusion list, no
"concentrate on X", no "a clean report is expected", corpus list given as
coverage with the revision each was measured at, and every finding
required to state what a user would see differently with "nothing" a
valid answer.

Ten findings. Nothing was found twice in a row in the same place, so the
same-place rule did not fire.

| what | where it went |
|---|---|
| The debounce does not fix 024.41, and three documents said it did | 024.41 rewritten; both changelogs; the spec replaced |
| A publish could outlive `didClose` and leave findings on a closed file | 024.52, fixed |
| The 30-day cache grace read a clock unrelated to the workspace being away | 024.53, fixed |
| 024.49/50/51 fixed but still published as current limitations | retired; `deferred_findings_spec` now checks the other direction |
| The cache-retention change was never walked through `DOCUMENTATION_MAP` row 34 | PRIVACY ×2, `site/security.html` ×2, both READMEs |
| `Show Version Information` did not print the new note | `extension.ts`; the note is now named by folder |

| Five behaviours with no test that fails when reverted | four pinned; see below for the fifth |
| Four comments claiming what the code no longer does | corrected in place |

**The findings that mattered most were about this release's own headline
change**, and none of them was the change being wrong — they were the
claims around it being wrong. That is a different failure from 0.2.1's,
where the loop kept reviewing new capabilities. Worth watching, not yet
worth a rule.

### Found while retargeting 024.41, not by the round

Moving one entry to 0.4.0 touches `ROADMAP.md`, README's matrix and the
site, and walking that row turned up drift nobody had reported:

- **`site/roadmap.html` and `site/ja/roadmap.html` were a whole release
  behind, on two separate moves.** 0.2.1 sent `activeParameter` to 0.4.0
  and brought `documentHighlight` and `@ivar` completion back to 0.3.0.
  The Markdown and README were updated both times; the site neither time.
- `roadmap_parity_spec` pairs README with `ROADMAP.md`, and
  `check_site_links.rb` pairs `capabilities.html` with README's matrix.
  **Nothing paired the roadmap with its own site pages** — the one edge
  of that triangle that was missing.

The site drifting from a Markdown document it mirrors is the *second*
occurrence of one shape. 0.2.1's was `capabilities.html`, and its
countermeasure was the row-count check — aimed at capabilities alone.
Per `CLAUDE.md`'s same-place rule this got the same countermeasure aimed
at the pair it missed: `check_site_links.rb` now compares roadmap items
per version, in both languages. It found both drifts the moment it was
written, before it was ever run in anger.

`DOCUMENTATION_MAP`'s own tail claimed in one section that the site is
machine-checked and in another that "the site has no parity guard".
Both are corrected, in both languages.

### A document can be wrong about behaviour that never existed

`024.55` is the one worth reading twice. Four documents — both
getting-started pages, both Marketplace READMEs — said OvalLSP "stops
before sending any feature request" on a version, protocol, build or
payload mismatch. `.stop(` occurs once in `extension.ts` and it is inside
a comment. So a Core whose *payload hash does not match* — a corrupted or
tampered build — has always gone on answering hover and completion, while
the page the user was sent to said they were protected from exactly that.

Not a regression, and not something a review of the diff would find:
nothing in this release touched it. It surfaced because
`DOCUMENTATION_MAP`'s Ruby/platform row names those pages and
`versionInfo.ts` was changed, so a reviewer walked the row and read what
was on the other end. **That is the argument for the map being a
checklist rather than a lookup**: the pages it sends you to are worth
reading even when your change is not about them.

0.2.2 corrected the documents and left the behaviour to `024.55`,
because stopping has a failure mode of its own — a false positive locks
the user out of the extension entirely, and this project has shipped a
version check that was wrong about a working combination twice.

### Two spec files, one constant

`SOURCE` in the new debounce spec landed on `Object`, where
`server_receiverless_spec.rb` had already put one. Files load in sorted
order, so the debounce spec ran two review rounds against *another
file's* heredoc, and the only symptom was a Ruby warning nobody read.

Second occurrence: `server_declaration_position_spec.rb` did the same
thing earlier in this release and was caught only because it happened to
break an example outright rather than quietly swap a fixture. So
`spec/meta/spec_constants_spec.rb` now fails on any constant defined in
more than one spec file.

### The debounce, found twice in a row

`CLAUDE.md`'s same-place rule fired for the first time in this release.
Round 32 found `didClose` racing an in-flight publish; round 33 found a
no-op `didChange` discarding a pending one. Different bugs, same three
pieces of state disagreeing — `@pending_publish`'s captured version,
`@document_store`'s current one, and whether a waiter is alive to
reconcile them.

The countermeasure is `server_publish_invariant_spec.rb`: one property —
*an open document's last published diagnostics are for its current
version, and a closed document's are empty* — asserted over a table of
notification sequences. A regression test pins the sequence someone
thought of; this pins the property, and the next defect adds a row.

`flush_pending_diagnostics` was the *second* place found twice: round 32
found a per-thread deadline, round 33 found the shared one that replaced
it still additive with `BackgroundTasks#shutdown`'s. Both were the same
mistake — those threads are tracked, so something already joins them
correctly and a second joiner had nothing to add but its own budget. The
method now only releases the waiters, and the countermeasure is a bound
on the whole of `#run` rather than on any one join: five hung waiters
against a 0.2 s background budget, asserted under 1.5 s. Both rounds'
shapes were checked against it by hand and both fail it.

### What round 33 raised and 0.2.2 did not do

- **`@pending_publish_mutex` is held across `publish_findings`**, which
  writes to the client. A background waiter blocked in `@output.write`
  holds it, and the next `didClose` blocks the dispatch thread on
  `cancel_pending_diagnostics`. Left alone deliberately: the check and
  the write have to be atomic against the close, and a stalled stdout
  already stalls the dispatch thread on its own writes.
- **`seconds_since_write`'s `rescue StandardError; 0`** — the fail-safe
  "keep it" branch — has no coverage in either direction.

### What round 32 raised and 0.2.2 did not do

- **`await_and_publish`'s `return if stopping` is still not pinned by
  outcome.** Removing it fails nothing: the flush and then
  `BackgroundTasks#shutdown` kill the thread anyway, so it is pinned in
  wall-clock duration only. It was rewritten in this round (the abandon
  branch now also releases the latch, which *is* pinned), but a spec that
  fails when the early return goes does not exist.
- **Nothing bounds the number of scope directories** now that absent ones
  survive for thirty days. `DEFAULT_MAX_GENERATIONS` bounds generations
  within one workspace and nothing bounds workspaces. Before 0.2.2 an
  absent workspace's scope was removed whole on the next sweep, so the
  question did not arise. A machine that opens many short-lived
  workspaces accumulates up to thirty days of them.

## What is left of round 31 that has no entry

- **`#bound_prefix_before?` still carries its own copy of the name-start
  rule**, without the `word_char?(text[left - 2])` guard that
  `#name_start_offset` has. No input was found where the two disagree —
  it is called at a `(` offset, where the unguarded step is what the
  `!`/`?` case needs — so it is a claim the code does not literally
  support rather than a defect. The countermeasure's premise is "one
  place decides"; there are still two.
- **`scripts/corpus_diagnostics.rb` was fixed to pass `signatures:`**,
  which means **every figure quoted before 0.2.1's last day was measured
  against a configuration no user runs**. The numbers in the 0.2.1
  changelog were taken before that fix. They are not known to be wrong —
  the shadow rule was reverted out of resolution too, which is the same
  direction — but the first corpus run of 0.2.2 should re-establish a
  baseline rather than diff against a recorded one.

## Measurement, before anything else in this release

The baseline to compare against is **0.2.1's tag**, not `main` at some
later commit, and it must be re-taken with the fixed
`corpus_diagnostics.rb`. `CLAUDE.md`'s measurement section carries the
five ways this release got it wrong; the short form is: one run at a
time, in the foreground, each side printing its own directory and
version, with a control category in the diff that the change cannot
affect.

## A correction worth repeating, not just recording

`024.47` described the *opposite* of the defect the release actually has,
in the register and in both languages' `KNOWN_LIMITATIONS`, from the day
it was written until 0.2.2 checked it. The entry was written mid-loop,
the behaviour it named was reverted three commits later as part of
returning 0.2.1 to its scope, and nothing went back to the entry.

A published limitation naming a defect the release does not have is worse
than no limitation at all: it sends a reader looking for something that
is not there, and it hides the one that is. The lesson is narrower than
"keep documents current" — it is that **a revert has the same
documentation trigger as a change**. `DOCUMENTATION_MAP`'s table is
written in terms of what you changed; reverting is changing.
