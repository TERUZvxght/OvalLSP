## P1 — コミット済み activeParameter の出荷条件を閉じる

**対象:** `Server#signature_help_result`、`#active_parameter_index`、既存の構造トークン、署名を返す QueryService、専用 spec、S4。

- まず既存実装を保持して、最初・次・最後の引数、入れ子の呼出し/配列/hash、文字列内の comma、改行、UTF-16 と非 ASCII、未完の呼出しを実 request で比較する。
- rest / keyword / overload / 引数超過を区別する。comma の数は「実引数の位置」であり、署名の parameter index と常に同じではない。パラメータ数だけで別 overload を選ぶ現在の決定にも反例を置く。
- rest が実際に受ける追加引数は rest の parameter に対応させる。keyword の順序が異なる場合は既存の署名情報で対応を確定できる範囲を扱う。確定不能の場合の辞退方法は client の実表示で確認し、単に範囲外数値や省略で「無強調になる」と仮定しない。
- 修正は現在の呼出しと署名の対応に限定する。全 AST walker、新しい overload 推論器、括弧なし呼出しへの全面拡張は足さない。未対応は S4 の文言と実例に一致させ、既知の誤表示を無条件の PASS 行で覆わない。
- Ruby 構文の期待は interpreter の実行記録、位置/表示の期待は CLIENT_BEHAVIOUR の根拠を先に置く。変える分岐には区別可能な fixture と pinned mutation を付ける。

**完了条件:** S4 の実例、専用 spec、既存 signature help / route helper が通り、公開説明がその範囲を正確に述べる。
コミット済みであることを再修正の免除にはしない。

## P2 — 診断設定を一つの契約にする

### 公開契約を固定する（条件1）

公開する設定は **`ovallsp.diagnostics.severities` のみ**。
WIP の `ovallsp.diagnostics.mode` は manifest とクライアント送信から取り除く。
公開設定は既存 safe の検査集合を広げず、現在の重要度を維持/格下げするか、none にする。

| check | 未指定時 | 設定できる値 |
|---|---|---|
| syntax-error | error | error / warning / information / hint / none |
| unknown-method、unknown-route-helper、argument-count、argument-type、unassigned-ivar | warning | warning / information / hint / none |
| unresolved-constant、未知の code | 公開設定の対象外 | schema では拒否、Core では入力を無視。設定を足して有効化しない |

severity を error にすれば確実になる、という解釈は禁止する。warning の check に error を指定しても
昇格せず、その不正指定を捨てて既定に戻す。none の解除は既定への復帰であり、未提供 check の有効化ではない。

初期化 wire は `diagnosticSeverities`、変更通知は `settings.ovallsp.diagnostics.severities`。
初期化と変更通知で同じ正規化を使用する。完全 snapshot として受け取り、
正しい diagnostics object 内で severities が欠落/空なら overrides を空にして既定へ戻す。
無関係な通知、diagnostics subtree が object でない通知は無視する。
不正な severity 値/非 object map は有効な override として採用しない。
`diagnosticSeverity` / `severity` / `info` / `off` 等の未公開 alias は作らない。

**既存 mode API との境界:** Engine の safe/standard/strict と、出荷済みの
`initializationOptions.diagnosticsMode` を使う既存 Server spec は保持する。
後者は `core/spec/ovallsp/server_diagnostics_spec.rb` に既存の互換契約として存在しているため、
公開設定を増やさない今回の条件から、その既存経路の削除までは導出しない。
標準 VS Code クライアントは diagnosticsMode を送らず、変更通知から mode を変える経路も追加しない。
この既存初期化 API を設定 UI/新しい公開能力/auto-require の前提へ昇格させない。
severity による unresolved-constant の有効化は、初期化/変更通知のどちらでも禁止する。

### 最小の責務分割

- **正規化:** `Diagnostics::Configuration` 相当の小さな値を使う。内部 map も freeze し、外部入力への参照を残さない。mode は初期化時に決まり動的変更では不変、severity map だけを正規化して新しい凍結値に載せる。LSP 数値と `:none` が Engine に混在する WIP は解消する。
- **Engine:** baseline mode が許可した check についてだけ、設定による抑制と格下げを適用する。severity は check を有効化する根拠に使わない。抑制を含めて Engine の出力契約にし、Server だけの後処理にしない。無効な check は無駄に全解析しない。
- **構文エラー:** syntax-error を none にしても、構文が壊れた木から意味診断を出してよいことにはならない。構文の正当性判定は維持し、出力抑制と分ける。
- **budget:** 表示される結果に適用する。none の finding が budget を消費して、表示すべき別 check を押し出さない。
- **Server:** 設定変更の所有、再解析の要求、公開順序だけを担う。`filter_severities` と `to_lsp_diagnostic` に分散した設定適用は撤去し、最後の LSP enum 変換だけを残す。

### 動的変更と競合

W0 着手前の WIP は開いている文書だけに `note_analysis_needed` を呼ぶ。閉じた文書の既存診断は更新されず、
severity は計算時と公開時に別々に読まれる。これは次の RED で確認してから修正する。

- 凍結設定オブジェクトの identity を**空の結果にも**付けて計算から公開まで運ぶ。独立した revision counter、設定履歴 cache、汎用 state framework は作らない。
- 設定は既存 publish の排他境界で一参照を交換する。計算はその参照を一度だけ取得し、公開時に `equal?` で現設定との同一性を同じ排他内で比較する。解析をその lock 内へ移さない。index lock より先に短く参照を取得して解放し、lock 順序を逆転させない。
- 旧設定での結果を新設定の後に公開させない。semantic generation や document version だけでは設定変更を表せない。設定変更のために index を偽更新する方法は使わない。
- open buffer は既存の settled analysis を使う。closed file は既存 workspace pass を再要求し、既に表示した対象が pass 上限などで取り残されないことも確認する。新しい background framework は作らない。
- 同値通知では元のオブジェクトを保ち再解析しない。A → B → A は値が戻っても最後の A を新しいオブジェクトにし、最初の A で計算した結果を復活させない。無関係な通知でも再解析しない。

### VS Code 側

folder ごとに Server が存在する現構成に合わせ、設定は resource scope とし、
`getConfiguration(..., folder.uri)` から初期値・変更値を取得する。
これは現 manifest の default window scope からの**設計選択**であり、今のコードが既に folder scope を約束しているという指摘ではない。
初期化と通知で同じ読み取りを使い、folder A の変更を B の値として送らない。
開始待ち・終了中・再起動の client へ送った通知の rejection は見える形で処理する。
開始中の変更を落とさず、起動後に現在の snapshot が届くことを実 host テストで示す。

manifest には既存 check code と severity の schema を置く。
診断設定が起動コマンドや trust 判定を変えないことを本番経路で確かめ、
`workspaceTrust.test.ts` の safe 分類へ理由つきで追加する。
テストを通すだけの restricted 化や guard の除外はしない。

### 必須の証明

| 層 | 区別する入力と期待 |
|---|---|
| Engine | safe の既定集合、格下げ/none/reset、昇格指定の拒否、unresolved key の無視、未知値、syntax none、budget。standard/strict の既存直接 API を対照に保ち、公開設定からの到達性とは区別 |

| Client | folder 別値、変更/reset、起動中変更、停止中通知、未信頼。configuration event から診断表示まで観測 |
| 公開能力 | severity の格下げ・none/reset の E2E 行を追加。公開 mode 行は追加しない。標準 client の初期化と更新で unresolved が出ないことを本番経路で確認 |

## P3 — 到達可能な auto-require CodeAction を作る

### 元の方針から変更する理由と採用案

GemIndex に短い対応表を加えるだけでは、require entrypoint の証拠も診断からの到達性も得られない。
require ファイル名を constant 名から underscore 化する方法、宣言元ファイルをそのまま require する方法は採らない。
宣言元とライブラリの公開 entrypoint は同じとは限らない。

**採用案:** 少数の stdlib/bundled library に対する、実行で検証した明示的な対応表を
CodeAction 側の小さな責務として持つ。JSON / URI / Pathname などは候補であり、
対応 Ruby・実行環境での証明前に採用済みとはしない。GemIndex の閉鎖性判定へこの表を混ぜない。
任意 gem、Rails autoload、workspace ファイルからの require_relative 推測はこの版の対象外とする。

RBS で既知の定数にも提案を届けるため、unresolved 診断だけに依存せず、
**明示された CodeAction range 内の検証可能な定数参照からも**候補を作る。
標準 client の経路は診断なしで成立させる。既存の内部検証経路で診断がある場合も、
提案は現文書から再判定する。unresolved-constant の有効化を P3 の依存に戻さない。
文書内に同じ require がないことを確認する。Rails では下記のロード状態の辞退条件を先に適用する。
plain Ruby でも間接ロードが不明な場合に「未ロードだから必要」とは断定しない。
表示は「Add require '...'」という編集内容にし、必須の修正と断定したり preferred にしたりしない。
これは safe default を維持しながら公約を使える経路にする設計変更であり、
実装前に ADR へ代替案・有限対応の制約・diagnostic 依存を外す理由を残す。

**成立確認を最初の RED にする:** 新規 Ruby 文書から実 codeAction request → 正しい提案 →
edit 適用 → 隔離した Ruby 実行で定数を使用できる、という一本道を組む。
既知 RBS 定数で診断が出ない safe 経路、Rails のロード済み/不明による辞退を区別する。
「unresolved 診断を fixture で注入したら action が返る」だけでは出荷しない。
もしこの限定契約でも有用な実例を成立させられなければ、Step 4 へ計画を差し戻す。
黙って対象を全面 gem 探索へ広げたり、auto-require を未実装のまま完遂と報告したりしない。

### Rails のロード状態による辞退（条件3）

- 既存の Rails 判定・Agent 状態と、その世代に属する既存 snapshot を使う。CodeAction のために Agent を新規起動/restart/eager-load しない。Rails 判定が不明な workspace も、plain Ruby と仮定して提案を広げない。
- Rails が対象定数を**現在の正確な identity でロード済み**と示す場合は、当該文書に require がなくても返す action は空。
- Rails だが Agent 不在、起動中、restart/reload で snapshot が古い、対象が index にない、autoload 待ち等の場合は**不明として辞退**する。index の欠落を未ロードの証明にしない。
- GemIndex の `knows?` は member の列挙可能性でありロード状態ではない。method_missing を持つロード済み定数も辞退する。必要なら既存 entry の完全名による存在照会だけを追加し、simple-name fallback を使わない。
- 現在の既存 snapshot では Rails の未ロードを安全に証明できないなら、この版の Rails 側は辞退に留める。load-state 用 RPC/網羅索引を追加して公約の依存を増やさない。対応範囲を能力行と日英の制限に明示し、Rails で auto-require が使えると無条件には書かない。
- 正常対照は、plain Ruby と確認した隔離 fixture の明示対応 constant。Rails のロード済み fixture では直書き require の有無にかかわらず提案なし、未知状態でも提案なし、どちらも request による追加ロードなしを示す。ready を模した mock だけで Rails 条件を達成扱いにしない。

### 提案を許可する条件

1. 開いた Ruby 文書の現在の構文・range に実在する定数参照である。ERB、コメント、文字列、壊れた対象式、読み取り不能な文書は辞退する。
2. fully qualified な identity と対応表の entry が一致する。裸の名前は lexical resolution と workspace の衝突検査で一意に証明できる場合だけ。simple-name fallback は証拠に使わない。
3. パスは対応表に検証根拠があり、対象環境で利用可能と確認できる。確認不能・複数候補・shadow では辞退する。Ruby 版・load path・bundle の違いを無視して Core 側にあるライブラリを利用者側にもあると断定しない。
4. 既存 require を構文として確認する。同等の静的 require、条件付き/動的 require によって安全な追加位置や必要性を判断できない場合は辞退する。コメント内の文字列を require 扱いしない。
5. 受信した診断の source/code/range を信用して編集位置を決めない。現文書から再取得する。`context.only` を守り、同一 edit の重複を除く。

通常の LSP request を受けるだけで、ユーザーコードの require、Gemfile 実行、gem install、ネットワーク探索、外部ファイルの書換えを行わない。
対応表の検証は開発時/CI の隔離 fixture で行う。未知の環境で動的実行して確かめる代替は使わない。

### 編集の形と検証

- 編集対象は依頼された文書だけ。先頭の shebang、encoding/frozen-string-literal 等の magic comment、改行形式を保持する。
- 挿入位置は保護すべき header の後、実行文の前。複雑な require 群の再配置・ソートはしない。安全な file-level 位置を確定できなければ辞退する。
- 文書版付きの WorkspaceEdit を使い、取得後に文書が変わった編集を誤適用させない。client capability と実適用を確認し、版付き編集を扱えない client に黙って無保護の代替を返さない。
- 空文書/最終改行なし/CRLF/非 ASCII/header/既存 require/名前衝突/古い diagnostic/古い文書版を区別する。適用後の再要求で重複を提案しない。
- 正常 fixture は生成文字列一致だけでなく、適用後の parse と隔離 Ruby 実行を確認する。異なる require パスを返す mutation を落とす。
- 既存の define-method、route helper、argument-count CodeAction の能力を対照として保持する。

### 撤退後も出荷を進める条件

新しく導入する日常経路の誤答と、個人情報/機械の安全性の退行は出荷不可。
既存の全負債をそのまま 0.4.0 の blocker に昇格しない。残存の影響・頻度・回避策を評価して判断する。
024.224 は退行を確認した時点でその実験 thread を停止する。別名正規化を足す二度目・三度目の手直しを続けない。
撤回前に tree 全体で参照を検索し、code/spec/ADR/changelog/能力/制限の残骸まで同じ単位で戻す。
利用者の既存 WIP や別公約の変更は巻き戻さない。

閉鎖は `ruby scripts/issues.rb close 024.N --released-in 0.4.0`。
制限段落を消す場合は内容を確認して `--drop-paragraphs` を使い、両言語の見出しも取り残さない。
後続へ送る場合は `ruby scripts/issues.rb retarget 024.N --to=V --why="個別の再現と処置理由"` を使う。
V は修復なら具体的な後続 patch、能力追加なら公開ロードマップ上の具体的な minor として Astra が決める。
未決のまま番号を機械的に一括変更せず、生成 index を更新する。
`ruby scripts/release.rb gate --accept 024.N --reason "..."` は、
その版が負わないと決めた課題の**記録手段**であり、再現/頻度判定や安全性検証の代わりではない。
「退行リスクのため先送り」だけでは、何が壊れ、何が残り、次に何をするのかを伝えられない。

`gate --accept` は task を変更して dirty にするので、その呼出しだけで gate 完了にはならない。
受容記録と課題処置を commit した後、clean tree で通常の gate を再実行する。
`core/tmp/` のローカル acceptance を失った場合は正式記録を読んで必要な操作を再実行し、guard を弱めない。

### Pattern B の後続とレビューの境界

**Step 4 は条件付き承認を受領済み。本書の Step 5 担当表に従って Step 6 へ進める。**
条件に反する再設計が必要になれば Astra が計画を改訂し、その変更を未見の Fable 5.1 に渡す。
機械的な適用のたびにユーザーへの承認待ちを挟まない。
レビューには元の要求、本書、Section 0、固定 revision/diff、確認済み/未確認の区別を渡す。
レビューの結論や探索箇所を限定せず、既知/意図的な判断も欠陥なら報告できるようにする。

Step 6 で並行化する場合も、同じ Server/Engine/type model を複数 writer が同時に変更しない。
コード、文書、独立した調査の境界を定め、隔離した差分を一人の統合担当が順に取り込む。
Opus/Sonnet/Gemini が遭遇した仕様判断は skill の規則どおり Astra へ戻す。

実装後の Step 7 は、Gemini の動作確認、Fable 5 の code/YAGNI、Fable 5.1 の要件整合性。
同じ固定 revision を読ませる。Step 8 で Astra が指摘をまとめて修正する。
`ruby scripts/review_round.rb start <method>` は clean tree で実装レビューを開くときに使う。
現在の dirty tree で start したことにしたり、計画レビューを製品の clean round に数えたりしない。
findings は開かれた本書の表へ到着時に記録し、修正で tree を動かす前に round を閉じる。
次 round は別 method と未見 reviewer。減少を信じる前に neutral round を置く。
三回の欠陥検出で終了する運用を無期限ループへ変えず、残存は正式記録する。
ただし安全性の退行や新規の日常的誤答を「三回済み」で公開可能にしない。

## P6 — 同じ成果物を公開し、PR を統合する

1. `ruby scripts/release.rb status` で現在位置を確認する。open 済みのブランチを再作成しない。
2. 課題処置・能力・両言語の release notes/roadmap を完成し、preflight 後に commit する。push 前には `ruby scripts/preflight.rb --install-prepush` を設定し、送出 range と noreply metadata を確認する。
3. `ruby scripts/release.rb bump` を実行し、全変更を確認、preflight 後に bump を commit する。版数を各所で手編集しない。
4. 個別受容があればその記録を先に済ませ、clean tree で `ruby scripts/release.rb gate`。gate 後に source/index が動いたら再 gate。必要な gate を省略する flag は使わない。
5. PR と required CI を候補 revision で成立させる。main の更新が必要なら release branch へ取り込み、競合解消後の候補を再検証する。公開物を確定した後に意味のある source 修正を紛れ込ませない。
6. `ruby scripts/release.rb publish` が作る実 VSIX の vendoring、payload hash、内容、semantic smoke、SBOM、privacy、native 依存を確認し、証拠を本書へ記録する。製品の通常設定変更でこの検査を代用しない。
7. 本書冒頭に記録したユーザーの **「publishやmergeもyes」** により、0.4.0 の publish/merge は許可済み。検証出力と残存事項を確認したらこの許可に基づき publish の最終 prompt に yes と応答する。同じ許可を再要求せず、検証が失敗している場合は先にその失敗を処理する。
8. `ruby scripts/release.rb record` で Marketplace 配信物の digest と built VSIX を比較する。不一致は未完了として止め、検証不能の hash を `--served` へ手入力しない。tag と buildCommit の対応を確認する。
9. artifact row と本書の実績を preflight 後に commit し、branch/tag を push。最終 PR の required CI を待ち、squash merge する。release branch は保持する。1.0.0 前の GitHub Release は作らない。
10. main 統合 SHA、tag/build SHA、version/channel/target、VSIX の built/served hash、閉鎖/受容/未検証課題、実行検証と許容 pending、残る保証範囲を最終報告する。公開と merge の一方だけで完遂とはしない。

### 着手・統合順とレビュー担当の独立性

| 段階 | 作業 | 並行してよいもの / 直列にするもの |
|---|---|---|
| 0 | W0、W6 の先行確認 | 読取り調査は並行可。全計測は W10 が一枠で管理 |
| 1 | W1、W2 の契約確定 → W4 の RED、W3 の client 側 RED | 別 worktree/別ファイルのみ並行可。共通 Server の変更はまだ統合しない |
| 2 | W1 の採用差分 → W2/W4 → W3 | release tree への適用と commit は W10 一人。W9 が companion 文書を各 commit に添える |

| 4 | W7 と W8 の採用分、W9 の残存記録 | 意味論/corpus は一 slice ずつ。採用を終えた tree で次 slice を試す |
