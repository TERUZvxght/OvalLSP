## 実装

### 全履歴secretスキャン

`gitleaks`(Homebrew経由でインストール、`brew install gitleaks`)で
`git log --all`相当の全履歴をスキャン。結果: 4件検出、すべて
`core/spec/ovallsp/redactor_spec.rb`内の**Redactor自身のテストフィクスチャ**
(偽のStripe形式キー・汎用トークン、うち1件は変数名/値に
明示的に"ExampleKeyValue"を含む)であり、実際の秘密情報ではないことを
コード確認済み。値はここに記載しない(位置・ruleIDのみ記録):

| ファイル:行 | ルール |
|---|---|
| core/spec/ovallsp/redactor_spec.rb:12 | generic-api-key |
| core/spec/ovallsp/redactor_spec.rb:24 | generic-api-key |
| core/spec/ovallsp/redactor_spec.rb:63 | stripe-access-token |
| core/spec/ovallsp/redactor_spec.rb:67 | stripe-access-token |

対応不要と判断(テストフィクスチャのpseudo-secretと実際のsecretの区別)。

### PR CI拡張(`.github/workflows/ci.yml`)

既存の`core`/`vscode`ジョブに加え、2つのジョブを追加:

- **`secret-scan`**: `gitleaks/gitleaks-action@v2`。`fetch-depth: 0`で
  全履歴を対象にする(shallow checkoutでは意味がないため)。
- **`package-contents-inspection`**: 実際に`npm run package`を実行し、
  生成VSIXを展開して`$HOME`(そのCI runner自身の絶対パス)が
  含まれていないか検証する。**広いパターン(`/Users/[a-zA-Z0-9_-]+`等)は
  意図的に使わない** — `rbs` gem自身が同梱するstdlib doc内の
  サンプルパス(`/Users/rhc`、コード例のコメント)への誤検知を避けるため。
  Task 023.6で発見・修正した native extension build byproduct
  (`mkmf.log`等)の絶対パス漏洩の再発防止regressionとして機能する。

### Apple Silicon release workflow(`.github/workflows/apple-silicon-release.yml`)

`workflow_dispatch`のみでトリガー(tag pushでの自動実行はしない —
公開プロセス自体がユーザーの明示承認を要求するため)。

**当初の想定(「arm64 GitHub-hosted runnerがない場合はローカルビルドのみ」)
を実地調査で修正**: GitHub-hosted `macos-14`以降のrunnerは実際には
Apple Silicon(M1)ネイティブであることを確認した(2023年10月以降)。
そのため、self-hosted runnerの追加やローカル専用ビルドへの後退は不要と
判断し、`runs-on: macos-14`を採用した。ワークフロー冒頭で
`uname -m`が`arm64`であることを明示的に確認するステップを入れ、
想定が崩れた場合(GitHubがrunner imageを変更した等)に沈黙して
x86_64ビルドを生成することがないようにした。

このworkflowは実際に: darwin-arm64向けにpackage → SHA-256計算 →
`vsix_semantic_smoke.rb`実行 → VSIXとSHA-256をworkflow artifactとして
アップロード、まで行うが、**`vsce publish`は一切呼ばない**
(`docs/PUBLISHING.md`参照 — publishはユーザーの明示承認を要する別工程)。
