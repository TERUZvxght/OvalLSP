incident (`027-0.2.2.md`), renumbered. Its opening rule is inherited

register entries and the hover/completion countermeasure." The first

## What this release is

A patch in `PUBLISHING.md`'s sense: nothing new is announced, and every
change makes the tree or the published record say what is actually
true. No engine behaviour changes. The one spec that changed behaviourally
(`store_spec`'s unusable-directory example) tests the same property
through a fixture that cannot be defeated by the runner's uid.

## The countermeasure moved again, and why

027 deferred "the hover/completion countermeasure" to this release. The
concrete candidate was 024.47's second shape — let the ancestor chain
hold both the workspace class and the RBS type — whose recorded cost
was "one spurious completion candidate on a literal".

It was evaluated against this tree before being built into it: a
monkeypatched simulation of the twin chain, plus a reading of every
engine check that consumes the chain. The recorded costing understated
every line of the bill:

- `"hello".upcase(:ascii)` — legal Ruby — becomes an `argument-count`
  false positive whenever the shadow class declares its own `upcase()`:
  `sole_source_declaration` keeps each source's answer singular while
  the receiver's identity is not, and `sole_declared_overload` has the
  symmetric RBS-side family. This is the exact false-report class 0.2.1
  reverted `self` inference over (024.46).
- A written `Billing::Range` gains the whole core `Range` API as
  spurious completion candidates — the "one candidate" costing was
  written from the literal side only.
- One hover popup mixes identities: an RBS overload label over a
  workspace `Defined:` link. The readers stop disagreeing about
  membership and start disagreeing about identity.
- Making literal receivers closed re-opens 024.13's family — `"".squish`
  under ActiveSupport-style direct additions becomes `unknown-method` in
  any workspace containing a shadow class.
- And the project's usual arbiter cannot arbitrate: gems that reopen
  core classes do it at the *top level*, where `substitution?` never
  fires, so a corpus diff is blind exactly where collisions live. If
  this shape is ever built, constructed fixtures watched failing are
  the gate, not corpus deltas.

024.47's own sentence — "neither is a patch" — was already the recorded
judgment, and the roll-back rule's step 3 already re-scoped this
problem once. Attempting it inside the release that owes the
documentation cleanup would have held the urgent half (published
documents that are false today) hostage to a review loop on the risky
half. So: the fix goes to its own task, with the honest bill recorded
in 024.47; this release delivers the record, not the code. What this
release *does* carry as a mechanical countermeasure is the site/version
guard below.

## A guard that could not see its input

`check_site_links.rb` compares the version the site's index pages
advertise against `vscode/package.json` — and it ran only from
`pages.yml`, which triggers only on `site/**` changes. A release that
bumps `package.json` without touching `site/` (0.2.2, whose review gate
was waived) never runs the check: the badge drifted to say `0.2.1`
against a published 0.2.2, the check was red on `main` for five days,
and nothing could fire it. The countermeasure is the same shape as
`024.41`'s: give the guard the input it could not see. The check now
also runs in `ci.yml` on every push, and `pages.yml` additionally
triggers on `vscode/package.json` so the deployed badge refreshes with
a version bump instead of waiting for the next site edit.

## Verified

Environment note, because it differs from the maintainer's: this
release was prepared on x86_64 Linux, Ruby 3.3.6, running as root in a
container whose `ps` reports pgid/sid 0 for every process. Three
environment-specific results follow from that and are *not* defects in
the tree — each was cross-checked against CI on `main` (green at
`c4c0be2`):

- `vscode` unit: 174 of 175 pass locally; the process-group
  termination test needs a kernel whose `ps` reports process groups.
  CI (`ubuntu-latest`) runs it and is green.
- The old `store_spec` fixture *failed* here (and littered `/`) —
  which is the finding, not an obstacle: root is exactly the uid the
  fabricated-path assumption breaks under. The rewritten example
  passes under every uid.
- `test:integration:packaged` and VSIX packaging are Apple Silicon
  steps and were not run here; they remain on the maintainer's
  pre-publish list (`PUBLISHING.md`), along with recording the
  artifact's SHA-256 in `docs/RELEASE_ARTIFACTS.md` once published —
  the step `release_artifacts_spec` audits per tag.

The record, all on this machine unless stated:

- `bundle exec rspec` (core, full): 1,917 examples, 1 failure at
  baseline — the `store_spec` fixture above, i.e. the tree's own
  defect, fixed in this release; re-run after the change set: see the
  review-loop section for the final numbers.
- `spec/e2e/capabilities_spec.rb` + `spec/integration/real_rails_spec.rb`
  run explicitly with local `rails 8.1.3.1`/`sqlite3 2.9.6`: **73
  examples, 0 failures** — non-zero, matching 027's recorded count, so
  the suites ran rather than skipped.
- 2 pending both runs: `release_artifacts_spec`'s two tag-dependent
  examples, self-skipping in a tagless clone with the reason printed.
- The new unusable-directory example was watched failing in both
  directions: against the un-rescued `ensure_directory` (the error
  propagates) and against an `ensure_directory` that skips `mkdir_p`
  (the cache wrongly activates; caught by the example's `enabled?`
  assertion). The old fixture's failure under root was itself observed
  at baseline (seed 38500).
- `ruby scripts/check_site_links.rb`: red before (both index badges),
  green after.
- `find lib spec -name '*.rb' -print0 | xargs -0 -n1 ruby -c`: clean.
- `gitleaks` over the working tree and the outgoing range: recorded at
