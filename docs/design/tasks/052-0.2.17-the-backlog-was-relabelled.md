# 052 — 0.2.17: rename that does not break the file, and a backlog that was relabelled

The release closes **42 entries**, 24 of them user-visible. Two things
decided its shape, and neither was planned at the start.

## The rename oracle, and why nine passing specs were not enough

Nine shapes of local-variable rename were wrong, and every one had a
passing spec beside it. A spec asserts an edit list. Whether the program
still parses, and still means what it meant, is a property of the
program, and no fixture in this repository was asking that question.

`scripts/rename_oracle.rb` asks it: every local in a corpus renamed
through the real Server, the edits applied, the file re-parsed, and the
sequence of local-variable names compared with the new name mapped back.
Over 1,043 files of activesupport, activerecord, actionpack, railties and
i18n — 3,123 renames, with `refused`, `shadowed` and the corpus
identical on both sides as the control:

| | v0.2.16 | 0.2.17 |
|---|---|---|
| unparseable | 6 | **0** |
| meaning-changed | 704 | **74** |

The 74 are `024.273` and `024.274`, both published: a binding whose
declaration is a parameter or an underscore-prefixed target is left
behind, so the uses that *were* rewritten stop resolving.

**This is the countermeasure `CLAUDE.md`'s same-place rule asked for.**
The scope-frame work produced findings about the same place in two
consecutive rounds, and the rule says the third pass is a machine check
rather than a third hand-fix. It was owed from 0.2.17's first half and is
paid here.

**The comparison took two attempts, and the first one was wrong in the
way this repository keeps recording.** `Prism::Node#inspect` embeds
source offsets, which shift the moment the new name is a different length
— so the first version reported every *correct* rename in the corpus as a
change of meaning. The second version compared local-variable names with
the new name mapped back, and that is satisfied by a **partial** rename:
an occurrence left behind still reads as the old name, and so does the
same position in the before-sequence. It reported the pre-0.2.17 tree
clean on the very shapes this release is about. A leftover is its own
condition now, and the spec asserts both halves so removing either fails.

## The backlog was relabelled rather than cleared

`051` closed with "What is left of 0.2.x: **Nothing.**" It was read off a
register saying the opposite: 64 open entries named 0.3.0, 35 of them
user-visible, in a release `045` declares capability-only.

0.2.16's closing pass had retargeted **54 entries**, and 53 of them
justified it with one of three paragraphs, byte-identical within each
group, each asserting how *that* entry had been verified — driven with a
control in its own fixture (40), confirmed live against HEAD (21),
blocked on the gem index (13). Seven of the forty have an Area entirely
under `docs/`, where there is no fixture to put a control in.

Driven, three of them were false in three different ways:

- **`024.163`** had been fixed before 0.2.15 shipped, by a commit that
  says in as many words that the sentence "has been corrected to this
  one". It was carried open for two releases under a paragraph saying it
  still reproduced.
- **`024.20`** carries its own **Direction** one paragraph above the
  sentence claiming it needs to know what gems define. The entry now had
  two contradictory reasons for its target and the false one was the one
  a reader reached last.
- **`024.267`** said nothing checks for a spec constant defined in two
  files. `spec_constants_spec.rb` has done exactly that since 0.2.3, and
  it fired during this release on a `ROOT` written inside a new meta
  spec's `describe` block.

All 54 are re-triaged, each with a reason of its own. The triage rule is
`docs/PUBLISHING.md`'s own table: a wrong answer is a repair and belongs
on the patch line; a silence turned into an answer is capability and
belongs in a minor; something about this repository's own checks or
record is neither and belongs on the patch line. **25 moved to 0.2.18;
27 kept 0.3.0 on an argument of their own** — for `024.76`, `024.83` and
`024.106` that argument really is the enumeration question, which `045`
records as D2.

`DeferredFindings.repeated_paragraphs` is the countermeasure. It groups
open entries by verbatim paragraph and fails on any shared by three or
more; the threshold is read off the distribution rather than picked —
570 paragraphs appeared in exactly one open entry and four in two, then
nothing until 6, 13, 21 and 40.

It cannot tell a true reason from a false one and does not try. What it
can see is that forty entries gave the same one. **What it does not do is
make a reason true**: a release that moves 25 entries to 0.2.19 can still
give each a distinct sentence saying nothing. What it removes is the
cheapest way to do it, and the one that happened.

## A live disclosure, found by widening a scan

`024.189` predicted that the home-path scanner could not see an agent
scratchpad's hyphen-joined spelling of a real path. Widening the pattern
found that spelling of the maintainer's own home directory **already
committed to this public repository**, in a register entry written
*after* the finding was raised — because nothing could see it. Removed.

The username in it is the published Marketplace publisher id in
`vscode/package.json`; the directory layout was not. Three further holes
in the same scan are closed (`024.187`, `024.188`, `024.190`): a file
with one stray byte was dropped whole rather than read, a symlink was
dereferenced instead of having the string git stores read, and 28
annotated tag bodies — hand-written at release time and pushed publicly
— were read by nothing at all.

## What the release contains, by area

- **Rename** (`024.244`, `024.251`, `024.258`–`024.266`, `024.271`,
  `024.272`): nine shapes, plus the two `ensure` defects underneath them.
- **Constant and type resolution** (`024.246`–`024.257`): one bad
  `include` in a project's RBS, unions answered inconsistently by
  completion and the diagnostic, and a compact class path whose head was
  glued to the enclosing frame instead of resolved.
- **Privacy** (`024.187`–`024.190`).
- **The measured-claim machinery** (`024.159`, `024.181`,
  `024.184`–`024.186`): scans the whole tree, reads every marker on a
  line, compares the marker's number with the sentence beside it, refuses
  a dated claim a deriver cannot answer, and counts a lock by parsing
  rather than by grepping — `mutex-sites` had been counting a comment.
- **The register's own keys** (`024.173`): the shipped-target guard reads
  every open entry rather than only defects, and `released-in:` has a
  reader for the first time, which found five resolved entries carrying
  none.
- **Test quality** (`024.267`–`024.270`): `#force_kill` was reached by no
  example, `#alive?` was asserted only in the false direction.
- **The record** (`024.161`, `024.163`, `024.165`, `024.196`): a
  correction that recorded work it had not done, a decision kept on a
  false reason, and one measurement quoted in three places and matching
  none of them.

## What is left of 0.2.x, stated so the next session can check it

**25 entries target 0.2.18**, 11 of them user-visible. Several say in
their own bodies that they want a change set of their own: `024.230`
(the owner a top-level `def` is recorded under, read by every feature at
once), `024.45`/`024.57` (the debounce, and a published numeric
requirement missed by an order of magnitude), `024.19`/`024.47` (type
name resolution, where `024.47` records a rollback).

**27 target 0.3.0**, and that release is capability-only by `045`. Three
of them wait on `024.R7`; the rest are silences that become answers,
which is what a minor is for.

`ruby scripts/deferred_findings.rb --targeting 0.2.18` is the list, and
it is the tool rather than this paragraph that should be believed — this
file will go stale and that command will not.
