### 実機での通し実行で発見した問題と対応

#### 1. ロケール依存のクラッシュ(修正済み)

`assert_rspec_json_clean`(および`ci.yml`・`generate_sbom.rb`の同型処理)
が`File.read(path)`を明示的なencoding指定なしで呼んでおり、`LANG`が
未設定のシェル(このマシンの実際の状態)では外部encodingがUS-ASCIIへ
fallbackし、RSpec JSON出力に含まれる非ASCII文字(em dash等、この
コードベースのコメント・テスト記述に多用されている)でクラッシュする
ことを、実際にスクリプトを実行して発見した。`File.read(path, encoding:
"UTF-8")`へ修正(3箇所)。

#### 2. bashの構文エラー(修正済み)

上記1の修正コメントに含めたアポストロフィが、`ruby -e`へ渡す
シングルクォート文字列を早期終了させ、bash構文エラーを引き起こした。
コメントをシングルクォート文字列の外(bashコメント)へ移動して解決。
`bash -n`で構文検証済み。

#### 3. Native extension自体への絶対パス埋め込み(未解決、既知のギャップとして記録)

`package-contents-inspection`ステップの初回実行で、
`prism.bundle`/`rbs_extension.bundle`にこのビルドマシン自身の絶対パス
(`$HOME`)が含まれていることを検出した。調査の結果、これは
`mkmf.log`等とは性質が異なることが判明した:

- `otool -L`で確認したところ、これはビルドログの副産物ではなく、
  コンパイル済みバイナリ自体が持つ`LC_LOAD_DYLIB`(動的リンクの依存先)
  として、このマシンのrbenv libruby絶対パス
  (`/Users/<username>/.rbenv/versions/3.4.7/lib/libruby.3.4.dylib`)が
  埋め込まれていた。
- `otool -l`で確認したところ、`LC_RPATH`エントリは存在せず、相対パスへの
  フォールバック機構がない。
- prismはRubyGems.org上で"ruby" platform gem(ソースのみ)としてのみ
  配布されており、`bundle install`のたびに必ずこのマシン上でローカル
  コンパイルされる。
- **これがengine/version/platformが一致する別マシンでの動的リンク解決に
  実際に影響するかどうかは、本セッション内では検証できていない**
  (このマシン以外のApple Silicon Mac、または異なる絶対パスにRubyを
  持つ環境が利用できなかったため)。`install_name_tool`によるポータブルな
  `@rpath`参照への書き換えは、安全性を検証できない状態で実施するのは
  リスクが高いと判断し、本セッションでは実施しなかった。

対応: `package-contents-inspection`ステップを、この種のcompiled native
extension(`.bundle`/`.so`/`.dylib`)についてはhard failの対象から除外し、
**非致命的warning**として報告するよう変更した(検出結果を隠さない)。
`docs/KNOWN_LIMITATIONS.md`と`docs/RELEASE_CHECKLIST.md`の両方に、
この未検証のリスクを明示的に記録した。

**この項目は、Marketplace公開前に別のApple Silicon Mac(または異なる
絶対パスにRubyがインストールされた環境)で実際にVSIXをインストールし、
Core Serverが正常に起動する(特にprism/rbsが正しくロードされる)ことを
実機確認することを強く推奨する** — `.github/workflows/apple-silicon-release.yml`
(GitHub-hosted `macos-14`、このマシンとは異なる絶対パスにRubyが
インストールされる)がまさにこの検証に使えるが、実際にpushして
トリガーするところまでは本セッションのスコープ外(ユーザー承認が必要)。

## Review B(Task 023.6〜023.8の独立レビュー)での追加修正

Review Bで、上記「3. Native extension自体への絶対パス埋め込み」を
非致命的warningとして処理した判断そのものが**誤りである**と指摘された。
指摘の要旨: rbenv/ruby-buildが`--enable-shared`でコンパイルしたRubyは
一般的にlibrubyのinstall nameを絶対パスのまま記録する既知の挙動であり、
ADR-0005のcompatibility check(engine/version-majorminor/platformのみ
比較)ではこの絶対パス不一致を検知できない。エンドユーザーの絶対パスが
packaging machineと一致することは通常ありえず(ユーザー名が違うだけで
発生する)、「まれなエッジケース」ではなく「ほぼ全てのエンドユーザーで
発生する」重大な機能不全である可能性が高いという指摘だった。

**このマシン上で直接再現・修正を検証した**(2台目のマシンは利用できな
かったが、このマシンには既にRuby 3.4.7と3.4.5の両方がrbenv経由で
インストールされており、両者は`RUBY_VERSION`のmajor.minorが同じ"3.4"
でありながら絶対パスが異なるため、ADR-0005のcompatibility checkが
"compatible"と判定するにもかかわらず絶対パスが異なる、という実際の
状況を過不足なくシミュレートできた):

1. Ruby 3.4.7でvendoringした`prism.bundle`を、Ruby 3.4.5から`require`
   すると、実際に`LoadError: linked to incompatible
   .../libruby.3.4.dylib`で失敗することを確認(再現成功)。
2. `DYLD_LIBRARY_PATH`を実際に実行中のRuby(3.4.5)自身の`lib`ディレクトリ
   へ設定した状態で同じ`require`を実行すると、正常にロードできることを
   確認(修正案の直接検証)。
3. `child_process.spawn`相当のNode APIで、Extension側が実際に使う
   env継承方法(`{ ...process.env, DYLD_LIBRARY_PATH: ... }`)を通じて
   同じ検証を再現し、修正が実際の起動経路でも機能することを確認。

**修正**: `vscode/src/serverConfig.ts`に`deriveNativeExtensionLibraryPath`
を追加。解決されたRuby実行系の絶対パスから、mise/asdf/rbenv/Homebrewが
共通して従う`<prefix>/bin/ruby` + `<prefix>/lib/libruby*`という
レイアウトに基づき兄弟`lib`ディレクトリを導出する(darwinのみ、絶対パス
でない`ruby`コマンドの場合は何もしない — 導出元がないため)。
`vscode/src/extension.ts`の`startClientForFolder`で、Core Server起動時の
spawn環境へ`DYLD_LIBRARY_PATH`/`DYLD_FALLBACK_LIBRARY_PATH`として設定。
macOSの動的リンカはこれらの環境変数を、依存ライブラリに記録された絶対
パスを参照する前に、ファイル名(leaf name)ベースで優先的にチェックする
ため、埋め込まれた絶対パス自体は残るが機能的な問題は解消される。

`vscode/src/test/unit/serverConfig.test.ts`に
`deriveNativeExtensionLibraryPath`のテストを追加(rbenv/Homebrewスタイル
パスからの導出、darwin以外でのundefined、絶対パスでない`ruby`コマンドでの
undefined、計4テスト)。`test:integration`・`test:integration:packaged`も
修正後green(実際のspawn経路を経由した確認)。

副次的な指摘として、`scripts/vsix_semantic_smoke.rb`にも同種の
(このセッションでは実害のない)`File.read`のencoding未指定箇所が
見つかったため、同様に`encoding: "UTF-8"`を明示した。
