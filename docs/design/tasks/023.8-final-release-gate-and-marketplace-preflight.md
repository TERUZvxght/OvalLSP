### 実機での通し実行で発見した問題と対応

#### 1. ロケール依存のクラッシュ(修正済み)

`assert_rspec_json_clean`(および`ci.yml`・`generate_sbom.rb`の同型処理)
が`File.read(path)`を明示的なencoding指定なしで呼んでおり、`LANG`が
未設定のシェル(このマシンの実際の状態)では外部encodingがUS-ASCIIへ
fallbackし、RSpec JSON出力に含まれる非ASCII文字(em dash等、この
コードベースのコメント・テスト記述に多用されている)でクラッシュする
ことを、実際にスクリプトを実行して発見した。`File.read(path, encoding:
"UTF-8")`へ修正(3箇所)。

#### 2. bashの構文エラー(修正済み)

上記1の修正コメントに含めたアポストロフィが、`ruby -e`へ渡す
シングルクォート文字列を早期終了させ、bash構文エラーを引き起こした。
コメントをシングルクォート文字列の外(bashコメント)へ移動して解決。
`bash -n`で構文検証済み。

#### 3. Native extension自体への絶対パス埋め込み(未解決、既知のギャップとして記録)

`package-contents-inspection`ステップの初回実行で、
`prism.bundle`/`rbs_extension.bundle`にこのビルドマシン自身の絶対パス
(`$HOME`)が含まれていることを検出した。調査の結果、これは
`mkmf.log`等とは性質が異なることが判明した:

- `otool -L`で確認したところ、これはビルドログの副産物ではなく、
  コンパイル済みバイナリ自体が持つ`LC_LOAD_DYLIB`(動的リンクの依存先)
  として、このマシンのrbenv libruby絶対パス
  (`/Users/<username>/.rbenv/versions/3.4.7/lib/libruby.3.4.dylib`)が
  埋め込まれていた。
- `otool -l`で確認したところ、`LC_RPATH`エントリは存在せず、相対パスへの
  フォールバック機構がない。
- prismはRubyGems.org上で"ruby" platform gem(ソースのみ)としてのみ
  配布されており、`bundle install`のたびに必ずこのマシン上でローカル
  コンパイルされる。
- **これがengine/version/platformが一致する別マシンでの動的リンク解決に
  実際に影響するかどうかは、本セッション内では検証できていない**
  (このマシン以外のApple Silicon Mac、または異なる絶対パスにRubyを
  持つ環境が利用できなかったため)。`install_name_tool`によるポータブルな
  `@rpath`参照への書き換えは、安全性を検証できない状態で実施するのは
  リスクが高いと判断し、本セッションでは実施しなかった。

対応: `package-contents-inspection`ステップを、この種のcompiled native
extension(`.bundle`/`.so`/`.dylib`)についてはhard failの対象から除外し、
**非致命的warning**として報告するよう変更した(検出結果を隠さない)。
`docs/KNOWN_LIMITATIONS.md`と`docs/RELEASE_CHECKLIST.md`の両方に、
この未検証のリスクを明示的に記録した。

**この項目は、Marketplace公開前に別のApple Silicon Mac(または異なる
絶対パスにRubyがインストールされた環境)で実際にVSIXをインストールし、
Core Serverが正常に起動する(特にprism/rbsが正しくロードされる)ことを
実機確認することを強く推奨する** — `.github/workflows/apple-silicon-release.yml`
(GitHub-hosted `macos-14`、このマシンとは異なる絶対パスにRubyが
インストールされる)がまさにこの検証に使えるが、実際にpushして
トリガーするところまでは本セッションのスコープ外(ユーザー承認が必要)。

## Review B(Task 023.6〜023.8の独立レビュー)での追加修正

Review Bで、上記「3. Native extension自体への絶対パス埋め込み」を
非致命的warningとして処理した判断そのものが**誤りである**と指摘された。
指摘の要旨: rbenv/ruby-buildが`--enable-shared`でコンパイルしたRubyは
一般的にlibrubyのinstall nameを絶対パスのまま記録する既知の挙動であり、
ADR-0005のcompatibility check(engine/version-majorminor/platformのみ
比較)ではこの絶対パス不一致を検知できない。エンドユーザーの絶対パスが
packaging machineと一致することは通常ありえず(ユーザー名が違うだけで
発生する)、「まれなエッジケース」ではなく「ほぼ全てのエンドユーザーで
発生する」重大な機能不全である可能性が高いという指摘だった。

**このマシン上で直接再現・修正を検証した**(2台目のマシンは利用できな
かったが、このマシンには既にRuby 3.4.7と3.4.5の両方がrbenv経由で
インストールされており、両者は`RUBY_VERSION`のmajor.minorが同じ"3.4"
でありながら絶対パスが異なるため、ADR-0005のcompatibility checkが
"compatible"と判定するにもかかわらず絶対パスが異なる、という実際の
状況を過不足なくシミュレートできた):

1. Ruby 3.4.7でvendoringした`prism.bundle`を、Ruby 3.4.5から`require`
   すると、実際に`LoadError: linked to incompatible
   .../libruby.3.4.dylib`で失敗することを確認(再現成功)。
2. `DYLD_LIBRARY_PATH`を実際に実行中のRuby(3.4.5)自身の`lib`ディレクトリ
   へ設定した状態で同じ`require`を実行すると、正常にロードできることを
   確認(修正案の直接検証)。
3. `child_process.spawn`相当のNode APIで、Extension側が実際に使う
   env継承方法(`{ ...process.env, DYLD_LIBRARY_PATH: ... }`)を通じて
   同じ検証を再現し、修正が実際の起動経路でも機能することを確認。

**1回目の修正案(不完全、レビューの再指摘で発覚)**: 当初
`vscode/src/serverConfig.ts`に`deriveNativeExtensionLibraryPath`を追加し、
解決されたRuby実行系の絶対パスから`<prefix>/bin/ruby` → `<prefix>/lib`
という形でパスの見た目だけから兄弟`lib`ディレクトリを導出し、Core Server
起動時のspawn環境へ`DYLD_LIBRARY_PATH`として設定する方式を実装した。

レビューへ再確認を依頼したところ、この方式には**2つの独立した欠陥**が
あることが指摘・実証された:

1. **パス導出自体が誤り**: mise/asdf/rbenvの`rubyResolver.ts`戦略は
   いずれも実体の`bin/ruby`ではなく**shimスクリプト**
   (`~/.rbenv/shims/ruby`等、`~/.rbenv/versions/<version>/`配下ではなく
   `~/.rbenv/shims/`直下に存在する)を返す。このパスに対して
   `<prefix>/bin/ruby → <prefix>/lib`を適用すると`~/.rbenv/lib`という、
   libruby自体が存在しないディレクトリを導出してしまう — 最も優先度の
   高い、最も一般的な解決経路(rbenv/asdf/mise)で修正が機能しない状態
   だった。
2. **`DYLD_LIBRARY_PATH`をshim自体の起動環境に設定しても効果がない**:
   実際にこのマシン上で検証したところ、macOSは`/bin/bash`を経由して
   起動されるプロセスに対し`DYLD_*`環境変数を(親プロセスが何を設定して
   いても)無効化することを確認した(rbenv固有の挙動ではなく、単純な
   `#!/bin/bash`スクリプトでも同じく無効化されることを直接確認)。
   rbenv/asdf/miseのshimはいずれもbashスクリプトであり、最終的な
   `ruby`実行系へ`exec`する過程で複数回bashを経由するため、shim自体の
   起動時に設定した`DYLD_LIBRARY_PATH`は実体のRubyプロセスには一切
   到達しない。

**最終的な修正**: パスの見た目からの推測をやめ、解決されたRuby実行系へ
`RbConfig::CONFIG["bindir"]`と`["libdir"]`を直接問い合わせる方式へ変更した
(`vscode/src/platformCompatibility.ts#queryRubyConfigPaths`、shimを経由
して問い合わせても、shim自身がバージョン選択を終えた後の実際のRuby
プロセスが応答するため、この問い合わせ自体はshim非依存で正しく機能する)。
そのうえで、Core Server本体の起動には**shimではなく`<bindir>/ruby`という
実体のバイナリを直接起動する**よう変更し(`vscode/src/extension.ts`)、
そのバイナリへの起動環境として`DYLD_LIBRARY_PATH`/
`DYLD_FALLBACK_LIBRARY_PATH`を設定する。実体バイナリを直接起動するため
bashを経由せず、macOSの動的リンカがこれらの環境変数をファイル名
(leaf name)ベースで正しく参照できる。

このマシン上で最終的な修正を、実際のrbenv shim(`RBENV_VERSION`環境変数で
3.4.5へ強制)経由で再現・確認した: (1) shim経由でCore起動を模した場合に
実際に`LoadError`が再現すること、(2) `queryRubyConfigPaths`相当の問い合わせを
同じshim経由で実行し正しい`bindir`/`libdir`(3.4.5側)を取得できること、
(3) 取得した`bindir/ruby`を直接起動しDYLD環境を設定した場合に実際に
`require "prism"`が成功することを確認した。

`vscode/src/test/unit/platformCompatibility.test.ts`の
`queryRubyConfigPaths`テスト(実際にRubyを起動してbindir/libdirを
取得・比較する実機テストと、存在しないコマンドでのreject確認、計2件)、
`vscode/src/test/unit/serverConfig.test.ts`からは古い(誤った)
`deriveNativeExtensionLibraryPath`のテストを削除。
`test:integration`・`test:integration:packaged`も最終修正後green
(実際のspawn経路 — 全てのCore起動がこの新しい解決を経由する — を
経由した確認)。

副次的な指摘として、`scripts/vsix_semantic_smoke.rb`にも同種の
(このセッションでは実害のない)`File.read`のencoding未指定箇所が
見つかったため、同様に`encoding: "UTF-8"`を明示した。

### Review B、3回目の再指摘: `cwd`の欠落によるバージョン誤解決

上記の修正案を再度レビューへ確認依頼したところ、**新たな、独立した
regressionが実機で再現された**: `queryRubyConfigPaths`
(および既存の`queryRubyIdentity`)の`execFile`呼び出しに`cwd`オプションが
渡されていなかった。rbenv/asdf/miseのshimは、カレントディレクトリの
`.ruby-version`/`.tool-versions`に基づいて「どのインストール済み
バージョンを実際に使うか」を決定する。`cwd`を渡さない場合、この問い合わせは
extension host自身の(ワークスペースフォルダとは無関係な)カレント
ディレクトリを基準に実行されてしまい、ワークスペースが特定のRuby
バージョンにpinしている場合、**完全に別バージョンのRubyのbindir/libdirを
誤って取得し、それを直接起動してしまう**(DYLD問題以前の、そもそも
間違ったインタプリタを起動するという、より重大な機能不全)。

このマシン上で直接再現した: 2つの一時ディレクトリにそれぞれ異なる
`.ruby-version`(3.4.7 / 3.4.5)を置き、実際のrbenv shim
(`~/.rbenv/shims/ruby`)を無関係な第三のディレクトリから呼び出すと、
本来意図しないバージョンのbindirが返ることを確認した。

**修正**: `queryRubyIdentity`・`queryRubyConfigPaths`の両方に`cwd`引数を
追加し、`execFile`の`cwd`オプションへ渡すよう変更。
`checkBundledCoreCompatibility`にも`cwd`引数を追加し、注入された
`queryIdentity`へ転送する。`vscode/src/extension.ts`の呼び出し箇所では
両方に`folder.uri.fsPath`(そのワークスペースフォルダ自身のパス)を渡すよう
修正。

`vscode/src/test/unit/platformCompatibility.test.ts`に2件のテストを追加:
(1) `checkBundledCoreCompatibility`が注入された`queryIdentity`へ`cwd`を
正しく転送することを確認するテスト、(2) `queryRubyConfigPaths`が実際に
指定した`cwd`でクエリを実行することを、自前の偽`ruby`スクリプト
(渡された`cwd`をそのまま`pwd`で返すだけのシェルスクリプト)を使って
確認する実機テスト — 実際のrbenv環境がないCI環境でも意味を持つよう、
実在のバージョンマネージャに依存しない形で構成した。

git-stash-revert検証: `execFile`呼び出しから`cwd`オプションを取り除いた
状態(修正前の状態を再現)で実行したところ、(2)のテストが実際に失敗する
ことを確認(`/tmp/...`ではなく`vscode/`という誤ったcwdが返った)。
復元後、VS Code unit 69 examples全てgreenに戻ることを確認。
`test:integration`・`test:integration:packaged`も最終確認済み。
