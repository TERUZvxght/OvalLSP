# 057 — 0.3.3: the record the 0.3 line left behind

**Branches:** `release/0.3.3` for the record repair,
`release/0.3.3-cut` for the version, changelog and site panels, and
`release/0.3.3-published` for the artifact row — all merging into `main`
by pull request. `CLAUDE.md`'s "Where a release's
work lives" has the rule, and `scripts/check_release_pointers.rb` fails
when a release branch exists that no task document names, which is what
these lines are.

**Two branches for one release, and it was not the plan.** The record
repair merged first, without a version. Cutting the version then meant
either a second branch or resetting `release/0.3.3` to `main` and
force-pushing — and the second option destroys the two commits that
branch holds, because `main` squash-merges and they are reachable from
nowhere else. `CONTRIBUTING.md`'s "A merged release branch is kept" is <!-- deleted -->
about exactly that. So the branch stands as it was and the cut got its
own, which is the cheaper of the two mistakes available.

## Why this release exists

0.3.2 closed the 0.3 line's backlog and the maintainer asked a plain
question: *is anything still marked 0.3.x or below and unresolved?*

The first answer given was **yes, nothing is left** — and it was too
strong. It rested on `ruby scripts/deferred_findings.rb --targeting`,
run four times. That script compares `fields["target"] == version`,
**exact string equality**, so four probes tested four of the thirty-five
versions at or below 0.3.2. Enumerating instead, across both register
files:

    open entries        45
    distinct targets    0.4.0 -> 42,  1.0.0 -> 3
    open with no target  0
    open with released-in 0

So the engineering answer was right and the method was not, which is the
distinction this release turns on: **no work is outstanding at 0.3.x or
below; the record of it was wrong in about forty-five places.**

## What was wrong

Six sources of record were swept and every candidate adversarially
verified. Forty-five survived. The ones that mattered:

- **The public site advertised 0.3.0 as unshipped.** `site/roadmap.html`
  rendered its 0.3.0 panel as `tl-item--future` with every item marked
  as a plan, on a page already carrying shipped panels for 0.3.1 and
  0.3.2; and the front page told visitors that indexing what the gems
  define "is planned for 0.3.0". Both had been deployed live since the
  0.3.0 merge. `054`'s own "not done here, and owed at release" section
  names those two pages, and they were never flipped — through three
  releases.
- **`024.R3`'s parity table** left the "Shipped in" cell empty for five
  capabilities 0.3.0 shipped, under a preamble reading "Everything below
  without a shipped in is still absent".
- **Two headings in each language had no body**, left when 0.3.0 fixed
  the limitations under them. With nothing beneath it a heading *is* the
  claim, and both asserted defects the product does not have.
- **`024.224` was closed on half of itself in 0.3.2**, and the published
  paragraph was rewritten in both languages to say the limitation was
  gone. The repository's own reproduction still failed the whole time.
- **`024.151` was closed on one instalment of about eleven**, its own
  closing text saying the class was not closed.

## What was done

Both entries are reopened, narrowed, at 0.4.0. Every stale marker was
corrected in place rather than deleted: this repository keeps its history
in its prose, and a sentence that was true when written stays, marked as
superseded.

**Two mechanical countermeasures**, because two of these are the third
instance of their class and `CLAUDE.md` says the third is where a hand
fix stops being the answer:

- `scripts/check_bodyless_headings.rb` — every tracked Markdown document,
  flagging a heading immediately followed by one of the same level. The
  rule was measured rather than chosen: the looser form finds one extra
  thing in this tree, a heading introducing a quoted document, so the
  same-level restriction needs no exemption list. In the suite and in
  preflight.
- `DeferredFindings.undocumented` no longer filters `kind == "defect"`.
  Seven open `friction` entries declaring a user-visible half were never
  required to be published, and `024.290` was undocumented by this
  guard's reckoning while `docs/ISSUES.md` published "None". `024.173`
  fixed the identical filter in the sibling reader and did not reach
  here. The exclusion is now written as "not a roadmap plan", so a kind
  added later is included by default and fails towards being checked.

## What this release did not do

No capability row moved and no behaviour changed. The only edits to
`core/lib` are comments.

**The audit did not re-run a single corpus measurement**, so most 0.3.x
closures resting on a number remain unverified by anything but their own
author. Two were re-derived here, and both hold:

- the `argument-type` check driven over all seventeen installed gems that
  ship their own `sig/` — rbs 3.8.0, 4.0.3 and 4.2.0 among them, each
  with its own signatures loaded — reports **nothing** on any of them.
  That is what makes the narrowed `024.224` paragraph honest about how
  rare the remaining shape is, rather than resting on the rbs corpus
  alone;
- `024.238`'s recorded control, re-run on this tree:

      corpus-files=335                     (activesupport 8.1.3.1 + i18n 1.15.2)
      count.unresolved-constant=916        (the entry records 916)

  which is the number the entry names, from the corpus the entry names.

Ten remain. The ones that would need a Rails application and a Runtime
Agent — `024.87`, `024.305`, `024.R7` — are the ones worth doing next,
and they are an experiment to set up rather than a command to run.

## Why this is a patch, and why it is published at all

`docs/PUBLISHING.md`'s table defines a patch as "nothing new is
announced -- the release makes the extension do what some earlier release
already claimed", and lists documentation among its contents. That is
this release exactly. No capability row was turned, and the one row whose
*label* changed was narrowed rather than promoted: "code actions / quick
fixes for each diagnostic" overclaimed, and there are three.

It is published rather than left on `main` for one reason: `vscode/`'s
README is the Marketplace description, it shipped inside the 0.3.2 VSIX
carrying a policy this project had retired, and nothing but a publish
replaces it. The site fix reaches readers on merge; that one does not.

## Shipped

Published to the Marketplace Pre-Release channel from `main`. The
artifact's hash is in
[`docs/RELEASE_ARTIFACTS.md`](../../RELEASE_ARTIFACTS.md), compared
against what the Marketplace actually serves rather than against what
`vsce` reported: byte-identical, 4,139,716 bytes. `v0.3.3` is tagged.

The reason for publishing was checked *inside the served artifact*, not
only in the tree: `extension/README.md` in the downloaded VSIX no longer
carries the retired Ruby 4.0 policy and carries the current one. That is
the difference between a release that fixed the Marketplace copy and one
that only fixed the repository's copy of it.
