## Round 23's findings, in the order a user notices them

All but one are fixed; each is kept with what it was, because the shape
of the mistake is the part worth reading. **What is still open is the
second half of A** — `a.` followed by a line that parses cleanly — and
it wants debouncing rather than another check.

### A. Typing a `.` produces false diagnostics naming the next line

Two reviewers found this independently. `Diagnostics::Engine#analyze`
runs every semantic check against Prism's error-recovery tree, and
`Server` publishes on every `didChange` with no debounce.

```ruby
a = Article.new
a.
b = "str"
```
→ ``Article has no method named `b=` `` and ``QqTyping has no method
named `b` ``. There is no syntax error — `a.b = "str"` parses — so
nothing marks it as mid-edit. At end of method the same edit gives
``Article has no method named `end` ``.

**User sees:** false Problems entries on essentially every dot typed,
pointing at a line they did not touch. The dot is the trigger character
for completion, so this is the commonest editing action there is.

**Direction:** the gate belongs in `analyze`, not in each check —
nothing currently prevents a future check from asserting about a node
error recovery invented. Suppressing semantic checks while
`summary.diagnostics` is non-empty covers the `end` case but not the
`a.b = "str"` case, which parses cleanly; that one needs the *edit
position* to be known, or the check to decline a call whose message
range starts on a different line from its receiver.

### B. Hover on a receiverless call answers nothing

`server.rb`'s `hover_lines` adds the signature / Origin / Defined /
documentation lines only when `receiver_type_before_dot` succeeds.

```ruby
charge_it(1)              # hover -> ""
QqWide.new.charge_it(2)   # hover -> "charge_it(amount)\nOrigin: source declaration\n…"
```

`EXTENSION_CAPABILITIES` **H5** ("Hovers a method call | its parameter
list | PASS") carries no receiver qualifier in either language, and
`README.md`'s row has no footnote. H7 and the `[^doc]` footnote *do*
carry the qualifier; H5 does not.

0.2.0 gave go-to-definition and signature help a receiverless path
(`scope_at(...).self_type`); hover was not given the same and nobody
noticed because H5's example writes a receiver.

**User sees:** hovering `article_params` in their own controller — the
commonest way Ruby calls a method — shows an empty popup.

### C. 024.14 does not reproduce: project-wide diagnostics work end to end

024.14 is `status: open` and says a never-opened probe file produced no
diagnostic within 45 seconds. A reviewer ran exactly that procedure
against `spec/fixtures/rails_real` and got:

```
unopened probe: [unknown-method: UnopenedProbe has no method named `definitely_not_here`]
```

whether the original 45-second measurement had the same shape.**

Five documents carry consequences of the non-reproducing claim:

"a capability with no E2E row is not a capability"), `README` marks the
row ⚠️ `[^ws]`, `KNOWN_LIMITATIONS` repeats it, `vscode/CHANGELOG.md`
hedges, and `site/capabilities.html` shows Unverified.

**User sees:** a headline 0.2.0 feature they are receiving, described
across five documents as unverified and unpromised.

**Do not simply close it.** Reproduce the failure first, then decide
whether the entry was wrong or whether something since fixed it — the
answer changes what the capability row should say.

### D. A workspace class named after a core class shadows the builtin

`WorkspaceIndex#guessed_type_name?` says a bare name matching exactly one
type is not a guess. For a name the engine has RBS for, one same-named
workspace class *is* a wrong substitution.

```ruby
module Serializer
  module Elements
    class String < Element; end
    class Symbol < Element; end
  end
end
```
Then `title.upcase` where `title = "hello"` → ``String has no method
named `upcase` ``. Completion after `title.` offers the namespaced
class's members. **Hover on the same position still answers
`upcase() -> String`** — hover, completion and diagnostics disagree.

Scale: `rubygems/safe_marshal/elements.rb` declares `Symbol`, `String`,
`Integer`, `Hash` and `Array` under `Gem::SafeMarshal::Elements` and is
solely responsible for 604 `unknown-method` reports in prism's
`dispatcher.rb` on the round-22 corpus. Indexing `dispatcher.rb` without
it gives 0.

This overlaps 024.19 and the receiver-offset fix in `4719de7` — measure
what remains before acting. 024.19's text and `025-…-handover.md` both
claim the cause "is now refused for every diagnostic"; it is not, and
024.19's "not reproduced from a fixture" is false (a 20-line fixture
does it).

### E. Range, Regexp, lambda and `!`/`&&`/`||` have no type

`LocalInferencer#eval_type` and `MethodAnalyzer#eval_node` have no case
for `Prism::RangeNode`, `RegularExpressionNode`, `LambdaNode` or the
boolean operators. Everything falls to Unknown.

```

x = /abc/;  x.  -> 0
hover on 1..5, /abc/, !true, true && false, 1 || 2 -> ""
```

`EXTENSION_CAPABILITIES` **H4** promises "Hovers a literal … `String`,
`Integer`, `Array[Integer]`", `README` markets "Hover: literals,
constructors, locals ✅", and nothing in `KNOWN_LIMITATIONS` excludes
these in either language.

### J. Unpinned decisions — **fixed in `c06cca4`**

Reverse-applied individually, suite green each time:

- `query_service.rb`'s `names.uniq.each` — without it, a name declared
  by two ancestors of one nominal in a two-member Union is offered as
  *unconditional* when it exists on one branch. Reasoned from the code,
  not measured on the wire.
- `server.rb`'s `return [] if receiver_dot_before?` in
  `receiverless_definitions` — **measured**: removing it makes F12 on a
  call to an untyped receiver jump into the enclosing class's same-named
  method.
- `query_service.rb`'s `owners.empty? ? [[nominal.name, singleton]] : owners`
- `method_resolver.rb`'s `next if entry.name.nil?`
- `local_inferencer.rb`'s `RationalNode` → `Rational`

All five live inside hunks that added a method wholesale — the blind
spot `CLAUDE.md` names, and the reason a file-granularity sweep called
those files pinned.

Four are behaviour and now have a test that fails with the line
reverted. The fifth — `names.uniq` — turned out not to be behaviour at
all: `normalize_union_conditionals` recomputes `conditional` for every
candidate whenever the receiver is a Union, and that is the only
receiver shape where the count it fed could be anything but `false`.
Two sources were computing a number that was always overwritten or
always the same, and one of them (`add_model_members`) counted
*per origin*, so a name supplied by a column on one branch and by RBS on
the other read as conditional. The count is gone from both; the one
place that decides now decides alone, and removing it fails three
examples.

Worth keeping from this: **"unpinnable" and "wrong" are different
findings, and the sweep cannot tell them apart.** A line no test can be
written against is either dead or superseded, and the fix is to remove
it rather than to invent a fixture that reaches it.

### K. `activeParameter` is never sent — **fixed**

Neither signature-help path set it, so VS Code bolded the **first**
parameter whichever argument the cursor was on. `README` listed active
parameter highlighting as 0.4.0, so it was disclosed as unbuilt — but
what a user saw was a *wrong* highlight, not an absent one, which is why
this was worth pulling forward rather than leaving on the roadmap.

Counted from the call's `(` to the cursor, skipping commas nested in
another call, in an array or hash literal, or in a string. Text rather
than AST, for the same reason the enclosing-call scan is: signature help
is asked for mid-typing, when the argument list is unfinished by
definition. Shipped as capability row `S4` with its own example, and the
row moved out of 0.4.0 in both roadmaps, both READMEs and all four site
matrices.

### L. The deferred-findings guard cannot tell documentation from a mention — **fixed**

`deferred_findings_spec.rb`'s `undocumented` passes an entry if the bare
number appears anywhere in each language's `KNOWN_LIMITATIONS`. 024.20
was cited in a paragraph describing a different consequence while its
actual user-facing half — the largest false-positive family the engine
had — appeared nowhere, and the guard was green. It is
`DOCUMENTATION_MAP`'s named enforcement for the "A known limitation"
row, so that row was enforced in name only. 024.25 records why
prose-parsing attempts were rolled back, and the first reading of this
finding concluded there was no cheap fix. There was one, and 024.25
already named it.

Fixed by giving that end a grammar too, which is what 024.25's own
lesson says to do: the document carries an
`<!-- documents: 024.N -->` marker at the end of the line that documents
the finding, and the guard requires exactly one per language, with prose
in front of it. A machine still cannot judge whether the paragraph is
adequate — but a marker is a claim someone made deliberately, and a
number occurring in a sentence never is. Sixteen findings, both
languages.

## Measurement methods that produced false results, and how each was caught

Three this release. Each invented a result that would have changed a
decision, and none was a subtle mistake:

| what | what it invented | caught by |
|---|---|---|
| Diffed a file still being written | 79 introduced findings | the completion notification arriving *after* the diff |
| Diffed two runs over *different corpora* (one included `core/lib`) | 10 introduced findings | reading the "introduced" lines one by one — they were this repo's own class names |
| `cd` in a compound command persisted, so both sides ran from the same worktree | "the fix changes nothing" | the result contradicting a spec already watched failing |

The third is the one to remember: **the check that caught it was a test,
not a second look at the numbers.** A measurement that disagrees with a
spec you have seen fail is wrong until proven otherwise.

### Three things about method

- **A falling count says nothing about a rising one.** Round 23 found 12,
  round 24 found 10 — and round 24's largest finding is bigger than
  anything in round 23. The counts are not comparable and were not read
  as if they were.
- **Four of round 24's ten are about round 23's own changes, and every
  one is a different place.** That is the loop working, not the
  two-rounds signal, and `CLAUDE.md`'s rule was rewritten during this

  a third finding in the same place rolls the thread back.
- **"Do not modify the repository" needs saying, and needs checking.**
  A reviewer that mutates the tree invalidates every other reviewer

### What round 26 found

Two reviewers, and the round was **not clean** — which is what a release
gate is for. The heaviest were all in code this release wrote:

- the backward scan lost its early exit, so with balanced parens it ran
  to offset 0 asking a per-character mask about each character: **8 s** on
  a 603 KB file with one Japanese comment, on a serial server;
- the byte→character conversion was O(offsets × filesize), which is the
  same defect from the other side: **13 s** to index a 530 KB file once,
  four times worse per doubling;
- `%w[` was classified as code and its closing `]` was not, so the
  brackets counted asymmetrically and `%i[...]` as an argument bolded the
  wrong parameter;
- `activeParameter` indexed into an overload that did not have that
  parameter, because `activeSignature` was never sent;
- `@article.` answered nothing in the actions a `before_action` assigns
  it, while the `@` popup a keystroke earlier said `Article` — 0.2.1
  seeded the `@` list and left the receiver path behind;
- three documents still described the Ruby-compatibility behaviour that
  *this release changed*, including the 3.3 row edited in the same commit
  that changed it.

Both scans now walk structural tokens rather than characters, which
removes the whole class: `%w(`'s parenthesis is a delimiter Prism names,
so it never appears among them, and there is no per-character work left
to be slow.

The stale-number problem got the countermeasure it had earned after
three releases: `core/spec/meta/documented_counts_spec.rb` compares the
figures documents cite against the running suite, and the extension's
count was deleted from `RELEASE_CHECKLIST` rather than guarded — there is
no reason to write a growing number in two places.

## How 0.2.1 actually ended

**Nine rounds, and the clean-round gate was waived deliberately.**
`CLAUDE.md` says to repeat until a full round reports no findings. Rounds
23 through 31 each found something, and the last three found their worst
findings in code added *during* the loop. The maintainer's call was that
the shipped state is better than 0.2.0 on every axis the release is
about, and that continuing to hold it was costing more than it bought.

Recorded rather than done quietly, because a rule broken in silence stops
being a rule. Two things make the waiver defensible and are worth
repeating if it happens again:

- **The change set was cut back first.** Three capabilities added
  mid-review went back to the roadmap, and `self` inference was reverted
  on a measurement. What shipped is smaller than what round 31 reviewed,
  not larger.
- **Everything still open has an entry.** 024.41 through 024.47 are in
  the register with a `KNOWN_LIMITATIONS` paragraph in both languages, so
  nothing is carried forward on memory.

**The loop's own lesson, for 0.2.2.** Seven of the nine rounds found a
defect in code the previous round had written. That is not the loop
failing; it is the loop being asked to review a change set that kept
growing. A review round is for finding what is wrong with a *fixed* thing
— every capability added between rounds resets it. The rule that follows:
**during a review loop, fix; do not add.** A capability a reviewer asks
for is a finding to record, not work to do before the next round.
