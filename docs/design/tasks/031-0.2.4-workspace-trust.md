# Task 031: 0.2.4 — an untrusted workspace could choose what the extension runs

A security patch, cut from the `v0.2.3` tag rather than from the
foundation branch, and shipped ahead of it.

## What was wrong

`vscode/package.json` declared `untrustedWorkspaces.supported: "limited"`
and told the user, in the manifest's own description, that the Runtime
Agent "only starts once the workspace is trusted". It declared no
`restrictedConfigurations`.

VS Code marks a configuration property `restricted` only if that list
names it (1.132.0, `workbench.desktop.main.js`: `restrictedProperties =
supported === 'limited' ? …restrictedConfigurations : undefined`, and the
settings parser drops a key only when `skipRestricted && property.restricted`).
With the list absent, nothing was withheld in Restricted Mode, and a
repository's own `.vscode/settings.json` supplied
`ovallsp.rubyExecutablePath`, `ovallsp.ruby.command`,
`ovallsp.server.path` and `ovallsp.observation.testCommand` verbatim.
`extension.ts` reads them during `activate` and spawns the result. The
only two `isTrusted` reads in the extension are a display field and a
post-grant restart; neither is upstream of the spawn.

Opening a repository was therefore arbitrary code execution, in a build
on the Marketplace.

## How it was established, and the trap on the way

Reproduced against the **published** artifact: the Marketplace 0.2.3
VSIX, installed into an isolated extensions/user-data directory, opened
on an untrusted folder carrying a hostile settings file, executed that
folder's script **seven times, starting about two seconds** after the
window appeared. Verified after the fix the same way: **zero
executions**, with a positive control in the same run — the extension
activated and Core spawned under the real interpreter, so the absence is
the fix rather than a dead harness.

The `.code-workspace` settings block was tested as a separate vector,
each side controlled: blocked on 0.2.4, **seven executions on 0.2.3**.
A trusted window still honours the settings, checked two ways, so the
legitimate feature is intact.

**The trap.** The first attempt at this harness reported zero executions
against the *published* build — which, read alone, would have been taken
as the fix working. The cause was the `--user-data-dir` path: VS Code
creates `<udd>/1.13-main.sock` there, and beyond about 103 characters it
fails `listen EINVAL` and the main process dies before any window
exists. A scratchpad path was long enough to trigger it. The procedure
and its two guards — short user-data-dir, and never read
marker-absence without a positive control — are in
`docs/RELEASE_CHECKLIST.md`.

## What ships

- `restrictedConfigurations` naming the four settings that can name a
  binary or a command.
- `vscode/src/test/unit/workspaceTrust.test.ts`, which **fails closed**:
  every configuration key must be declared restricted or argued in the
  spec to be incapable of influencing what is executed. A setting added
  later cannot become a vector silently.
- `release.sh` refuses to publish when `.vsce-pat.local` is readable
  beyond its owner. It shipped in the same patch because that script runs
  during this very publish; excluding it meant publishing again with a
  world-readable token. The file was mode 644 and the script had
  documented `chmod 600` without ever checking it.

## Why this number

`docs/PUBLISHING.md`'s table makes this a patch: the manifest already
promised trust-gating, and the release makes it true. It is not a minor —
after the fix a user can do strictly *less*, and the test that document
gives is "whether a user can do something they could not do before".

The foundation release that had been scoped as 0.2.4 became **0.2.5**,
and `029` records that move. Neither release adds a capability row, so
no number was being competed for, and the alternative was a security fix
waiting behind a multi-milestone engine release.

## Not in this patch, deliberately

The security audit that found this also found: trust checked at exactly
one call site, with `restart_agent`, `run_observed_tests_result` and
`load_static_plugins` ungated (unreachable from today's shipped
extension); `Marshal.load` in the plugin parent defeating fork isolation;
the `$HOME` leak check never running against the *shipped* darwin
artifact; and gaps in `check_home_paths.rb` (case sensitivity, silent
skips, no history mode). Each needs a review loop rather than a patch,
and each is routed to 0.2.5.

Unverified here: Windows and Linux — the reproduction and the fix were
both established on macOS only. Whether granting trust mid-session
re-honours the settings was reasoned about, not clicked through.
