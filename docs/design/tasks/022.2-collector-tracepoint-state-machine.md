# Task 022.2 (extended): Observation::Collector TracePoint state machine

Companion note, written after independent review rounds 20–22 each found a
genuine correctness bug in `Ovallsp::Observation::Collector`'s TracePoint
handling, with every fix revealing that the *previous* fix's premise was
still wrong (round 20: unbalanced push/pop across non-workspace callees;
round 21: an unwound frame's fabricated `nil` return; round 22: `:raise`
itself does not mean a frame ended). That pattern — three consecutive
rounds, same file, each correcting the last one's assumption — was treated
as evidence the design itself, not just its edge-case coverage, needed
re-examining before another incremental patch went in.

This note is the state model, transition table, and invariants that came
out of that exercise, and the reasoning for why the fix is a structural
extraction (`CallStackMachine`) rather than one more conditional in
`Collector` itself.

## Why a separate state machine

Before this pass, `Collector` mixed three concerns in one class: translating
real `TracePoint` events into abstract call/return/raise transitions,
looking up and caching per-method metadata (symbol_id, fingerprint,
parameter names), and aggregating recorded evidence. The actual bug surface
in rounds 20–22 was entirely in the first concern — a handful of methods
(`handle_call`, `handle_return`, `handle_raise`, `unwind_to`,
`return_type_for`) implementing an ad hoc stack machine, verified only by
constructing specific Ruby call shapes and running them through the real
`TracePoint` API.

That made every fix expensive to verify (spin up real Ruby processes/
threads/fibers, trigger an actual CRuby event, read the aggregate) and
impossible to fuzz (no way to hand the "stack machine" a synthetic event
sequence directly). `Ovallsp::Observation::CallStackMachine`
(`core/lib/ovallsp/observation/call_stack_machine.rb`) is that first
concern pulled out whole: a plain Ruby object with three inputs — `#push`,
`#pop_matching`, `#note_raise` — no `TracePoint`, no threads, no I/O, so
its invariants can be checked by feeding it a sequence of symbolic events
directly (`spec/ovallsp/observation/call_stack_machine_spec.rb`), including
generated/fuzzed sequences that never construct real Ruby call shapes at
all.

`Collector` is now purely the glue: one `CallStackMachine` per fiber
(fiber-local, same reasoning as before — see the machine's own docs),
translating `tp.event` into the machine's three inputs, plus the parts
that were never in question — method-info caching, symbol/fingerprint
computation, and aggregate recording.

## Invariants the state machine must hold

These are the properties `call_stack_machine_spec.rb` pins directly, independent
of any particular Ruby call shape:

- **I1 — One machine per fiber.** A machine's stack is reachable only from
  the fiber that pushed onto it. `Collector` enforces this by storing one
  machine per fiber in fiber-local storage; the machine itself has no
  thread/fiber awareness at all (it doesn't need any — see I8).
- **I2 — `#push` never raises and always succeeds.** Every observed
  `:call`, tracked or not, becomes exactly one `#push`. A method outside
  the workspace still gets a frame (with a caller-supplied "not tracked"
  payload) so the stack stays balanced; only *recording* is skipped later,
  not pushing.
- **I3 — `#pop_matching` finds the *nearest* (topmost) frame whose key
  matches, not the top of the stack unconditionally**, and discards
  everything above the match along with it. Precision worth stating
  explicitly, because it is easy to over-credit this mechanism: for an
  ordinary single-fiber event stream (rows 1–10 of the transition table
  below), CRuby already delivers exactly one `:return` per `#push`, in
  strict inner-to-outer order — recursion included, multi-frame unwinding
  included (row 7) — so a *bare* `pop` (ignore the key, always take the
  top) gets every one of those rows right on its own, with no scanning
  needed. What matching-by-identity is actually load-bearing for is I4.
- **I4 — `#pop_matching` with no match anywhere in the stack is a no-op**
  that returns `nil` and leaves the stack untouched, rather than falling
  back to "pop whatever's on top anyway". This is the one case a bare pop
  gets wrong, and it is the mechanism round 20's shape actually depends
  on today — see "Which mechanism is load-bearing" below, which corrects
  an earlier version of this note that credited I2 instead. The "discard
  everything above the match" part of I3 is separately defensive
  generality (I7) rather than something today's real TracePoint delivery
  is known to exercise; `call_stack_machine_spec.rb`'s generative section
  deliberately constructs sequences with no attempt to mirror real Ruby
  code, to hold this class to a contract stronger than "correct for the
  cases observed so far".
- **I5 — `#note_raise` never touches the stack.** It only advances a
  monotonic per-machine `raise_epoch` counter. A raise is evidence that
  *some* frame *might* be abandoned later, not that any particular frame
  has ended — round 22's finding was that treating `:raise` as a close-out
  event is simply wrong, because CRuby fires `:raise` at the frame the
  exception originated in whether or not that frame ever unwinds.
- **I6 — A popped frame records the `raise_epoch` value at push time**, so
  the caller (`Collector#return_type_for`) can tell a frame that was
  abandoned by an exception (its epoch is stale relative to the *current*
  epoch at pop time) from one that returned normally (epoch unchanged).
  This is the only use `raise_epoch` has; the machine does not interpret
  it itself.
- **I7 — The machine never raises, for any input.** A caller feeding it
  malformed or unexpected event sequences (see the transition table's
  "unmatched return" and "return depth exceeds push depth" rows) gets a
  well-defined answer (usually `nil`), never an exception. `Collector`'s
  own `rescue StandardError` around the whole `handle` dispatch is a
  second, independent backstop — the machine itself does not depend on it.
- **I8 — The machine has no notion of time, threads, or process
  lifecycle.** It does not clean anything up on its own; a machine (and
  whatever frames are still on it) is simply garbage the moment nothing
  references it any more (the fiber that owned it has died). This is
  deliberate: rounds 17/18 already established, for `AgentProcessManager`'s
  registry, that "add a pruning mechanism" is the wrong fix when "hold
  nothing that isn't already needed" is available instead. See
  `Collector#current_stack`'s own docs for why fiber-local storage gives
  this for free.

## Which mechanism is load-bearing (review round 23 correction)

An earlier version of this note asserted that I2 ("push a frame for
*every* `:call`") is what fixes round 20, and that matching-by-identity
(I3/I4) is load-bearing only for table row 11's calls-already-in-flight.
Re-measured directly, by reverting each mechanism separately and running
`collector_spec.rb`, both halves of that were wrong:

| Reverted | `collector_spec.rb` result |
|---|---|
| `#pop_matching` → bare `@stack.pop`, I2 intact | **green** (23/23) |
| I2 → push only tracked calls, matching intact | **green** (23/23) |
| Both (= round 20's original code) | 3 failures, incl. both round-20 examples |

Re-measured in round 24 against the enlarged file (now 28 examples), with
the round-23 example in place: bare pop → **1** failure (that example, and
only it); I2 reverted → still **green**; both → 4 failures. So the gap is
closed for `#pop_matching`, and I2's status is unchanged: it remains
removable with the suite green, deliberately, because with matching correct
it is genuinely redundant rather than merely untested. An untracked key is
untracked *deterministically* (`compute_method_info` is a memoized function
of `[defined_class, method_id]`, so no key is ever both tracked and
untracked in one run), which means an unmatched `:return` can never collide
with a tracked frame's key and a missing untracked push therefore cannot
misattribute anything. I2's remaining value is bounding `#pop_matching`'s
scan and I7's defence in depth, not correctness.

So the two mechanisms are *mutually redundant* for every shape the suite
covered, and neither was independently pinned. Row 11 does not close the
gap either: a call already in flight when `#start` runs is strictly
*outermost*, so its stray `:return` arrives when everything pushed after
`#start` has already been popped — a bare pop finds an empty stack and is
harmlessly a no-op.

The shape that genuinely requires matching is a push `Collector`
**skipped**: `#handle_call` can raise before reaching `#push`
(`symbol_id_for` reads `defined_class.name`, and real code — ORMs,
proxy/delegator gems — does override `name`), and `#handle`'s blanket
rescue swallows it, while `#handle_return` pops unconditionally. The
unmatched `:return` then arrives in the *middle* of a live stack, and a
bare pop answers it with the caller's frame — recording the callee's
return value against the caller's symbol_id, which is round 20's bug
verbatim. Measured on a fixture whose callee returns Integer and whose
caller returns String: bare pop reports the caller as returning Integer.

Pinned by `collector_spec.rb`'s "keeps a live frame when a `:return`
arrives for a call that was never pushed", which fails with a bare pop
and passes with matching. I2 is kept as deliberate defense in depth
(I7's spirit), not as the load-bearing half — a note worth keeping,
because this class's own docs invite simplifying `#pop_matching` to a
bare pop on the grounds that it gets rows 1–10 right.

## TracePoint event / state transition table

Every row is a case this pass explicitly constructed and observed on Ruby
3.4.7 (CRuby), or is a `CallStackMachine`-level abstract case verified
without going through real `TracePoint` at all. "Owner" is which piece of
code is responsible for the row holding: the machine itself (structural,
pinned by `call_stack_machine_spec.rb`), or `Collector`'s translation logic
(pinned by `collector_spec.rb`).

| # | Event / situation | CRuby behavior (verified) | State transition | Owner |
|---|---|---|---|---|
| 1 | Ordinary method call → return | `:call` then `:return`, `return_value` = the real value | push on `:call`; matching pop on `:return`, real value trusted | Machine (push/pop) + Collector (value trust) |
| 2 | Nested calls (`a` calls `b` calls `c`) | `call a, call b, call c, return c, return b, return a` | Each `:return` finds its match already at the top — a bare LIFO pop would get this right too (see I3's note); matching-by-identity doesn't need to scan here | Machine |
| 3 | Recursion (direct: `f` calls `f`) | Each recursive `:call` pushes its own frame with the same key; each `:return` closes the innermost live one, in the same strict LIFO order as row 2 | Same as row 2 — the innermost invocation is always already on top when its `:return` arrives, so matching by identity and a bare LIFO pop agree; verified with real direct/mutual/`send`-based recursion (round 21) precisely to confirm this, not to exercise scanning | Machine |
| 4 | Mutual recursion (`a`→`b`→`a`) | Same as above, different keys interleaved | Same as row 3 — no cross-talk between the two keys' entries, and no scan needed | Machine |
| 5 | `b_call`/`b_return` (plain block yield/return) | **Not traced.** `Collector`'s `TracePoint.new` only requests `:call, :return, :raise`. A block invocation produces no event at all under this filter | No transition; the block's own body's *method* calls still fire normally | Deliberate scope limit (overhead budget), documented in `Collector` |
| 6 | `c_call`/`c_return` (C-implemented methods) | **Not traced**, same filter. Verified: a method whose entire body is C calls (`@name.freeze.upcase.to_sym`) still fires its own `:call`/`:return` correctly — the *absence* of C-method events cannot desync the stack, because nothing pushes for them in the first place | No transition for the C call; the enclosing Ruby method's own push/pop is unaffected | Deliberate scope limit, verified round 22 |
| 7 | Exception raised and propagates across N frames | `:raise` fires **once**, attributed to the frame it originated in (see row 9); each of the N unwound frames still gets exactly one `:return` with `return_value = nil`, in inner-to-outer order, as the exception unwinds past them | `:raise` → `#note_raise` only (no pop). Each unwound frame's `:return` → `#pop_matching` finds and closes it, tagged with its own `raise_epoch` for the fabricated-nil check | Machine (pop) + Collector (epoch check) |
| 8 | `ensure` block runs during unwind and itself calls a workspace method | The `ensure` body's calls push/pop normally, *after* the raise that triggered the unwind — so their frames carry the *current* (post-raise) epoch, not the pushing method's original one | Their `#push` happens after `#note_raise`, so their own returns are correctly trusted even though a raise is "in flight" for the frame(s) below them | Machine (epoch is per-push, not global-flag) + Collector's regression test for exactly this ordering |
| 9 | `rescue` catches a raise **in the same method body** that raised it (guard clause, `begin/rescue` in one method) | CRuby still fires `:raise` (attributed to that same frame) *and then* a normal `:return` with the method's real return value — the method's frame was never actually abandoned | `:raise` → `#note_raise` (no pop, so the frame survives); `:return` → `#pop_matching` finds it and returns the real value, trusted normally | Machine (no premature pop) — this was round 22's fix; rounds 20–21 both got this row wrong |
| 10 | A raise inside a block passed to a workspace method (`xs.each { raise Stop }`), rescued by an outer method | `:raise` attributed to the frame that *wrote* the block (per row 9's rule, since block bodies aren't separately traced — row 5); that frame is not popped by `:raise`; its own later `:return` closes it with the real value | Same as row 9 — `:raise` never pops, so nothing above the raising frame is prematurely discarded either | Machine + regression test (round 22, "raises_in_yielded_block") |
| 11 | Calls already in flight when `#start`/`TracePoint#enable` runs (Harness installs via `-r`, so RubyGems'/Bundler's own loader frames are mid-call) | Those frames' eventual `:return` fires with no matching `:call` ever having been pushed for them | `#pop_matching` finds no match (its key was never pushed) → no-op, returns `nil` (I4) | Machine — this is exactly what "no match anywhere" means; no special-case needed |
| 12 | Frames still open when `#stop`/`TracePoint#disable` runs | No more events fire once disabled; whatever's left on any fiber's machine is simply never popped | Nothing — the machine (and its stack) becomes unreachable garbage the moment the fiber holding it exits or is dropped (I8) | Machine (nothing to do) + `Collector`'s fiber-local storage (nothing to prune) |
| 13 | A `:return` with no logical `:call` at all reachable in the abstract sense (defensive case — should not occur given rows 1–12, but the machine must not assume it can't) | N/A (constructed only in `call_stack_machine_spec.rb`, not from real Ruby) | `#pop_matching` on an empty stack, or with a key that matches nothing → `nil`, no exception (I4, I7) | Machine, fuzz-tested |
| 14 | Method redefined mid-run (`class_eval` over an already-observed method) | `method_id` is an interned Symbol; the redefinition reuses the same cache key | Out of `CallStackMachine`'s scope entirely — this is `Collector#@method_cache`'s concern, not the stack machine's. Documented residue: stale parameter names degrade to `Types::UNKNOWN` (under-collection, not fabrication) | Collector (unchanged by this pass; see its own docs) |
| 14a | The *same* method dispatched through different receivers: an inherited class method (`Child.build` where `build` is defined on `Base`), or `super` between two singleton methods | `tp.defined_class` is `#<Class:Base>` for both; `tp.self` is `Child` for both — the receiver, not the definer. Verified on 3.4.7 | The symbol_id must be a function of `defined_class` alone (`#attached_object`), because `@method_cache` is keyed by `[defined_class, method_id]` and its docs assert every cached field is invariant per key. Deriving it from `tp.self` broke that: first receiver wins for the whole run — round 24's bug | Collector (`#symbol_id_for`, fixed round 24) |
| 14b | A module is `prepend`ed into the class a frame belongs to (an instrumentation gem patching app code, or the app patching a gem) | `tp.defined_class` is the class itself for the inner frame, but `prepend` puts the module *ahead of* that class in its own ancestor chain, so `defined_class.instance_method(method_id)` resolves to the **wrapper**, not to the frame. Verified on 3.4.7 | Resolve the definition whose `#owner` *is* `defined_class`, walking `#super_method` past any prepended wrapper. Everything `#compute_method_info` derives — the workspace-containment test, the fingerprint, the parameter-name list — must describe the frame, not whatever dispatch would find. Reading the wrapper was round 25's bug | Collector (`#defined_method`, fixed round 25) |
| 15 | Fiber switches away mid-call (an `Enumerator`, `Async`, or hand-rolled scheduler) and is later resumed, or is dropped without ever resuming | Each fiber has its own machine (I1); a suspended fiber's machine is untouched by any other fiber's events; a dropped fiber's machine (and any stranded frames) becomes garbage with it | No transition — this is exactly the isolation fiber-local storage buys structurally, not a case the machine has to detect | Collector (`current_stack`'s fiber-local key) |
| 16 | Two threads executing workspace methods concurrently | Each thread's fibers get their own machine (same mechanism as row 15 — a Thread's main execution context is itself a Fiber) | No cross-thread interaction at the machine level at all | Collector |
| 17 | The Collector's own code (inside `handle`, or inside a machine method) triggers a nested `TracePoint` event | **Does not happen.** A `TracePoint` handler block does not re-enter itself by default (verified: Ruby suspends tracing for the extent of the handler's own execution unless `TracePoint#allow_reentry` is used, which this code never calls) | N/A — no re-entrant events are ever delivered while `handle` is executing | CRuby's own `TracePoint` semantics, not something this code has to defend against; noted here so a future change doesn't need to rediscover it |

## What is *not* fixed, and why

Three residues survive this pass, all previously identified (rounds 21–22)
and now stated here as the single place they're tracked, all sharing the
same shape: CRuby delivers **no event of any kind** that distinguishes them
from a genuine `nil` return, so the state machine has nothing to key its
epoch check on.

- `throw`/`catch` unwinding a frame.
- `break` out of a block, ending the method that yielded to it.
- A non-local `return` from inside a block, ending the enclosing method.
- `Thread#kill` on a thread parked inside a workspace method.

All four produce `:call` then a bare `:return` with `return_value = nil`
and no `:raise` anywhere on that fiber — indistinguishable, at the level of
events this Collector subscribes to, from the method actually evaluating to
`nil`. Re-verified on Ruby 3.4.7 in review round 23, with one precision
correction: it is the *intermediate* frames these unwind past that get the
fabricated `nil` (`throw`'s middle frames, the method that yielded to a
`break`ing block, a method a `proc`'s non-local `return` unwound through).
The frame that actually catches or owns the transfer reports its real
value normally — `catch`'s own frame returns the thrown value, and the
method a non-local `return` returns *from* reports that value. Crucially,
every one of these cases stays **stack-balanced**: each `:call` still gets
exactly one `:return`, so none of them can strand a frame that a later
`#pop_matching` would wrongly match. The residue is bounded to a
fabricated `nil` in one union, as stated. Distinguishing them would require also tracing `:c_call`/`:b_return`
(both fire on every C call and every block return respectively, in *any*
Ruby process, workspace code or not), which was measured to cost enough
overhead to fail this module's own budget test
(`spec/ovallsp/observation/overhead_spec.rb`). All four are rarer in
practice than an ordinary `raise`, and the failure mode is bounded — one
fabricated `nil` added to one method's return-type union, not the
systematic wrong-attribution or lost-evidence shape rounds 20–22 fixed.

`Collector#@method_cache` staleness under method redefinition (table row
14) is likewise deliberately out of scope for this pass: it is not a
`CallStackMachine` concern, its failure mode is under-collection (a stale
parameter name degrades to `Types::UNKNOWN`), and it was already reviewed
and left alone in round 22.

## Round 24: two defects outside the stack machine, in the same class

Round 24 re-derived everything above (all 17 rows re-observed on 3.4.7, the
revert-and-measure table reproduced, the `UnnameableOwner` example
adversarially mutated) and found the machine itself and its coverage sound.
Both defects it did find were in `Collector`'s *other* two concerns —
exactly the parts the extraction above declared "never in question":

1. **`#symbol_id_for` derived a singleton method's owner from `tp.self`**,
   the receiver dispatched through, rather than the class the method is
   defined on (table row 14a). Three consequences: the observed evidence
   was filed under a symbol_id no static declaration matches (ParserService
   declares `def self.x` under its lexical class); `@method_cache`'s stated
   per-key-invariance premise was violated, so the *first* receiver to call
   an inherited class method decided the attribution for the whole run; and
   `super` between two singleton methods collapsed two different methods
   into one signature, unioning their parameter lists position-wise
   (measured: `parameter_types = [Integer, Symbol]` for a one-parameter
   method). Fixed by using `defined_class.attached_object`, which is a pure
   function of the cache key. Same family as rounds 20–22: confidently
   wrong evidence, from ordinary application code.
2. **`#workspace_method?` tested containment with a bare string prefix**,
   so any sibling directory whose name merely begins with the workspace
   root's was treated as inside it (`/srv/app` accepted
   `/srv/application/lib/x.rb`), and everything defined there was reported
   as the user's own workspace evidence. Same path-boundary class rounds
   1–2 fixed in `BundleEnvironment`; `ColdIndexer#real_path_stays_inside_root?`
   already used the correct idiom, and `Collector` was the outlier.

Round 24 also found that `@method_cache` itself was a mechanism nothing
pinned — deleting it outright left the entire suite green, including the
overhead example its own comment credited with guarding it (measured: 12x
slower, still 50x inside that example's deliberately loose bound). Given
finding 1, the cache is not merely an optimization — the run's whole
attribution is keyed off it. It is now pinned by a *count*-based example in
`overhead_spec.rb` (one source-file digest per method, never per call),
which cannot go flaky on slow hardware the way a duration bound would.

## Round 25: the third concern, `#defined_method`, was reading the wrong method

Round 25 re-verified rounds 23 and 24 independently (each fix reverted
separately, each measured symptom reproduced from scratch rather than taken
from the commit message, each new example adversarially mutated) and found
all of it sound and correctly targeted. The machine remains untouched.

Both defects it found are, again, in `Collector`'s translation layer rather
than in the machine — and this time in the one concern rounds 20–24 had all
taken for granted: **which method object a frame is actually about**.

1. **`#defined_method` resolved the frame's definition with
   `tp.defined_class.instance_method(tp.method_id)`** (table row 14b). That
   answers "what would dispatch find starting here", which is a different
   question from "what is this frame", and the two diverge for exactly one
   construct: `prepend`, which inserts a module *ahead of* a class in that
   class's own ancestor chain. Every field `#compute_method_info` derives
   then described the wrapper instead of the frame. Measured three ways at
   once:

   - A gem prepending into a workspace class (how ActiveSupport and every
     APM/instrumentation gem patch app code) made `#workspace_method?` read
     the *gem's* `source_location`, so the app's own method produced **no
     evidence at all** for the whole run.
   - The workspace prepending into a gem's class made the same test read
     the *workspace's* `source_location`, so the **gem's** method was
     collected and reported as the user's own evidence — round 24's
     containment defect again, reached by a different route and past the
     boundary fix that round installed.
   - The parameter-name list and the fingerprint came from the wrapper, so
     a one-parameter method was reported with the wrapper's two parameter
     slots (both `Types::UNKNOWN`, since the wrapper's names don't resolve
     in the real frame's binding) and fingerprinted against a file whose
     edits `Store#invalidate_changed` would then track *instead of* its own
     — evidence that outlives the edit that invalidates it.

   Fixed by walking `#super_method` down to the definition whose `#owner`
   is `defined_class` itself. This also completes round 24's premise rather
   than merely sitting beside it: the cached entry was previously not a
   function of `[defined_class, method_id]` even in the temporal sense, since
   prepending mid-run changed the answer for an unchanged key.

2. **`#positional_param_names` looked every slot up by name**, and Ruby
   permits the same name in two positional slots (`def m(_, _)`), binding
   only the first. `Binding#local_variable_get` therefore answered every such
   slot with the same value: measured, `m(1, "s")` reported
   `[Integer, Integer]`. Now those slots are kept (so every later slot stays
   at its own position) but carry `Types::UNKNOWN` — under-collection over
   fabrication, as everywhere else in this module.

Both are rounds 20–22's family once more: not lost evidence but confidently
wrong evidence, from ordinary application code.

Re-audited and found correct, for the record, so a later round need not
redo them: `#fingerprint_for` is symlink-safe by construction (the digest
is over file *content*, so which path it was read through cannot change it,
and `File.realpath` failing degrades to a `nil` fingerprint); `attached_object`
handles every input it can receive (a singleton class of a singleton class
yields an unnamed `Module` and a plain object yields a non-`Module`, both of
which already fall through to "no symbol_id"); refinements and anonymous
classes/modules likewise produce no evidence rather than wrong evidence; and
`include`/`extend`/`alias_method`/`define_method`/inheritance/private
methods were all measured to attribute correctly both before and after this
pass. `File.realpath` in `#initialize` is now also pinned as load-bearing
for the `@workspace_prefix` construction, not merely for symlinks: a root
handed in with a trailing separator would otherwise build a doubled one and
match nothing.

The remaining known imprecision, unchanged and deliberate: a `req`/`opt`
parameter that follows a `*rest` (`def m(a, *rest, b)`) is reported at the
slot index it occupies *after* rest parameters are dropped, not at its
index in the declaration. `ObservedSignature#parameter_types` has no
representation for rest at all (documented scope limit), and no consumer
joins it positionally against a declaration today — `ovallsp/showTypeEvidence`
renders the list as text. Giving rest parameters a representation is a
design change, not a review fix. Round 26 measured this residue and pinned
it with an example rather than leaving it as prose only (see below).

## Round 26: the shadowed-name guard asked its question of the projection

Round 26 re-derived rounds 23–25 independently — each fix reverted
separately, each claimed symptom reproduced from scratch rather than read
off the commit message. All of it holds. Reverting the `#super_method` walk
fails exactly 2 examples and reproduces all three of its symptoms (a
workspace method a gem prepends into vanishes; a gem method the workspace
prepends into is collected as the user's own; a one-parameter method is
reported with the wrapper's slot count — measured independently at 3 slots
for a 3-deep wrapper, all `Unknown`). Reverting the shadowed-name
deduplication fails exactly 1 and reproduces `[Integer, Integer]` for
`pair(1, "s")`. Dropping `File.realpath` from `#initialize` fails exactly 1.

The walk itself was held to an objective oracle — at a `:call` event
`tp.lineno` *is* the frame's own `def` line, so the resolved definition's
`source_location` must equal it — across 15 generated configurations and 54
frames: prepend chains 1–4 deep, a wrapper module with its own prepend, a
prepend on a superclass *and* on the subclass reached through it, `include`
plus prepend on both the module and the class, singleton-class prepend
chains, the same module prepended twice, `alias_method` over a prepend, and
`extend` of a prepended-into module. Every frame resolved to its own
definition, and the walk terminated in at most 4 steps in every case
(`#super_method` returns `nil` at the end of a finite ancestor chain, which
ends the `while` — verified on a subclass-`alias` frame, where no method in
the chain is owned by `defined_class` at all and the result is correctly no
evidence rather than the wrong method's).

The walk cannot land on a *different* method owned by `defined_class`: a
module owns at most one method per name, so if the frame's definition is
owned by `defined_class` it is the only candidate the walk can stop on.
The one construct that looked like it could break that — `alias` of a
prepended method, which makes `Klass.instance_method(:m2).owner` report the
class while the body comes from the wrapper — does not, because CRuby
already reports `tp.defined_class` as the *body's* origin module for alias
copies (measured).

The defect it did find is one kind boundary over from round 25's own:

**`#positional_param_names` counted the repeat over the list it returns
rather than over the declaration.** The property that licenses a by-name
read is "this slot is the only parameter with this name" — a fact about the
whole declaration — but the tally ran over the `req`/`opt` slots left after
filtering, so a name shared with a `*rest`, `**kw`, `&blk` or `key:`
parameter was never seen as a repeat. Ruby rejects duplicate parameter
names except `_`-prefixed ones, and `Binding#local_variable_get` answers
with the *leftmost* declaration, so the reachable wrong-evidence shape is
the one where the filtered-out duplicate is declared first — which only
`*rest` can be. Measured on `def m(*_a, _a)`, legal Ruby:
`m(1, 2, "the-real-tail")` reported `[Array]` for its single slot, the
trailing required parameter, which plainly holds a String. The repeat is
now counted over `method_obj.parameters` entire.

Narrow — `def m(*_a, _a)` is not code anyone writes — but the same family
as rounds 20–22, 24 and 25: not lost evidence but confidently wrong
evidence. Pinned by its own example, which rejects dropping the slot
instead of blanking it, emitting a slot for the rest parameter, and the
over-broad "blank every positional slot of any method that has a rest
parameter" — that last one being rejected by the new control example that
also pins the rest-index residue above.

Re-audited and found correct, so a later round need not redo them: `:call`
fires *after* the argument prologue, so an omitted optional argument reads
back as its evaluated default (`def opts(a, b = Defaults.side, c = a.to_s)`
called as `opts(1)` reports `[Integer, String, String]`, never `NilClass`),
and the default expression's own calls stay balanced on the stack; keyword
arguments mixed with positional ones do not disturb the positional
by-name reads; `tp.method_id` is the name a method was *defined* as, never
the name it was called as (`tp.callee_id` is that), so an `alias` files its
evidence against the definition it actually shares and `@method_cache`'s key
unifies both call names; a `method_missing`-based dynamic call is attributed
to `#method_missing` itself, which is the frame that really ran; a
singleton class of a singleton class, a refinement module and a
never-named anonymous class all still produce no evidence rather than wrong
evidence; and `@method_cache`'s per-key invariant now genuinely holds under
a mid-run `prepend` (measured: patching a class between two observed calls
leaves the wrapped method's own slot count, types and sample count intact,
and files the wrapper separately).

## Round 27: the aggregate's shape was decided by whichever call arrived first

Round 27 re-derived round 26 independently: reverting
`#positional_param_names`' tally to the filtered `req`/`opt` list fails
exactly 1 example and reproduces `[Array]` for
`trailing_after_rest(1, 2, "the-real-tail")`, confirmed a second time
outside the collector entirely (`def m(*_a, _a)` reports
`parameters == [[:rest, :_a], [:req, :_a]]` and
`binding.local_variable_get(:_a) == [1, 2]` inside the frame). The round-26
example is specific in both directions: dropping the shadowed slot instead
of blanking it fails it *and* round 25's; emitting a slot for the rest
parameter fails it *and* its control; while an unrelated revert (the
`#super_method` walk) fails 2 other examples and leaves it green.

Parameter handling was then swept exhaustively rather than sampled, since
that is where rounds 25 and 26 both lived — 15 declarations measured
end-to-end through a real `Collector`, and none produced wrong evidence:

- A name shared between two *non-positional* kinds is legal Ruby
  (`def m(a, **_x, &_x)`, `def m(a, *_x, &_x)`) and is a non-event here:
  neither kind occupies a positional slot, and the slot that does exist
  reports its own class.
- Anonymous parameters (Ruby 3.2+ bare `*`, `**`, `&`, and `...`) do **not**
  produce `name == nil` — CRuby reports them as the symbols `:*`, `:**`,
  `:&`, all distinct — so they can neither collide with each other nor be
  filtered out by the `name &&` guard. `def m(*, b)` correctly reports `b`'s
  own class, which is round 26's shape with the collision removed.
- Nameless parameters do occur, from destructuring (`def m(a, (b, c))` →
  `[[:req, :a], [:req]]`), including two at once; each keeps its slot and
  degrades to `Unknown`, and the `name &&` guard keeps two nil names from
  tallying as a repeat.
- A collision where the *positional* slot is declared first
  (`def m(_a, _a: 5)`, `def m(_a, &_a)`, `def m(_a = 1, *_a)`) blanks a slot
  whose by-name read would in fact have been correct. That is
  under-collection, this module's stated preference, not wrong evidence.
- Numbered block parameters (`_1`, `it`) inside a traced method body do not
  interact at all: blocks are not traced and the read happens at `:call`,
  before the body runs.

The defect found is in aggregation rather than in how any single call's
evidence is derived — a different shape from every round since 20:

**`#record` sized an aggregate's per-slot array once, from whichever
observation happened to arrive first.** A `symbol_id` is
`[kind, owner-name, method-name]`, so two *distinct* `Class` objects that
answer `#name` with the same string legitimately share one aggregate — which
is what a Rails/Zeitwerk constant reload, a bare `remove_const` + redefine,
and rspec-mocks' `stub_const` each produce inside a single run — and they
need not share an arity. When the later definition was wider,
`agg[:param_type_sets][index]` was `nil` and `nil << type` raised
`NoMethodError` straight into `#handle`'s blanket rescue, which exists so a
plugin's own bug cannot take down the user's test run, not to absorb this
class's own index errors. `#record` is not atomic either, so the aggregate
was left half-applied: every slot before the overflow had already taken the
new call's type while `samples` and the return type never did.

Measured on a class reloaded mid-run from `m(a)` to `m(a, b, c)`, called
once narrow and twice wide: a *single* slot reading
`Integer | String | Symbol` — a union of all three calls' slot-0 arguments —
reported next to `samples: 1`, with both wider calls' return types dropped
and two whole parameter slots reported as not existing. `samples` is the
confidence signal `ovallsp/showTypeEvidence` renders verbatim and sums into
`sampleCount` (`Server#type_evidence_response`), so this is rounds 20–22 and
24–26's family once more: not lost evidence but confidently wrong evidence.

The slot array now grows per slot, so its length is a function of every
observation rather than of the first. Holes are impossible by construction
rather than by a guard: indices are visited in ascending order from 0, so
slot *n* cannot be reached before slot *n − 1* exists, and `#results` never
sees a `nil` where it expects a `Set`. Pinned by two examples — the wider-
later one fails without the fix, and a narrower-later control rejects the
over-broad "resize to the latest call's arity", which would silently discard
every slot the newest definition no longer has.

`CallStackMachine` is untouched by this round.

## Unexpected-event-sequence policy

Per-case policy for anything the abstract machine receives that a real
`TracePoint` stream (rows 1–12) would never actually produce (row 13's
category) or that represents `Collector`-level bookkeeping rather than a
stack-shape problem:

| Situation | Policy |
|---|---|
| `#pop_matching` finds no match | Ignore: return `nil`, leave the stack untouched (I4) |
| `#pop_matching` called on an empty stack | Ignore: return `nil` (a degenerate case of the above) |
| `#note_raise` called with no frames on the stack | Ignore: still advances the epoch (a raise from outside any tracked frame is legitimate — e.g. from a non-workspace method with nothing recorded above it — and a later frame's genuine-nil check still needs to see it) |
| Any exception inside `Collector`'s own event-handling code (method-info lookup, fingerprinting, param extraction) | Caught by `Collector#handle`'s blanket `rescue StandardError`, independent of the machine; degrades to "this one event produced no evidence", never crashes the observed process (unchanged by this pass) |
| An internal invariant genuinely violated (should be unreachable given the table above) | The machine still does not raise (I7) — there is no diagnostic-logging path today because every case in the table above is either handled structurally or explicitly out of scope; a future change that finds a genuinely new reachable case should extend the table, not add a rescue |
