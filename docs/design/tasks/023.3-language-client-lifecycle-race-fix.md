# Task 023.3: LanguageClient lifecycleと遅延起動競合の修正

## Goal

以前の独立レビューで指摘された、停止済みのはずのclientに対して遅延して
`client.start()`が呼ばれてしまうraceを、局所的なif分岐ではなく明示的な
lifecycle状態機械として構造的に修正する。

## Depends on

- Task 023.2(この上に`runVersionHandshake`が乗る)

## Out of scope

- version handshakeの内容自体の変更(Task 023.2で完了済み)
- 実際のE2E(Extension Development Host上での)race再現テスト — 状態機械
  自体をdeferred Promiseで決定論的に検証する方式を採用し、実際の
  `LanguageClient`/タイマーへの依存を避けた(下記「必須テスト」参照)

## 問題

`vscode/src/extension.ts`の`startClientForFolder`は、`client.start()`を
呼ぶ前に非同期の互換性probe(`checkBundledCoreCompatibility`)を実行する:

```ts
void checkBundledCoreCompatibility(...).then((compatibility) => {
  ...
  client.start().then(...);
});
```

このprobeが完了する前に`stopClient(key)`(deactivate、workspace folder
削除、`OvalLSP: Restart Server`)が呼ばれると、`stopClient`は
`clients.delete(key)`して`client.stop()`を呼ぶが、**probeの`.then()`
継続はこれを一切知らない**まま後から解決し、そのまま`client.start()`を
呼んでしまう。結果、どこからも追跡されない(`clients`マップにいない)Core
子プロセスが起動し、`deactivate()`のクリーンアップにも引っかからない
まま永続的にリークする。

単純な真偽値フラグでは不十分: 同じfolderに対する2回目の起動
(activate直後のrestartなど)と、1回目の起動の遅延probeを区別できない。

## 設計

`vscode/src/clientLifecycle.ts`(新規、`vscode`/`vscode-languageclient`に
一切依存しない純粋なmodule)に`ClientLifecycleManager`を実装。

### 状態

`pending` → `starting` → `running`、および任意の時点から`stopping` →
`stopped`(要求元の指示通りの5状態)。

### generation番号

folder keyごとに、`beginStart`を呼ぶたびにgenerationをインクリメント。
`markStarting`/`markRunning`は、渡されたgenerationが**現在の**generationと
一致し、かつ状態遷移として妥当な場合のみ`true`を返す。一致しない
(古いgenerationからの遅延呼び出し)場合は`false`を返し、呼び出し側は
何もしない(`client.start()`を呼ばない)。

### `stopClient`との連携

`stopClient`は`client.stop()`をawaitする**前に**同期的に`requestStop`を
呼ぶ。これにより、そのgenerationのprobe/start継続は次にチェックした瞬間
必ず停止要求を検知する — `stopClient`自身の非同期処理がどれだけ時間を
要しても関係ない。

### start()自体の最中に競合した場合

`client.start()`はプロセス起動+`initialize`応答待ちを含み、瞬時には
終わらない。この最中に停止要求が来た場合、`markRunning`が`false`を返す
— この場合、呼び出し側(`extension.ts`)はその場で
`client.stop()`を呼び、`ClientLifecycleManager`へ`markStopped`を報告する。
「どこからも追跡されないプロセス」を発生させないための、この設計唯一の
責務境界。

### `extension.ts`側の変更

- `startClientForFolder`: `lifecycle.beginStart(key)`でgenerationを取得
  → probe解決後`lifecycle.markStarting(key, generation)`が`false`なら
  return(start自体を呼ばない)→ `client.start()`後
  `lifecycle.markRunning(key, generation)`が`false`ならその場で
  `client.stop()`
- `stopClient`: 冒頭で`lifecycle.requestStop(key)`、`client.stop()`完了後
  `lifecycle.markStopped(key, generation)`

## Acceptance criteria

- [x] 明示的な5状態(pending/starting/running/stopping/stopped)を持つ
- [x] probeがgenerationと紐付けられ、停止後の遅延probe完了が`start()`を
      呼べない
- [x] `stopClient`が保留中のstart継続をキャンセル(実質的に無効化)する
- [x] `start()`自体の最中の停止競合でも、最終的にプロセスが確実に停止される
- [x] restartは新しいgenerationのみを起動する(古いgenerationは無効化)
- [x] watcher/client/promise/timer/processの単一の所有者
      (`ClientLifecycleManager` + `extension.ts`の`clients`/`watchers`マップ)
- [x] クリーンアップが有界かつ冪等(`markStopped`は同じgenerationに対して
      複数回呼ばれても安全、`stopClient`は追跡されていないkeyに対しても
      安全)

## 必須テスト

`vscode/src/test/unit/clientLifecycle.test.ts`(新規、11 examples)。
`setTimeout`による固定sleepは一切使わず、`Deferred<T>`(自前の
resolve関数を外に持つPromise)で「probeが解決する前に停止要求が来る」
「start()自体の最中に停止要求が来る」という順序を明示的に再現:

- 通常経路(pending→starting→running)
- probe中の停止要求 → `markStarting`が`false`を返す
- start()自体の最中の停止要求 → `markRunning`が`false`を返し、
  呼び出し側がその場で停止する想定を検証
- restartが新generationのみを許可し、古いgenerationの遅延probeは無効
- workspace folder削除も同じ停止要求として扱われる
- 追跡されていないkeyへの`requestStop`は安全なno-op
- `markStopped`はgeneration一致時のみ有効、古いgenerationからのstragglerは無視
- `markStarting`は同一generationに対して1回しか成功しない(非冪等)
- `markRunning`は`markStarting`前には発火しない
- 複数folderが独立して追跡される

git-stash-revert検証: `markStarting`を「常にtrueを返す」(修正前の
無条件動作)に置き換えたところ、11件中7件が実際に失敗することを確認
(`takes the normal path`、`refuses to start once a stop was requested`、
`a restart only ever lets the newest generation actually start`、
`workspace folder removal mid-probe`、`markStopped is a no-op for a stale
generation`、`markStarting is not idempotent`、`tracks multiple folders
independently`)。復元後、59 examples全てgreenに戻ることを確認。

`npm run test:integration`・`npm run test:integration:packaged`(実際の
Extension Development Host上での起動)双方もgreenのまま(この修正が
通常の起動経路を壊していないことを確認)。

## Review A(Task 023.1〜023.5の独立レビュー)での追加修正

独立レビューで、本タスクの実装に新たなP0が見つかった:
`vscode/src/extension.ts`の`stopClient`が`client.stop()`を無条件に
呼んでいたが、`vscode-languageclient`自身の`LanguageClient.shutdown()`
(`node_modules/vscode-languageclient/lib/common/client.js`)は、client内部
状態が正確に`Running`でない限り(`Starting`を含む)例外を**投げる**
(`"Client is not running and can't be stopped"`)。`client.start()`が
まだ解決していない(probeがCore応答待ちで遅い)ウィンドウで停止要求が
来ると、`stopClient`のPromiseが例外で reject し、`ovallsp.restartServer`
の`await stopClient(key)`が静かに失敗して以降のclient再作成が実行され
なくなる、という具体的な再現可能なバグだった。

**修正**: `stopClient`は`client.stop()`を呼ぶ前に
`lifecycle.getState(key) !== 'running'`をチェックし、`running`でなければ
即座に返す(`requestStop`は引き続き同期的に呼ぶ)。`pending`/`starting`の
generationに対しては、`startClientForFolder`側の`client.start().then(...)`
継続の`markRunning`が`false`を返した際に呼ぶ`client.stop()`が、その時点で
既にlibrary内部状態が`Running`に達しているため安全に働く — 二重に
呼ぶ必要はなく、むしろ`stopClient`側から先に呼ぶと確実に例外を投げていた。

**既知の残存ギャップ(意図的にスコープ外とした)**: Core自身が`initialize`
に永久に応答しない(真のhang)場合、`client.start()`のPromiseは解決も
rejectもされず、`markRunning`分岐そのものが一切実行されない — この
ケースでは今回の修正後も子プロセスを止める経路が存在しない。
`vscode-languageclient`の`LanguageClient`はCoreの子プロセスへの
参照(`_serverProcess`)をprivateかつ型定義に含まれない内部フィールドと
してのみ保持しており、公開APIを通じて`Starting`状態のまま強制killする
手段がない。これを完全に閉じるには、`ServerOptions`を関数形式へ変更し
自前で子プロセスをspawnして参照を保持する、という別の(より大きな)
アーキテクチャ変更が必要であり、本タスクの範囲を超えると判断した。
Core側の同種のhang(`initialize`到達前の無応答)は、このプロジェクトの
過去のレビューラウンド(round 10〜13、Core側のkillが効かないケースの
修正)で既に個別に対応されてきた領域であり、Extension側からの強制killが
効かない残余ケースは、別issueとして追跡する(Task 023.8の
"post-Preview non-blocker work"、またはTask 023.7のCI整備と合わせて
検討)。

修正後、VS Code unit 61 examples(Task 023.5で追加した分含む)、
`test:integration`・`test:integration:packaged`いずれもgreenを再確認。

### この修正自体のregressionテスト(レビューエージェントの再指摘への対応)

レビューエージェントに修正内容を確認させたところ、ロジック自体は正しいと
確認された一方、「この修正がなければ失敗するテストがまだ存在しない」
という指摘を受けた(`extension.ts`の`stopClient`/`startClientForFolder`は
`vscode`モジュールに依存するため直接unit testできない)。

対応として、`ClientLifecycleManager`に`stopIfRunning(key, stopFn)`
メソッドを追加し、`stopClient`側の「`running`でなければ`client.stop()`を
呼ばない」という判断ロジック自体を`ClientLifecycleManager`へ移した
(`extension.ts`は`lifecycle.stopIfRunning(key, () => client.stop())`を
呼ぶだけになった)。これにより、`vscode-languageclient`実物の
`LanguageClient.shutdown()`と同じ契約(`running`でない限り
reject/throwする)を再現するstub関数を使い、`vscode`モジュールなしで
直接テストできるようになった。

`vscode/src/test/unit/clientLifecycle.test.ts`に`stopIfRunning`の
describeブロックを追加(4 examples)。うち1件は
"regression: reproduces the exact real-world race"として、実際の
race(probe解決直後、`client.start()`未解決の状態での停止要求)を
deferred Promiseで再現し、`stopIfRunning`が例外を伝播しないことを検証。

git-stash-revert検証: `stopIfRunning`を「常に`stopFn`を呼ぶ」(修正前の
無条件呼び出しを再現)に置き換えたところ、4件中3件が実際に
`"Client is not running and can't be stopped."`で失敗することを確認
(残る1件"calls stopFn when running"は無条件呼び出しでも偶然成功する
ケースのため失敗しない — 想定通り)。復元後、VS Code unit 65 examples
全てgreenに戻ることを確認。`test:integration`・
`test:integration:packaged`も再度green。
