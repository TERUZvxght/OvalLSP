## 調査結果を実装条件へ変換する際の補正

報告の数値は元コーパス・revision・生ログをまだ本計画で検証していない。
過去の値を現行の速度・競合頻度・改善率として再掲しない。

| 論点 | 現行コードから確認できること | 計画への反映 |
|---|---|---|
| 同期解析 | `Server#run` が settle drain を実行し、診断は外側ロックを保持する | CPU 削減と dispatch へ戻る機会を別々に検証する |
| parse の重複 | Engine、ParserService、LocalInferencer に全体 parse の呼び出しがある | 「最大何回」は経路別に数え、全体 parse と断片 parse を区別する |
| 依存ファイルの再解析 | `note_dependents_need_analysis` は他の open document を列挙するが、呼び出し元は `dependable_shape` の変化で条件付けされている | 本文編集も常に全ファイル再解析、とは扱わない。宣言・本文・位置移動の差分で測る |
| scope の遅延実体化 | 毎文 `env.dup` へ置換しても、増え続ける Hash を毎回コピーする総量は残る | 定数倍の削減候補としてのみ扱い、二次増加の解消・024.38 の全面解決とは呼ばない |
| 推論器の並行性 | Server の主要経路は現在の外側ロックで直列化される | GVL や stress の無失敗ではなく、全 entry point の状態所有を検証する |
| 検索 | `workspace_symbol_result` は WorkspaceIndex の検索結果だけから応答を作る | この要求だけ外側ロックを外す候補。他の意味解析要求へ一般化しない |
| 検索の残る競合 | 検索も index 更新も WorkspaceIndex の内側ロックを使う | 外側ロック解除だけで 024.137 の全 contention が解消したとはしない |
| ColdIndexer | Server 以外に `benchmark/cold_index_benchmark.rb` と専用 spec がある | 直接更新の削除前に全呼び出し元を列挙・移行する |
| 048 の教訓 | 再構成の費用と便益を比較する必要がある | ストア物理統合の全案が反証済みという一般化はせず、更新境界の一本化を優先する |
| fixture | real Rails のコピー・process ごとの cache とランナーは実装済み。minimal fixture の共有参照と serial 指定が残る | 既存機構を使って残る資源を隔離し、並列許可を検証して広げる |

## 作業順・統合単位

各段階を独立して検証・取り消しできる差分にする。論理上の依存は
P0 → (P2契約 + P3実装) → P4統合 → P5 → P6 → P7。
P1a の隔離と P4 の index 内部実装はファイル所有を分けて並行できる。
P1b の CI 接続は P1a 検証後の別差分で、workers=1 を維持する。
P2 は独立実装フェーズではなく P3 の状態所有契約である。実際の並行起動・統合順は
末尾の担当表による。各差分に RED の記録、GREEN、意味論対照、採否を付ける。
挙動不変の移動だけなら、人工的な RED を作らず既存テストと不変条件で検証する。

## P0 — 基準点と測定器を先に固定する

**対象ファイル:** `scripts/measure_typing_publishes.rb`、
`scripts/corpus_diagnostics.rb`、`core/spec/support/analysis_stack_helper.rb`、
`core/lib/ovallsp/analysis_stack.rb`。既存 typing harness が必要な latency を取れない
場合に限り、`scripts/measure_edit_latency.rb` を新設する。

1. 実装開始 revision、差分 digest、Ruby/Prism/RBS/Rails・OS・CPU、設定、
   corpus の相対パス一覧と内容 digest を保存する。旧版/新版を同じ環境で順に測る。
2. `net/http.rb`、`uri/generic.rb`、`rubygems/specification.rb` の実体を固定して
   同一コピーを使用する。Rails の実コードと小さい正常・異常コードも対照に入れる。
   LOC はその実体から導出し、過去の表から写さない。
3. 実 stdio Server を起動し initialize/didOpen 後の診断を待って warm にする。
   単発の didChange ごとにその版の publish を待つ。連続入力は別のケースにする。
   didSave の効果と混同せず、計測起点は編集通知送信時と明記する。
4. 解析中に hover/completion/workspace symbol を送信し、送信→応答を request ID
   で計測する。別スレッドから private result メソッドを呼ぶ値は本番 latency にしない。
5. parse、reference resolution、各診断、推論、lock wait/hold を補助計測し、
   CPU profile・allocation・GC・RSS を wall latency と分離する。計測用 hook は
   テスト/測定経路に閉じ、ソース本文や個人パスを公開ログへ含めない。

**測定案:** 各単発編集シナリオは warm-up を除く最低30観測を取り、p50/p95/max と
全標本数を出す。連続入力は固定された入力列と間隔を使い、最終入力→最終診断、
publish の版列、開始/完了/中断した解析数を取る。冷起動は別表。標本が揺れる場合は
追加測定理由を記録する。性能比較中は full suite 等を走らせない。

**安全境界:** 診断件数減少を高速化と取り違えない。既知の誤呼び出しを検出する
positive control、正常コード、変更で動かない診断カテゴリーを同時に保存する。
`scripts/corpus_diagnostics.rb` は standard モードなので、default safe の LSP 実測とは
別の証拠として扱う。計画段階では性能達成を主張しない。

## P1 — fixture の残存共有をなくして並列実行を検証する

**変更対象:** `core/spec/support/rails_fixture.rb`、必要なら新規
`core/spec/support/minimal_rails_fixture.rb`、`core/spec/test_hygiene.rb`、
`core/spec/ovallsp/agent_process_manager_spec.rb`、
`core/spec/ovallsp/rails_bootstrap_spec.rb`、`core/spec/integration/agent_lifecycle_spec.rb`、
`core/spec/integration/real_rails_spec.rb`、`core/spec/e2e/capabilities_spec.rb`、
`core/spec/tiers.json`、`scripts/test_runner.rb`、`.github/workflows/ci.yml`。
`scripts/test_environment.rb` はコピー/準備の契約変更が必要な場合だけ変更する。

1. minimal fixture を読む全利用者をコピー先に移行する。変更可能な例は
   `example_tmpdir` 内の専用コピーを使用し、同一 process の例間でもフラグが漏れない
   ようにする。real Rails の既存 group 単位コピーは維持する。
2. `.disable_archived_route` を片方のコピーに作った状態で、別 process のコピーでは
   archived route が存在することを同期点で検証する。元 fixture は変更しない。
3. DB/tmp/log/.bundle/XDG cache/環境変数、Agent の pid・socket・子 process、
   shared client の before/after hook を監査する。終了前に Agent を停止し、コピーの
   cleanup は所有 process が既存の削除箇所で行う。破壊テストは `Dir.mktmpdir` 内のみ。
4. 対象ごとの隔離が成立したら `tiers.json` の resources と parallel 指定を変更する。
   real_rails だけでなく capabilities と minimal 利用3ファイルも検証対象とする。
   未隔離資源があるファイルだけ具体的理由付きで serial に残す。
5. workers 1/2/4 を順番に測り、必要なら8も比較する。fixture 準備・census・Rails boot
   を含む wall と実行部分を分ける。同じ seeds と exact example ID 集合を比較し、
   pending は既存の許可済み ID/理由以外を認めない。複数 seed で再現性を確認する。
6. **P1a** は fixture・資源検証・ローカル並列測定までとする。**P1b** は別差分で
   CI の dependency prepare、secret/skip 等の guard を保ったまま runner + verify を接続し、
   明示的に `--workers 1` を使用する。性能差分と CI 配線の障害を別々に戻せる形にする。
   worker default も1のまま。CI の複数 worker 化は serial 接続成功と CI 環境での資源・
   性能証拠が揃ってからの別判断とし、0.4.1 の必須条件にしない。
   ファイル単位分割を先に評価し、example 分割や新しい並列基盤は追加しない。

**ランナーの資源契約:** 現行 `shards` は `parallel` と tier を使い、`resources` を
排他スケジューリングには使っていない。resources に名前を書くだけで安全になるとは
説明しない。P1a で各ラベルと使用箇所を読み取り専用・process/例に隔離済み・共有書込に
分類し、ファイル単位で確認する。同じ `rails` / `sqlite3` 名でも実パスが分離されていれば
同時実行可能であり、名前の一致だけで serial 化しない。共有書込・分類不明は
`parallel: false` に残す。manifest 検証は既存の明示的共有ラベルを true にする矛盾と
未知ラベルを拒否し、隔離済みへの変更には利用コードの対照例を伴わせる。汎用 resource
scheduler の新設はしない。

**資源の決定的テスト:** temp repository の共有資源を使う偽 worker に開始/解放 barrier
を持たせ、serial shard 開始前に active worker が全終了すること、serial 実行中に
別 shard が起動しないこと、isolated resource は同時に進めることを process 間で確認する。
`test_runner_spec.rb` の shard 配列検査だけでは済ませず、例外終了・cleanup・最大 worker
数と exact example ID も検証する。core/tmp/tests の report 等は run 単位資源なので、
別ランナーの同一 checkout 同時実行は引き続き禁止する。

**回帰テスト:** `core/spec/meta/test_runner_spec.rb`、`cache_isolation_spec.rb`、
fixture 利用 spec、CI 配線検証。source fixture の前後比較は相対パスと内容で行う。
親終了/例外時の cleanup と orphan process も検証する。

**測定の注意:** ランナーの timings / current report / prepared lock は同じ checkout に
ある。独立したランナーを同じ checkout で同時実行しない。各 run の直後に verify し、
次の run が旧証拠を無効化する前に比較用サマリを保存する。timings の学習条件を揃える。
一度の並列 GREEN だけでは隔離の証拠にしない。

## P2 — P3 と一体の状態所有契約、scope 最適化は任意

**変更対象:** `core/lib/ovallsp/local_inferencer.rb`、`analysis_stack.rb`、
`semantic/query_service.rb`、`views/controller_ivars.rb` と関連 inferencer spec。
この節は P3 の AnalysisSession 導入と一つの設計・差分として実装する。
独立した Walk クラスや全補助メソッドの移動を先に行うフェーズは設けない。

1. entry point とインスタンス変数の対応表を作る。`scope_at` / `infer_at` / `infer_span`
   に加え、ivar 推論、before_action、render target、class body の補助 entry point も対象。
   steps/budget、self type、lexical nesting、singleton flag、target span、scope capture、
   class body stack/cache の寿命を P3 の session と対応付ける。
2. AnalysisSession は parse/receiver memo を共有し、必要な可変 traversal 状態は
   推論呼び出しごとに作る。session 内でも再入・複数推論は別状態であり、1個の mutable
   context の使い回しで済ませない。既存 API に小さい context を渡す形を優先し、
   外側ロックを一般解除した将来のためだけの抽象化を作らない。`ControllerIvars` が
   連続推論で共有する budget は明示的に渡す。必要な entry point を覆えなければ
   024.39 は部分対応として残し、全体を thread-safe と呼ばない。
3. shared cache は不変の key/result 組として扱い、必要な同期は読み取りと公開だけに
   限定する。parse/walk 全体に新しい mutex を置かない。キーは URI/version だけでなく
   buffer identity と内容・抽出された Ruby を識別し、同 URI の再 open を区別する。
4. **任意・部分改善（出荷必須ではない）:** P3 の実装・測定後、追加効果が見込める場合だけ、
   scope の現行 capture と同じ地点で env の shallow snapshot と
   self type を退避し、通常終了/従来の BudgetExceeded・StandardError 経路で一度だけ
   locals/ivars/Scope を実体化する候補を試す。ensure は cleanup に限定し、結果を壊さない。
   安全な最終地点の snapshot は、その後の statement、代入 RHS 復帰、stack pop に
   影響されないことを確認する。値自体を変更する経路があれば shallow copy 案は再設計する。
5. **任意案の採否:** これは変換・Scope 生成を減らす候補であり、毎文の Hash copy 自体は残る。
   capture 回数だけでなくコピーした binding 総数を測る。通常コードで改善がなく
   複雑性だけ増すなら scope 部分を採用しない。persistent environment や undo journal に
   自動拡張せず、024.38 の残りを記録する。4/5 の未実施は出荷を止めない。

**必須から外す根拠:** 024.38 の「0.2.18: the curve is real and no real code is on it」
に記録された過去実測では、Rails gems と Ruby stdlib の methods の **98.84% が locals
10未満**で、locals 10 の `scope_at` は **0.021ms** だった。これは当時の分布と機械の値で
あり、現行版での再測定ではない。section 0.4 の頻度による優先順位付けに従い、
少数の大きな scope の最適化は任意に下げる。実施して効果があっても二次コピーが残れば
「部分改善」、実施しなければ「見送り」と記録し、状態所有の変更だけで 024.38 を close
しない。採用する数値を公開説明へ昇格させる場合は P0/P7 で再導出する。

**回帰テスト:** locals と self type が異なる二つの文書を Queue/barrier で交差させ、
単独実行時の結果と比較する。全 entry point の連続・再入・例外終了、budget の独立、
initial_env の非破壊、同 URI の再 open を検証する。scope は空行、代入 RHS、block、
class/module/singleton、ivar、budget 中断の直前に完了した statement と途中 statement を
区別する。通常 budget でも中断する大きさの再現を含める。

**実測:** locals 数とネスト深さを別々に増やす。scope/type/ivars を corpus 上の同一位置で
比較し、途中中断時の結果も比較する。024.39 の無競合 stress は補助証拠であり、
外側ロックが隠している無失敗を状態分離の証明にはしない。

**変更対象:** `core/lib/ovallsp/diagnostics/engine.rb`、`parser_service.rb`、
`local_inferencer.rb`、`semantic/reference_resolver.rb`、`semantic/receiver_resolution.rb`、
`diagnostics/semantic_context.rb`、必要なら新規 `diagnostics/analysis_session.rb`。
`AnalysisStack` から本番・corpus・spec の組み立てを揃える。

1. P2 の必要最小限の状態所有を同時に実装する。一度の analyze に閉じた AnalysisSession
   を作り、解析対象の document、Ruby 抽出結果、
   parse result、summary、receiver memo を所有させる。AST は FileSummary や disk cache に
   入れず、解析終了・中断で session とともに解放する。
2. Engine の全体 parse を共有 result に接続し、ParserService は既存 API を維持した上で
   同じ parse を受け取れる内部経路を設ける。断片 parse は別 source の処理として残す。
   Server の reindex summary を再利用する場合は buffer/content/source の一致を確認し、
   不一致では再生成する。P3 の第一差分で reindex の永続 AST 保持まで広げない。
3. raw receiver 解決と診断専用の辞退処理を分離したまま、同一 candidate の raw 結果を
   resolver と診断で共有する。位置だけをキーにせず、session 内の candidate identity と
   推論入力を識別する。nil/Unknown も成功した結果として memo するが、中断はしない。
4. `written_self?`、guessed/shadowed/rooted receiver の診断固有のガードは維持する。
   同じ名前だからと QueryService の補完結果まで共有しない。

**回帰テスト:** parse 呼び出しを source 別に計数し、同じ全体ソースを重複 parse しない
ことを決定的に確認する。receiver raw 推論の再実行数と、辞退/有効診断の両方を検証する。
Ruby/ERB、UTF-8 の複数バイト文字、同じ位置の異なる文書、syntax error、再 open、
safe/standard、severity、変更後の結果更新を含める。

**実測・採否:** P0 と同一 corpus の出力を比較し、CPU/allocations/RSS と実 LSP latency を
再測定する。parse の回数削減だけで 300ms 達成とはしない。新キャッシュの寿命を
request/session 内に限定し、無制限な AST/文書保持を作らない。

## P4 — 更新ファサードと依存入力に基づく無効化

**主に改善する経路は「宣言集合が変わらない本文編集」**である。過去の024.45の profile
と Step 2 報告では SymbolId 構築・索引走査が支配的で、parse の重複排除だけで
300ms に届くとは見込まない。memo を編集ごとに捨てて同じ名前・祖先を繰り返し組み立てる
費用を減らす。宣言集合が同じことは必要な選別条件であって保持の十分条件ではなく、
以下の依存入力・位置・返り値の一致も検証する。全入力に対する増分解析は約束しない。

**変更対象:** `core/lib/ovallsp/server.rb` の `apply_file_summary` /
`remove_index_contribution`、`cold_indexer.rb`、`benchmark/cold_index_benchmark.rb`、
`workspace_index.rb`、`semantic/hierarchy_index.rb`、`semantic/generated_method_index.rb`。
`semantic/reference_index.rb` と `method_summary_store.rb` は更新契約の検証対象。

1. ColdIndexer の constructor / callback 全利用箇所を検索し、Server の `on_summary`
   経路、benchmark、直接生成する spec を列挙する。cold path は必須の summary sink に
   渡す形へ移行し、条件付きの workspace + hierarchy 直接更新と `on_indexed` 分岐を廃止する。
   benchmark は目的を維持した明示的 sink を渡す。旧 constructor を他の公開経路が使うなら
   先に互換性の扱いを記録し、未使用と決めつけて削除しない。
2. 本番で複数 store を更新する所有者は Server の既存ファサードとする。apply の
   stale 判定に失敗したら他 store/generation/dirty token に副作用を出さない。
   remove と apply の全経路を通し、disk→buffer 昇格と read_sequence を維持する。
   各 store の物理統合や汎用 store 基底クラスは作らない。
3. memo の依存入力を返り値から逆に列挙する。Workspace の型解決は型候補集合・kind・
   順序等の実入力で判定する。Hierarchy は ancestor/alias だけでなく workspace の
   型解決・宣言・Concern 判定、GemIndex、RBS と返り値の location/origin も含める。
4. 最初は依存入力の完全な一致を証明できる置換だけ memo を保持し、それ以外は clear
   する。本文1文字編集でも依存する位置が移れば clear してよい。比較費用も計測する。
   `ancestor_facts == old` だけの判定や location を除いた形状だけでの保持はしない。
5. file/version と公開順序に使う既存 generation は従来どおり更新する。cache を保持する
   ために generation を止めない。memo 専用の入力比較と公開の鮮度は別契約とする。
6. 依存再解析の既存 `dependable_shape` guard を維持し、本文・位置・arity・visibility・
   superclass・generated method の変更ごとにキュー数を計測する。依存グラフの完全性が
   証明できない場合、開いたファイルへの保守的 fan-out を削らない。本文の戻り値変更も
   別ファイルの型に影響し得るため、現行 guard の妥当性自体も回帰例で確認する。

**回帰テスト:** body-only 編集で再計算を省ける例と、定数追加/削除・namespace 衝突・
class/module 変更・include/prepend/extend・alias・位置移動・gem 交換・RBS reload で
必ず結果が変わる例を対にする。reopen、disk race、削除、cold cache hit/miss、依存先の
arity/戻り値変更も検証する。省略される compute の回数を計数し、意味論 corpus を通す。

**安全境界:** 独立した ReferenceIndex の遅延解決、MethodSummaryStore の依存無効化は
残す。未使用経路をなくすこととすべての store の整合性を解決することは分けて判定する。
024.62 は実際に一本化された範囲を記録し、残存する更新漏れリスクまで閉じたと推定しない。

## P5 — workspace symbol の外側ロックを限定解除する

**変更対象:** `core/lib/ovallsp/server.rb` の dispatch / `workspace_symbol_result`、
`workspace_index.rb`、`core/spec/ovallsp/server_spec.rb`、`workspace_index_spec.rb`、
`workspace_index_benchmark_spec.rb`、`core/spec/meta/workspace_index_cost_spec.rb`。

1. search が返す symbol/uri/location の読み取り専用性と応答変換の依存を確認する。
   必要な返り値の保護は生産側で行う。索引更新後も返した値が書き換わらない契約を置く。
2. `workspace/symbol` だけ `with_index_snapshot` の対象から外し、WorkspaceIndex 内側
   mutex 内で得た一つの状態から応答する。他の意味解析要求は外側ロックを維持する。
3. server_spec の「全読取り要求が外側 lock を持つ」テストを、複数 store の一貫性を
   必要とする要求と workspace-only の要求に分け、挙動を検証する。単に検査を消さない。
4. search と replace/remove を barrier で競合させ、返り値が旧または新の完全な状態で
   あり混在しないこと、順序・limit・重複宣言が維持されることを確かめる。

**実測:** 空/1文字/複数文字/不一致 query と規模別 corpus で、search 総時間、
内外 lock hold/wait、background 分析と indexing の進行を比較する。内側ロックによる
indexing 待ちは残り得る。dispatch が解析中に占有される問題は P6 で検証する。

**採否:** 外側を外すことで何が進めるようになったかを示せた範囲で採用する。
キー配列だけをコピーして再ロックする旧案は採用しない。ranking の lock 外実行は、
残る contention が測定上必要と分かった場合に限る別差分とし、本計画の必須条件にしない。
024.137 を閉じるには残る内側の待ちも評価し、未解消なら limitation を狭めて残す。

## P6 — 協調的中断で解析から dispatch へ戻る

**変更対象:** `core/lib/ovallsp/server.rb` の run / drain / publish、
`diagnostics/engine.rb`、P3 の AnalysisSession、`local_inferencer.rb`、
`semantic/reference_resolver.rb` と profile で長い区間が確認された walk。
`io/framed_reader.rb` は nonblocking readiness の契約に不足がある場合に限り変更する。

1. 解析セッションに「入力待ちを検査する checkpoint」を渡す。Engine の候補ループ、
   診断フェーズ境界、長い推論 walk の一定作業量ごとに確認する。新しいタイマー、
   編集ごとの Thread、Thread#kill、lock を持ったままの再帰 dispatch は導入しない。
2. 入力が待っていれば解析を中断し、スタックを完全に抜けて外側ロックを解放してから
   run loop へ戻る。中断を Unknown/空 findings/正常完了へ変換しない。
   内部専用 token の catch/throw を第一候補とし、既存の広い StandardError rescue に
   握り潰されない経路にする。ensure が実行されることと catch の境界をテストする。
3. 中断した URI と未着手 URI を pending に戻し、同じ drain 内では即再実行しない。
   入力を順序どおり dispatch した後、最新の document/buffer/config/generation から
   session を作り直す。保存済みの古い context を再開しない。
4. pending は URI ごとに有界に重複排除する。didClose の URI は除き、reopen の新しい
   buffer を処理する。中断で未完了の findings を publish せず、完了した解析だけ既存の
   publication funnel を通す。途中の method summary/cache 書き込みも点検し、完成した
   値だけ保存する。中断した計算の in-progress marker が残らないようにする。
5. FramedReader は main thread の所有を維持する。readiness は完全な message の保証では
   ないため、分割 header/body、内部 buffer、EOF、malformed frame を含めて検証する。
   parse の最中に read_message を呼ばず、中断後に既存 framing 処理へ戻る。
   EOF による空回りを防ぎ、正常 shutdown/EOF 時の既存 drain 契約を保持する。
6. background の workspace 分析には stdin の readiness を直接渡さない。必要な中断は
   文書/意味世代の supersession 等の別条件で扱い、既存の外側 lock 契約を維持する。
   foreground の中断だけで background lock 待ちが解消したと主張しない。

**飢餓上限（本計画で提案する内部定数、公開設定ではない）:** pending の
`[uri, buffer_id]` ごとに最初の待機時刻（monotonic clock）と連続中断数を保持する。
**連続3回の協調的中断、または最初の pending から1,000ms経過**の早い方で強制完走対象と
する。同じ buffer の didChange / hover 到着・version 更新では両方をリセットしない。
成功した解析の publish が受理された時、または close でのみ当該記録を解消する。
reopen は別 buffer として登録する。失敗や世代不一致による publish 拒否を成功扱いにしない。

run loop は入力が常に ready でも **各 dispatch 完了後**に期限を点検する。
次の通常 drain を待たず、期限到達済み URI の中から公平な FIFO/round-robin で1件を取り、
その時点で store にある最新文書を一度完走させる。この回だけ入力到着による協調的中断を
無効にし、終わったら少なくとも1メッセージを dispatch して次の強制完走へ進む。
未到着/未dispatch の編集を先取りして解析せず、結果には計算元の version を付ける。
未期限の解析を同じ drain で何度も再試行しない。期限判定より先に EOF/shutdown を
処理した場合は既存の終了契約を優先し、壊れた入力で強制解析を無限に再試行しない。

この上限が保証するのは **入力の継続による無限延期をなくすこと**であり、1,000ms以内の
publish ではない。強制完走そのもの・background の lock 待ち・先行 dispatch は時間を要する。
完走中は hover/didChange も待たされるというトレードオフを ADR と KNOWN_LIMITATIONS に
記録する。例外や継続的な意味世代変更がある環境まで鮮度の wall 上限を保証しない。
定数を調整するときはこの表の契約・テスト・最終測定を一緒に更新し、無制限に戻さない。

**飢餓の決定的テスト:** 注入可能な fake monotonic clock と checkpoint/barrier を使う。
時刻が進まなくても中断1/2/3回後の次回が完走すること、中断数が少なくても期限の
直前/到達で分岐すること、入力が途切れなくても dispatch 後に強制対象が選ばれることを
検証する。連続 didChange で待機年齢がリセットされない例、二つの URI がどちらも進む例、
publish 拒否時・close/reopen・失敗時の記録管理を含める。強制完走中は中断 callback が
要求しても完了し、その間に届いた hover は完了後に応答することまで観測する。

**副作用付き ensure の方針:** `Server#publish_diagnostics` の現在の ensure
（計画基準 tree の server.rb:603 付近）は `answer_pending_ancestry_questions` を呼び、
Runtime Agent の single-flight worker を起動し得る。catch/throw の unwind でも ensure は
走るため、そのまま残さない。session/lock/in-progress 状態の cleanup は必ず ensure で
行うが、Agent 質問の発行は ensure から外し、run の安全な後処理境界へ移す。
中断時は既存 registry の質問を保持して「後処理が必要」を重複排除して記録し、まず入力を
1件 dispatch した後（通常完了/通常の解析失敗ならその処理終了後）に既存 single-flight
入口を一度呼ぶ。未処理の質問を中断のたびに破棄したり新 Thread を起動したりしない。
background 呼び出しは main の入力境界を待てないので、その呼び出し終了後・lock 解放後の
既存 worker 管理へ委ねる。質問が持つ世代、trust、Agent restart/give-up/active 条件を
維持し、終了開始後には新 worker を起動しない。これは「解析中断が質問への回答を無効に
する」という決めつけではなく、既存の質問の有効性判定を保った発行タイミングの変更である。

**ensure 回帰例:** 中断→hover dispatch→後処理の順序、通常完了・通常例外でも質問が
失われないこと、連続中断でも worker が増殖しないこと、既存 worker へ追加された質問の
処理、close/Agent restart/trust 変更/shutdown 時の拒否を同期点で検証する。Agent 起動失敗
の slot 解放とログ契約を維持し、他の副作用付き ensure も同じ基準で一覧確認する。

**決定的回帰テスト:** 実 pipe と checkpoint の同期 hook で、分析開始→次入力到着→
中断→lock 解放→hover 応答→最新解析完了を観測する。時刻 sleep に依存せず、
hook のない stdio E2E も実行する。異なる URI の入力、連続 hover、変更なし request、
syntax error、設定変更、close/reopen、解析例外、途中の EOF/protocol error、
複数 pending、shutdown、最後の1編集を含める。`server_settled_analysis_spec.rb`、
stdio integration、publication/identity spec に追加し、thread 数が入力数とともに増えない
ことも確認する。

**限界と実測:** 協調的中断だけでは、入力が来ない一回の解析は速くならない。
parse や長い leaf 処理の最中には checkpoint に戻れない。区間の最長時間と checkpoint
自体の費用、再実行による CPU/RSS、入力停止後の最終 publish を測る。
hover の連打でも上記の強制完走が生じることを測定する。checkpoint 間隔は profile と
実 LSP latency から決め、飢餓上限とは別の値として記録する。

| P6 の実測シナリオ（それぞれ独立した結果行） | 測るもの |
|---|---|
| foreground 単発解析中の hover | request→response、checkpoint までの時間、中断/再実行費用 |
| **background workspace pass 中の hover** | 実 stdio dispatch からの応答時間、外側 lock wait/hold、pass 完了時間。直接 hover_result を呼ばない |
| 連続入力/hover による強制完走 | 中断数、pending 年齢、強制完走の開始/終了、待たされた hover、publish version 列 |
| background pass と強制完走が重なる場合 | lock 待ちと foreground 計算を分離し、全体の待ち時間・最終 publish・他 URI の進行 |

background 行も P0 の baseline と最終 tree の双方で測る。foreground だけの改善を
「解析中の hover 改善」と一般化しない。background pass 開始を同期 hook で観測する
決定的テストと、hook なしの性能測定を分ける。

この変更が新しい誤答・publish 消失・継続的な再計算増幅を生むなら P6 差分を採用しない。
固定 worker や全面 snapshot アーキテクチャへその場で拡大せず、P3/P4 の速度改善を残し
024.45 の未達範囲を記録する。採用する scheduling と中断方式のトレードオフは実装前に
`docs/design/adrs/` へ ADR を置き、決定と本書の採否記録を相互に参照する。

## P7 — 統合検証と出荷判断

**0.4.1 は 300ms 未達が残ることを前提にした部分改善リリース**として計画する。
SymbolId の構築・索引走査の残存費用を測り、P3/P4/P6 の効果を分離する。
300ms は元の製品目標と024.45の閉鎖条件として残すが、本版の出荷成立条件にはしない。
正確性を保つ実測改善・飢餓上限・残存待ち時間の公開を成果とし、未達なら024.45は open。
実装結果で目標を満たしたときだけ、対象シナリオと環境を再確認して閉鎖を判断する。

変更ごとの対象 spec → 意味論 corpus → full 直列/並列 → 実 LSP 性能測定の順に進める。
中間差分の性能数値は基準と条件を明記し、最終 tree でも再測定する。

```sh
ruby scripts/test_environment.rb check --profile unit
ruby scripts/test_environment.rb prepare --profile full --offline
ruby scripts/test_runner.rb list --format json
ruby scripts/test_runner.rb run --tier full --workers 1 --seed 3501
ruby scripts/test_runner.rb verify --report core/tmp/tests/full.json
ruby scripts/test_runner.rb run --tier full --workers 2 --seed 3501
ruby scripts/test_runner.rb verify --report core/tmp/tests/full.json
ruby scripts/check_doc_links.rb
ruby scripts/check_doc_triggers.rb
ruby scripts/preflight.rb
```

上記の full 比較は途中でソースを変えず、各 verify 後に run の比較用証拠を保存する。
実測では P1 の worker/seed 行列を追加する。corpus は同じ digest の入力を使い、
`scripts/corpus_diagnostics.rb --expect-control=CODE:N` の CODE/N は変更前に導出して
固定する。LSP 性能 harness の CLI と corpus manifest は P0 で確定し本書へ追記する。
実装前に存在しない測定スクリプトを実行済みとしない。

| 課題 | 閉鎖/採用の証拠 | 未達時の扱い |
|---|---|---|
| 024.45 | 定義した単発再解析シナリオの p95 <= 300ms と、解析中の対話 latency、出力正確性 | 300ms を満たさなければ改善率だけで close しない。達成環境/未達シナリオを limitation に残す |
| 024.38 | 任意案を採用した場合のみ、中断/例外時を含む scope 一致と費用削減 | 必須から除外。二次コピーが残れば部分改善、未実施なら見送りとして open を維持 |
| 024.39 | entry point 全体の状態所有、決定的 interleaving、逐次/再入 corpus 一致 | Server のロック下で無競合という理由だけで close しない |
| 024.137 | 一貫した検索結果と実 dispatch/更新の lock 待ち改善、残存 inner contention の評価 | 外側だけ解放なら残る検索費用・index 待ちを明記する |
| 024.62 | 本番の apply/remove 所有者と cold callback の一本化、stale/no-op の副作用検証 | 更新境界以外の重複が残ることを明記し、元 entry の全主張を照合して close を判断する |
| 024.71 | source fixture 不変、process/例の隔離、全 example ID 一致、繰り返し並列実行、CI 証拠 | 未隔離ファイルを serial とする理由と時間を残す。並列 runner の存在だけで close しない |

**共通安全境界:** 型/未定義メソッドの positive control を維持する。辞退を増やして速度を
作らない。既存の public generation・buffer identity・index source 優先順位・出力順序・
