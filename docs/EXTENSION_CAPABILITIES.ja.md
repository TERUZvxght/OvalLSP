# 拡張機能のケイパビリティ: 「動く」とは何か

[English](EXTENSION_CAPABILITIES.md)

この文書が存在するのは、拡張機能が数バージョンにわたって「問題なく
インストールでき、問題なく起動し、正常なステータスを報告し、しかし
利用者が気づくことはほとんど何もしない」状態で出荷されたためです。
当時あった検査はすべて、利用者が問わない質問に答えていました。
プロセスは起動するか。payloadのハッシュは一致するか。テストは通るか。
*ドットを打ったときに補完候補が出るか*に答えるものは1つもありませんでした。

そこでこの文書は、実際に動かなければならないことを「利用者が何をして、
何が見えなければならないか」という形で列挙します。各行は
`core/spec/e2e/capabilities_spec.rb` が実在のRailsアプリケーションに対して
end-to-endで検証します。拡張機能と同じように実際のCoreをstdioで駆動し、
Runtime AgentとCold Indexの完了を待ってから問い合わせます。

**E2Eの行を持たない機能はケイパビリティではありません。行がスキップされる
機能は出荷されていません。** まだ通せない行は、理由とともに `NOT YET` として
この文書に残します。欠落が単に「書かれていない」のではなく、見える形で
残るようにするためです。

## この保証が対象とする環境

以下の各行は、ただ1つの環境についての約束です。

- **Railsアプリケーション**(`bin/rails` と `config/environment.rb` が存在)を、
  **信頼済み**ワークスペースとして、**darwin-arm64** 上で、拡張機能に同梱された
  Coreで開いた場合。

E2Eスイートがこの環境で走るので、検証されているのはこの環境です。素のRuby
プロジェクトは、これらの行の対象に**含みません**。エンジンの多くはそこでも
動作しますが、この文書は素のRubyについて何も規定しておらず検証もしていません。
中途半端に両対応すると、どちらの説明も悪くなります。Rails規約に明示的な境界を
設け、素のRubyでの体験を規定する作業はロードマップ項目 024.R1(0.2.0)です。

未信頼のワークスペースについては本文書末尾のとおりです。Runtime Agentを起動
しないため、Rails由来のケイパビリティは設計どおり静的解析のみの回答に縮退します。

## 検証の方法

2層あります。別々の主張だからです。

1. `core/spec/e2e/capabilities_spec.rb` が実際のCoreをstdioで駆動し、実在の
   Railsアプリに対して以下の全行を検査します。`OVALLSP_E2E_CORE_BIN` に
   *ビルド済みVSIX内の* Coreを指定すると、ビルド元のソースではなく利用者が
   実際にインストールする成果物を検証できます。
2. `vscode/scripts/verify-installed-extension.sh <vsix> <workspace>` が、その
   VSIXを使い捨てのVS Codeにインストールし、Railsフォルダを開き、VS Codeが
   拡張機能を認識し、起動し、CoreとRuntime Agentをspawnし、終了時に何も
   残さないことを確認します。

2層目が必要なのは、1層目では「拡張機能が何もしない」に最も似た失敗を検知
できないからです。すなわち、ディスク上には存在するがVS Codeに登録されておらず、
読み込まれず、ログも出ない状態です。このプロジェクトは実際にその状態にありました。

`core/spec/e2e/capability_coverage_spec.rb` が本文書とスイートの対応を維持します。
すべての行にexampleがあり、すべてのexampleに行があることを検査します。

## 凡例

- **PASS** — 壊れれば落ちるE2Eの行によって検証済み。
- **NOT YET** — 規定済みでE2Eの行もあるが、現在は失敗または保留。拡張機能が
  これを行うとは主張しません。

## 前提: 拡張機能が実際に動いていること

| # | 利用者の操作 | 起きなければならないこと | 状態 |
|---|---|---|---|
| B1 | RailsプロジェクトでRubyファイルを開く | Coreが起動し `initialize` に応答する | PASS |
| B2 | 少し待つ | `ovallsp/status` がRailsアプリでは `ready-rails`(それ以外は `ready`)に到達する | PASS |
| B3 | ウィンドウを閉じる | Core・Runtime Agent・runnerのいずれのプロセスも残らない | PASS |

## Hover: この式は何か

| # | 利用者の操作 | 起きなければならないこと | 状態 |
|---|---|---|---|
| H1 | コンストラクタ由来のローカル変数(`w = Widget.new`)にhoverする | `Widget` | PASS |
| H2 | Active Recordのファインダ由来のローカル変数(`a = Article.find(id)`)にhoverする | `Article` | PASS |
| H3 | コントローラのアクションが代入した`@ivar`にビュー内でhoverする | そのアクションで推論された型 | PASS |
| H4 | リテラル(`"s"`、`1`、`[1]`)にhoverする | `String`、`Integer`、`Array[Integer]` | PASS |
| H5 | メソッド呼び出しにhoverする | 引数一覧(`documented(first, second)`) | PASS |
| H6 | キーワード引数・配列・ハッシュ・`case`・`while`・`return` の内側の式にhoverする | 外側の構造ではなくその式自身の型 | PASS |
| H7 | 直上にRDoc/YARDコメントがあるメソッドにhoverする | 型の下にそのコメントが表示される | PASS |

## 補完: 最も使われる機能

| # | 利用者の操作 | 起きなければならないこと | 状態 |
|---|---|---|---|
| C1 | `s` がStringのとき `s.` と打つ | 標準ライブラリのメソッド(`upcase`、`split` など) | PASS |
| C2 | `w` がワークスペースのクラスのインスタンスのとき `w.` と打つ | そのクラス自身のインスタンスメソッド | PASS |
| C3 | `article` がActive Recordのインスタンスのとき `article.` と打つ | そのモデルのカラムと関連 | PASS |
| C4 | 同上 | Active Record自身のインスタンスAPI(`save`、`update`、`destroy`、`valid?` など) | PASS |
| C5 | `Article.`(定数)と打つ | Active RecordのクラスAPI(`all`、`find`、`where`、`create`、`new` など) | PASS |
| C6 | Widgetがワークスペースのクラスのとき `Widget.` と打つ | そのクラス自身のシングルトンメソッド(`def self.build`) | PASS |
| C7 | ビューで `article_p` と打つ | ルートヘルパー(`article_path`、`article_url`) | PASS |
| C8 | 引数が既知のメソッドの補完を確定する | 呼び出しが書き出され、各引数がタブストップになる(`takes_two(first, second)`) | PASS |
| C9 | 引数を取らないメソッドの補完を確定する | 名前のみ。括弧は付かない | PASS |
| C10 | 引数の形が不明なメソッドの補完を確定する | `where($1)` — 括弧が開き、カーソルが中に入る | PASS |
| C11 | ERBテンプレート内で `post.` と打つ | HTMLではなくテンプレートのRuby領域から解決したメンバー | PASS |
| C12 | レシーバなしで `Art` と入力する | 宣言済みクラス、スコープ内のローカル変数、その位置で呼べるメソッド | PASS |
| C13 | RDoc/YARDコメント付きで宣言されたメソッドの補完候補を選択する | そのコメントが候補のドキュメントとして表示される | PASS |

C4・C5・C6はいずれも壊れており、現在は修正済みです。C5とC6は原因を共有して
いました。裸の定数が `Unknown` と推論されるため、下流がクラスレシーバを一度も
見ていなかったのです。C4とC5はもう1つの原因を共有していました。モデルの
`ApplicationRecord` より上位の祖先はワークスペース外にあり署名も存在しないため、
Active Record自身のAPIが不可視でした。現在はRuntime Agentが、実際にロード
されたクラスからそのAPIを報告します(モデルごとではなく全モデルで1回)。
それこそがRuntime Agentの存在意義です。

## 定義へ移動

| # | 利用者の操作 | 起きなければならないこと | 状態 |
|---|---|---|---|
| D1 | ワークスペースのメソッド呼び出しで定義へ移動する | その `def` へ飛ぶ | PASS |
| D2 | Active Recordのカラム・関連で定義へ移動する | 所有するモデルクラスへ飛ぶ | PASS |
| D3 | 標準ライブラリのメソッドで定義へ移動する | RBSの宣言へ飛ぶ | PASS |

## 診断

| # | 利用者の操作 | 起きなければならないこと | 状態 |
|---|---|---|---|
| G1 | 構文エラーを書く | その位置にパース診断が出る | PASS |
| G2 | **ワークスペースのクラス**に存在しないメソッドを呼ぶ | 「has no method named」 | PASS |
| G3 | 存在しないルートヘルパーを参照する | 「no route named」 | PASS |
| G4 | **Active Recordモデル**に存在しないメソッドを呼ぶ | 「has no method named」 | PASS |
| G5 | **引数の個数**が合わない呼び出しを書く | 「takes N arguments, but M given」 | PASS |
| G6 | 親クラスがgemの定数であるクラス(`< Rails::Application`)でRails DSLを呼ぶ | 何も出さない。そのクラスの本当のメソッド集合をここでは知らないため | PASS |
| G7 | 親クラスが式であるクラス(`< ActiveRecord::Migration[8.1]`)でDSLを呼ぶ | 何も出さない | PASS |
| G9 | ERBテンプレートでローカル変数のメソッドを呼ぶ | HTMLについて何も出さない。テンプレート文字列ではなくRuby領域を解析する | PASS |
| G10 | レイアウトに `<%= yield %>` を書く | 何も出さない。展開後のRubyはトップレベルだがテンプレートでは正当 | PASS |
| G11 | 引数に対してメソッドを呼ぶ(`User.find(params[:id])`) | 何も出さない。内側の呼び出しは自身のレシーバに属する | PASS |
| G12 | Runtime Agentがルートを報告する前から開いていたファイルがある | ファイルに触れなくても、ルート到着時に診断が消える | PASS |
| G13 | gemにあるクラスを再オープンする(`test/test_helper.rb` の `ActiveSupport::TestCase`) | 何も出さない。静的な継承チェーンが何と言おうと、そのクラスはワークスペースのものではない | PASS |
| G14 | 再オープンされたgemクラスを継承したテストを書く(`class FooTest < ActiveSupport::TestCase`) | 何も出さない。再オープンはレシーバだけでなく継承チェーンの途中にもある | PASS |
| G15 | RBS/RBIの署名が宣言する型になりえない引数を渡す | 呼び出し全体ではなく、その引数の位置で報告される | PASS |
| G16 | どのアクションもコールバックも代入しない `@ivar` をビューで読む | 報告される | PASS |

G4はかつてC4と同じ「祖先が不明」問題に起因していましたが、現在は解消済みです。
Runtime Agentが各モデルの実際の応答可能メソッドを報告するため、モデルを閉じた
レシーバとして扱えます。ただしモデルが `method_missing` を定義している場合や、
カラムを読めなかった場合は、推測せず黙ります。

G5は意図的に狭く作ってあります。レシーバがただ1つのソース宣言に解決でき、
呼び出しにsplatも `...` もなく、宣言に `*rest` もない場合**のみ**報告します。
それ以外は何も言いません。動作するコードに対する誤った「引数の数が違う」は、
引数検査が無いことより悪いためです。

引数の**型**検査は意図的にこの表にありません。本文書自身の規則が「E2Eの行を
持たない機能はケイパビリティではない」である以上、検証するものが無い約束は
表ではなく下記の非目標に属します。

## 本文書が意図的に約束しないこと

- 静的型検査器が言う意味での型検査。フロー依存の解析も、組み込みコンテナ形状を
  超えるジェネリクスも、網羅性検査もありません。引数の*型*を検査するものは
  何もなく、G5は引数を数えるだけで、それが何であるかについては何も述べません。
- 構文の色付け。TextMate文法はファイルを表示用にどうトークン化するかを決める
  もので、表示上の関心事であり、このエンジンが何かを知っている領域ではありません。
  VS Code同梱のRuby拡張が既に`.erb`を関連付けており、他のRuby拡張も独自の文法を
  持っています。ここでもう1つ登録しても、それらと衝突するだけで得るものがありません。
  *セマンティック*ハイライトは別物で、0.2.0で提供しています(下記S1)。
  こちらはこのエンジンが実際に持っている意味 — `foo` がローカル変数かself上の
  呼び出しか — を、使われている文法の上に重ねるもので、`.rb`とERBテンプレートの
  Ruby領域の双方が対象です。
- ワークスペースフォルダの外にあるRubyファイルについての一切。
- 未信頼のワークスペースでの一切。Runtime Agentが起動しないため、Rails由来の
  ケイパビリティ(C3・C4・C5・D2・G3・G4)はすべて設計どおり静的解析のみの回答に
  縮退します。
