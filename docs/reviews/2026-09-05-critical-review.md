# OvalLSP 批判的レビュー — 2026-09-05

本レビューの結論は、**個別の解析例を成立させる仕組みと回帰防止策は充実しているが、ファイルを変更し続ける実際の利用で、答えの正しさと更新を維持する保証が不足している**、というものです。特に、キャッシュの掃除が外部ディレクトリに到達する問題、意味を壊すリネーム、不正な呼び出しを生成する補完、索引・診断の更新順序を優先して扱うべきです。

「指摘が既に記録されている」「意図的な制限である」「テストが通る」は、利用者への影響を消しません。一方で、未実装の将来計画をすべて現在の不具合と呼ぶこともしません。以下では、再現した不具合、静的に確認した問題、既知の能力不足、設計・運用への提案を区別します。

## R01 — キャッシュ外の削除を防ぐ境界が文字列比較に留まる

**場所:** [cache/store.rb](../../core/lib/ovallsp/cache/store.rb) の `prune_generations_of`、`remove_within`、`inside?`（140行付近、404–417行付近）。

`inside?` は `File.expand_path(path).start_with?(root + separator)` で判定します。中間ディレクトリのシンボリックリンクは解決しません。一方、掃除側はリンク先の子ディレクトリを列挙するため、文字列上はキャッシュ内、実体は外部という削除対象を作れます。

再現では一つの一時ディレクトリの下に `cache/` と `outside/` を作り、`cache/scope` を `outside/` へリンクしました。外部に既定の保持数を超える世代相当のディレクトリを置き、通常の `prune_generations(cache_root:, current:)` を呼ぶと、古い `outside/victim/valuable.txt` がディレクトリごと消えました。現世代と、関係のない対照ファイルは残りました。[スクリプト](2026-09-05-critical-review/cache-probe.rb)・[出力](2026-09-05-critical-review/cache-probe.json)。すべて `Dir.mktmpdir` の中で完結しています。

これは一般の利用者がキャッシュ内にリンクを作っている場合、またはキャッシュに書き込める何者かがリンクを置いた場合の問題です。**ワークスペースのコードだけでそのリンクを作れる、あるいは権限昇格できると確認したものではありません。** それでも、掃除処理が自身の管理領域を越えて削除するという安全上の欠陥は残ります。`tighten_tree` にも同じ境界で外部を走査する懸念があり、削除と権限変更を一緒に点検すべきです。

### 改善案

修正は、削除直前の場所で実体の包含関係を保証することです。キャッシュのルート自体を移設するリンクと、配下から外部へ抜けるリンクを区別し、中間成分を辿る場合と置換競合も検討する必要があります。既存の「兄弟パスを拒否する」対照に加え、**中間リンク経由で外部を消さない**ことを実ファイルで固定すべきです。単に呼び出し元へチェックを足すだけでは、既存の事故対策が目指した性質を取り戻せません。

- **実装の範囲:** 管理ルートを確定した上で、世代の列挙・削除・権限変更が配下のリンクを辿らない方針を共有します。包含関係を保証できない対象は掃除せず、理由を記録します。`realpath` の事前比較だけで置換競合も解消したとは扱いません。
- **確認する条件:** 一時ディレクトリで通常の古い世代は削除され、兄弟パス・中間リンク・壊れたリンクの先は削除も chmod もされないことを確認します。削除直前のリンク置換も順序を制御して試します。

## R02 — リネームは override を触らなくても意味を壊す

**場所:** [rename/planner.rb](../../core/lib/ovallsp/rename/planner.rb) の冒頭の設計説明、`plan`、`locations_for`（10–20、177–197、215–224行付近）。

設計説明は、別の SymbolId を持つ override を編集しないことをもって、安全な境界が構造的に満たされるとしています。しかし、名前が結ぶ継承関係そのものがリネームの対象外になっています。

```ruby
class Parent
  def hello = 1
end
class Child < Parent
  def hello = super + 1
end
class Consumer
  def go = Child.new.hello
end
```

`Parent#hello` を `world` へ変更する Server の編集は受理されます。適用後も構文解析は成功しますが、Ruby の実行結果は `2` から `NoMethodError` に変わります。子の `super` はそのまま親の `hello` を探すためです。`probes.json` の `override_rename` が変更後のソースと実行結果を記録しています。

### 改善案

解決策は一律に override 全体を書き換えることではありません。継承、`super`、別名などの意味上の参照を調べ、整合した編集を作れない場合に拒否する必要があります。現在の [rename_oracle.rb](../../scripts/rename_oracle.rb) はローカル変数を対象とするため、この保証を代行していません。

- **最初の修正:** 親子の同名メソッドと `super` の依存を編集前に調べ、意味の保存を確認できないリネームは理由付きで拒否します。索引の外にある継承先や動的な参照まで保証できるという扱いにはしません。
- **確認する条件:** 親を変更する場合・子を変更する場合・複数段の継承・無関係な同名メソッドを対照にします。受理した編集は合成 Ruby を実行して結果を比較し、拒否した場合は編集を一切返さないことを確認します。

## R03 — キーワードの種類を捨ててから補完を生成している

**場所:** [semantic/query_service.rb](../../core/lib/ovallsp/semantic/query_service.rb) の `source_parameter_names`（401–410行）、[server.rb](../../core/lib/ovallsp/server.rb) の `completion_snippet`（3337–3344行）。

`def take(required:)` に対して Server が返す補完は `take(${1:required})` です。名前だけを tab stop にしたため、キーワードを表す `required:` がありません。利用者が値を入力しても、たとえば `take(1)` になり、必要なキーワード引数を渡す呼び出しにはなりません。`probes.json` の `keyword_completion` は実際の completion 応答です。

### 改善案

根本は `Parameter#kind` を途中で捨てることです。signature help は `Parameter#label` によって種類を保持していますが、補完経路にはその情報が届きません。呼び出し用の表現をパラメータの種類から生成し、たとえば `take(required: ${1:required})` とする必要があります。単純な位置引数と、必須・任意のキーワードを混ぜた fixture で、**挿入した呼び出しが宣言に bind するか**を検証すべきです。

- **実装の範囲:** completion まで名前と種類を保持し、位置引数・キーワード・rest・block の挿入方針を明示します。宣言を表示するラベルと呼び出しを生成する処理は用途が違うため、同じ文字列の流用で済ませないようにします。
- **確認する条件:** snippet に具体的な値を入れて合成メソッドを呼び、位置引数とキーワードが意図した値を受け取ることを検証します。tab stop の番号、必須・任意キーワードの混在、引数なしの補完も確認します。

## R04 — 初回索引の read_sequence は読み取り後に発行される

**場所:** [cold_indexer.rb](../../core/lib/ovallsp/cold_indexer.rb) 157–162行。[server.rb](../../core/lib/ovallsp/server.rb) の `reindex_from_disk` は逆に読み取り前に発行しています。

初回索引が古い内容を読んだ後、ファイルが更新され、watcher が新しい内容を索引へ入れても、初回索引はその後でより新しい `read_sequence` を取得できます。その結果、新しい内容を古い内容で上書きします。

再現は読み取りの継続点を制御しています。ディスクが `class NewVersion; end`、watcher 相当の読み取りが先に登録済みの状態から、初回索引を再開すると索引には `::OldVersion` が残ります。`probes.json` の `cold_race`。自然な競合の発生率を測ったものではなく、合法な実行順で破綻することを示しています。

### 改善案

読み取り開始時に発行した順序を、その読み取りの内容と一緒に持ち運ぶ必要があります。ディスクから summary を作る複数の経路で、順序の意味を統一すべきです。索引の `stale?` が正しくても、渡される順序が逆なら防げません。

- **実装の範囲:** cold index、watcher、再索引の各経路が同じ発行元から読み取り開始前に順序を取得し、その値を summary の登録まで保持します。キャッシュからの復元も、いつの読み取りとして採用するかを明示します。
- **確認する条件:** 古い読み取りを停止して新しい読み取りを先に登録する順序と、その逆を同期用の barrier で固定します。どちらも最新の内容が残り、変更のない初回索引も成立することを確認します。sleep の長さに依存するテストにはしません。

## R05 — 索引の無効化と、利用者が見ている診断の更新が接続されていない

**場所:** [server.rb](../../core/lib/ovallsp/server.rb) の `reindex`、`apply_file_summary`、`handle_did_change_watched_files`（509–518、1466–1479、3830–3910行付近）。

開いている `Target#take(x)` と、その利用側 `Target.new.take(1)` を用意しました。宣言を `take(x, y)` へ変更して処理を drain しても、利用側への publish は増えません。同じ利用側を強制再解析すると、初めて `takes 2 arguments, but 1 given` が出ます。解析器は不整合を判断できますが、判断を要求する契機がありません。

RBS でも同様です。`take: (Integer) -> void` を `(String) -> void` へ保存すると、署名環境と summary cache は更新されますが、開いている `take(1)` の診断はそのままです。強制再解析では `expects String here, but Integer is given` が出ます。`probes.json` の `dependent_refresh` と `signature_refresh`。

これは見逃しと古い誤報の両方につながります。利用側が変更されないまま待っていても、更新を保証する後続処理がありません。

### 改善案

summary の依存関係を「キャッシュを捨てる」だけで終わらせず、再解析が必要なファイルをスケジューラへ渡す必要があります。RBS の変更は影響範囲が広いため、開いたファイルを優先し、未開放ファイルはまとめて更新する方針が妥当です。

- **実装の範囲:** 無効化した依存先を診断キューへ渡し、連続変更は URI ごとにまとめます。影響範囲を確定できない RBS 変更では開いた文書を再解析する方法から始め、精密な依存追跡は実測に応じて追加します。
- **確認する条件:** 利用側を編集しなくても、呼び出し先の変更で警告が出て、元に戻すと消えることを Server の通知で確認します。以前は未解決だった名前の追加、宣言の削除、RBS の変更・復元も対象にします。

## R06 — ディスク診断には、古さを拒否する条件がない

**場所:** [server.rb](../../core/lib/ovallsp/server.rb) の `publish_findings`（660–709行）、[workspace_diagnostics.rb](../../core/lib/ovallsp/workspace_diagnostics.rb) の `publish_for`。

バッファの結果には `buffer_id`・version の検査がありますが、`version: nil` のディスク結果は「現在開いていない」だけで通ります。新しい空の診断を publish した後に、古いファイルの警告を送っても受理されます。削除時の `clear_findings` の後でも同じです。`probes.json` の `disk_stale_publish`、`disk_after_clear`。

`publish_for` は解析後に開放状態を再確認しますが、ファイルが削除されたか、同じ URI の内容が置換されたか、その解析世代がまだ有効かを最後の publish へ渡しません。workspace pass と watcher のバッチは別スレッドなので、この到着順は実装上可能です。今回の検証は競合の到着順を部品境界で明示したもので、実時間の発生率の測定ではありません。

### 改善案

**診断のリストとは別に**、解析した文書の同一性、内容または読み取り順、知識の世代を持たせるべきです。空リストからは `Finding#generation` を取り出せないという問題も同じ設計上の欠落です。最後の送信箇所で、削除や新しい解析より古い結果を拒否できる必要があります。クライアント側が診断 version を無視する事実は [CLIENT_BEHAVIOUR](../CLIENT_BEHAVIOUR.md) と実際の `vscode-languageclient` の記述を照合しました。

- **実装の範囲:** 解析開始時の文書識別情報と世代を結果全体に付け、空結果も同じ検査を通します。削除・clear は旧結果を無効にする世代更新として扱い、有効性確認と publish の間に更新が割り込まない所有権を定めます。
- **確認する条件:** 古い警告と新しい空結果、削除と遅延結果、同じ URI の削除・再作成、解析中のファイル開放を順序制御で試します。最新の空結果が正しく古い警告を消す対照も必要です。

## R07 — guard の有効範囲がファイル全体のメソッド名になる

**場所:** [diagnostics/engine.rb](../../core/lib/ovallsp/diagnostics/engine.rb) の `unknown_method_findings` と `RespondToGuardCollector`（113–136、328–366行付近）。

正常な `optional if self.respond_to?(:optional)` は `unknown-method` になります。`self.` を外すと警告が消え、Ruby はどちらも正常に実行します。一方、あるクラスの guard が `absent` を名指しているだけで、同じファイルの別クラスにある無条件の `absent` 呼び出しまで診断が消えます。無関係なクラスを単独で解析すると警告が出ます。

`probes.json` の `explicit_guard`、`bare_guard`、`guard_control`、`guard_leaks` に双方の対照があります。

### 改善案

単に `node.receiver.nil?` を緩めるだけでは、広すぎる免除は残ります。guard を「文字列の名前の集合」で扱わず、receiver の同一性と有効な制御フロー範囲に結び付ける必要があります。024.328 の修正の意図は妥当ですが、その局所修正が別の見逃しと表記差による誤報を作っています。

- **実装の範囲:** まず今回の `if` と後置 `if` について、guard が真である枝の呼び出しだけを免除します。同じ実行文脈の暗黙 receiver と `self` を対応させ、別メソッド・別クラスへ情報を持ち越さないようにします。
- **確認する条件:** guard の内側と外側、真の枝と偽の枝、明示・暗黙の `self`、異なる receiver、別クラスの同名呼び出しを対照にします。正常例の誤報を消しても、無関係な欠落の警告が残ることを確認します。

## R08 — メソッド名にもローカル変数の代入文法を適用する

**場所:** [rename/planner.rb](../../core/lib/ovallsp/rename/planner.rb) の `valid_identifier?`、`reserved_word?`（298–336行付近）。

予約語を拒否するため、`Prism.parse("#{name} = nil")` をメソッド名にも使っています。Ruby の通常の `world!`・`world?` は代入先としては成立しないため拒否されます。Server は `hello → world` を受理し、`hello → world!` と `hello → world?` を拒否しました。`end` を拒否する対照も維持されています。

### 改善案

- **実装の範囲:** 種別ごとの識別子検証へ分け、メソッドには制約した定義・呼び出しの構文を使って検証します。任意の入力を構文断片へ埋め込むだけにせず、解析された名前とノード構造が期待どおりかも確認します。
- **確認する条件:** `world`・`world!`・`world?` への編集を適用して定義と参照が一致すること、予約語・空白・式の混入を拒否することを確認します。setter と演算子は対応範囲を別に定めます。

## R10 — 正しい URI 変換器を作っても、全経路が使わなければ位置情報は壊れる

## 能力と製品計画への批判

### 正しさを優先する規則が、検出できる範囲の拡大を保証していない

`primitive_typo` では `'hello'.uppcase` が Ruby では失敗し、診断は空です。同名の誤りを workspace class に置く `custom_typo` では警告が出ます。`module_typo` も沈黙しました。既知の 024.129、024.106 に関係するもので、新発見としては扱いません。

`missing_keyword` と `extra_keyword` では、Ruby が `ArgumentError` を返す呼び出しに診断が出ません。位置引数の不足を置いた `positional_control` は検出されます。現在の arity 検査が位置引数中心であることと一致します。実装の狭い仕様に照らせば能力不足ですが、第0節が目指す基本的保証には残された仕事です。

`argument-type` も、署名が存在し、実際の型が十分確定する範囲に限られます。型宣言のない Rails コードへ導入したとき、何を検出でき、何が未判定かを測らなければ、「型チェックがある」という機能名だけでは価値を説明できません。全スイートにも同名型・名前空間などの既知の問題を表す pending が残っています。[検証記録](2026-09-05-critical-review/verification.json)に出所を載せました。

#### 改善案

警告件数の増減だけを成果にせず、代表的な利用経路ごとに、正しい検出・誤検出・見逃し・未判定を分けることです。実アプリへ意図的な誤りを入れた対照も使い、誤報を消す修正が単に全体を黙らせていないかを測る必要があります。これはテストを増やすこと自体が目的ではなく、導入によって手書きテストから何を引き取れるかを説明するためです。

まず literal、workspace class、module、キーワード引数の今回の対照を評価集合へ移し、検出可能な条件と未判定の理由を記録します。改善候補は代表アプリでの遭遇頻度と誤報の影響から選び、同じ入力で検出範囲が広がったことを確認してから capability の公開表へ反映します。

### 0.4.0 と 1.0.0 の公開計画には、能力軸との接続が必要

[061](../design/tasks/061-0.4.0-what-this-release-is-for.md) が既に認識している通り、per-check severity、auto-require、activeParameter の公開計画は依存関係を持ちます。現時点の `package.json` に per-check 設定はなく、署名ヘルプは activeParameter を返しません。auto-require の前提である定数から require path への対応も未構築です。これらは開発中の約束であり、今のバージョンの回帰とはしません。

一方、[ROADMAP](../ROADMAP.md) は 1.0.0 を「能力を追加しない」「環境と plain Ruby の保証」と強く表現しています。第0節が定める型・未定義メソッド検出の実用性は、現状で自動的に達成されるものではありません。残る検出範囲をどう改善するか、どれを既知の制限として受け入れるかを能力軸で結び直すべきです。**1.0.0 の準備を、環境別テストの追加だけへ縮めてはいけません。**

#### 改善案

第0節の保証を、利用経路・現状の検出範囲・残る制限・受け入れ条件に対応付けます。0.4.0 の公開機能には必要な依存を記し、準備できない項目は実装前に公開計画を揃えて見直します。1.0.0 には通常の Ruby/Rails コードで満たす能力条件と環境条件を別々に置きます。

代表アプリでの頻度を根拠に、修正するものと既知の制限として受け入れるものを決めます。判断後に ROADMAP・両言語の README・サイト・課題の target を同じ内容へ更新し、計画の整合を確認します。これは本レビューで版の割当てを決定したという意味ではありません。

### Rails を中心に保証するなら、Rails の通常形で検出範囲を示すべき

`before_action` など未読の class-body macro で診断を控えることには誤検出回避の理由があります。しかし 024.304 のように通常の controller で検査対象が大幅に減るなら、単純な閉じた class の G2 だけでは利用者への保証を代表しません。partial locals、concern 由来の ivar、relation 上の model scope も、現在の制限として別に記録されています。

ここではそれらをすべて再現したとは主張しません。文書と実装経路を読んだ上で、通常の Rails アプリの controller・model・view・job ごとの「判定できた範囲」を示す評価が必要だと指摘しています。既知の課題の数を減らすことと、通常の Rails を良くすることを分けるべきです。

#### 改善案

通常の controller・model・view・job と、callback・concern・relation・partial を含む代表 fixture を選びます。それぞれに正常な例と、型やメソッド名を意図的に壊した例を置き、どこで解析を断念したかまで記録します。署名と Agent の有無を揃えた条件で比較します。

未読 macro を一律に既知として警告を再開するのではなく、実測で影響の大きい DSL から必要な意味をモデル化します。変更した機能だけでなく通常の画面編集の流れを通し、誤報を増やさず検出範囲が改善したことを公開保証の根拠にします。

## テスト・再現の記録

### 実行したものと、成功と呼べる範囲

Core の全 RSpec を、固定した複製上で実行しました。実装例の failure はありませんでしたが、**全スイートは green ではありません**。失敗は次の種類でした。

- detached HEAD のため、0.4.0 準備中というブランチ情報を参照する changelog/課題のメタチェックが失敗。
- 検証用に `node_modules` をリンクしたため、ファイル列挙・ホームパス検査がそのリンクを通常のファイルとして扱って失敗。
- 開始時点の未追跡 spec の追加分が、文書上の suite 件数にまだ反映されていないため失敗。作業中の状態として記録し、別の製品不具合には数えていません。

前二つは検証用配置の問題なので、対象ソースが変わっていないことを確認した上で、元の `release/0.4.0` 作業ツリーで該当メタチェックを再実行し成功を確認しました。既知の意味上の pending は、全実行の JSON で個別に記録しています。Rails と capability suite が依存不足で丸ごと skip された実行ではありません。

拡張機能の `npm run test:unit` は compile を含めて成功しました。今回、実 VS Code host の統合テスト、配布 VSIX の生成・インストール、他 OS/Ruby の組合せ、秘密情報の全 Git 履歴スキャン、hunk sweep、pinned mutation の全適用は実行していません。コードを改変する sweep は利用者の作業を保護するため今回のレビューに含めませんでした。

数値と失敗・pending の出所は [verification.json](2026-09-05-critical-review/verification.json) を参照してください。ここでの結果はレビュー時の実行記録であり、以後のツリーの保証値ではありません。

### 再現用ファイル

主な意味解析・更新順序の再現は [probes.rb](2026-09-05-critical-review/probes.rb) と
[probes.json](2026-09-05-critical-review/probes.json) に集約しています。
別途 [overload の再現器](2026-09-05-critical-review/overload-probe.rb) と
[拡張側の再現器](2026-09-05-critical-review/platform-probes.cjs) を添付しました。

再現スクリプトは製品コードを変更しません。模擬ファイルの作成・削除は一時ディレクトリ内に限定しています。`probes.rb` の Ruby 実行も、スクリプト内に書いた合成例だけが対象です。既存アプリケーションを boot したり、任意のプロジェクトコードを評価するものではありません。

```sh
# リポジトリの core/ から、プロジェクトが要求する Ruby を選択して実行
bundle exec ruby -Ilib ../docs/reviews/2026-09-05-critical-review/cache-probe.rb
bundle exec ruby -Ilib ../docs/reviews/2026-09-05-critical-review/probes.rb
bundle exec ruby -Ilib ../docs/reviews/2026-09-05-critical-review/overload-probe.rb
bundle exec ruby -Ilib ../docs/reviews/2026-09-05-critical-review/performance.rb
```

最初の起動では検証用ディレクトリに切り替えたことで OS 付属の古い Ruby を拾い、Bundler の解決に失敗しました。Ruby 3.4.10 を明示してやり直した後の実行だけを結果に採用しています。再現する際も、ディレクトリ変更で別の Ruby に切り替わっていないかを確認してください。

glob と Ruby resolver の対照は、`vscode/` で compile 済みの `out/` を指定します。

```sh
# リポジトリのルートから
node docs/reviews/2026-09-05-critical-review/platform-probes.cjs "$PWD/vscode"
```

これらのスクリプトは現象を表示する再現器であり、失敗を exit code にする回帰テストではありません。修正するときは正常例と反例を suite へ移し、修正前に必要な assertion が失敗することを確認してください。

## 対応順と引き継ぎ

1. **R01 の削除境界を最初に扱う。** 修正の境界は掃除の呼び出し元ではなく、削除・権限変更が実行される場所です。
2. **R02・R03 の編集結果の正しさを保証する。** 返した編集を実際に適用し、構文だけでなく呼び出しの意味が保たれるかを対照にします。
3. **R04–R06 の更新モデルを揃える。** ディスク読み取りの順序、影響を受けるファイルの再解析、最後の publish の有効性を一つの変更契約として考えます。
4. **0.4.0 の診断設定を公開する前に R07・R09 と検出範囲を判断する。** 誤報を減らすだけの大域的な免除で見逃しを隠さないことが必要です。
5. **R15 と能力評価を同じ代表入力で追う。** 速くなったが何も判定しなくなった、という改善を受け入れないためです。
