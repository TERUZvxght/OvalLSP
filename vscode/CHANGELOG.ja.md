# 変更履歴

[English version](CHANGELOG.md)

OvalLSP VS Code拡張機能の注目すべき変更をすべて記録しています。各リリース
はまず「何が変わったか」を示し、その理由・実測値・棄却した方針は下の
**詳細**にまとめてあります。

## 0.1.12 — 書き直され続けた規則と、自分自身を過少申告していたプライバシー一覧

- 修正: `send`・`__send__`・`public_send`・`instance_exec` が、存在しない
  メソッドとして報告されなくなりました。
- 修正: `::User.find(1)` が `User` に解決されるようになりました(`User.find(1)`
  は元から解決されていました)。ルートスコープのモデルレシーバは型を失い、
  Active Record のメソッド検査も黙って無効になっていました。
- 修正: キーワード引数を取るメソッドで、シグネチャヘルプが `()` と表示
  しなくなりました。`Array#shuffle` は引数なしと読めていました。
- 修正: Sorbet の `.rbi` で宣言された、通常の位置引数を取るメソッドに
  対して、シグネチャヘルプが `x:` と入力するよう促さなくなりました。
- 修正: `< ::BasicObject` と書かれたクラスで、未知メソッドの検査が黙って
  無効化されることがなくなりました。0.1.11 と同様、これまで沈黙していた
  クラスが、見逃されていた誤りを報告し始めることがあります。
- 修正: 名前空間付きのクラスが、同名のトップレベルモデルのデータを借用
  しなくなりました。`:company` に委譲した `Admin::User#name` は、
  トップレベルの `User` の関連から答えられていました——型が欠けるのでは
  なく、自信をもって誤った型を返していました。
- 修正: `Widget` の中で `self` と `Widget.new` が同じ型になりました。
  一致していなかったため、その両方が代入される変数は和型になり、未知
  メソッドの検査がそこで沈黙していました。`::Widget.new` も同様です。
- 修正: Active Record のカラム・関連に対する定義ジャンプが、
  `class Admin::Company` と書かれたモデルだけでなく
  `module Admin; class Company` と書かれたモデルにも届くようになりました。
- 修正: Sorbet の `.rbi` で `def f(...)`・`def f(**nil)`・分解代入の
  `def f(a, (b, c))` を宣言したメソッドが、署名を失わなくなりました。
  このリリース内で作り込み、このリリース内で直したもので、公開済みの
  バージョンには含まれていません。
- 修正: `PRIVACY.ja.md` が、型観測の記録内容をすべて記述するようになり
  ました。記載より多くを記録していました——機微な内容ではありませんが、
  プライバシー文書が自分自身を過少に記述しているのは、ずれの向きが
  どちらであっても誤りです。

`docs/PUBLISHING.ja.md` のバージョン規約における patch リリースです。
ケイパビリティは追加していません。

### 詳細

0.1.11 では「owner名は修飾済み」という1つの規則を `SymbolId` に移し、
すべての呼び出し側をそこに通しました。写しは2つ生き残っており、どちらも
`SymbolId` をまったく構築しないためで、症状が出ていたのはそのうち1つ
だけでした。`chain_reaches_root?` は
`entry.name == "BasicObject"` と尋ねており、`< ::BasicObject` と書かれた
クラスは `::` を伴うエントリを生みます。そのチェーンはルートに到達して
いないと判定され、レシーバは「閉じている」とみなされず、検査はそのクラス
について何も言わずに沈黙していました。手で書かれ、片方の綴りだけを見る——
先行する8箇所とまったく同じです。しかも隣のサブシステムの
`ROOT_SUPERCLASS_NAMES` は既に両方の形式を列挙しており、それがこれを
判断ではなく見落としにしています。2つ目の写しは
`Server#find_controller_uri` で、検索の前に `::` を手で付けていました。
実測したところ、この関数の呼び出し側は2つとも既に修飾済みの名前を渡して
おり、そのため誤動作したことはなく、仮に誤っていても何も検出できません
でした。現在は委譲しています——そして正規化そのものを検索側へ移しました。
自分のキーがどういう形をしているかを知っているのは、そこだけだからです。

`send` 系は別の不具合で、`::BasicObject` の修正がそれを差し迫ったものに
しました。RBSは「何でも受け取る」を `(?)` と書き、パラメータ一覧をまったく
持たない関数オブジェクトとして表現します。ここに突き当たる宣言は2種類あり
ます。`Proc#call` と `Method#call` は自身が `(?)` であり、`send`・
`__send__`・`public_send`・`instance_exec` は通常の署名を持ちつつ*ブロック*
が `(?)` です。前者3つの綴りは `?{ (?) -> untyped }`、`instance_exec` は
`{ (?) [self: self] -> U }` で、こちらはブロックが必須かつ self 束縛
付きです。2つの変換側(`TypeConverter` と `Environment`)はどちらも、
そうした関数にかまわず位置引数を
尋ねており、生じたエラーは署名構築を囲む包括的なrescueに飲み込まれ、
メソッドは「署名なし」として返っていました。未知メソッドの検査はこれを「RBSがこのメソッドを宣言していない」
と読みます。その結果、`send` は閉じたレシーバすべてで報告されていました。
差し迫ったものになった理由は、`__send__` がまさに `< BasicObject` と書く
プロキシや委譲のコードで中核的に使われる語法だからです。上の修正は、
沈黙を解いたそのクラス群に対して誤った報告を出すところでした。

プライバシーの一覧は、観測が「class/module名、method識別子、パラメータ
位置、呼び出し回数、呼び出しが例外を送出したかどうか」を記録すると
書いていました。実際にはこれに加えて、各パラメータ位置*で*観測された
クラスの集合、メソッドが返したクラスの集合、メソッドが含まれるファイルの
ダイジェストとその行番号(そのメソッドがその後編集された可能性を検出する
目的にのみ使用)、実行の識別子、および実行の終了時刻を記録します。いずれもあなたのプログラム
の値ではありません——文書が明示するようになった区別は、クラス*名*と
オブジェクトそのものの違いです。`User` は記録されますが、そのユーザーは
記録されません。保証自体は変わっておらず、その保証が何を対象にするかの
一覧が不完全でした。

同じ文書へのもう1つの訂正のほうが、一覧よりも重要です。この文書は
「パースキャッシュ以外ディスクには何も書かない」と述べていました。観測の
実行は一時ファイルを2つ書き、そのうち1つは、あなた自身のテストコマンドの
標準出力と標準エラーがリダイレクトされる先です。Railsアプリであれば
SQLが日常的に含まれます。OvalLSPはそのログを読みも保持もせず、実行終了時に
削除されますが、それが存在する間「ディスクには何も書かない」は真では
ありませんでした。文書はこの2ファイルが何であるかを述べ、旧文が暗黙に
していた線引きを明示しました——「記録しません」という保証は OvalLSP が
抽出して保持するものについてであり、あなた自身のスイートが出力するものに
ついてではありません。

この不足は、このプロジェクト自身のWebサイトを独立に点検した際に見つかり
ました——ただしサイトのほうは、プライバシー文書より多くではなく*少なく*
しか記述していないことが判明しました。どちらも正しくありませんでした。
サイトは、このリリース自身のドキュメント対応表が「この種の変更で古くなる」
と定めるページ一覧に載っており、ここで訂正した2つの主張を今も抱えたまま
です。ディスクに関する記述の誤りは、レビュー担当が文書ではなく観測
ランナーのコードを読んだことで見つかりました。

ラウンド3・4では、このリリースが扱っている当の問題がさらに3箇所見つかり
ました。`::User` は `ModelRegistry` に一致しません。レジストリはRails自身の
修飾なしの `model.name` をキーにしているためです。これを使う5つの
サブシステムにまたがる22箇所(20行)の呼び出し側ではなく、レジストリの
4つの検索メソッド側で正規化しました。0.1.11 がまさにそのために存在します。
`LocalInferencer` も、定数レシーバ・Active Record のクラスレベルfinder・
`is_a?` による絞り込みの3箇所で `::` 付きの Nominal を作っていました。そして `MethodAnalyzer` は委譲元の
owner を*単純名*で照合しており、`Admin::User` がトップレベルの `User` の
関連を借用していました。これとは別に、ラウンド2で `*rest` について直した
シグネチャラベルが、キーワードのみの署名に対しては依然として引数ゼロと
主張していた点も直しています。

ラウンド3はまた、このリリースが自分自身について述べていた誤りを2件捉え
ました。新しく書いたプライバシーの一文は、例外を送出した呼び出しが「何も
寄与しない」と述べていましたが、実際には件数と引数のクラスを寄与し、
伏せられるのは戻り値の型だけです。そしてもう1つ、2つのフィールドは固定
できないとする注記——これは実際には適用されていなかった変異に基づいて
書かれたものでした。どちらも訂正しました。後者は名指ししておく価値が
あります。変異スイープの結果は、その裏にある編集が実際に適用された分の
価値しかなく、今回のそれは無価値でした。

ラウンド5では、同じ規則を手で書いている箇所がさらに2つ見つかり、どちらも
それ以前のラウンドが読んでいたコードの中にありました。加えて同じ系統の
不具合がもう1件ありました。`MethodAnalyzer` は
`::Widget.new` のソース上の綴りからそのまま型を作っており——ラウンド3・4が
`LocalInferencer` で直したのとまったく同じ行が、隣のサブシステムで手つかず
のまま残っていました——さらに `self` には*索引側*の綴りで owner を与えて
いたため、同じクラスの中で `self` と `Widget.new` が別の型になっていました。
どちらも本来1つの Nominal であるべきところに和型を作り、和型こそが未知
メソッドの検査を無効にするものです。どちらも、誰かが報告するような症状は
出しません。検査がただ何も見つけなくなるだけです。

その3件目が、上の定義ジャンプの項目です。`QueryService` はモデルのクラスを
`owner: nil` で `SymbolId` を組み直して探していましたが、owner は*レキシカルに*
記録されます——`module Admin; class Company` は owner `::Admin` で索引され、
組み直したキーはコンパクト形式の `class Admin::Company` にしか一致しません
でした。Agent 由来のカラム・関連から定義へ飛ぶと、通常の書き方をした
モデルすべてで黙って何も返らない状態でした。現在は `WorkspaceIndex` に
修飾名で問い合わせます。このリリースの `find_controller_uri` と同じ手です。

ラウンド5が見つけたRBIの不具合は、二度読む価値があります。これを引き起こ
したのはこのリリース自身だからです。Sorbet の `params(x: Integer)` は
名前と型の対応表でしかなく、`def f(x)` と `def f(x:)` を区別できません。
パーサはすべての項目を必須*キーワード*として記録しており、コメントには
それが「arity照合のためだけ」と書かれていました。キーワードを表示するもの
が無かったため、表には出ませんでした。そこへこのリリースがシグネチャ
ラベルにキーワードを表示させた——その結果、`def combine(x, y)` と宣言された
メソッドが `x:` と入力するようユーザーに指示し始めました。ラベルが不具合
だったのではなく、既にあった虚偽を読める形にしたのです。修正は、その
コメントが先送りしていた当のものです。sig の下の `def` こそが引数の形の
正であり、パーサは元からそのノードを手にしていたので、形は def から、
型は `params(...)` から取るようにしました。これは arity の誤りも両方向で
正します——2引数のメソッドに対する `sig { void }` は、引数を取らないと
主張していました。

このリリースが公表した数値のうち2つが誤りで、どちらも私のものです。
「4つの呼び出し側」はレジストリ側のメソッド数であって呼び出し側の数では
ありませんでした。またキーワードのみの署名の数を29としていましたが、
正しくはメソッド単位で26、オーバーロード単位で数えるなら30であり、29は
そのどちらでもありません。何を数えているかを明示する形に訂正しました——
この数値はもともと「この形が例外的ではなくありふれている」ことを示すため
だけにあり、再現に暗黙の絞り込みを要する数値ではそれを示せません。

ラウンド6では、ラウンド5のRBI修正自体が3つの正当な引数の書き方を壊して
いたことが判明しました。引数の形を `def` から読むということは、Rubyの
引数文法すべてに向き合うということです。`def f(...)`・`def f(**nil)`・
分解代入の `def f(a, (b, c))` は、いずれも `#name` に応答しないノードを
引数リストに置きます。それを尋ねると例外になり、`handle_sig` の包括的な
rescue がそれを警告に変え、そのメソッドの署名はまるごと捨てられていました。
このリリース以前は解析できていた `.rbi` が、それらのメソッドについて
ホバー・シグネチャヘルプ・宣言を出さなくなっていたということです。これは
0.1.12 における唯一の真の退行で、ラウンド5から6の間だけ存在しました。
現在は `...` が両方のrestスロットを開き、`**nil` はキーワード側を閉じ、
分解代入の引数は Unknown 型の位置引数スロットを保ちます。

ラウンド6はこのリリース自身のタイトルも読み、それが誤りであることを
見つけました。「規則の最後の写し」は、残る写しが1つだと考えられていた
時点で書かれたもので、その後のラウンドが次々と追加を見つけていきました。
同ラウンドで帰属の誤りも2件訂正し(ラウンド1の功績としていた
`LocalInferencer` の修正は実際はラウンド3・4、「ラウンド3で2箇所」は
実際は3箇所)、`LocalInferencer` の3箇所を共通のヘルパー経由に変えました。
うち2箇所はバイト等価なリファクタで、残る1箇所はそもそも正規化が無く、
答えを変えられないのはどの利用側も独自に正規化しているからにすぎません。

ラウンド7は、その*差し替えたほうの*タイトルを反証しました。「残る写しを
すべて」は1日ももちませんでした。grep をかけると、規則のどちらかの向きを
手で書いた箇所がツリーに10箇所残っており、そのうち1つ——`ModelRegistry` の
`lookup_key`——はこのリリース自身が書いたものでした。4箇所は
レキシカル修飾メソッドのバイト単位で同一の写しで、`ParserService`・
`LocalInferencer`(2箇所)・`RbiParser` にありました。そこでタイトルからは
数の主張を外し、`Index::SymbolId` が3方向すべて——`qualify_owner`・
`bare_name`・`qualify_within`——を所有する形にしました。10箇所すべてが
そこへ委譲します。`ReceiverResolution.canonical_receiver_name` も同様で、
その旧本体こそ一行コピーの1つでした。挙動は変わっていません——統合を通して
1275 examples が緑のままでした。それこそが要点です。これらの写しは誤って
いたのではなく、誤りになるのを待っていただけです。

ラウンド7はまた、このリリースが公表した5件目の誤った数値も見つけました。
「21箇所の呼び出し側」は私が書いたもので、しかも「4つの呼び出し側」を
訂正した次のラウンドでの誤りです。正しくは20行にまたがる22の呼び出し式
です。そして数値の誤りより価値のあるものも見つかりました。私自身が
「観測不能」と断じた正規化箇所の1つが、実際には観測可能だったのです。
`k = ::Widget` の `k` にホバーすると `ClassOf[::Widget]` と表示され、
`k = Widget` では `ClassOf[Widget]` でした——どのテストにも見えない、
ユーザーに見える差です。現在は固定済みで、`class_declarations` の未テスト
だった `module` 分岐も併せて固定しました。逆に2行は固定ではなく削除
しました。到達不能な nil ガードと、両腕が同じ文字列を返す三項演算子です。

  メソッドとして報告されなくなりました。
- 修正: ルートスコープの定数参照(`::JSON`・`::Rails`)が、解決不能として
  報告されなくなりました。
- 修正: `include ::SomeModule` と書かれたクラスでは、未知メソッドの検査が
  黙って無効になっていました。有効になったため、これまで見逃されていた
  誤りが新たに報告されることがあります。
- 修正: コア class を再オープンして追加したメソッド
  (`lib/core_ext/object.rb` など)が、定義に解決され、補完に出て、未知
  メソッドとして報告されなくなりました。そこに private で定義したものは
  補完に出ません。
- 修正: 2つのスレッドが同時に送信した際に、あるメッセージの
  `Content-Length` が別のメッセージの本体の前に出ることがあった問題を

### 詳細

はじめの2つは、この検査が出してはならない種類の報告——動作するコードへの
報告です。署名環境は*修飾済み*の名前を解決しますが、そこに届く名前は
両方の形で来ます。`HierarchyIndex` はクラス*自身*の祖先エントリを修飾済み
(`::Widget`)で返し、継承したものは修飾なし(`Object`)で返します。
一方、定数参照はソースに書かれたままの形で届きます。正規化せずに `::` を
付け足すと `::::Widget` を問い合わせることになり、何にも一致しません
でした。Rubyにメソッドを書かずRBSでクラスを記述するのは通常の運用であり、
`::JSON` も通常のRubyです。どちらも報告されていました。

この規則はコードベース全体で8箇所に書き写されていました。うち3箇所は
逆に書かれており、さらに規則が必要なのに書かれていない箇所が2つ——
インデックスとメソッド解決側——最初の修正のあと、レビューで見つかりました。

現在は `SymbolId`——owner とは何かを知っている当のもの——に1度だけ書き、
他のすべてはそこに委譲します。ここには一言にする価値のある教訓があります。
呼び出し側ごとに書き写された規則はいつかどこかで書き間違えられる規則であり、
「何箇所が誤っていたか」を数えたことが、まだ誰も報告していなかった残りを
見つける手がかりになりました。

2つ目は、バックグラウンドスレッドから診断が再送されるとき——Runtime Agentが
利用可能になる、再起動する、ルートやモデルが再取得される、保留していた
祖先の回答が届く——にディスパッチスレッドがリクエストに応答していると
発生しえました。フレームは2回の `write` として
書き出され、両者を直列化するものが何もなかったため、あるメッセージの
ヘッダが別のメッセージの本体の前に出ることがありました。これは
クライアントが復帰できない唯一の framing エラーです——推測で再同期する
しかありません。

フレームは現在、直列化され、かつ1回の呼び出しで書き出されます。これは
別々の要件です。直列化はミューテックスが担い、書きかけのフレームが
クライアントから観測されないようにします。1回の書き込みはミューテックス
では得られないほうを担います——`Thread#kill` に対する防御にはならず、
終了時の join はまさに送信するスレッドを kill するからです。

### 詳細

クラスの再オープンは、そのクラスを定義するコードと構文上まったく同じ
です。したがってファイルをいくら読んでも区別はできません — 代わりに
Runtime Agentに問い合わせます。答えはそのクラスの実際の祖先で、同じ
プロセス自身の`Object.ancestors`を基準に測るため、`Object`に何かを混ぜて
いるアプリケーションが自分で基準を較正します。クラスがまだ読み込まれて
いない場合は、autoloadの登録元で答えます。アプリケーション自身のクラス
ならワークスペース配下の絶対パス、gemのクラスならgemが書いたままの素の
requireパスです。

この問い合わせは、レシーバだけでなく継承チェーン上のワークスペースが宣言
したクラスすべてに対して行います。これが最も多いケースに届くための条件
です。`ActiveSupport::TestCase`を再オープンすると、その名前はワーク
スペース自身のものになるため、`class FooTest < ActiveSupport::TestCase`
はいずれも「完全に見える」継承チェーンを引き継ぎます。

この判定のために何かを読み込むことはありません。autoload登録済み定数への
`const_get`は読み込みを実行してしまい、実際のアプリケーションではbundle外
のgemから`Gem::LoadError`が発生しました。Runtime Agentが存在しない場合 —
信頼されていないワークスペース、Railsアプリでないプロジェクト — の挙動は
従来どおりです。

`Object.const_source_location`を最初に試しましたが、この問いには答えられ
ません。返すのは定数が**登録された場所**であり、Zeitwerk管理下の`app/`の
クラスはすべてZeitwerk内部の1行を指します。この方針では
`ApplicationController`をアプリ外のクラスと判定し、アプリケーション全体で
検査を黙らせていたはずです。反証と、棄却した他の2案、そしてこの方針でも
なお取りこぼすケースは
`docs/design/tasks/024-deferred-review-findings.md`(024.R5)に記録して
あります。

### 詳細

`before_action`の推論は、継承、`skip_before_action`、リテラルの
`only:`/`except:`セレクタ、コールバックからアクションへの型の流れを
カバーします。opt-inのruntime観測は、他にUnknownとなる戻り値に対する低
優先度のフォールバックとしてのみ使用します。

## 0.1.4 — 「Payload hash mismatch」の誤警告を実際に修正

- 修正: 起動のたびに出ていた「Payload hash mismatch」警告。0.1.3はこれを
  試みて成功していませんでした。
- 追加: `scripts/verify-packaged-payload-hash.js`。`release.sh`とCIに
  組み込み、同じ乖離が二度と利用者に届かないようにしました。

### 詳細

下記の0.1.3の診断(`vsce publish`が自身のprepublishフックを再実行し、
native extensionを再ビルドしていた)は実在の問題であり修正済みのままです
が、この警告の原因では**ありませんでした**。

実際の原因: `scripts/copy-core.js`はステージングした`core/`ツリー(815
ファイル)に対してsha256を記録する一方、`.vscodeignore`が独立して
`core/vendor/bundle/ruby/*/cache/**` — 4つのBundlerの`.gem`アーカイブ —
をVSIXから除外していました。したがってインストール済みの拡張機能は常に
811ファイルであり、起動時に再ハッシュしても記録されたハッシュを再現できる
ことは、どのマシンでも決してありませんでした。「payloadとは何か」の定義が
2つ独立に存在し、静かに食い違っていたのです。実際にインストールされた
0.1.3を再ハッシュし、ステージングツリーとパッケージ済みツリーを比較して
確認しました。

ハッシュ側にパッチを当てるのではなく構造的に修正しました。これらの
キャッシュアーカイブはステージング時に削除します(純粋なビルド副産物です。
`bin/ovallsp`は`$LOAD_PATH`に`**/gems/*/lib`しか追加せず`cache/`は決して
追加しません)。これによりステージングツリー**そのもの**が出荷ツリーと
なり、ハッシュを取ることに意味が生まれます。`.vscodeignore`の該当ルールは
削除し、`core/**`をこれ以上除外しないよう注記を残しました。

新しい検査は**パッケージ済み**VSIXを再ハッシュし、そのVSIX自身のmanifest
と比較します — 拡張機能が起動時に実行するのと同じ検査を、ビルド時に実行
します。古い`.vscodeignore`のルールを一度戻して検査が失敗することを確認
し、元に戻して通ることを確認済みです。

## 0.1.3 — 修正: `vsce publish`が検証済みビルドを公開せず拡張機能を再ビルドしていた

- 修正: Marketplaceに届いていたのが、直前にsmoke testしハッシュを取った
  ビルドではなく、再ビルドされた未検証の成果物だった問題。
- **訂正:** このリリースは「Payload hash mismatch」の誤警告も修正したと
  考えて公開されました。実際には修正できていません — 実際の原因は0.1.4を
  参照してください。

### 詳細

`vsce publish`は、先行する`npm run package`とは独立に自身の
`vscode:prepublish`フックを実行します。つまりCoreのvendoring済みnative
extension(Prism、RBS)を静かにもう一度ゼロから再ビルドします。native
extensionのコンパイルは実行ごとにバイト単位で再現可能ではないため、実際に
Marketplaceへ届いていたのは、直前にビルドしsmoke testしハッシュを取った
成果物では決してありませんでした。

すでにビルド済みのVSIXファイルを`vsce publish --packagePath <file>
--pre-release`で公開することで修正しました。end-to-endで検証済みです。
この変更後は、ビルドのディスク上のpayloadハッシュがpublish手順によって
変化しないことを証明できます。変更前は同じ手順で2つの異なるハッシュが
生成されていました。

## 0.1.1 — 修正: 公開されたVSIXに同梱Core Serverが入っていなかった

- 修正: 公開された0.1.0のVSIXには`core/`ディレクトリがそもそも存在せず、
  Core Serverを起動できなかった問題。

### 詳細

0.1.0は`vsce publish`を直接実行して公開されましたが、このコマンドは本
プロジェクト独自の`npm run package`ラッパー経由でない限りCore Serverの
vendoring(`vscode/scripts/copy-core.js`)を自動では行いません。
`vscode:prepublish`のnpmスクリプトを追加することで構造的に修正しました。
これは`vsce package`/`vsce publish`のどちらも、どのように呼び出されても

起こり得なくなりました。
