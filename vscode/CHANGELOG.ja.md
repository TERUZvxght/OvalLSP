# 変更履歴

[English version](CHANGELOG.md)

OvalLSP VS Code拡張機能の注目すべき変更をすべて記録しています。各リリース
はまず「何が変わったか」を示し、その理由・実測値・棄却した方針は下の
**詳細**にまとめてあります。

## 0.2.1 — 誤報を減らし、すでに公開していた約束に追いつく

新しく覚えることはありません。このリリースは、エンジンが事実でないことを
言う回数を減らすことと、サイト・README・ケイパビリティ表が約束していながら
ビルドがやっていなかった箇所を埋めることに費やしています。

- 修正: レシーバが `]` や `)` で終わる呼び出し — `[widget].each`、
  `handlers[:on_save]&.call` — が未知のメソッドとして報告されていました。
  レシーバを1文字内側の位置で引いていたため、レシーバ自身の最後の要素が
  返っていたためです。Ruby 3.4.7 の標準ライブラリ、Rails 8.1.3 の5つのgem、
  minitest 6.0.6 に対する計測で、**未知メソッドの報告 3,747件のうち 1,656件が
  消えました**。新たに出るのは4件で、いずれも別に記録済みの事例(024.13)です。
  実在のRailsアプリケーションでは、両ビルドの報告は完全に一致します。
  (この項目はリリース最終日まで「3,362件のうち1,556件」と書いていました。
  4コミット前に、しかも別のminitestに対して計測した数字で、測り直すと総数が
  動きました。消えた集合と、新たに出る4件は動きませんでした。)
- 修正: モデルやコントローラのクラス本体で `delegate`、`class_attribute`、
  `mattr_accessor`、`thread_mattr_accessor`、`concerning`、`deprecate` が
  未知のメソッドとして報告されていました。Runtime Agent がクラスメソッドを
  `base.methods - Object.methods` として読んでおり、`Object` 自身がクラス
  オブジェクトであるため、`Module` が定義するものがすべて引かれていました。
  scaffold したアプリケーションで5件の誤報がありましたが、いまは0件です。
- 修正: コアクラスと同名のワークスペースのクラスが、コアクラスの代わりに
  答えることがなくなりました。自作の `Serializer::Elements::String` が
  リテラルの生む `String` の代わりに立っていたため、`"hello".upcase` が
  未知と報告される一方、同じ位置のホバーは `upcase() -> String` と答えて
  いました。
- 修正: 構文が壊れているファイルには、構文エラーだけを出すようにしました。
  メソッドの末尾で `.` を打つと `a.end` が呼び出しとして解釈され、クラスに
  `end` というメソッドがないと報告していました — もっともよくある編集操作に
  対してです。もう半分は直っていません。`a.` の次の行が `b = "str"` の場合は
  `a.b =` として正しく解釈されるため、そのまま報告されます。
- 修正: `Range` と `Regexp` のリテラルに型が付きました。`(1..10).` は何も
  補完せず、`/abc/` のホバーは空のポップアップを返していました。リテラルの型を
  約束するケイパビリティ行に反していました。
- 変更: `A` と打った時点で候補が出ます。0.2.0 ではワークスペースのクラスが
  並ぶまでに2文字必要で、それはサイトが例として挙げていた場面そのものでした。
  外す前に計測したところ、この下限が買っていたのは1打鍵あたり 0.4ms でした。
  実在のアプリケーションでは `A` の候補が2件から14件になり、ローカル変数は
  依然としてどのクラスより上に並びます。
- 追加: レシーバを書かない呼び出しにホバーが答えます。自分のコントローラの
  `article_params` は空のポップアップを返していました。定義へ移動と
  シグネチャヘルプは 0.2.0 でこの読み方を得ていて、ホバーだけが得ていません
  でした。
- 追加: シグネチャヘルプが、カーソルのある引数を示します。これまでは
  パラメータを並べるだけでどれを書いているかを言わなかったため、エディタは
  呼び出し全体で常に最初のパラメータを強調していました。最初のカンマから先は、
  何も指していないのではなく、間違ったパラメータを指していたことになります。
- 修正: **アップグレードで上記の修正が実際に届くようになりました。** parse
  キャッシュのキーはworkspace・Ruby・Prism・`Gemfile.lock`・RBSでしたが、
  OvalLSP自身のバージョンが入っていませんでした。キャッシュの中身は特定の
  ビルドのパーサが出した結果なので、バイトの変わっていないファイルには前の
  リリースの結果が返り続けていました。再起動でも `Re-index Workspace` でも
  消えない誤報が1件、実際に残っていました。使われなくなったキャッシュ
  ディレクトリの掃除も入れました(直近8つを保持)。これまで一度も回収されて
  いませんでした。
- 修正: ホバー・定義へ移動・シグネチャヘルプが、呼び出しでないものについて
  メソッドを答えることがなくなりました。コメントや文字列の中の語、`def` の
  引数名、メソッドと同名のローカル変数にカーソルを置くと、そのメソッドの
  署名・出自・「Defined:」リンク・docコメントが出ていました。そこでRubyが
  解決するのはスコープ内のローカル変数であり、いまはそれが返ります。
- 修正: 前の引数の文字列やコメントの中に対応の取れていない括弧があっても
  (`raise ArgumentError, "bad )"` など)、シグネチャヘルプが消えなくなり、
  内側の呼び出しを答えることもなくなりました。
- 修正: `activeParameter` が標準ライブラリやgemのメソッドでも効きます。
  エディタが強調するのに必要なパラメータ一覧を持っていたのは自分で書いた
  メソッドだけだったため、`"abc".sub(` ではカーソルを動かしても何も
  強調されませんでした。ルートヘルパー末尾の `options = {}` も対象です。
- 修正: コアクラスと最後の区切りを共有するワークスペースのクラス
  (`Serializer::Elements::String`)が、**補完でも**コアクラスの代わりに
  答えることがなくなりました。0.2.1 は診断だけ直してこちらを残しており、
  `"hello".` はそのクラスのメソッドを出し、Stringのメソッドを1つも出して
  いませんでした。
- 追加: 出現箇所のハイライト。識別子にカーソルを置くと、同じファイル内の
  他の使用箇所が印されます。無いあいだエディタは語を文字列として一致させて
  いたため、`@articles` は `# GET /articles` というコメントの中の `articles`
  を光らせ、ローカル変数 `article` はすべての `@article` を光らせていました。
- 追加: `@` の後の補完。打っても何も出ないため、エディタがバッファ中の語を
  代わりに提案していました — シジルの付かないインスタンス変数名です。いまは
  スコープ内のインスタンス変数が、推論された型とともに出ます。
- 修正: `->() {}`・`!x`・`a && b`・`a || b` に型が付きました。
  `name || "anonymous"` と書いた既定値は、何も分からない値ではなくStringです。
- 修正: **名前が `!` や `?` で終わるメソッドにも答えるようになりました。**
  ホバー・定義へ移動・シグネチャヘルプのいずれも名前を `!` で読み終えて
  いたため、`@article.destroy!` は空のポップアップ、F12 は「定義が見つかり
  ません」、`(` を打ってもパラメータが出ませんでした。`save!`・`valid?`・
  `update!` — Railsのコントローラがほぼそれで出来ている名前です。補完は
  その間ずっとそれらを出していました。
- 修正: 配列リテラル・ブロック・ラムダ・括弧付きの引数の後で、シグネチャの
  ポップアップが間違ったパラメータを太字にしなくなりました。`%w(...)` や
  `puts (1)` の後で消えることもなくなりました。
- 修正: 大きなファイルでのシグネチャヘルプ。「ここにシグネチャは無い」と
  答えるのにファイルを1文字ずつ走査しており、数百KBで非ASCII文字が1つでも
  あると数秒かかっていました。Coreは要求を1つずつ処理するので、ホバーも
  補完も診断もその後ろで待っていました。
- 修正: まだ書き途中の引数の中にカーソルがあるとき(`create(tags: [1, |2],`)、
  シグネチャのポップアップが消えなくなりました。囲む呼び出しが無い位置で、
  前の行の呼び出しを答えることもなくなりました。
- 修正: 名前が `!` や `?` で終わる `def` や `def self.` の引数リストの中で、
  シグネチャのポップアップが出なくなりました。宣言しているメソッド自身を
  答えていました。

### 詳細

6つのケイパビリティ行が PASS と読める一方、その例は行の約束より狭いことしか
検証していませんでした。1行(`C7`)は、約束したものに一致しえない接頭辞を
要求していました。7件とも、いまは書いてあることと試していることが一致します。

`024.14` — 「プロジェクト全体の診断がE2Eでは何も出さない」として記録されて
いたもの — は再現しません。実在のRailsアプリケーションでは、一度も開いて
いないファイルがプロセス起動から 1.35秒 で答え、42のURIが発行されます。
0.2.0 が付けずに出したケイパビリティ行と例が、いまはあります。

このリリース中、コーパスの計測が3回、自信に満ちた誤りを出しました。書き込み
途中のファイルを差分にかけたもの、異なるコーパス同士を比べたもの、そして
複合コマンド中の `cd` が残って両側が同じビルドを走らせたものです。いずれも
記録してあります。3つ目を捕まえたのは、数字の読み直しではなく、すでに失敗を
確認していたテストでした。

### 詳細

前置きなしの補完は、その大部分が*順位付けと打ち切り*の問題であり、
レシーバ経由の補完とは別種の問題です。レシーバがあれば答えは1つの型の
メンバに絞られますが、前置きなしの場合ははるかに多くに一致します。
アルファベット順に並んだ千個の候補を渡されたエディタは、何も渡されない
エディタより悪い——正解は4ページ目にあり、ユーザーはそのキーを押すのを
やめることを学びます。順序はカーソルからの近さです。ローカル変数、
self上のメソッド、ワークスペースの定数、Kernel の順で、これを `sortText`
に書き出します。エディタが実際に並べ替えに使うのはそちらだからです。
1文字の場合は前の2つだけを返します。残りの2つはその長さでは事実上
すべてに一致するためです。一覧は上限で打ち切り、`isIncomplete` を返す
ので、入力が絞られるにつれてエディタが再度問い合わせます。

ワークスペース全体の診断はバックグラウンドスレッドで走り、バッファで
開かれているファイルには一切答えません(それらはバッファの版と未保存の
内容を知っている経路の担当です)。また、世代が更新された走査はファイル
単位で中断します。既に古いと分かっている結果を出し切ることには意味が
ないからです。走査は、答えがワークスペース全体で変わりうるたびに再実行
されます。とりわけ重要なのは Runtime Agent が利用可能になったときで、
未知メソッドの検査は Agent なしでは推測せず保留するため、これまでは
開いていないファイルすべてが Agent 到着前の答えのままでした。

新しい2つの検査は、引数の個数の検査と同じ基準で作られています——動作する
コードに対する誤った報告は、検査がないことより悪い。引数の型は、期待型が
*明示*されている場合(RBS/RBI の宣言で、オーバーロードが1つだけ、`*rest`
なし)にのみ比較し、しかも期待型と推論された型の両方が具体クラスで、
継承関係がないときにのみ報告します。RBS の `int`/`string`/`boolish` は
除外しています。これらはクラスではなく「変換できる何か」を意味するため
です。`@ivar` の検査はビューに限定しました。ビューはコントローラの
アクションとコールバックチェーンが代入するものをそのまま受け取ります。
この検査の安全性は「文脈を確立できなかった」と「アクションが何も代入
しない」の区別に懸かっており、前者では何も報告しません。

セマンティックハイライトは、パーサだからこそ決着でき正規表現には決着
できないものだけを報告します——ローカル変数の読み取りとレシーバなしの
呼び出しの区別、インスタンス変数、パラメータ、定数です。キーワードや
文字列、数値は塗り直しません。文法定義が既に正しく扱っており、そこに
食い違う2つ目の意見を加えても、ちらつくだけだからです。パースできない
ファイルには何も返しません。半分だけ返すと、入力するたびにハイライトが
剥がれ落ちるように見えるためです。

ドキュメントはソースから読みます。元々そこにあるものであり、コメントを
索引化する仕組みは持ちません。補完では一覧に載せず
`completionItem/resolve` を経由します。候補すべてについてソースを読むのは
1項目あたり1ファイル読み込みであり、ユーザーがドキュメントを見るのは
多くても1つだけだからです。

## 0.1.15 — クラスボディの修正を、修正する

0.1.14 は誤報告を約12,000件取り除き、同時にいくつか持ち込みました。本
リリースはその後始末です。公開済みのコードに対する2つの独立レビューが
見つけ、同じ計測手順で直しました。

- 修正: ワークスペースが `Object` や `Module` に追加したメソッド(Rails では

## 0.1.14 — `private` は未定義メソッドではない

- 修正: クラスボディに書かれた `private`・`protected`・`public`・
  `attr_reader`・`attr_writer`・`attr_accessor`・`private_constant`・
  `alias_method`・`module_function`・`define_method`・`include`・`extend`
  が、未定義メソッドとして報告されなくなりました。これらは `Module` の
  メソッドであり、クラスボディの暗黙のレシーバはそのクラスだからです。
- 修正: `attr_reader`・`attr_writer`・`attr_accessor` が定義するメソッドが、
  未定義メソッドとして報告されなくなりました。これらは宣言として記録されて
  おらず、祖先が完全に既知のクラスでは属性リーダーがことごとく「存在しない」
  と読まれていました。

`docs/PUBLISHING.ja.md` のバージョン規約における patch リリースです。
ケイパビリティは追加していません。既に「動く」と謳っていた機能から誤った
報告を取り除くものです。

### 詳細

欠けていたものが2つあり、どちらか一方だけでも報告は出ていました。

`HierarchyIndex#ancestors(singleton: true)` は継承鎖をたどって止まって
おり、クラスオブジェクトが「何であるか」——`Class` であり、`Module` で
あり、`Object` である——を末尾に付けていませんでした。そのため
`Module#private` は探索対象の鎖に入っていませんでした。インスタンス側は
以前から `Object, Kernel, BasicObject` の末尾を持っていましたが、
シングルトン側には何もなかったのです。モジュールの末尾は同じ並びから
`Class` を除いたものです。`superclass` がクラスには答えてモジュールには
答えないのは、これが理由です。親が解決できない場合
(`class Widget < Struct.new(:a)`)は引き続き末尾を付けません。鎖の途中が
不明なのに「`Class` で終わる」と言うのは、完全に把握できていると主張する
ことになるためです。

2つ目はパーサ側です。1つのフラグが2つの問いに答えていました——「ここでの
修飾なしの `def` はシングルトンメソッドを宣言するか」(真になるのは
`class << self` の中だけ)と、「ここでの `self` は Class/Module オブジェクト
か」(クラスボディ直下や `def self.x` の中でも真)です。レシーバなしの
呼び出しは前者の答えを使っていたため、クラスボディの `private` は
*インスタンス*側の鎖に対して解決され、そこには存在しませんでした。この2つ
の問いは分けて追跡するようにしました。

`attr_reader :name` は `def name` と同じくメソッドを宣言しますが、索引は
呼び出ししか記録していませんでした。クラスボディのモデル化が誤っている間は
これが隠れており、`define_method` のボディを正しく読むようにしたことで
Thor の `attr_accessor :options` で表面化しました。したがってこれは注記では
なく本リリースの内容として直しています——修正が、それまで無かった報告を
利用者に渡してはならないからです。動的な引数(`attr_reader(*names)`)は
引き続き何も記録しません。そこで推測すると、存在しないかもしれないメソッドを
宣言したうえ、本物の報告を黙らせることになります。`class << self` の中では
シングルトンメソッドとして宣言し、開いている可視性セクションは `def` と
同じように適用されます。

`scripts/corpus_diagnostics.rb` での実測。このリポジトリ自身の `core/lib`
では `unknown-method` が **60件から4件**へ、ActiveSupport 8.1.3 では
**785件から265件**へ(このエントリを出荷した時点ではこの2つの「before」が
誤っており、別ツリーの値でした。0.1.15 で同一コーパスに対して測り直し、
訂正しています)、Ruby 3.4.7 の標準ライブラリ全体では
**15,982件から3,848件**へ減少します。そして**標準ライブラリのどこにも、
新たに増えた報告は1件もありません**。目的は「事実でないことを言うのを
やめる」ことなので、重要なのはこちらの数字です。副次的に、誤った
`argument-count` は36件→13件、誤った `unknown-route-helper` は48件→8件に
減ります。宣言に解決できる名前は、もう推測されないためです。

これらの残差は別の欠落として追跡しています。024.19 の引数型フォールバックと、
空のルート表が「そんなルートはない」と答える件(024.24)です。後者は本
リリースで減りはしますが、直ってはいません。

エンジンにはこの一覧のうち1つの名前だけが既に特例化されていました。`new`
です。そのコメント自身が「Class/Module の鎖を誰もモデル化していない」と
書いていました。その特例は不要になりました。ここに並ぶ名前はRubyのもので
あって、このプロジェクトが抱えて維持する一覧ではありません。

## 0.1.13 — 索引はワークスペースに答える、編集履歴にではなく

- 修正: 定義ジャンプ・find references・rename・シグネチャヘルプ・
  `workspace/symbol` が、「最後にどのファイルを編集したか」で答えを変える
  ことがなくなりました。複数ファイルで宣言されたクラス——再オープンされた
  モデル、関心事ごとに分割されたコントローラ、1つの名前空間の2通りの綴り
  ——は、そのいずれかを再索引するたびに宣言の順序が入れ替わっており、これら
  の機能はいずれも先頭の1件を取るか、一覧を打ち切ります。

ケイパビリティは追加していません。

### 詳細

`WorkspaceIndex` は再索引時にそのuriのエントリを削除して新しいものを末尾に
追加するため、ファイルの宣言は自分が属するすべてのリストの末尾へ移動して
いました。無関係なファイルで1文字入力するだけで十分です。修飾なしの `User`
が `Admin::User` に解決されたり `Api::User` に解決されたりし、祖先チェーンと
未知メソッドの検査がそれに追随しました。いま見ていたファイルのクラスが、
打ち切られた `workspace/symbol` の結果から落ちました。シグネチャヘルプは
再オープンされたメソッドについて別の定義側の引数を表示しました。読み出し側は
少なくとも11箇所あり、いずれも順序を持たない保存構造の `.first` を取るか、
それを打ち切っていました。「少なくとも」と書くのは、この数を2度数え違え、レビューでさらに
増えたからです。それこそが、読み出し側ではなく保存側を直す理由です。

0.1.12 はこれを4回直そうとし、毎ラウンド読み出し側を1つずつソートして、
2つの退行を出したうえでスレッドごと巻き戻され、`024.15` として記録されました。
現在、順序は保存側にあります。エントリのリストは書き込み時に uri 順、次に
ソース位置順で並べられ、クエリが単純名の索引を読む唯一の箇所が修飾名・種別・
所有者で並べます。1つのクラスは書き方の数だけそこに登録され、それらは名前を
共有するからです。
`workspace/symbol` のランク付けは完全一致優先の規則を保ったまま末尾のキーを
得ました。結果が打ち切られる以上、索引順で決まるタイは「どのシンボルが生き
残るか」を変えるからです。

再索引で退行しうる例はすべて再索引を通ります。それがこの欠陥の住む状態で
あり、これまでの4回の試行がいずれも通さなかった状態です。ただしそれだけでは
不十分でした。`workspace/symbol` の末尾キーは、8ファイルすべてが1つのクラスを
宣言する再索引フィクスチャの陰で未固定のまま出荷されており、`replace_file` が
既に並べているエントリのリストしか動かしていなかったのです。この部分が担って
いるのは*別々の*シンボル同士のタイであり、それには専用のフィクスチャが要ります。
その後さらに3つ、同じやり方で見つかりました。ファイル名の順と行番号の順が
一致していてキーのどちらか片方だけで満たせたもの、1つの名前を2ファイルに置いた
——つまり単一のシンボルなので、書かれた目的である走査を一度も通らないもの、
そして最初に挿入したファイルを再索引していて、偶然正しい答えに着地するものです。

併せて見つかったテスト側のギャップが2件。いずれもユーザーには見えません。

ケイパビリティE2Eスイートは、41例すべて(42行を覆い、うち1行は対になって
います)をスキップしても exit 0 になりえました。`docs/EXTENSION_CAPABILITIES.md` は「スキップされた行のケイパビリティ
は出荷していない」と定めていますが、CIはreal-Rails統合スイートについてしか
それを強制しておらず、`capability_coverage_spec.rb` はスペックファイルの
ソーステキストを読むため結果を見られません。現在は両方を検査します。

そして拡張機能で最大のモジュールである `extension.ts` は、どのワークフロー
でも実行されない統合スイートにしか覆われていませんでした。ユーザーに見える
判断を2つ、`vscode` を import しないモジュールへ移しました——クライアントが
どのファイルに接続するか(Rubyは言語id、ERBは拡張子。VS Codeが `.erb` に

**RBS と RBI の署名。** RBSは「何でも受け取る」を `(?)` と書き、パラメータ一覧を
まったく持たない関数オブジェクトとして表現します。ここに突き当たる宣言は2種類
あります。`Proc#call` と `Method#call` は自身が `(?)` であり、`send`・
`__send__`・`public_send`・`instance_exec` は `(?)` の*ブロック*を持ちます——
前者3つの綴りは `?{ (?) -> untyped }`、`instance_exec` は
`{ (?) [self: self] -> U }` で、こちらはブロックが必須かつ self 束縛付きです。

位置引数を尋ねており、生じたエラーは署名構築を囲む包括的なrescueに飲み込まれ、
メソッドは「署名なし」として返っていました。未知メソッドの検査はこれを

`< BasicObject` と書くプロキシや委譲のコードで中核的に使われる語法なので、上の
`::BasicObject` の修正は、沈黙を解いたそのクラス群に対して誤った報告を出すところ
でした。

restスロットだけを受け取るものが106個あります。現在はどちらも表示されます。

コメントには「arity照合のためだけ」と書かれていました。キーワードを表示するものが

sig の下の `def` こそが引数の形の正であり、パーサは元からそのノードを手にして
いたので、形は def から、型は `params(...)` から取るようにしました。その最初の

(`::Widget`)で返し、継承したものは修飾なし(`Object`)で返します。
一方、定数参照はソースに書かれたままの形で届きます。正規化せずに `::` を
付け足すと `::::Widget` を問い合わせることになり、何にも一致しません
でした。Rubyにメソッドを書かずRBSでクラスを記述するのは通常の運用であり、
`::JSON` も通常のRubyです。どちらも報告されていました。

逆に書かれており、さらに規則が必要なのに書かれていない箇所が2つ——
インデックスとメソッド解決側——最初の修正のあと、レビューで見つかりました。

別々の要件です。直列化はミューテックスが担い、書きかけのフレームが

終了時の join はまさに送信するスレッドを kill するからです。

なら、その接続断は私たちのものです。世代が更新済みの場合も停止扱いです。

`Hash` と `Set` を持たないため、この修正が名前に冠している2つの型に関しては
それは理由になりません。

目に見える変化として1つ挙げておきます。複数の型を取りうる値が、コンテナの
メンバーを正直に数えるようになりました。`x = flag ? User.new : []` に続く
`x.name` は、レシーバが持たない可能性のある呼び出しなので、参照検索に
現れなくなり、リネームでも書き換えられません。0.1.7 はこれを一覧に含めて
いましたが、それは `[]` の分岐を無視した上でのことでした。

レシーバしか理解しないため、コンテナクラスに対するワークスペース自身の
宣言が、コンテナの値からは見えていませんでした。これは以前からそうでしたが、
今回の変更でその状態に到達する頻度が上がるところでした。リゾルバは、ジェネリックなレシーバを
「それが総称しているクラス」として読むようになりました。ただし `Relation`
と `CollectionProxy` は除外します。これらは誰かが宣言するクラスではなく
Active Record の「形」の名前であり、クラス名として読むと
`Model.where(...)` のレシーバが、ワークスペースが偶然 `Relation` と名付けた
クラスへ解決されてしまうためです。

### 詳細

クラスの再オープンは、そのクラスを定義するコードと構文上まったく同じ
です。したがってファイルをいくら読んでも区別はできません — 代わりに
Runtime Agentに問い合わせます。答えはそのクラスの実際の祖先で、同じ
プロセス自身の`Object.ancestors`を基準に測るため、`Object`に何かを混ぜて
いるアプリケーションが自分で基準を較正します。クラスがまだ読み込まれて
いない場合は、autoloadの登録元で答えます。アプリケーション自身のクラス
ならワークスペース配下の絶対パス、gemのクラスならgemが書いたままの素の
requireパスです。

この問い合わせは、レシーバだけでなく継承チェーン上のワークスペースが宣言
したクラスすべてに対して行います。これが最も多いケースに届くための条件
です。`ActiveSupport::TestCase`を再オープンすると、その名前はワーク
スペース自身のものになるため、`class FooTest < ActiveSupport::TestCase`
はいずれも「完全に見える」継承チェーンを引き継ぎます。

この判定のために何かを読み込むことはありません。autoload登録済み定数への
`const_get`は読み込みを実行してしまい、実際のアプリケーションではbundle外
のgemから`Gem::LoadError`が発生しました。Runtime Agentが存在しない場合 —
信頼されていないワークスペース、Railsアプリでないプロジェクト — の挙動は
従来どおりです。

`Object.const_source_location`を最初に試しましたが、この問いには答えられ
ません。返すのは定数が**登録された場所**であり、Zeitwerk管理下の`app/`の
クラスはすべてZeitwerk内部の1行を指します。この方針では
`ApplicationController`をアプリ外のクラスと判定し、アプリケーション全体で
検査を黙らせていたはずです。反証と、棄却した他の2案、そしてこの方針でも
なお取りこぼすケースは
`docs/design/tasks/024-deferred-review-findings.md`(024.R5)に記録して
あります。

### 詳細

Core Serverは拡張機能自体に同梱されます — 別途のインストール手順は不要
で、拡張機能と一体で更新されます。互換性のない、あるいは破損したCore
Serverのビルドは、黙って、あるいは部分的に失敗させるのではなく明確に報告
します。
