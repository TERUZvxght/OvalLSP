# 変更履歴

[English version](CHANGELOG.md)

OvalLSP VS Code拡張機能の注目すべき変更をすべて記録しています。各リリース
はまず「何が変わったか」を示し、その理由・実測値・棄却した方針は下の
**詳細**にまとめてあります。

## 0.1.13 — 索引はワークスペースに答える、編集履歴にではなく

- 修正: 定義ジャンプ・find references・rename・シグネチャヘルプ・
  `workspace/symbol` が、「最後にどのファイルを編集したか」で答えを変える
  ことがなくなりました。複数ファイルで宣言されたクラス——再オープンされた
  モデル、関心事ごとに分割されたコントローラ、1つの名前空間の2通りの綴り
  ——は、そのいずれかを再索引するたびに宣言の順序が入れ替わっており、これら
  の機能はいずれも先頭の1件を取るか、一覧を打ち切ります。

`docs/PUBLISHING.ja.md` のバージョン規約における patch リリースです。
ケイパビリティは追加していません。

### 詳細

`WorkspaceIndex` は再索引時にそのuriのエントリを削除して新しいものを末尾に
追加するため、ファイルの宣言は自分が属するすべてのリストの末尾へ移動して
いました。無関係なファイルで1文字入力するだけで十分です。修飾なしの `User`
が `Admin::User` に解決されたり `Api::User` に解決されたりし、祖先チェーンと
未知メソッドの検査がそれに追随しました。いま見ていたファイルのクラスが、
打ち切られた `workspace/symbol` の結果から落ちました。シグネチャヘルプは
再オープンされたメソッドについて別の定義側の引数を表示しました。読み出し側は
少なくとも11箇所あり、いずれも順序を持たない保存構造の `.first` を取って
いました。「少なくとも」と書くのは、この数を2度数え違え、レビューでさらに
増えたからです。それこそが、読み出し側ではなく保存側を直す理由です。

0.1.12 はこれを4回直そうとし、毎ラウンド読み出し側を1つずつソートして、
2つの退行を出したうえでスレッドごと巻き戻され、`024.15` として記録されました。
現在、順序は保存側にあります。エントリのリストは書き込み時に uri 順、次に
ソース位置順で並べられ、単純名の索引を読む唯一の箇所が修飾名で並べます。
`workspace/symbol` のランク付けは完全一致優先の規則を保ったまま末尾のキーを
得ました。結果が打ち切られる以上、索引順で決まるタイは「どのシンボルが生き
残るか」を変えるからです。

再索引で退行しうる例はすべて再索引を通ります。それがこの欠陥の住む状態で
あり、これまでの4回の試行がいずれも通さなかった状態です。ただしそれだけでは
不十分でした。`workspace/symbol` の末尾キーは、8ファイルすべてが1つのクラスを
宣言する再索引フィクスチャの陰で未固定のまま出荷されており、`replace_file` が
既に並べているエントリのリストしか動かしていなかったのです。この部分が担って
いるのは*別々の*シンボル同士のタイであり、それには専用のフィクスチャが要ります。

併せて見つかったテスト側のギャップが2件。いずれもユーザーには見えません。

ケイパビリティE2Eスイートは、41行すべてをスキップしても exit 0 になりえま
した。`docs/EXTENSION_CAPABILITIES.md` は「スキップされた行のケイパビリティ
は出荷していない」と定めていますが、CIはreal-Rails統合スイートについてしか
それを強制しておらず、`capability_coverage_spec.rb` はスペックファイルの
ソーステキストを読むため結果を見られません。現在は両方を検査します。

そして拡張機能で最大のモジュールである `extension.ts` は、どのワークフロー
でも実行されない統合スイートにしか覆われていませんでした。ユーザーに見える
判断を2つ、`vscode` を import しないモジュールへ移しました——クライアントが
どのファイルに接続するか(Rubyは言語id、ERBは拡張子。VS Codeが `.erb` に
組み込みの言語idを与えないため)と、ステータスバーの表示内容です。後者には
「ここにクライアントがいない」(非表示)と「クライアントが応答しなかった」
(非表示にしてはならない)の区別も含みます。

## 0.1.12 — 書き直され続けた規則と、自分自身を過少申告していたプライバシー一覧

ここにある修正はすべて、OvalLSPが既に「できる」と謳っていたことの修復です。
その多くは同じ欠陥が姿を変えたもの——クラス名に関する1つの規則が、必要な場所
ごとに手書きされていたことに由来します。

**プライバシーとparseキャッシュ** — コードではなく、文書の記述の訂正です:

- **`PRIVACY.ja.md` の「parseキャッシュにソースコードの内容は含まれない」と
  いう記述を撤回しました。実際には一部が含まれます** — 各メソッドの本文
  テキストと各パラメータのデフォルト式をそのまま、加えて各ファイルの絶対
  パスです。キャッシュは以前からこれらを保存しており、0.1.11 までの全
  バージョンで文書のほうが誤っていました。
- `PRIVACY.ja.md` の「パースキャッシュ以外ディスクには何も書かない」という
  記述を撤回しました。観測の実行は一時ファイルを2つ書き、そのうち1つは
  あなた自身のテストコマンドの出力——Railsアプリなら日常的にSQL——を受け取ります。
- `PRIVACY.ja.md` が、型観測の記録内容をすべて列挙し、記録していないものを
  列挙するのをやめました。記載より多くを記録しており(各パラメータで観測された
  クラス、返されたクラス、ファイルのダイジェストと行番号、実行の識別子、
  終了時刻)、かつ「例外を送出したかどうか」という、どこにも記録されていない
  項目を挙げていました。
- parseキャッシュの場所は `$XDG_CACHE_HOME/ovallsp/` であり、常に
  `~/.cache/ovallsp/` ではありません。これを削除するトラブルシューティング
  手順は、この環境変数に空でない値を設定している利用者にとって誤っていました。

**誤検出の除去** — 動作するコードが「壊れている」と報告されていたもの:

- `send`・`__send__`・`public_send`・`instance_exec`・`Proc#call`・
  `Method#call` が、存在しないメソッドとして報告されなくなりました。前者4つと
  後者2つは、2つの異なる経路で同じ理由により失敗していました。
- `< ::BasicObject` と書かれたクラスで、未知メソッドの検査が黙って無効化される
  ことがなくなりました。0.1.11 と同様、これまで沈黙していたクラスが、見逃されて
  いた誤りを報告し始めることがあります。

**誤っていた型・失われていた型:**

- `::User.find(1)` が `User` に解決されるようになりました(`User.find(1)` は
  元から解決されていました)。ルートスコープのモデルレシーバは型を失い、
  Active Record のメソッド検査も黙って無効になっていました。
- `Widget` の中で `self` と `Widget.new` が同じ型になりました。一致して
  いなかったため、その両方が代入される変数は和型になり、未知メソッドの検査が
  そこで沈黙していました。`::Widget.new` も同様です。
- 名前空間付きのクラスが、同名のトップレベルモデルのデータを借用しなく
  なりました。`:company` に委譲した `Admin::User#name` は、トップレベルの
  `User` の関連から答えられていました——型が欠けるのではなく、自信をもって
  誤った型を返していました。
- プラグインがクラス宣言を登録した場合に、修飾なしの名前が別のクラスに解決
  されうる問題を修正しました。
- `klass::Error.new` が1つあるだけで、そのメソッドのインスタンス変数の型が
  すべて失われることがなくなりました。定数部分に定数でない要素を含むパスは
  正当なRubyで、ファクトリ系のコードでは一般的です。その名前を Prism に
  尋ねると例外になり、それが離れた場所で捕捉されてメソッドの推論結果ごと
  破棄されていました——ビューには型が一切届きませんでした。

**シグネチャヘルプ:**

- 名前を挙げていない引数を受け取るメソッドに対して `()` と表示しなくなり
  ました。`Array#shuffle` は引数なしと読めていました。`*rest`/`**rest` を
  受け取る106個のメソッド(`Array#push`・`#concat` を含む)も同様でした。
- Sorbet の `.rbi` で宣言された、通常の位置引数を取るメソッドに対して `x:` と
  入力するよう促さなくなりました。
- Sorbet の `.rbi` で `def f(...)`・`def f(**nil)`・分解代入の
  `def f(a, (b, c))` を宣言したメソッドが、署名を失わなくなりました。この
  リリース内で作り込み、このリリース内で直したもので、公開済みのバージョンには
  含まれていません。

**定義ジャンプ:**

- Active Record のカラム・関連に対する定義ジャンプが、`class Admin::Company`
  と書かれたモデルだけでなく `module Admin; class Company` と書かれたモデルにも
  届くようになりました。

`docs/PUBLISHING.ja.md` のバージョン規約における patch リリースです。
ケイパビリティは追加していません。

### 詳細

**1つの規則が、必要な呼び出し側ごとに手書きされていた。** 0.1.11 は「クラス名・
owner名は修飾済み」という規則を `SymbolId` に移し、呼び出し側をそこに通しました。
写しは生き残っており、このリリースは11ラウンドかけてそれらを見つけました。
そしてその数を5回公表し、5回とも誤り、いずれも過少でした——それがこの教訓です。
ここに数は書きません。取り除いた箇所は `git diff main...HEAD -- core/lib` で
見られますし、いくつあるかは `entry.name == "BasicObject"` や
`split("::").last` を同じ規則と数えるかどうかで変わります。まさにその曖昧さが、
毎回違う数を生んでいました。
`chain_reaches_root?` は `entry.name == "BasicObject"` と尋ねており、
`< ::BasicObject` と書かれたクラスは `::` を伴うエントリを生むため、そのチェーンは
ルートに到達していないと判定され、レシーバは「閉じている」とみなされず、未知
メソッドの検査は何も言わずにそのクラスで無効になっていました。`ModelRegistry` は
Rails自身の修飾なしの `model.name` をキーにしているため `::User` は何にも一致
しませんでした——現在はこれを使う5つのサブシステムにまたがる22箇所の呼び出し側
ではなく、レジストリの4つの検索メソッド側で正規化しています。`MethodAnalyzer` は
委譲元の owner を*単純名*で照合しており、`Admin::User` がトップレベルの `User` の
関連を借用していました。`LocalInferencer` は6箇所で `::` 付きの型を作っていました。(この段落の
以前の版は、そのうち1箇所がユーザーに見えるものだったとして `k = ::Widget`
のホバーの差を挙げていました。これは誤りです。0.1.11 の時点で既にその箇所は
正規化されており、差が現れるのは変異を加えた場合だけでした。壊れていたので
はなく、テストされていなかったのです。)
同ファイルの7箇所目は、隣接する2箇所が既に持っていたガードなしに定数パスの
名前を Prism に尋ねており、`klass::Error.new` で例外を出してそのメソッドの
インスタンス変数を巻き添えにしていました。現在はすべて、例外ではなく nil を
返す1つのヘルパー経由です。

現在は `Index::SymbolId` が、この1つの決定の3方向すべて——`qualify_owner`・
`bare_name`・`qualify_within`——を所有し、写しはすべてそこへ委譲します。
`ReceiverResolution.canonical_receiver_name` も同様で、その旧本体は、いま
呼び出している当のものとバイト単位で同一だった2つの写しの一方でした。この型は
文書化しかしていなかった不変条件も強制するようになりました——クラス自身の名前も
修飾済みである、という条件です。これまでは `ParserService` がたまたまそう生成して
いたから成り立っていただけで、プラグインが登録した宣言では成り立ちません
でした。

**RBS と RBI の署名。** RBSは「何でも受け取る」を `(?)` と書き、パラメータ一覧を
まったく持たない関数オブジェクトとして表現します。ここに突き当たる宣言は2種類
あります。`Proc#call` と `Method#call` は自身が `(?)` であり、`send`・
`__send__`・`public_send`・`instance_exec` は `(?)` の*ブロック*を持ちます——
前者3つの綴りは `?{ (?) -> untyped }`、`instance_exec` は
`{ (?) [self: self] -> U }` で、こちらはブロックが必須かつ self 束縛付きです。
2つの変換側(`TypeConverter` と `Environment`)はどちらも、そうした関数に
位置引数を尋ねており、生じたエラーは署名構築を囲む包括的なrescueに飲み込まれ、
メソッドは「署名なし」として返っていました。未知メソッドの検査はこれを
「RBSがこのメソッドを宣言していない」と読みます。`__send__` はまさに
`< BasicObject` と書くプロキシや委譲のコードで中核的に使われる語法なので、上の
`::BasicObject` の修正は、沈黙を解いたそのクラス群に対して誤った報告を出すところ
でした。

その署名が生むラベルは、名前を挙げられないものすべてについて引数ゼロと主張して
いました。このリリースが読み込むRBSコアには、キーワードだけで位置引数を持たない
メソッドが29個(オーバーロード単位では33個)あり、名前を持つ引数が1つもなく
restスロットだけを受け取るものが106個あります。現在はどちらも表示されます。
29個のうち3個——`Dir.[]`・`Kernel#warn`・`Ractor.new`——は `*rest`(位置引数側)
も取ります。これが29と、以前の版が挙げていた26との差のすべてです。4つ目の
`Exception#detailed_message` は `**` 側のrestなので、この3個には含まれません。
引数を受け取りながら `()` と表示されていたメソッドは合計135個でした。

RBIの不具合は、このリリース自身が引き起こしたものです。Sorbet の
`params(x: Integer)` は名前と型の対応表でしかなく、`def f(x)` と `def f(x:)` を
区別できません。パーサはすべての項目を必須*キーワード*として記録しており、
コメントには「arity照合のためだけ」と書かれていました。キーワードを表示するものが
無かったため表には出ませんでしたが、このリリースがラベルにキーワードを表示させた
結果、`def combine(x, y)` と宣言されたメソッドが `x:` と入力するよう指示し始め
ました。ラベルが不具合だったのではなく、既にあった虚偽を読める形にしたのです。
sig の下の `def` こそが引数の形の正であり、パーサは元からそのノードを手にして
いたので、形は def から、型は `params(...)` から取るようにしました。その最初の
実装は、`def f(...)`・`def f(**nil)`・分解代入の `def f(a, (b, c))` という3つの
正当な引数の書き方で例外を出しました——いずれも `#name` に応答しないノードを引数
リストに置くためで、包括的なrescueがそれぞれを「署名の消失」に変えていました。
リリース内で修正済みで、公開済みのバージョンには含まれていません。

**プライバシー文書が誤っていた点。** 3つの記述で、いずれもこのリリースより古い
ものです。parseキャッシュにはソースコードの一部が含まれます。観測の実行中には
一時ファイルが2つ書かれ、うち1つはあなたのスイート自身の出力を受け取ります。
そして観測が記録する内容の一覧は、両方向に同時に誤っていました——5項目足りず、
かつ存在しない項目を挙げていました。これらはいずれもコードの動作を変えるもの
ではありません。あなたのプログラムの*値*は記録しないという保証は当時から成り
立っており、今も成り立ちます。変わったのは、文書がそれを正確に記述するように
なったことと、「記録しません」という約束は OvalLSP が抽出して保持するものに
ついてであって、あなた自身のテストスイートが出力するものについてではない、と
明示したことです。

**11ラウンドのレビューがこの文書に強いたもの。** このリリースノートが公表した
数値の多くは一度は誤っており、導き直す必要がありました。スイートの examples 数が
2回、変異の回数が1回、そして上記の写しの数が3回です。ここに合計を書かないのは、
合計もまた誰にも検証できない数値になるからです。リリースのタイトルは2度、次の
ラウンドが反証する完全性の主張を掲げました。このリリースで最も強い訂正——parseキャッシュがソースコードを保持して
いること——は、11人のレビュー担当がそれぞれ読んだ文書の中で、10ラウンドにわたり
どの箇条書きにも載っていませんでした。そしてもう1つの系統は、出荷せず巻き戻し
ました。索引が「最後に編集されたファイル順」で結果を返す問題に4ラウンドを費や
しましたが、いずれも順序を持たない保存構造に対して*読み出し側*を1つずつソート
する試みで、ラウンド10はラウンド9の修正を同じメソッドで退行させました。この
欠陥はこのリリースより古く、本来必要な修正——読み出し側ではなく保存側を順序
付けること——を明記した独立の項目(024.15)を設けています。上記の記述は、以前の
草稿ではなくコードから導き直しています。数値が出てくる箇所は、実際に数えた
ものです。

## 0.1.11 — 至る所に書き写され、どこにも憶えられていなかった規則

- 修正: プロジェクト自身の `sig/` だけで宣言したメソッドが、存在しない
  メソッドとして報告されなくなりました。
- 修正: ルートスコープの定数参照(`::JSON`・`::Rails`)が、解決不能として
  報告されなくなりました。
- 修正: `include ::SomeModule` と書かれたクラスでは、未知メソッドの検査が
  黙って無効になっていました。有効になったため、これまで見逃されていた
  誤りが新たに報告されることがあります。
- 修正: コア class を再オープンして追加したメソッド
  (`lib/core_ext/object.rb` など)が、定義に解決され、補完に出て、未知
  メソッドとして報告されなくなりました。そこに private で定義したものは
  補完に出ません。
- 修正: 2つのスレッドが同時に送信した際に、あるメッセージの
  `Content-Length` が別のメッセージの本体の前に出ることがあった問題を
  修正しました。

`docs/PUBLISHING.ja.md` のバージョン規約における patch リリースです。
ケイパビリティは追加していません。いずれも退行ではなく、0.1.5 より前から
存在していたもので、これまでのすべてのリリースに含まれていました。0.2.0 の
作業中に見つかったものですが、そちらを待たずにここで修正します。

### 詳細

はじめの2つは、この検査が出してはならない種類の報告——動作するコードへの
報告です。署名環境は*修飾済み*の名前を解決しますが、そこに届く名前は
両方の形で来ます。`HierarchyIndex` はクラス*自身*の祖先エントリを修飾済み
(`::Widget`)で返し、継承したものは修飾なし(`Object`)で返します。
一方、定数参照はソースに書かれたままの形で届きます。正規化せずに `::` を
付け足すと `::::Widget` を問い合わせることになり、何にも一致しません
でした。Rubyにメソッドを書かずRBSでクラスを記述するのは通常の運用であり、
`::JSON` も通常のRubyです。どちらも報告されていました。

この規則はコードベース全体で8箇所に書き写されていました。うち3箇所は
逆に書かれており、さらに規則が必要なのに書かれていない箇所が2つ——
インデックスとメソッド解決側——最初の修正のあと、レビューで見つかりました。

現在は `SymbolId`——owner とは何かを知っている当のもの——に1度だけ書き、
他のすべてはそこに委譲します。ここには一言にする価値のある教訓があります。
呼び出し側ごとに書き写された規則はいつかどこかで書き間違えられる規則であり、
「何箇所が誤っていたか」を数えたことが、まだ誰も報告していなかった残りを
見つける手がかりになりました。

2つ目は、バックグラウンドスレッドから診断が再送されるとき——Runtime Agentが
利用可能になる、再起動する、ルートやモデルが再取得される、保留していた
祖先の回答が届く——にディスパッチスレッドがリクエストに応答していると
発生しえました。フレームは2回の `write` として
書き出され、両者を直列化するものが何もなかったため、あるメッセージの
ヘッダが別のメッセージの本体の前に出ることがありました。これは
クライアントが復帰できない唯一の framing エラーです——推測で再同期する
しかありません。

フレームは現在、直列化され、かつ1回の呼び出しで書き出されます。これは
別々の要件です。直列化はミューテックスが担い、書きかけのフレームが
クライアントから観測されないようにします。1回の書き込みはミューテックス
では得られないほうを担います——`Thread#kill` に対する防御にはならず、
終了時の join はまさに送信するスレッドを kill するからです。

`Hash` と `Set` を持たないため、この修正が名前に冠している2つの型に関しては
それは理由になりません。

メンバーを正直に数えるようになりました。`x = flag ? User.new : []` に続く

現れなくなり、リネームでも書き換えられません。0.1.7 はこれを一覧に含めて
いましたが、それは `[]` の分岐を無視した上でのことでした。

レシーバしか理解しないため、コンテナクラスに対するワークスペース自身の
宣言が、コンテナの値からは見えていませんでした。これは以前からそうでしたが、
今回の変更でその状態に到達する頻度が上がるところでした。リゾルバは、ジェネリックなレシーバを
「それが総称しているクラス」として読むようになりました。ただし `Relation`
と `CollectionProxy` は除外します。これらは誰かが宣言するクラスではなく
Active Record の「形」の名前であり、クラス名として読むと
`Model.where(...)` のレシーバが、ワークスペースが偶然 `Relation` と名付けた

### 詳細

クラスの再オープンは、そのクラスを定義するコードと構文上まったく同じ
です。したがってファイルをいくら読んでも区別はできません — 代わりに

プロセス自身の`Object.ancestors`を基準に測るため、`Object`に何かを混ぜて
いるアプリケーションが自分で基準を較正します。クラスがまだ読み込まれて
いない場合は、autoloadの登録元で答えます。アプリケーション自身のクラス
ならワークスペース配下の絶対パス、gemのクラスならgemが書いたままの素の
requireパスです。

この問い合わせは、レシーバだけでなく継承チェーン上のワークスペースが宣言
したクラスすべてに対して行います。これが最も多いケースに届くための条件
です。`ActiveSupport::TestCase`を再オープンすると、その名前はワーク
スペース自身のものになるため、`class FooTest < ActiveSupport::TestCase`
はいずれも「完全に見える」継承チェーンを引き継ぎます。

この判定のために何かを読み込むことはありません。autoload登録済み定数への
`const_get`は読み込みを実行してしまい、実際のアプリケーションではbundle外
のgemから`Gem::LoadError`が発生しました。Runtime Agentが存在しない場合 —
信頼されていないワークスペース、Railsアプリでないプロジェクト — の挙動は
従来どおりです。

`Object.const_source_location`を最初に試しましたが、この問いには答えられ
ません。返すのは定数が**登録された場所**であり、Zeitwerk管理下の`app/`の
クラスはすべてZeitwerk内部の1行を指します。この方針では
`ApplicationController`をアプリ外のクラスと判定し、アプリケーション全体で
検査を黙らせていたはずです。反証と、棄却した他の2案、そしてこの方針でも
なお取りこぼすケースは

前者では検知できない失敗であり、このプロジェクトが実際に陥っていた状態

スペースのファイルは、そのクラスを定義しているファイルと区別がつかない

## 0.1.4 — 「Payload hash mismatch」の誤警告を実際に修正

- 修正: 起動のたびに出ていた「Payload hash mismatch」警告。0.1.3はこれを
  試みて成功していませんでした。
- 追加: `scripts/verify-packaged-payload-hash.js`。`release.sh`とCIに
  組み込み、同じ乖離が二度と利用者に届かないようにしました。

### 詳細

下記の0.1.3の診断(`vsce publish`が自身のprepublishフックを再実行し、
native extensionを再ビルドしていた)は実在の問題であり修正済みのままです
が、この警告の原因では**ありませんでした**。

実際の原因: `scripts/copy-core.js`はステージングした`core/`ツリー(815
ファイル)に対してsha256を記録する一方、`.vscodeignore`が独立して
`core/vendor/bundle/ruby/*/cache/**` — 4つのBundlerの`.gem`アーカイブ —
をVSIXから除外していました。したがってインストール済みの拡張機能は常に
811ファイルであり、起動時に再ハッシュしても記録されたハッシュを再現できる
ことは、どのマシンでも決してありませんでした。「payloadとは何か」の定義が
2つ独立に存在し、静かに食い違っていたのです。実際にインストールされた
0.1.3を再ハッシュし、ステージングツリーとパッケージ済みツリーを比較して
確認しました。

ハッシュ側にパッチを当てるのではなく構造的に修正しました。これらの
キャッシュアーカイブはステージング時に削除します(純粋なビルド副産物です。
`bin/ovallsp`は`$LOAD_PATH`に`**/gems/*/lib`しか追加せず`cache/`は決して
追加しません)。これによりステージングツリー**そのもの**が出荷ツリーと
なり、ハッシュを取ることに意味が生まれます。`.vscodeignore`の該当ルールは
削除し、`core/**`をこれ以上除外しないよう注記を残しました。

新しい検査は**パッケージ済み**VSIXを再ハッシュし、そのVSIX自身のmanifest
と比較します — 拡張機能が起動時に実行するのと同じ検査を、ビルド時に実行
します。古い`.vscodeignore`のルールを一度戻して検査が失敗することを確認
し、元に戻して通ることを確認済みです。

## 0.1.3 — 修正: `vsce publish`が検証済みビルドを公開せず拡張機能を再ビルドしていた

- 修正: Marketplaceに届いていたのが、直前にsmoke testしハッシュを取った
  ビルドではなく、再ビルドされた未検証の成果物だった問題。
- **訂正:** このリリースは「Payload hash mismatch」の誤警告も修正したと
  考えて公開されました。実際には修正できていません — 実際の原因は0.1.4を
  参照してください。

### 詳細

`vsce publish`は、先行する`npm run package`とは独立に自身の
`vscode:prepublish`フックを実行します。つまりCoreのvendoring済みnative
extension(Prism、RBS)を静かにもう一度ゼロから再ビルドします。native
extensionのコンパイルは実行ごとにバイト単位で再現可能ではないため、実際に
Marketplaceへ届いていたのは、直前にビルドしsmoke testしハッシュを取った
成果物では決してありませんでした。

すでにビルド済みのVSIXファイルを`vsce publish --packagePath <file>
--pre-release`で公開することで修正しました。end-to-endで検証済みです。
この変更後は、ビルドのディスク上のpayloadハッシュがpublish手順によって
変化しないことを証明できます。変更前は同じ手順で2つの異なるハッシュが
生成されていました。

## 0.1.1 — 修正: 公開されたVSIXに同梱Core Serverが入っていなかった
