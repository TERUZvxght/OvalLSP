# 変更履歴

[English version](CHANGELOG.md)

OvalLSP VS Code拡張機能の注目すべき変更をすべて記録しています。各リリース
はまず「何が変わったか」を示し、その理由・実測値・棄却した方針は下の
**詳細**にまとめてあります。

## 0.2.0 — 最初の一文字からの補完と、開いていないファイルの診断

- 追加: `A` と打った時点で候補が出るようになりました。これまでは先に `.`
  が必要で、宣言済みクラス・スコープ内のローカル変数・その場で呼べる
  メソッドは、名前を全部打ち終えるまで何も出ませんでした。
- 追加: 開いていないファイルの誤りも報告されるようになりました(プロセス内
  検証済み。実際のRailsアプリに対するend-to-end検証は024.14として未解決です)。
- 追加: 型の合わない引数を報告するようになりました。これまでは引数の
  **個数**しか見ていませんでした。
- 追加: 一度も代入されない `@ivar` の読み取りを報告するようになりました。
- 追加: hoverと補完に RDoc/YARD のドキュメントが表示されるようになりました。
- 追加: セマンティックハイライトに対応しました(`.rb` とERBテンプレートの
  Ruby領域の両方)。
- 修正: プロジェクト自身の `sig/` だけで宣言されたメソッドが、存在しない
  メソッドとして報告されなくなりました。
- 修正: 2つのスレッドが同時に送信した際に、あるメッセージのヘッダと別の
  メッセージの本体が混ざることがあった問題を修正しました。

`docs/PUBLISHING.ja.md` のバージョン規約における minor リリースです。
6つのケイパビリティを追加し、このバージョンに予定されていたロードマップ
項目3件(024.R2・024.R6・024.R8)を解消します。

### 詳細

前置きなしの補完は、その大部分が*順位付けと打ち切り*の問題であり、
レシーバ経由の補完とは別種の問題です。レシーバがあれば答えは1つの型の
メンバに絞られますが、前置きなしの場合ははるかに多くに一致します。
アルファベット順に並んだ千個の候補を渡されたエディタは、何も渡されない
エディタより悪い——正解は4ページ目にあり、ユーザーはそのキーを押すのを
やめることを学びます。順序はカーソルからの近さです。ローカル変数、
self上のメソッド、ワークスペースの定数、Kernel の順で、これを `sortText`
に書き出します。エディタが実際に並べ替えに使うのはそちらだからです。
1文字の場合は前の2つだけを返します。残りの2つはその長さでは事実上
すべてに一致するためです。一覧は上限で打ち切り、`isIncomplete` を返す
ので、入力が絞られるにつれてエディタが再度問い合わせます。

ワークスペース全体の診断はバックグラウンドスレッドで走り、バッファで
開かれているファイルには一切答えません(それらはバッファの版と未保存の
内容を知っている経路の担当です)。また、世代が更新された走査はファイル
単位で中断します。既に古いと分かっている結果を出し切ることには意味が
ないからです。走査は、答えがワークスペース全体で変わりうるたびに再実行
されます。とりわけ重要なのは Runtime Agent が利用可能になったときで、
未知メソッドの検査は Agent なしでは推測せず保留するため、これまでは
開いていないファイルすべてが Agent 到着前の答えのままでした。

新しい2つの検査は、引数の個数の検査と同じ基準で作られています——動作する
コードに対する誤った報告は、検査がないことより悪い。引数の型は、期待型が
*明示*されている場合(RBS/RBI の宣言で、オーバーロードが1つだけ、`*rest`
なし)にのみ比較し、しかも期待型と推論された型の両方が具体クラスで、
継承関係がないときにのみ報告します。RBS の `int`/`string`/`boolish` は
除外しています。これらはクラスではなく「変換できる何か」を意味するため
です。`@ivar` の検査はビューに限定しました。ビューはコントローラの
アクションとコールバックチェーンが代入するものをそのまま受け取ります。
この検査の安全性は「文脈を確立できなかった」と「アクションが何も代入
しない」の区別に懸かっており、前者では何も報告しません。

セマンティックハイライトは、パーサだからこそ決着でき正規表現には決着
できないものだけを報告します——ローカル変数の読み取りとレシーバなしの
呼び出しの区別、インスタンス変数、パラメータ、定数です。キーワードや
文字列、数値は塗り直しません。文法定義が既に正しく扱っており、そこに
食い違う2つ目の意見を加えても、ちらつくだけだからです。パースできない
ファイルには何も返しません。半分だけ返すと、入力するたびにハイライトが
剥がれ落ちるように見えるためです。

ドキュメントはソースから読みます。元々そこにあるものであり、コメントを
索引化する仕組みは持ちません。補完では一覧に載せず
`completionItem/resolve` を経由します。候補すべてについてソースを読むのは
1項目あたり1ファイル読み込みであり、ユーザーがドキュメントを見るのは
多くても1つだけだからです。

## 0.1.10 — 実装を1つに、そしてテストできなかった4つの挙動

- 変更: 拡張機能のクライアント停止処理を、ユニットテストできない
  モジュールの外に出し、テストで固定しました。
- 修正: macOS で、起動直後(約57ms)にCoreが落ちた場合に取り残されて
  いたRuntime Agentが、正しく終了されるようになりました。
- 変更: Cold Index のテストが、バッファで開かれているファイルの
  ケースを実際に検証するようになりました。

`docs/PUBLISHING.ja.md` のバージョン規約における patch リリースです。
ケイパビリティは追加していません。
`docs/design/tasks/024-deferred-review-findings.md` の残る4つの不具合
項目(024.1・024.6・024.8・024.10)を解消し、残るのはロードマップ項目と
024.13 のみになります。

### 詳細

重複したコールバックチェーンは、厄介な種類の重複でした。どちらの複製も
正しく動いていたため見た目には何も壊れておらず、しかも間違ったほうに
対して書かれた回帰テストは、実際に動く経路について何も固定していません
でした。削除は `#infer_ivars_for_method`・`#find_static_render_target`・
`#find_method_node`、そしてそれらのためだけに存在していた
`MethodLocator` ビジターにまで波及しました。

テストは一緒に削除していません。サーバが今も呼び出している部品を
対象にしていたものは、その部品そのものに繋ぎ直しました。`except:` の
両側、アクションによるコールバックの代入の上書き、静的に解決できない
`if:` 条件、条件付きの `skip_before_action`、存在しないコールバック
メソッド、そして `before_action` と `skip_before_action` の複数名指定
——この7つは動作する経路に対応するテストが存在しなかったため、サーバに
対するend-to-endのテストとして書き直しました。そのうえで7つのフィクスチャ
それぞれについて、逆の挙動なら*異なる*答えになることを確認しています。
両者を区別できないフィクスチャは、どちらでも通ってしまうからです。

macOSでのリークは、これを引き起こしていた2行を「どの答えも変えられない」
と判断して*削除しようとした*ときに見つかりました。実際には変えられます
——削除こそが修正でした。
Coreが終了すると、追跡側はポーリングを終了します。以前は同じ場所で
pid由来の所有権も破棄しており、削除の根拠は「この分岐にはrootが不在と
判明してからしか到達せず、その時点で所有権は何も与えない」というもの
でした。しかしどちらも成り立ちません——不在フラグはパスの最後に立てられ、
またrootは子プロセスが生きている間しか追跡されないため、rootの行が
存在していても未追跡でありえます。`core-session.rb` が `setsid` に
到達する前にCoreが落ちると、まさにこの状態になります。そしてmacOSでは
他に手掛かりがありません(`ps -o sess=` は全プロセスで0を返します)。
所有権はそこで恒久的に破棄され、実際に終了処理を行うパスはその後に
走っていました。2行は削除したままとし、セッションIDの破棄が復活すれば失敗する
回帰テストを追加しています(対になるグループIDの破棄は対称性のために
一緒に削除したもので、こちらは原理的にどの答えも変えられないため、
テストで固定することはできません)。

`extension.ts` は `vscode` をimportしており、ユニットテストのスイートは
それを読み込めません。そのため、このファイルにある処理は手動でしか検証
できませんでした。4つの判断がその状態にありました——うち3つは孤児と
なったCoreプロセスを残さないためのもの(クライアントの停止を投げっぱなし
にせず待つこと、フォルダに追跡中の世代がないときに未処理のプロセス回収を
出し切ること、ホストが既に終了処理に入っている最中に追加された
ワークスペースフォルダに対してサーバを起動しないこと)、残る1つは
「どちらの再起動をユーザーに伝えるか」です。これらは `vscode` を一切
importしないモジュールに移しました。それぞれについて、実際に変異させて
スイートが赤くなることを確認しています。

最後の1つは、2度手間になった経緯を残しておく価値があります。通知の
文字列を2つexportして `extension.ts` に選ばせる形では、固定できたのは
文言だけでした。コマンドとメッセージの対応付けは呼び出し側に残ったまま
で、入れ替えてもスイートは緑のままだったのです。現在固定されているのは
「選択が存在しないこと」です——各コマンドは自身のIDを1度だけ書き、
確認通知はその同じIDから引かれます。各コマンドが実際に*何をするか*は
`vscode` に依存する通常のコードのままで、そこは他と同様に手動で確認して
います。

## 0.1.9 — 型エンジンの3つの修正

- 修正: ハッシュリテラルが、他のコンテナと同じ形で表示されるように
  なりました。`{}` と `{a: 1}` は `Hash`、`[]` は `Array[Unknown]`、
  `Hash.new` は `Hash[Unknown]` ——同じ種類の値の書き分けに対して、
  2つの答えが返っていました。
- 修正: `untyped` と書かれたプロジェクトの署名が、そのメソッドを無効化
  しなくなりました。自分の `sig/` に `def self.build: (...) -> untyped` と
  書くと、`build` の呼び出しがソースの内容に落ちずに、すべて解決不能に
  なっていました。
- 修正: `before_action` を読み取る処理が、その宣言自身の
  `only:`/`except:` セレクタを消費しなくなりました。

`docs/PUBLISHING.ja.md` のバージョン規約における patch リリースです。
ケイパビリティは追加していません。
`docs/design/tasks/024-deferred-review-findings.md` の3項目
(024.12・024.3・024.4)を解消します。

### 詳細

コンテナの表示は1箇所ではなく2箇所を直しています。リテラルだけを直すと、
不一致が1回の呼び出し分だけ移動するためです——`{}` へのhoverと、`{}` を
返すメソッドへのhoverとが食い違うことになります。そこでメソッドサマリの
解析側もジェネリック形を返すようにしました。

`untyped` の件は `.new` では既に正しく扱われていました。情報を持たない
答えを除外して先へ進んでいたのです。それ以外のシングルトン呼び出しは
それを返していました。その地点に到達する答えが情報を持つことはあり得ません。
情報を持つ署名の答えは、その手前のガードがすべて返し終えているからです。
したがって修正は「そこで返すのをやめる」ことです。

ハッシュリテラルをコンテナとして表示することには、書いておくべき帰結が
1つあります。未定義メソッドと引数個数の検査は素のクラス名を要求するため、
ハッシュリテラルのレシーバは検査対象から外れます。`Hash` を再オープン
しているワークスペースでは、`h = {}; h.totally_bogus_method` が従来は
報告されていましたが、報告されなくなります。同じ検査は
`{}.deep_symbolize_keys`(ActiveSupportのもので、標準ライブラリのRBSには
ありません)も未定義として報告していたので、誤った報告も正しい報告と一緒に
なくなります。これらのレシーバを正しく検査するには「ワークスペースが
そのクラスの一部を宣言している」ことと「そのクラスを所有している」ことを
区別する必要があり、024.13 として記録しています。

`before_action` の変更は、今日に限って無害でした。`pop` は Prism が
所有する配列を操作するため、宣言を読むとその宣言自身のセレクタが壊れます。
気づかれなかったのは、呼び出し側がたまたま毎回ドキュメントを再パースして
いたからです。それは呼び出し側の性質であってこのコードの性質ではなく、
ツリーをキャッシュしたり再走査したりする最初の実装が、静かに誤った答えを
引き継ぐことになっていました。ノードを覗くのではなく結果で固定しています。
同じツリーを2回走査したら同じことを言わなければならない——言いませんでした。

## 0.1.8 — 積み残しの修正

- 修正: サーバーを繰り返し再起動しても「The OvalLSP server crashed 5
  times in the last 3 minutes」が出なくなりました。これらは拡張機能自身が
  意図的に停止したものであり、それがクラッシュとして報告されていました。
- 修正: 要素の型が不明なコンテナの表示が、経路によらず統一されました。
  `Hash.new` と、ユニオン経由で同じ値に到達した場合とで、片方は
  `Hash[Unknown]`、もう片方は `Hash` と食い違っていました。
- 修正: 自分のコードがコンテナクラスに追加したメソッド(再オープンした
  `Hash` など)が、コンテナの値(`Hash[Unknown]`、`Array[String]`)に対する
  定義へ移動と補完で見つかるようになりました。標準ライブラリのメンバーは
  従来から機能しており、見つからなかったのはワークスペース自身の宣言です。
- 削除: 到達不能な参照インデックス処理と、プロセス所有権の判断に一切
  影響しない1行。

`docs/PUBLISHING.ja.md` のバージョン規約における patch リリースです。
ケイパビリティの行は追加していません。3項目目は、本来届いているべき
レシーバに届いていなかった既存のケイパビリティの修正です。
`docs/design/tasks/024-deferred-review-findings.md` の4項目
(024.9・024.2・024.5・024.7)を解消します。

### 詳細

クラッシュ通知は vscode-languageclient のもので、自分が要求していない
接続断をすべて数えます。その一部は私たちのものです。まだ `starting` の
クライアントを停止する場合、その状態で `client.stop()` を呼ぶのは安全で
ないため、Coreを直接終了させています。ライブラリにはクラッシュとの区別が
つきません。そこで抑制の判定に、従来認識していた自前の拒否理由だけでなく
ライフサイクル状態を加えました。**その世代**に対して停止を要求していた
なら、その接続断は私たちのものです。世代が更新済みの場合も停止扱いです。
置き換えのために破棄された世代であり、そのクライアントは後から接続断を
報告しうるためです。誰も停止を要求していないクライアントは、従来どおり
失敗の内容に応じて報告されます。

この判定は `vscode` を import しないモジュールへ移したため、手動検証では
なく単体テストで検証できるようになりました。`extension.ts` から切り出せた
024.10 の最初の一部です。

コンテナの表示はジェネリック形を正とし、ユニオンの規則をそれに合わせて
修正しました。エンジンは既に `[]` に対して `Array[Unknown]` を返して
おり、歩調が合っていなかったのはユニオン側でした。ジェネリック形を残す
ことは、コンテナ規則がディスパッチするための型引数を残すことでもあります。
これが効くのは `Array` とActive Recordのコレクションです。コンテナ規則は
`Hash` と `Set` を持たないため、この修正が名前に冠している2つの型に関しては
それは理由になりません。

目に見える変化として1つ挙げておきます。複数の型を取りうる値が、コンテナの
メンバーを正直に数えるようになりました。`x = flag ? User.new : []` に続く
`x.name` は、レシーバが持たない可能性のある呼び出しなので、参照検索に
現れなくなり、リネームでも書き換えられません。0.1.7 はこれを一覧に含めて
いましたが、それは `[]` の分岐を無視した上でのことでした。

その後の独立レビューで、ジェネリック形に統一したことは問題を塞ぐのではなく
既存の欠落を露出させていた、と判明しました。メソッドリゾルバは素のクラス
レシーバしか理解しないため、コンテナクラスに対するワークスペース自身の
宣言が、コンテナの値からは見えていませんでした。これは以前からそうでしたが、
今回の変更でその状態に到達する頻度が上がるところでした。リゾルバは、ジェネリックなレシーバを
「それが総称しているクラス」として読むようになりました。ただし `Relation`
と `CollectionProxy` は除外します。これらは誰かが宣言するクラスではなく
Active Record の「形」の名前であり、クラス名として読むと
`Model.where(...)` のレシーバが、ワークスペースが偶然 `Relation` と名付けた
クラスへ解決されてしまうためです。

## 0.1.7 — 再オープンされたgemクラス

- 修正: ワークスペースが**再オープン**しているだけのクラスに対して、gem
  自身のメソッドが存在しないと報告することがなくなりました
  (`test/test_helper.rb`の`parallelize`・`fixtures`)。実際のアプリケー
  ションでの実測: 修正前2件、修正後0件。
- 修正: そのクラスを継承するテストファイル
  (`class FooTest < ActiveSupport::TestCase`)が、gemのAPI全体を未定義と
  報告していた問題を解消しました。
- 修正: 通ってはいるが何も検査していなかったテスト2件。ケイパビリティIDの
  `G10`以降が一度も突き合わされていなかった件と、一時ファイルのリーク検査
  がプロセス全体のfd数を数えていた件です。

`docs/PUBLISHING.ja.md`のバージョン規約におけるpatchリリースです。誤った
報告を1つ取り除くだけで、何も追加しません。

### 詳細

クラスの再オープンは、そのクラスを定義するコードと構文上まったく同じ
です。したがってファイルをいくら読んでも区別はできません — 代わりに
Runtime Agentに問い合わせます。答えはそのクラスの実際の祖先で、同じ
プロセス自身の`Object.ancestors`を基準に測るため、`Object`に何かを混ぜて
いるアプリケーションが自分で基準を較正します。クラスがまだ読み込まれて
いない場合は、autoloadの登録元で答えます。アプリケーション自身のクラス
ならワークスペース配下の絶対パス、gemのクラスならgemが書いたままの素の
requireパスです。

この問い合わせは、レシーバだけでなく継承チェーン上のワークスペースが宣言
したクラスすべてに対して行います。これが最も多いケースに届くための条件
です。`ActiveSupport::TestCase`を再オープンすると、その名前はワーク
スペース自身のものになるため、`class FooTest < ActiveSupport::TestCase`
はいずれも「完全に見える」継承チェーンを引き継ぎます。

この判定のために何かを読み込むことはありません。autoload登録済み定数への
`const_get`は読み込みを実行してしまい、実際のアプリケーションではbundle外
のgemから`Gem::LoadError`が発生しました。Runtime Agentが存在しない場合 —
信頼されていないワークスペース、Railsアプリでないプロジェクト — の挙動は
従来どおりです。

`Object.const_source_location`を最初に試しましたが、この問いには答えられ
ません。返すのは定数が**登録された場所**であり、Zeitwerk管理下の`app/`の
クラスはすべてZeitwerk内部の1行を指します。この方針では
`ApplicationController`をアプリ外のクラスと判定し、アプリケーション全体で
検査を黙らせていたはずです。反証と、棄却した他の2案、そしてこの方針でも
なお取りこぼすケースは
`docs/design/tasks/024-deferred-review-findings.md`(024.R5)に記録して
あります。

提供しているように見えて実際には提供していなかったものです。

### 詳細

追加した2つの診断は意図的に狭く作ってあります。未定義メソッドの検査は、
`method_missing`を定義しているモデルや、カラムを読めなかったモデルに
対しては黙ります。引数の個数の検査は、splatも`*rest`も持たない単一の定義
に解決できる呼び出しに限って報告します。それより確実でないものは何も
報告しません。

Railsが形を公開していない引数を取るメソッド(`where(*, **, &)`)は
`where()`となりカーソルが括弧の中に入ります。引数を取らないメソッドは
名前のままです。`save()`はRubyの書き方ではないためです。

検証は2層に分けています。別の主張だからです。
`core/spec/e2e/capabilities_spec.rb`は実在のRailsアプリケーションに対して
実際のCoreをstdioで駆動し、Runtime AgentとCold Indexの完了を待ってから
問い合わせます。`vscode/scripts/verify-installed-extension.sh`は別途、
実際のVS Codeがパッケージ済み拡張機能をインストールし、起動し、実行する
こと、そしてウィンドウを閉じた後に何も残らないことを確認します。後者は
前者では検知できない失敗であり、このプロジェクトが実際に陥っていた状態
です。

既知の制限(0.1.7で修正): gemのクラスを**再オープン**しているワーク
スペースのファイルは、そのクラスを定義しているファイルと区別がつかない
ため、未定義メソッドの検査は祖先が完全だと読んでしまいます。
`test/test_helper.rb`の`class ActiveSupport::TestCase`がすべてのRails
アプリケーションでまさにこの形をしており、その`parallelize`と`fixtures`の
呼び出しが未定義として報告されます。1プロジェクトあたり1ファイルで2件です。

## 0.1.4 — 「Payload hash mismatch」の誤警告を実際に修正

- 修正: 起動のたびに出ていた「Payload hash mismatch」警告。0.1.3はこれを
  試みて成功していませんでした。
- 追加: `scripts/verify-packaged-payload-hash.js`。`release.sh`とCIに
  組み込み、同じ乖離が二度と利用者に届かないようにしました。

### 詳細

下記の0.1.3の診断(`vsce publish`が自身のprepublishフックを再実行し、
native extensionを再ビルドしていた)は実在の問題であり修正済みのままです
が、この警告の原因では**ありませんでした**。

実際の原因: `scripts/copy-core.js`はステージングした`core/`ツリー(815
ファイル)に対してsha256を記録する一方、`.vscodeignore`が独立して
`core/vendor/bundle/ruby/*/cache/**` — 4つのBundlerの`.gem`アーカイブ —
をVSIXから除外していました。したがってインストール済みの拡張機能は常に
811ファイルであり、起動時に再ハッシュしても記録されたハッシュを再現できる
ことは、どのマシンでも決してありませんでした。「payloadとは何か」の定義が
2つ独立に存在し、静かに食い違っていたのです。実際にインストールされた
0.1.3を再ハッシュし、ステージングツリーとパッケージ済みツリーを比較して
確認しました。

ハッシュ側にパッチを当てるのではなく構造的に修正しました。これらの
キャッシュアーカイブはステージング時に削除します(純粋なビルド副産物です。
`bin/ovallsp`は`$LOAD_PATH`に`**/gems/*/lib`しか追加せず`cache/`は決して
追加しません)。これによりステージングツリー**そのもの**が出荷ツリーと
なり、ハッシュを取ることに意味が生まれます。`.vscodeignore`の該当ルールは
削除し、`core/**`をこれ以上除外しないよう注記を残しました。

新しい検査は**パッケージ済み**VSIXを再ハッシュし、そのVSIX自身のmanifest
と比較します — 拡張機能が起動時に実行するのと同じ検査を、ビルド時に実行
します。古い`.vscodeignore`のルールを一度戻して検査が失敗することを確認
し、元に戻して通ることを確認済みです。

## 0.1.3 — 修正: `vsce publish`が検証済みビルドを公開せず拡張機能を再ビルドしていた

- 修正: Marketplaceに届いていたのが、直前にsmoke testしハッシュを取った
  ビルドではなく、再ビルドされた未検証の成果物だった問題。
- **訂正:** このリリースは「Payload hash mismatch」の誤警告も修正したと
  考えて公開されました。実際には修正できていません — 実際の原因は0.1.4を
  参照してください。

### 詳細

`vsce publish`は、先行する`npm run package`とは独立に自身の
`vscode:prepublish`フックを実行します。つまりCoreのvendoring済みnative
extension(Prism、RBS)を静かにもう一度ゼロから再ビルドします。native
extensionのコンパイルは実行ごとにバイト単位で再現可能ではないため、実際に
Marketplaceへ届いていたのは、直前にビルドしsmoke testしハッシュを取った
成果物では決してありませんでした。

すでにビルド済みのVSIXファイルを`vsce publish --packagePath <file>
--pre-release`で公開することで修正しました。end-to-endで検証済みです。
この変更後は、ビルドのディスク上のpayloadハッシュがpublish手順によって
変化しないことを証明できます。変更前は同じ手順で2つの異なるハッシュが
生成されていました。
